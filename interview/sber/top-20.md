## 1. Объекты передаются по ссылке или по значению?

В переменной лежит не сам объект, а ссылка на него в памяти. Присваивание и передача в функцию копируют эту ссылку. Спецификация называет это копированием значения ссылки: скопировали адрес, не содержимое. После `const second = first` оба имени смотрят на один объект.

Дальше всё решает, мутируете вы объект или переприсваиваете переменную.

```js
const first = { name: 'Hello' };
const second = first;

first.name = 'Bye';
second.name; // 'Bye' — поле поменяли у того же объекта

let next = first;
next = { name: 'Other' };
first.name; // 'Bye' — next теперь смотрит на другой объект
```

Массив устроен так же: это объект. `push`, `sort`, `arr[0] = 1` меняют общий массив, и это видят все, кто держит ту же ссылку. `arr = arr.slice()` или `[...arr]` создают новый массив. Старые переменные про него не узнают. `sort` мутирует исходный массив, `toSorted` возвращает новый.

Примитивы копируются целиком: число, строка, boolean, `null`, `undefined`, `symbol`, `bigint`. Функция тоже объект, её передают ссылкой.

Отсюда два бытовых бага. Функция изменила поле аргумента, и снаружи объект тоже изменился: вызывающий код этого не ждал. И обратный: разработчик сделал `obj = { ...obj, name }` внутри функции и думает, что обновил внешний объект. Обновилась только локальная переменная.

Если функция не должна трогать вход, она работает с копией. Поверхностной хватает, когда вложенные объекты не меняют. Если меняют дерево, нужна глубокая копия или иммутабельное обновление по пути, который реально затронут. `structuredClone` копирует глубоко, но не переносит функции и некоторые специальные объекты.

На собесе часто дают тот же пример, что в задаче Сбера: `secondObj = firstObj`, потом `firstObj = { name: 'Bye' }`. В консоли у `secondObj` останется старое имя, потому что третья строка не мутирует объект, а записывает в переменную новый адрес.

## 2. Чем `||` отличается от `??` и когда какой?

`||` — логическое ИЛИ. `??` — оператор нулевого слияния.

Оба возвращают левую часть, если она «достаточно задана», иначе правую. Разница в том, что считать незаданным.

Логическое ИЛИ считает незаданным любое falsy: `false`, `0`, `NaN`, `''`, `null`, `undefined`.

Оператор нулевого слияния считает незаданным только `null` и `undefined`. Ноль, пустая строка и `false` остаются как настоящие значения.

```js
const count = input ?? 1; // 0 останется 0
const countOr = input || 1; // 0 превратится в 1

const title = name ?? 'Гость'; // '' останется пустой строкой
const titleOr = name || 'Гость'; // '' станет 'Гость'
```

`??` ставят там, где ноль и пустая строка осмысленны: количество, цена, индекс, текст поля, флаг «пользователь явно выключил опцию». `||` ставят там, где любой falsy и есть запасной показ: запасной заголовок, запасная картинка, строка, которую нельзя показать пустой.

Путаница в форме выглядит так. Поле количества с `value={count || ''}` стирает ноль, и пользователь не может оставить «0 штук». Поле поиска с `query ?? 'все'` не подставит слово «все» на пустую строку, потому что пустая строка для `??` уже значение.

`||` и `??` нельзя смешивать в одном выражении без скобок, движок требует их явно. С опциональной цепочкой они стыкуются нормально: `user.address?.city ?? '—'`. Цепочка даёт `undefined`, если по пути нет объекта, `??` подставляет текст.

Дефолт в деструктуризации срабатывает по тем же правилам, что и отсутствие значения: только на `undefined`, не на `0` и `''`. Это ближе к `??`, чем к `||`.

## 3. Как работают `Promise.all` и `Promise.allSettled`?

`Promise.all` принимает итерируемое: промисы, thenable или уже готовые значения. Обычное значение считается успешным результатом, поэтому `Promise.all([1, fetch(url)])` допустим.

Успех наступает, когда успешно завершился каждый элемент. Наружу выходит массив значений в порядке входа, не в порядке завершения. Третий запрос может вернуться первым, его значение всё равно ляжет в индекс 2.

Если любой элемент отклонился, `all` сразу отклоняется той же причиной. Остальные промисы при этом не отменяются: запрос в сеть доработает, просто этот `all` его результат уже не отдаст. Отмена делается отдельно, через `AbortController` на каждый `fetch`. Пустой список резолвится сразу в `[]`.

`Promise.allSettled` тоже ждёт все элементы, но чужая ошибка не валит весь набор. Его промис успешно резолвится, когда все устаканились. Каждый элемент результата описывает исход:

```js
{ status: 'fulfilled', value }
{ status: 'rejected', reason }
```

Порядок снова как во входе. Дальше успешные показывают, по упавшим собирают причины.

`all` берут, когда частичный результат бесполезен или опасен: заказ оформляют, только если прошли и цена, и резерв, и профиль. `allSettled` берут для независимых кусков: виджеты дашборда, пачка справочников, несколько картинок. Один упавший эндпоинт не должен стирать остальные.

Рядом, если спросят: `Promise.race` отдаёт первый завершившийся исход, успех или ошибку. `Promise.any` отдаёт первый успех и игнорирует отклонения, пока успех вообще есть. Ни один из четырёх сам не отменяет сеть.

## 4. Чем стрелочная функция отличается от обычной в работе с `this`?

У обычной функции `this` задаёт вызов, а не место, где функцию написали.

- `obj.method()` — `this` равен `obj`;
- просто `method()` в strict mode — `this` равен `undefined`;
- `fn.call(ctx)`, `apply` и `bind` подставляют контекст явно;
- `new Fn()` — `this` это новый экземпляр.

Если метод оторвать от объекта и отдать колбэком (`button.addEventListener('click', obj.save)`), в момент клика вызов уже без базы. Внутри `save` это будет не `obj`.

У стрелки своего `this` нет. Она берёт его из внешней функции в момент создания. `call`, `apply` и `bind` этот `this` не перебивают. Поэтому стрелка удобна как колбэк внутри метода: она видит тот же `this`, что и метод. И поэтому стрелка не годится как метод, которому контекст должны выдать снаружи, и не годится как конструктор.

В классовом поле `handleClick = () => { ... }` стрелка создаётся на экземпляре и уже замкнула его. Такой обработчик передают в JSX без `bind`. Обычный метод класса, переданный как `this.handleClick`, снова потеряет экземпляр, пока его не привяжут.

Мемоизация функцию не привязывает. `useCallback` сохраняет ссылку, а `this` по-прежнему зависит от вызова. Рабочие варианты: вызывать как `obj.method()`, заранее сделать `bind`, либо обернуть в стрелку `() => obj.method()`. `bind` прямо в JSX на каждом рендере даёт новую функцию, и `memo` у ребёнка от этого не срабатывает.

## 5. Зачем дженерики и какие утилитарные типы реально используют?

Дженерик связывает тип входа и тип выхода, не фиксируя конкретный тип заранее.

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

const id = first([1, 2, 3]); // number | undefined
const name = first(['a', 'b']); // string | undefined
```

Если параметр объявить как `any[]`, на выходе будет `any`, и проверка дальше выключится. Если написать отдельную функцию на строки и отдельную на числа, одна и та же логика разъедется. Дженерик оставляет одну функцию и переносит тип элемента в результат.

Ограничение пишут через `extends`, когда внутри правда нужны поля: `<T extends { id: string }>`. Без ограничения у `T` нельзя прочитать `id`. В компоненте списка тот же приём: `renderItem` получает ровно тип элемента, а не `unknown`.

Утилитарный тип строит новый тип из старого, чтобы не копировать поля руками.

| Тип | Зачем |
| --- | --- |
| `Partial<T>` | патч формы, пришли не все поля |
| `Pick<T, K>` / `Omit<T, K>` | узкие пропсы: взять или убрать ключи |
| `Record<K, V>` | словарь, ключи заранее известны |
| `Required<T>` | все поля снова обязательны |
| `Readonly<T>` | поля нельзя перезаписать, вложенные объекты это не защищает |
| `ReturnType<F>` | тип возврата функции, чтобы не дублировать его |
| `NonNullable<T>` | выкинуть `null` и `undefined` |

`Partial` и `Readonly` работают на один уровень. Вложенный объект остаётся как был.

`{}` в TypeScript не значит «объект без ключей». Это почти любое значение кроме `null` и `undefined`. Пустой объект, в который нельзя записать свойство, описывают как `Record<string, never>`.

## 6. Какой тип у ошибки в `catch` и как прочитать `message`?

В JavaScript `throw` и `reject` принимают что угодно: `Error`, строку, число, объект с бэкенда. TypeScript не имеет права считать, что в `catch` всегда `Error`.

При `useUnknownInCatchVariables`, а он входит в современный `strict`, переменная `catch` имеет тип `unknown`. Пока тип не сузили, у значения нет полей, и `error.message` не скомпилируется.

Сужение делают проверкой в рантайме:

```ts
try {
  await save();
} catch (error: unknown) {
  if (error instanceof Error) {
    console.log(error.message);
  }
}
```

Ту же проверку выносят в type guard. Это функция с возвращаемым типом-предикатом `value is Error`, а не просто `boolean`. Если она вернула `true`, в этой ветке компилятор считает значение `Error`. Guard обязан быть честным: компилятор не проверяет тело, он верит аннотации.

`instanceof Error` не ловит plain object `{ message, code }`, который часто приходит с API. Для него пишут отдельный guard: это объект, не `null`, в нём есть строковый `message`. Массив тоже `typeof 'object'`, поэтому до чтения полей отсекают `Array.isArray` и `null`.

В React та же граница. Ошибку рендера ловит error boundary. Ошибку в `onClick` и reject, который никто не пробросил в рендер, boundary не видит: там свой `catch` и уже перевод в состояние, которое можно нарисовать.

## 7. Что происходит от Enter на адресе банка до первого кадра?

Браузер разбирает ввод как URL и при необходимости подставляет `https://`. Дальше смотрит свой HTTP-кэш, service worker и HSTS: не обязан ли этот хост открываться только по защищённому соединению.

DNS переводит имя в IP: кэш браузера, система, резолвер провайдера. Затем TCP-соединение и TLS: сертификат и ключи. Только после этого уходит HTTP-запрос с методом, путём, заголовками и cookie этого хоста. Сервер отвечает статусом и HTML.

Парсер читает HTML сверху вниз и строит DOM. Внешний CSS он запрашивает отдельно и до CSSOM может блокировать первую отрисовку: без стилей неизвестна геометрия. Синхронный скрипт без `async` и `defer` останавливает парсер, пока файл не скачается и не выполнится.

Когда есть и DOM, и CSSOM, браузер собирает дерево отрисовки из видимых узлов. `display: none` и `<head>` в него не входят. Дальше layout считает размеры и координаты, paint записывает пиксели, composite собирает слои. Пользователь видит кадр.

Если страница — SPA, в этом HTML ещё мало интерфейса. Каркас появится после JS, запроса данных и клиентского рендера или гидрации. Поэтому «страница загрузилась» и «пользователь увидел контент» — разные точки. TTFB ждёт первый байт, FCP — первую отрисовку, LCP — крупнейший элемент контента.

На уточнении «где тут JavaScript» переходят к следующему вопросу: синхронный скрипт, `defer` и `async` стоят в разных местах этого же пути.

## 8. Когда выполняется JavaScript во время парсинга HTML?

Парсер идёт по документу. Классический `<script src>` без атрибутов останавливает этот проход: браузер качает файл и выполняет его сразу, потом читает следующие теги. Скрипт в `<head>` в этот момент не увидит ещё не разобранный `<body>`.

`defer` качает файл параллельно с продолжением парсинга. Выполнение откладывается до конца разбора документа, до `DOMContentLoaded`. Несколько таких скриптов сохраняют порядок в HTML. Так подключают код приложения: DOM уже собран, порядок зависимостей предсказуем.

`async` тоже качается параллельно, но выполняется сразу, как файл готов, не дожидаясь соседей. На время выполнения парсер снова стоит. Порядок между двумя `async` не гарантирован. Так подключают независимую аналитику, которой всё равно, разобран ли документ и кто из скриптов приедет первым.

Инлайн-скрипт без `src` выполняется в ту секунду, когда парсер до него дошёл. `<script type="module">` по умолчанию ведёт себя как `defer`.

Практический вывод. Приложение — `defer` или модуль. Виджет «как можно раньше и сам по себе» — `async`. Скрипт без атрибутов в середине страницы оставляют только если следующий HTML должен увидеть результат этого скрипта, и понимают, что парсинг в этом месте стоит.

## 9. Что такое cookie и зачем `HttpOnly`, `Secure`, `SameSite`?

Cookie — пара имя/значение, которую сервер просит запомнить заголовком `Set-Cookie`. Браузер сам прикладывает её к следующим запросам на подходящий хост, путь и схему. Из JavaScript её видно через `document.cookie`, если доступ не закрыли.

`HttpOnly` закрывает доступ из скрипта. Код, попавший на страницу через XSS, не прочитает сессию из `document.cookie`. Сам браузер cookie на запрос всё равно отправит, поэтому подделка запроса с чужого сайта этим флагом не лечится.

`Secure` означает, что браузер отправит cookie только по HTTPS.

`SameSite` решает, уйдёт ли cookie с чужого сайта. `Lax` отправляет её при обычном переходе к вам по ссылке и не отправляет при чужом POST. `Strict` не отправляет даже при переходе по внешней ссылке. `None` отправляет кросс-сайтово и обязана стоять вместе с `Secure`.

Сессию и refresh-токен кладут в cookie с `HttpOnly`, `Secure` и `SameSite=Lax` или `Strict`. Тогда токен не лежит в `localStorage`, откуда его читает любой скрипт на странице. CSRF при этом закрывают отдельно: `SameSite`, проверка origin, анти-CSRF токен на небезопасных запросах. В cookie не кладут профиль целиком: она уходит на каждый запрос и ограничена по размеру.

Cookie сама по себе другие вкладки не будит. Логаут в соседней вкладке ловят через `storage` или `BroadcastChannel`, а не через факт смены cookie.

## 10. Как отслеживать изменения между вкладками?

Вкладки одного origin не делят память JavaScript. Общий канал нужно выбрать явно.

`localStorage` и событие `storage`. Запись в одной вкладке вызывает `storage` во всех остальных вкладках того же сайта. В той вкладке, которая писала, события нет. В объекте события есть ключ, старое и новое значение. Так делают логаут: одна вкладка пишет флаг, остальные его ловят и чистят свою память. `sessionStorage` так не работает, у каждой вкладки свой.

`BroadcastChannel` создают с одним именем. `postMessage` приходит всем открытым вкладкам этого origin. Можно слать не строку, а команду: `{ type: 'logout' }` или `{ type: 'theme', value: 'dark' }`. Канал закрывают, когда он больше не нужен.

`SharedWorker` — один воркер на несколько вкладок. Они подключаются к нему портами и могут держать общее состояние в воркере, а не только рассылать разовые сообщения.

Service worker видит свои вкладки через `clients.matchAll()` и может разослать им `postMessage`. Это уместно, если логика и так живёт в воркере: пуш, синхронизация кэша.

Cookie сама вкладки не уведомляет. Пока кто-то не прочитал её заново и не послал сообщение, соседи не узнают, что сессия изменилась. `storage` срабатывает только на `localStorage` и `sessionStorage`, не на запись cookie.

На собесе достаточно одного сценария. Логаут или смена организации: какая вкладка пишет событие, какие его слушают, что именно чистят. Назвать только `localStorage` без события `storage` мало: само хранилище вкладку не будит.

## 11. Зачем `key` и что происходит при его смене?

При обновлении списка React сопоставляет старых детей с новыми. `key` — личность элемента в этом сопоставлении. По нему видно, что пункт переехал, удалился или появился.

Если ключа нет, React опирается на индекс. Пока список только дописывается в конец, это часто незаметно. Вставка в середину, удаление и сортировка приклеивают состояние к позиции, а не к сущности. Инпут третьей строки показывает текст, который вводили во второй. Фокус и локальный `useState` едут вместе с номером.

Ключом делают стабильный id сущности. Индекс годится для статичного списка без состояния у пунктов и без перестановки.

Смена `key` у уже стоящего компонента — это не обновление пропсов. React размонтирует старый экземпляр и монтирует новый. Сбрасываются состояние, рефы и подписки. Сначала cleanup эффектов старого. Потом первый рендер нового, заполнение DOM-рефов, `useLayoutEffect`, кадр, `useEffect`.

Этим пользуются сознательно: `key={userId}` на форме обнуляет её при смене пользователя, и не нужно вручную чистить десять полей. Менять `key` на каждый символ ввода нельзя: компонент будет умирать на каждое нажатие, фокус пропадёт, запросы эффектов пойдут заново.

За сопоставлением стоит Virtual DOM: JSX возвращает описание дерева объектами, не настоящие узлы. React сравнивает новое описание с предыдущим и в настоящий DOM отправляет только разницу. `key` участвует именно в этом сравнении списков. Само сравнение не делает интерфейс быстрым: если компонент рендерится слишком часто, виртуальное дерево это не отменит.

## 12. Чем `useMemo` отличается от `React.memo`?

`useMemo` запоминает значение внутри компонента, пока не изменятся зависимости. Сам компонент при этом рендерится как обычно. Им кэшируют дорогой расчёт или ссылку на объект, которую дальше сравнивают.

`React.memo` оборачивает компонент целиком. Перед вызовом функции React поверхностно сравнивает пропсы через `Object.is`. Если все совпали, функцию не вызывают и на экран остаётся прошлый результат.

Это разные слои. `useMemo` не останавливает рендер. `memo` может остановить рендер ребёнка, но только если родитель передал те же ссылки. Новый объект или новая стрелка в JSX каждый раз пробивают `memo`, даже если содержимое то же.

Второй аргумент `memo` — своя функция `(prev, next) => boolean`. `true` значит «считай пропсы прежними». Она может вернуть `true` и при изменившемся поле. Так компонент формально не перерисуется. Делать так можно, только если проигнорированное поле не влияет на картинку. Иначе на экране останутся старые данные, и это будет выглядеть как зависший интерфейс. Обычно лишнее поле просто не передают.

`useCallback` — тот же приём, что `useMemo`, только для функции. Он нужен, когда функцию получает `memo`-ребёнок или её кладут в зависимости эффекта. Сам родитель от `useCallback` быстрее не рендерится. Пустой массив зависимостей при чтении свежего стейта внутри даёт устаревшее замыкание.

Порядок на практике такой. Сначала Profiler: кто рендерится и почему. Потом состояние опускают ближе к месту использования, контекст дробят, статичную часть передают через `children`. `memo` ставят на измеренный тяжёлый кусок, а не на каждый компонент файла.

## 13. Когда вызывается `useEffect` и чем он отличается от `useLayoutEffect`?

`useEffect` запускается после того, как React закоммитил изменения и браузер нарисовал кадр. Первый раз — после монтирования. Дальше — только если изменилась зависимость, сравнение через `Object.is`. Перед новым запуском и при размонтировании вызывается cleanup.

В Strict Mode в разработке React дополнительно монтирует, снимает и монтирует снова, чтобы всплыл пропущенный cleanup. В проде этого двойного цикла нет.

Эффект синхронизирует компонент с миром снаружи React: запрос, подписка, таймер, интеграция с библиотекой, которая сама трогает DOM. Им не копируют пропсы в стейт. Значение, которое считается из пропсов, считают прямо в рендере. Клик обрабатывают в обработчике, а не эффектом на изменение стейта. Подписку на внешний стор делают через `useSyncExternalStore`.

`useLayoutEffect` смотрит на те же зависимости и тоже умеет cleanup, но выполняется после обновления DOM и до показа кадра. Можно измерить узел и сразу поправить состояние, пользователь не увидит промежуточную геометрию. Пока эффект не закончится, этот кадр ждёт, поэтому тяжёлую работу и запросы туда не кладут.

Его берут для тултипа, который не должен вылезти за экран, для фокуса и скролла к только что вставленному узлу. На сервере он не выполняется. Если код общий для сервера и клиента, оставляют `useEffect`, иначе первый кадр гидрации может разойтись с HTML.

Порядок одного коммита: рендер, запись DOM, заполнение рефов, `useLayoutEffect`, отрисовка, `useEffect`.

## 14. Как убрать гонку, если второй запрос завершился раньше первого?

Сценарий. Ушли за `/users/1`. Быстро переключились на `/users/2`. Ответ про второго пришёл раньше и записал верные данные. Потом пришёл ответ про первого и затёр их. В адресной строке второй пользователь, на экране первый.

При смене URL предыдущий результат нужно выкинуть и по возможности оборвать сеть:

```tsx
useEffect(() => {
  const controller = new AbortController();
  let ignore = false;

  fetch(url, { signal: controller.signal })
    .then((response) => {
      if (!response.ok) throw new Error('Request failed');
      return response.json();
    })
    .then((data) => {
      if (!ignore) setData(data);
    })
    .catch((error: unknown) => {
      if (ignore) return;
      if (error instanceof DOMException && error.name === 'AbortError') return;
      setError(error);
    });

  return () => {
    ignore = true;
    controller.abort();
  };
}, [url]);
```

Cleanup выполняется перед эффектом с новым URL и при размонтировании. `abort()` отклоняет `fetch` ошибкой `AbortError`, её не показывают как ошибку продукта. Флаг `ignore` нужен на случай, если тело уже разобрали, а `setState` ещё впереди: аборт не всегда успевает раньше этой строки.

Одного флага хватает, чтобы не записать старые данные, но запрос докачается и займёт соединение. Аборт снимает и это. Тот же приём нужен при новом вводе в поиск, смене фильтра и уходе со страницы.

RTK Query и React Query делают это внутри по ключу запроса. Ручной эффект с `fetch` на новом экране не собирают, если в проекте уже есть такой слой.

Состояние запроса при этом лучше держать явным: покой, загрузка, успех, ошибка. `isLoading` и `error` двумя независимыми флагами легко включить одновременно. Ошибку поля и ошибку сети рисуют в разных местах.

## 15. Влияет ли `useRef` на жизненный цикл? Что будет, если реф заполнили до смены роли?

`useRef` возвращает один и тот же объект `{ current }` на всё время жизни экземпляра. Запись в `ref.current` не вызывает рендер и не перезапускает эффект с зависимостью `[ref]`: сам объект рефа не менялся.

Поэтому в реф кладут то, что надо помнить между рендерами и что не рисуют: id последнего запроса, экземпляр стороннего клиента, DOM-узел. Данные, от которых зависит картинка, кладут в `useState`.

Реф на DOM React заполняет до `useLayoutEffect`. Когда узел размонтируется, в такой реф запишется `null`. Своё значение, положенное руками, React не сотрёт. Это делает cleanup того эффекта, который значение туда положил. Смена `key` создаёт новый экземпляр и новый реф.

Отсюда баг со сменой роли. Эффект с пустыми зависимостями один раз создал клиент для обычного пользователя и записал его в реф. Потом `isAdmin` стал `true`, компонент перерисовался, эффект не запустился. Админская ветка видит заполненный реф и считает, что инициализация уже была. Внутри остаётся клиент, подписка или снятый с экрана узел с правами обычного пользователя.

Проверка `if (ref.current) return` без учёта роли путает «уже инициализировали когда-то» с «инициализировали для текущих прав».

Роль ставят в зависимости, в cleanup старое уничтожают и реф обнуляют, затем создают клиент уже новой роли. Иначе повышение прав не меняет то, чем хук реально пользуется.

## 16. Чем контролируемое поле отличается от неконтролируемого?

Контролируемое поле показывает то, что лежит в стейте React. Каждый ввод проходит через `onChange` и возвращается обратно пропом `value`. Пока `value` задан, DOM текст сам не хранит. Если в обработчике не вызвать сеттер, поле замрёт: пользователь печатает, а на экране остаётся старая строка.

Обработчик можно передать двумя способами, и оба оставляют поле контролируемым.

```tsx
<input value={text} onChange={(event) => setText(event.target.value)} />
```

```tsx
function handleChange(event: ChangeEvent<HTMLInputElement>) {
  setText(event.target.value);
}

<input value={text} onChange={handleChange} />
```

Короткая стрелка нормальна, когда тело — один `setText`. Именованную функцию берут, когда внутри ещё маска, фильтр символов или вызов наружу. Её проще тестировать и проще отдать ребёнку одной стабильной ссылкой.

Неконтролируемое поле хранит текст в DOM. Начальное значение задают через `defaultValue`, а читают через реф в момент отправки. Его берут, когда на каждый символ перерисовывать форму не нужно: черновик живёт в инпуте, React узнаёт о нём на submit.

`value` и `defaultValue` на одном инпуте не смешивают. Первое делает поле контролируемым на всё время жизни. Второе задаёт только старт неконтролируемого. Если `value` сначала `undefined`, а после загрузки данных становится строкой, React предупредит о переходе из неконтролируемого в контролируемое. Пока данных нет, держат `value={text ?? ''}`.

Сбрасывают такое поле сменой `key` у формы или явным `setText('')`. Очистить только DOM у контролируемого инпута нельзя: следующий рендер вернёт то, что в стейте.

## 17. Как данные проходят через Redux и почему компонент после этого перерисовывается?

Единственный предусмотренный способ изменить store — отправить экшен. Компонент вызывает `dispatch`. Экшен проходит цепочку middleware. Затем reducer получает прошлый state и экшен и возвращает следующий state. Store подменяет состояние и зовёт подписчиков.

Middleware стоит посередине и видит каждый экшен. Ей доступны `dispatch` и `getState`. Она может пропустить экшен, проглотить его или отправить другой позже. Так устроены лог и запрос. Reducer при этом остаётся чистой синхронной функцией: без `fetch` и без случайных чисел. Запрос живёт в thunk или другой middleware.

`useSelector` подписывает компонент на store. После `dispatch` селектор вызывают снова и сравнивают результат с прошлым через `===`. Изменился примитив или ссылка — компонент рендерится. Вернулась та же ссылка — из-за Redux рендера нет. Родитель всё ещё может перерисовать компонент по своей причине.

Лишний рендер появляется, когда селектор каждый раз собирает новый объект: содержимое то же, ссылка новая, `===` не проходит. Такой селектор мемоизируют через `createSelector` или выбирают примитив.

Контекст на этом фоне подписывает на всё значение провайдера. Выбрать из него одно поле нельзя: при любом новом `value` просыпаются все, кто контекст прочитал. Нет экшенов и истории изменений. Контекста хватает для темы и локали. Redux берут, когда нужны точечные подписки и видно, кто какое изменение отправил.

Redux Toolkit убирает ручные константы и `switch`. `createSlice` собирает состояние и экшены, Immer позволяет писать обновление как мутацию черновика, наружу выходит новый state. `configureStore` сразу включает thunk и DevTools. RTK Query поверх этого кэширует запросы и снимает ту же гонку, что ручной `useEffect`.

Селектор другого модуля вызвать можно: это функция от всего state. Нельзя устраивать цикл импортов между слайсами. Нормализация нужна, когда один и тот же пользователь скопирован внутрь десяти заказов: его кладут в `entities.users[id]` один раз, а списки хранят id.

## 18. Зачем микрофронтенды и чем они отличаются от npm-пакета?

Микрофронтенд — часть интерфейса, которую отдельная команда разрабатывает и выкатывает относительно самостоятельно. В браузере общий шелл даёт шапку, меню и авторизацию, а зона команды рисует свой раздел. Это ответ на общую очередь релизов: чужой красный тест больше не блокирует всех.

Цена высокая. Дублируются зависимости, сквозной сценарий зависит от комбинации версий, дизайн разъезжается. Маленькой команде на одном продукте это обычно лишнее.

Module Federation загружает кусок другого уже собранного приложения в рантайме. Ремоут объявляет, какие модули отдаёт. Хост знает адрес его `remoteEntry`. Общие библиотеки, прежде всего React, описывают как shared, чтобы на странице был один экземпляр. Два React ломают хуки и контекст. Хосту не нужны исходники ремоута на своей сборке, поэтому ремоут выкатывают отдельно.

npm-пакет подключается на сборке. Версия зафиксирована в lockfile. Чтобы получить чужой фикс, хост обновляет версию и собирается заново. Несовместимое изменение видно в CI хоста, а не в браузере пользователя.

Микрофронтенд подключается, когда страницу уже открывают. Шелл можно не пересобирать. Откат — выкладка предыдущего бандла ремоута. Совместимость приходится держать контрактом пропсов и событий, а не номером в `package.json`.

Независимый деплой ломается предсказуемо: переименованный проп выезжает в прод без сборки хоста, на странице две версии дизайн-системы, баг воспроизводится только на одной комбинации версий, упавший `remoteEntry` роняет экран без своего error boundary. Общие стили с одинаковым классом `.button` перетирают друг друга. Хеш CSS Modules снимает случайное совпадение имён. Две мажорные версии одной дизайн-системы это не лечит: их либо шарят одним экземпляром, либо изолируют, и держат такой режим только на время миграции.

Общаются через пропсы шелла, общий роутер и редкие договорённые события. Импорт внутренностей чужого ремоута и общий мутабельный стор без владельца снова склеивают команды, только уже в браузере.

## 19. Чем PWA отличается от SPA и как из SPA её сделать?

SPA — это способ навигации. После первой загрузки документа переходы рисует JavaScript, браузер не запрашивает всю страницу заново. Так устроен и чистый клиентский рендер, и уже гидратированное SSR-приложение.

PWA — это способ поставки. Приложение ставят на устройство: своя иконка, своё окно, часть сценариев живёт без сети или при плохой сети. PWA может быть не SPA, а SPA может так и остаться вкладкой в браузере.

Чтобы SPA начала ставиться, нужны четыре вещи. Сайт открывается по HTTPS. В корне подключён web app manifest: имя, иконки, `display: standalone`, стартовый URL. Со страницы регистрируется service worker. Браузер предлагает установку, когда выполнены его условия: manifest, воркер, HTTPS и достаточная вовлечённость. Обычно воркер собирают через Workbox, а не пишут кэш руками.

Офлайн сам не появляется. Надо решить, какую оболочку класть в кэш заранее, какие запросы можно отдать из кэша, и что показать, когда кэша нет. Оболочку и файлы с хешем в имени отдают из кэша. Запросы к API банка из кэша не отдают: на экране останутся вчерашние остатки. Для них сеть, а при обрыве — явный запасной экран, не старый JSON.

Воркер — отдельный от страницы скрипт. DOM ему недоступен. Он перехватывает `fetch` в своей зоне. Новый воркер ставится рядом со старым и ждёт, пока закроются открытые вкладки. Пока старый жив, пользователь сидит на прежнем приложении. Если в кэш навсегда положили `index.html`, релиз не доедет вообще: страница каждый раз берёт старую оболочку и старые имена чанков. HTML запрашивают из сети, а в кэш кладут уже собранные файлы с хешем.

Service worker не путают с Web Worker. Второй считает в фоне и не видит сеть страницы. Первый как раз про сеть, кэш и установку.
