## JavaScript

### Чем отличаются `let`, `var` и `const`?

`var` живёт в области функции (или всего скрипта, если объявлен снаружи). Объявление всплывает: до строки `var x = 1` переменная уже существует и равна `undefined`, ошибки нет. В одном scope можно объявить `var x` сколько угодно раз. В `for (var i = 0; ...)` на все итерации одна и та же `i`. Колбэк, созданный в цикле, увидит итоговое значение, а не значение на своей итерации. Свойство, объявленное через `var` на верхнем уровне браузерного скрипта, ещё и попадает в `window`.

`let` и `const` живут в блоке: `if`, цикл, просто `{ }`. До строки объявления к ним нельзя обратиться. Движок уже знает, что имя занято, но значение ещё не инициализировано. Это temporal dead zone, обращение бросает `ReferenceError`, а не отдаёт `undefined`. Повторное объявление того же имени в том же блоке — синтаксическая ошибка. В `for (let i = 0; ...)` на каждую итерацию своя привязка, колбэк замыкает именно её.

`const` отличается от `let` одним ограничением: саму привязку нельзя переприсвоить. `const user = { name: 'Ann' }; user.name = 'Bob'` законно, потому что меняется содержимое объекта, а не то, на что указывает `user`. `user = {}` уже нельзя. Для константы нужен ещё и `Object.freeze`, если важно запретить мутацию.

На практике по умолчанию пишут `const`. `let` оставляют там, где переменную переприсваивают: счётчик, аккумулятор, ссылка, которую меняют по ходу функции. `var` в новом коде не используют: его всплытие и общая переменная цикла слишком часто становятся багом.

### Чем стрелочные функции отличаются от обычных в работе с `this`?

У обычной функции `this` не зашит в момент создания. Его задаёт вызов.

- `obj.method()` — `this` равен `obj`;
- `method()` просто так, в strict mode — `this` равен `undefined`, без strict это глобальный объект;
- `fn.call(ctx, a)` / `fn.apply(ctx, args)` / `fn.bind(ctx)` подставляют контекст явно;
- `new Fn()` — `this` это новый экземпляр.

Если метод оторвать от объекта и отдать как колбэк (`button.addEventListener('click', obj.save)`), в момент клика вызов уже без базы, и `this` внутри `save` не будет `obj`.

У стрелочной функции своего `this` нет. Она берёт `this` лексически, из внешней функции, в момент создания стрелки. `call`, `apply` и `bind` этот `this` не перебивают. Поэтому стрелка удобна как колбэк внутри метода: она видит тот же `this`, что и метод. И поэтому стрелка не годится как метод, которому `this` должны выдать снаружи, и не годится как конструктор: `new` на стрелке нельзя.

Отдельно стрелка не имеет своего `arguments` и не может быть генератором. В классовом поле `handleClick = () => { this... }` стрелка создаётся на экземпляре и уже замкнула его. Такой обработчик можно передавать в JSX без `bind`. Обычный метод класса при передаче как `this.handleClick` снова потеряет экземпляр, пока его не привяжут.

### Как сохранить `this` у мемоизированного метода объекта?

Мемоизация (`useCallback`, кэш, `memoize`) сохраняет саму функцию, а не способ её вызова. `this` появляется только когда функцию вызывают как метод или через `call`/`bind`.

Три рабочих способа:

```js
obj.method(); // this === obj, если method обычная функция

const bound = obj.method.bind(obj); // this зашит в bound

const wrapped = (...args) => obj.method(...args); // this берётся из вызова obj.method
```

В React тот же выбор. Если передать в ребёнка `obj.method` и ребёнок вызовет её как обычную функцию, контекст пропадёт. Если обернуть в стрелку `() => obj.method()`, контекст сохранится, но на каждом рендере родителя это новая функция, и `React.memo` у ребёнка не сработает. Стабильный вариант: один раз сделать `bind` снаружи рендера или завернуть стрелку в `useCallback` с честными зависимостями.

`bind` прямо в JSX (`onClick={obj.method.bind(obj)}`) каждый рендер создаёт новую функцию. Для мемоизированного ребёнка это то же самое, что инлайн-стрелка: проп всегда «новый».

### Разница между `||` и `??`. Когда что использовать?

Оба оператора возвращают левую часть, если она «достаточно задана», иначе правую. Различаются тем, что считать незаданным.

`||` считает незаданным любое falsy-значение: `false`, `0`, `NaN`, `''`, `null`, `undefined`.

`??` (nullish coalescing) считает незаданным только `null` и `undefined`. Ноль, пустая строка и `false` проходят как настоящие значения.

```js
const count = input ?? 1;     // 0 останется 0
const countOr = input || 1;   // 0 превратится в 1

const title = name ?? 'Гость'; // '' останется пустой строкой
const titleOr = name || 'Гость'; // '' станет 'Гость'
```

`??` берут для числа, цены, количества, индекса, булева флага и текста поля: там `0` и `''` осмысленны. `||` берут, когда любой falsy и есть «покажи запасной вариант»: запасной заголовок, запасная картинка, запасная строка для UI.

`||` и `??` нельзя смешивать в одном выражении без скобок: у них разный приоритет, и движок требует скобки явно (`(a || b) ?? c`). Опциональная цепочка с ними стыкуется естественно: `user.address?.city ?? '—'`.

### Зачем `Object.freeze`?

`Object.freeze(obj)` запрещает добавлять, удалять и перезаписывать собственные свойства объекта. Свойства становятся non-writable и non-configurable. В strict mode присваивание бросает `TypeError`, без strict оно тихо не срабатывает.

Заморозка поверхностная. Если внутри лежит другой объект, его поля по-прежнему меняются. Чтобы закрыть дерево, freeze вызывают рекурсивно по всем вложенным объектам. Массив тоже объект: после freeze нельзя сделать `push` и нельзя заменить элемент по индексу.

На практике так защищают конфиг, таблицу констант, экшен-типы и объект, который отдают наружу и не хотят, чтобы вызывающий код его помутировал. В dev-сборках Redux похожая проверка ловит мутацию state. Freeze не делает копию и не заменяет иммутабельное обновление: замороженный объект просто нельзя менять, новый всё равно создают отдельно.

Проверки: `Object.isFrozen(obj)`. `Object.seal` слабее: нельзя добавлять и удалять ключи, но существующие можно перезаписывать. `Object.preventExtensions` запрещает только новые ключи.

### Массив — это объект. Объекты передаются по значению или по ссылке?

В переменной хранится не сам объект, а ссылка на него. Присваивание и передача в функцию копируют эту ссылку. Спецификация называет это копированием значения ссылки. Два имени после `const b = a` смотрят на один объект в куче.

```js
const first = { name: 'Hello' };
const second = first;
first.name = 'Bye';
second.name; // 'Bye' — мутация видна обоим

let next = first;
next = { name: 'Other' };
first.name; // 'Bye' — переприсваивание отцепило только next
```

То же с массивом: `push`, `sort` на месте, `arr[0] = 1` меняют общий массив. `arr = arr.slice()` или `[...arr]` создают новый массив, старые ссылки его не видят. `sort` мутирует исходный, `toSorted` возвращает новый.

Примитивы копируются целиком: число, строка, boolean, `null`, `undefined`, `symbol`, `bigint`. Функция тоже объект, её передают ссылкой.

Отсюда баг «поменял аргумент внутри функции, а снаружи тоже изменилось». Если функция не должна трогать вход, она делает копию. Поверхностной хватает, когда вложенные объекты не мутируют. Глубокая нужна, когда меняют дерево.

### Почему объект как ключ обычного объекта становится `"[object Object]"`? Число `7` тоже приводится к строке?

Ключ обычного объекта проходит через `ToPropertyKey`. Если это не `symbol`, значение приводят к строке.

У объекта по умолчанию `toString()` возвращает `"[object Object]"`. Поэтому `map[{}]` и `map[{ id: 1 }]` пишут в одно и то же свойство. Два разных объекта неразличимы как ключи. Свой `toString` или `Symbol.toPrimitive` меняет строку, но ключ всё равно строка, не ссылка на объект.

Число тоже приводится: `obj[7]` и `obj['7']` — одно свойство. Булево станет `"true"` / `"false"`. Массив станет строкой своих элементов через запятую: `[1, 2]` → `"1,2"`.

`symbol` в строку не склеивается. `obj[Symbol('id')]` живёт отдельным ключом, `Object.keys` его не покажет, `Object.getOwnPropertySymbols` покажет.

Когда ключ должен остаться объектом, берут `Map`: ключи сравниваются по `SameValueZero`, объект сравнивается по ссылке, разное содержимое при той же ссылке — один ключ. `WeakMap` держит ключ слабо: когда на объект больше нет обычных ссылок, запись может забрать сборщик. Ключи `WeakMap` только объекты.

### Как переписать присваивание через вложенную деструктуризацию?

Исходного сниппета в списке не было. Типовой переход такой: цепочка свойств превращается в зеркало структуры объекта.

```js
const city = user.address.city;
const name = user.profile.name;

const {
  address: { city },
  profile: { name },
} = user;
```

Имя слева от двоеточия — ключ в источнике. Справа — переменная, которую создаём. Если имена совпадают, двоеточие не пишут: `const { id } = user`.

Вложенность повторяет объект. `address: { city }` значит «возьми свойство `address`, из него достань `city`». Можно сразу переименовать: `address: { city: userCity }`.

Если промежуточного объекта нет, деструктуризация бросит: нельзя читать свойство у `undefined`. Поэтому на каждом уровне, который может отсутствовать, ставят дефолт:

```js
const { address: { city } = {} } = user;
```

Деструктуризация читает свойства в момент присваивания. Это не живая связь: потом `user.address.city = 'Kazan'` не обновит уже созданную `city`.

### Как добавить `stage` по умолчанию и не сломать деструктуризацию?

Дефолт в деструктуризации срабатывает, когда значение `undefined`. На `null`, `0` и `''` он не подставится.

```js
const {
  stage = 'dev',
  user: { name } = {},
} = config;
```

`stage` станет `'dev'`, только если в `config` нет `stage` или там `undefined`. Вложенный `user: { name } = {}` нужен отдельно: если `user` нет, без `= {}` упадёт чтение `name`.

Эквивалентность со старым кодом сохраняют так. Раньше было `const stage = config.stage`, и отсутствующее значение оставалось `undefined`. После добавления дефолта отсутствующий `stage` уже `'dev'`. Все места, которые проверяли `if (stage === undefined)`, начнут вести себя иначе. Это и есть смысл вопроса: дефолт ставят на новое поле и не меняют разбор старых полей.

Дефолт можно поставить и на весь аргумент функции:

```js
function boot({ stage = 'dev', user: { name } = {} } = {}) {}
```

Последний `= {}` спасает вызов `boot()` вообще без объекта.

### `Promise.all`: что принимает, когда резолвится, что возвращает, как обрабатывает ошибку?

`Promise.all` принимает итерируемое: массив промисов, набор thenable, или уже готовые значения. Обычное значение оборачивается в успешный промис, поэтому `Promise.all([1, fetch(url)])` допустим.

Успех наступает, когда успешно завершился каждый элемент. В результат попадает массив значений в порядке входа, а не в порядке завершения. Третий запрос может вернуться первым, но его значение всё равно ляжет в индекс 2.

Если любой элемент отклонился, `all` сразу отклоняется той же причиной. Это fail-fast: дожидаться остальных, чтобы сформировать массив, он не будет. Сами остальные промисы при этом не отменяются. Запрос в сеть доработает, просто его результат этот `all` уже не отдаст. Отмена — отдельно, через `AbortController` на каждый `fetch`.

Пустой список резолвится сразу в `[]`. Если нужен «первый успех», это `Promise.any`. Если нужен «первый итог, успех или ошибка», это `Promise.race`.

### Чем `Promise.allSettled` отличается от `Promise.all`?

`allSettled` тоже ждёт все элементы, но не считает чужую ошибку своей. Промис `allSettled` всегда успешно резолвится, когда все устаканились.

Каждый элемент результата — объект статуса:

```js
{ status: 'fulfilled', value: data }
{ status: 'rejected', reason: error }
```

Порядок снова совпадает со входом. Дальше список фильтруют: успешные показать, по упавшим собрать причины.

Его берут для независимых кусков: несколько виджетов дашборда, пачка картинок, несколько справочников. Один упавший эндпоинт не должен стирать остальные. `Promise.all` берут, когда частичный результат опасен или бесполезен: оформить заказ можно только если прошли и резерв, и цена, и профиль.

`allSettled` тоже не отменяет запросы. Он только честно дожидается их итога.

### Как сделать промис, который всегда успешно возвращает `1`? Как получить то же без обращения к классу `Promise`?

Прямой способ:

```js
Promise.resolve(1);
```

Это уже успешный промис со значением `1`. `new Promise((resolve) => resolve(1))` делает то же, но длиннее и всё ещё использует конструктор `Promise`.

Без обращения к классу `Promise` функцию объявляют через `async`. Такая функция всегда возвращает промис, а `return` становится успешным значением:

```js
const one = (async () => 1)();
```

`await 1` внутри async тоже завернёт число в промис, но снаружи имя `Promise` по-прежнему не нужно. `async`-функция, которая бросила, вернёт отклонённый промис. Чтобы он был именно успешным, из неё выходят через `return`, а не через `throw`.

### Разница между двумя массивами: только в первом и только во втором. Сложность?

Нужны элементы, которые есть в `a` и отсутствуют в `b`, и наоборот.

Наивный вариант — для каждого элемента одного массива пройти второй через `includes`. Это `O(n * m)` сравнений и почти никакой дополнительной памяти. На длинных списках id так делать не стоит.

Нормальный вариант — множество:

```js
function diff(a, b) {
  const setA = new Set(a);
  const setB = new Set(b);

  return {
    onlyA: a.filter((item) => !setB.has(item)),
    onlyB: b.filter((item) => !setA.has(item)),
  };
}
```

Построение двух `Set` — `O(n + m)` времени и памяти. Каждый `filter` ещё один проход, внутри `has` в среднем `O(1)`. Итого время и память `O(n + m)`.

`Set` сравнивает числа и строки по значению, объекты и массивы — по ссылке. Два объекта `{ id: 1 }` для него разные. Если сравнивать надо по полю, в множество кладут `id`, а не весь объект.

Дубликаты: `Set` хранит значение один раз, но `filter` идёт по исходному массиву и сохранит повтор, если он был в `a` и его не было в `b`. Если нужен результат без повторов, фильтруют уже сам `Set` или собирают результат во второй `Set`.

## TypeScript

### Какие встроенные типы есть?

Примитивы, которые совпадают с JavaScript: `string`, `number`, `boolean`, `bigint`, `symbol`, `null`, `undefined`. Отдельно есть литералы: не просто `string`, а конкретное `'asc' | 'desc'`, не просто `number`, а `1 | 2 | 3`.

Специальные типы:

- `any` отключает проверку. Значение можно отдать куда угодно и прочитать у него что угодно. Ошибка уедет в рантайм.
- `unknown` значит «значение есть, тип мы ещё не доказали». Прежде чем читать поле или вызвать метод, тип сужают.
- `never` — пустое множество значений. В эту ветку управление не приходит.
- `void` — функция завершилась, полезного возврата нет. Для колбэков, которые вызывают ради побочного эффекта.
- `object` — любой не-примитив. Слишком широкий, чтобы читать поля.

Составные: массивы `User[]` и `Array<User>`, кортежи `[string, number]`, объектные типы, `enum`, объединения `A | B`, пересечения `A & B`, дженерики и утилитарные типы из стандартной библиотеки.

`null` и `undefined` при `strictNullChecks` не входят молча в `string`. Их добавляют явно: `string | null`.

### Зачем дженерики?

Дженерик связывает типы входа и выхода, не фиксируя конкретный тип заранее.

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

const id = first([1, 2, 3]);       // number | undefined
const name = first(['a', 'b']);    // string | undefined
```

Если написать `any[]`, на выходе будет `any`, и компилятор перестанет помогать. Если написать отдельную функцию на строки и отдельную на числа, логика продублируется. Дженерик оставляет одну функцию и переносит тип элемента в результат.

Ограничение пишут через `extends`, когда внутри правда нужны поля:

```ts
function pluckId<T extends { id: string }>(items: T[]): string[] {
  return items.map((item) => item.id);
}
```

Без ограничения у `T` нельзя прочитать `id`. Несколько параметров описывают связь между сущностями: `function merge<A, B>(a: A, b: B): A & B`.

Дженерик у компонента React делает то же с пропсами: список не знает заранее, что в `item`, но `renderItem` получает ровно этот тип, а не `any`.

### Утилитарные типы и какие используют чаще

Утилитарный тип — готовый дженерик, который строит новый тип из старого. Свои поля руками не копируют.

| Тип | Что делает |
| --- | --- |
| `Partial<T>` | все поля становятся необязательными |
| `Required<T>` | все поля обязательны |
| `Pick<T, K>` | оставить только перечисленные ключи |
| `Omit<T, K>` | убрать перечисленные ключи |
| `Record<K, V>` | объект, у которого ключи типа `K`, значения типа `V` |
| `Readonly<T>` | поля нельзя перезаписать |
| `ReturnType<F>` | тип того, что возвращает функция |
| `Parameters<F>` | кортеж аргументов функции |
| `NonNullable<T>` | выкидывает `null` и `undefined` |
| `Extract<T, U>` / `Exclude<T, U>` | оставляют или убирают члены объединения |

На фронте чаще всего:

- `Partial<User>` для патча формы, где пришло не всё;
- `Pick<User, 'id' | 'name'>` и `Omit<ButtonProps, 'onClick'>` для узких пропсов;
- `Record<Status, string>` для словаря подписей по конечному набору статусов;
- `ReturnType<typeof fetchUser>`, чтобы тип ответа жил в одном месте — у функции.

`Readonly` не глубокий: вложенный объект по-прежнему мутабельный. `Partial` тоже на один уровень.

### Как типизировать пустой объект, чтобы он оставался пустым?

`{}` в TypeScript почти не значит «объект без ключей». Пустой объектный тип описывает любое значение, кроме `null` и `undefined`: в него можно положить строку, число и объект с полями. Это частый источник ложного ощущения, что тип «пустой».

Чтобы нельзя было записать ни одного свойства:

```ts
type Empty = Record<string, never>;

const draft: Empty = {};
// draft.id = '1'  ошибка: string не входит в never
```

`Record<string, never>` читается как «у любого строкового ключа значение типа `never`», а значения типа `never` не существует. Поэтому единственный обитатель такого типа — объект, в который ничего не кладут.

Если нужно именно «в эту функцию нельзя передать лишние поля», одного `Empty` мало: TypeScript структурный и лишние поля отсекает в основном у объектных литералов. Переменная более широкого типа в узкий параметр всё равно может пройти, если обязательные поля совпали.

### Где нужен `never`?

`never` ставится там, где значений не бывает.

Исчерпывающий `switch`. После всех вариантов объединения в `default` тип должен стать `never`. Если завтра в union добавят статус и забудут ветку, в `default` попадёт этот статус, присваивание в `never` упадёт на компиляции:

```ts
function label(status: 'open' | 'closed'): string {
  switch (status) {
    case 'open':
      return 'Открыт';
    case 'closed':
      return 'Закрыт';
    default: {
      const exhaustive: never = status;
      return exhaustive;
    }
  }
}
```

Функция, которая всегда бросает (`function fail(message: string): never`) или крутится бесконечно, тоже возвращает `never`. Её можно вызывать в ветке, после которой код не продолжается.

`never` появляется само, когда из объединения вычли все члены (`Exclude<'a' | 'b', 'a' | 'b'>`) или когда фильтр типов отсёк все варианты. Пустой массив сам по себе не `never`, но `[] as const` в неправильном контексте может привести к `never[]`, если компилятору не за что зацепиться.

### Какой тип у ошибки в `catch` и почему? Как безопасно прочитать `message`?

В JavaScript `throw` и `reject` принимают что угодно: `Error`, строку, число, объект с бэкенда, `undefined`. Поэтому TypeScript не имеет права считать, что в `catch` всегда `Error`.

При включённом `useUnknownInCatchVariables` (он входит в современный `strict`) тип переменной `catch` — `unknown`. Пока тип не сузили, у значения нельзя прочитать `message`: у `unknown` нет полей.

Сужение через `instanceof` — это и есть проверка типа в рантайме:

```ts
try {
  await save();
} catch (error: unknown) {
  if (error instanceof Error) {
    console.log(error.message);
  } else {
    console.log('Неизвестная ошибка');
  }
}
```

Та же проверка, вынесенная в функцию с предикатом `error is Error`, называется пользовательским type guard. После него в ветке `if` компилятор уже видит `Error`.

У ошибок API часто нет прототипа `Error`: пришёл plain object `{ message, code }`. `instanceof Error` тогда ложен. Для них пишут отдельный guard, который проверяет форму объекта, и только потом читают `message`.

### Как пишут пользовательские type guards?

Обычная функция, у которой возвращаемый тип — предикат `value is SomeType`, а не `boolean`.

```ts
type User = { id: string; name: string };

function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    typeof value.id === 'string' &&
    'name' in value &&
    typeof value.name === 'string'
  );
}
```

Снаружи это `boolean`. Для компилятора `true` означает «в этой ветке `value` имеет тип `User`». `false` означает «эту форму отсюда вычли».

Guard обязан быть честным. Если функция врёт и возвращает `true` для мусора, компилятор поверит, а падение случится позже, на чтении поля. `typeof null` в JavaScript равен `'object'`, поэтому проверку на `null` пишут отдельно. Массив тоже объект: если массив не подходит, его отсекают через `Array.isArray` до чтения полей объекта.

### Зачем `infer`?

`infer` объявляет переменную типа прямо внутри условного типа и «вытаскивает» кусок чужого типа.

```ts
type ElementOf<T> = T extends (infer Item)[] ? Item : never;
type Unpack<T> = T extends Promise<infer Value> ? Value : T;

type Id = ElementOf<string[]>;      // string
type Data = Unpack<Promise<User>>;  // User
```

Читается так: если `T` оказался массивом чего-то, назови это «что-то» `Item` и верни его. Если нет — `never`.

Так устроены библиотечные `ReturnType`, `Parameters`, `Awaited`, тип пропсов компонента. Свой `infer` пишут, когда тип завернут в дженерик (`AxiosResponse<T>`, `Promise<T>`, кортеж аргументов) и нужно достать внутренность, не копируя её руками.

`infer` работает только в ветке `extends` условного типа. Несколько `infer` в одном условном типе вытаскивают несколько кусков сразу, например аргумент и возврат функции.

### Зачем `satisfies`?

Аннотация `: SomeType` проверяет значение и одновременно расширяет его тип до `SomeType`. Узкие литералы при этом пропадают: `'/'` становится просто `string`.

`satisfies` проверяет совместимость и оставляет выведенный тип значения как был.

```ts
const routes = {
  home: '/',
  profile: '/profile',
} satisfies Record<string, string>;

routes.home; // тип '/' , не string
```

Опечатка в значении поймается: число вместо строки не пройдёт `Record<string, string>`. Лишний или забытый ключ тоже можно поймать, если справа более точный тип, а не бесконечный `Record<string, ...>`.

Его ставят на таблицы роутов, карты статусов на компоненты, конфиги, где по ключу потом индексируют и хотят автодополнение конкретного ключа. `as const` сужает ещё сильнее, но сам по себе форму не проверяет. Их можно совместить: `as const satisfies Expected`.

### Как типизировать JS-библиотеку без её исходников? Что лежит в declaration file?

Если у пакета нет типов и нет `@types/имя`, рядом с проектом пишут декларацию модуля. Исполняемого кода в ней нет, только формы значений:

```ts
declare module 'some-lib' {
  export function parse(input: string): { value: number };
  export const version: string;
}
```

Дальше `import { parse } from 'some-lib'` проверяется по этому файлу, а в рантайме по-прежнему выполняется настоящий JavaScript пакета. Декларация может соврать: компилятор не сверяет её с телом библиотеки. Поэтому описывают тот кусок API, которым реально пользуются, и помечают сомнительные места явно, а не через `any` на весь модуль.

В файле бывают `export function`, `export class`, `export interface`, перегрузки, `export default`. Для пакета, который вешает глобал, вместо `declare module` пишут `declare function` на верхнем уровне.

Если типы когда-нибудь появятся в самом пакете, свою декларацию убирают, иначе два описания одного модуля начнут пересекаться.

### Как объявить глобальную константу в `.d.ts` и куда положить файл?

Константу, которую кто-то кладёт в рантайм извне (webpack `DefinePlugin`, `window`), описывают без инициализации:

```ts
declare const __APP_VERSION__: string;
```

Такой файл без `import`/`export` является скриптом, и `declare const` становится глобальным.

Если в файле уже есть импорт, он модуль, и верхнеуровневый `declare` наружу не протекает. Глобал тогда кладут в `declare global`, а пустой `export {}` делает файл модулем сознательно:

```ts
export {};

declare global {
  const __APP_VERSION__: string;

  interface Window {
    dataLayer: Array<Record<string, unknown>>;
  }
}
```

Чтобы TypeScript вообще прочитал файл, он должен попасть в программу: лежать внутри `include` (часто `src/**/*.d.ts` или `global.d.ts` в корне) и не попасть в `exclude`.

За готовые типы из `node_modules` отвечают другие опции:

- `compilerOptions.typeRoots` — каталоги, где искать пакеты типов. По умолчанию `node_modules/@types`;
- `compilerOptions.types` — если массив задан, автоматически подключаются только перечисленные пакеты. Остальные `@types` придётся импортировать самому. Пустой массив отключает автоподключение;
- `include` / `files` — файлы самого проекта, в том числе свои `.d.ts`.

## Браузер и сеть

### Что происходит от Enter на `sberbank.ru` до отрисовки страницы?

Браузер разбирает введённое как URL. Если схема не написана, подставляет `https://`. Дальше проверяет кэш HTTP, service worker и HSTS: мог ли этот хост открываться только по защищённому соединению.

DNS резолвит имя в IP. Смотрит кэш браузера, операционную систему, резолвер провайдера. На это уходит отдельное время до первого байта.

Дальше TCP-соединение с сервером и TLS: проверка сертификата, обмен ключами. После этого канал шифрованный, и только тогда уходит HTTP-запрос. В запросе метод, путь, заголовки, cookie этого хоста. Сервер отвечает статусом и телом. Для первой загрузки страницы тело — HTML.

Парсер читает HTML сверху вниз и строит DOM. Внешний CSS он запрашивает и до построения CSSOM может блокировать первую отрисовку: без стилей браузер не знает геометрию. Скрипт без `async` и `defer` блокирует парсер: пока скрипт не скачается и не выполнится, разбор HTML стоит. Скрипт с `defer` качается параллельно и выполнится после разбора документа, до `DOMContentLoaded`, в порядке появления в разметке.

Когда есть и DOM, и CSSOM, браузер строит дерево отрисовки из видимых узлов. Дальше layout считает размеры и координаты, paint записывает пиксели, composite собирает слои на GPU. Пользователь видит кадр.

Если это SPA, в этом HTML ещё мало интерфейса. Каркас появится после выполнения JS, запроса данных и гидрации или клиентского рендера. Метрики на этом пути разные: TTFB ждёт первый байт, FCP — первую отрисовку, LCP — крупнейший контент.

### В какой момент выполняется JavaScript во время парсинга HTML?

Парсер идёт по документу. Классический `<script src="app.js"></script>` без атрибутов останавливает этот проход: браузер качает файл и выполняет его сразу, и только потом читает следующие теги. Поэтому такой скрипт в `<head>` не увидит ещё не разобранный `<body>`, если не дождётся DOM.

`defer` качает файл параллельно с продолжением парсинга. Выполнение откладывается до конца разбора документа. Несколько `defer` сохраняют порядок в HTML. Это нормальный способ подключать модули приложения.

`async` тоже качается параллельно, но выполняется как только файл готов, не дожидаясь соседей. На время выполнения парсер снова стоит. Порядок между двумя `async` не гарантирован. Так подключают независимую аналитику, которой всё равно, разобран ли уже весь документ.

Инлайн-скрипт без `src` выполняется в ту же секунду, когда парсер до него дошёл. `<script type="module">` по умолчанию ведёт себя как `defer` и тоже ждёт конца парсинга. `document.write` из отложенного скрипта уже не вставляет разметку в текущий проход так, как из синхронного.

### Как отслеживать изменения между вкладками?

Вкладки одного origin не делят JavaScript-память. Общие каналы такие.

`localStorage` плюс событие `storage`. Запись в одной вкладке порождает `storage` во всех остальных вкладках того же origin. В той вкладке, которая писала, события нет. В объекте события есть ключ, старое и новое значение. `sessionStorage` так не работает: у каждой вкладки свой.

`BroadcastChannel` создают с одним именем канала. `postMessage` получают все открытые вкладки origin, включая при желании отправителя, если слушать там же. Удобно слать не строку, а команду: `{ type: 'logout' }`.

`SharedWorker` — один воркер на несколько вкладок. Они подключаются портами и могут держать общее состояние в воркере.

Service worker видит подконтрольные клиенты через `clients.matchAll()` и может разослать им `postMessage`. Так делают, когда логика и так живёт в воркере: пуш, синхронизация кэша.

Cookie сама вкладки не будит. Пока кто-то не перечитает её и не пошлёт сообщение, другие вкладки не узнают, что сессия изменилась. Типичный продукт: логаут в одной вкладке пишет флаг в `localStorage` или шлёт сообщение в канал, остальные ловят его и чистят память.

### Какие есть типы и методы запросов?

Методы HTTP различают намерение.

- `GET` читает ресурс. Безопасный: не должен менять данные на сервере. Идемпотентный: повтор того же запроса даёт тот же эффект.
- `POST` создаёт ресурс или выполняет команду. Повтор может создать вторую заявку.
- `PUT` заменяет ресурс целиком. Повтор с тем же телом идемпотентен.
- `PATCH` меняет часть ресурса.
- `DELETE` удаляет. Повтор обычно идемпотентен: ресурс уже отсутствует.
- `HEAD` как `GET`, но без тела. Проверяют заголовки и кэш.
- `OPTIONS` спрашивает, какие методы и заголовки разрешены. Браузер сам шлёт его как CORS preflight перед «непростым» запросом.

По форме обмена:

- обычный запрос `fetch` или XHR: один запрос, один ответ;
- GraphQL чаще одним `POST` с текстом запроса, схема одна, выборка разная;
- SSE: одно длинное HTTP-соединение, сервер дописывает события клиенту;
- WebSocket: отдельный протокол поверх соединения, кадры в обе стороны;
- короткий и длинный опрос, если сокета нет.

Идемпотентность важна на оплате и создании заказа: повторный `POST` без ключа идемпотентности может списать деньги дважды. `GET` для этого не используют ещё и потому, что его кэшируют и пишут в логи целиком вместе с query.

### Long polling, short polling, WebSocket

В списке это прозвучало как longbilling / shortbilling. Речь про способы доставки обновлений.

Короткий опрос: клиент сам раз в N секунд делает обычный запрос. Реализация простая, сервер остаётся обычным HTTP. Цена — пустые ответы, нагрузка и задержка до следующего тика. Если интервал 10 секунд, событие может приехать через 10 секунд.

Длинный опрос: клиент открывает запрос, сервер не отвечает, пока не появится событие или не истечёт таймаут. Как только ответ пришёл, клиент сразу открывает следующий. Задержка меньше, висящих соединений много, обрывы и прокси с таймаутом надо учитывать. Между ответом и следующим запросом событие можно пропустить, если нет курсора или номера последнего события.

WebSocket после рукопожатия держит соединение, и обе стороны шлют кадры когда угодно. Подходит для чата, статусов, совместного редактирования, живых котировок. Дороже в инфраструктуре: липкие сессии, балансировка, переподключение, порядок сообщений, что делать с офлайном.

Если данные идут только от сервера к клиенту, часто хватает SSE: это HTTP, автоматический reconnect, проще прокси. Сокет нужен, когда клиент тоже часто пишет в тот же канал.

### Что такое cookie, `HttpOnly` и `Secure`? Где они на практике?

Cookie — маленькая пара имя/значение, которую сервер просит браузер запомнить заголовком `Set-Cookie`. Браузер сам прикладывает её к следующим запросам на подходящий хост, путь и схему. JavaScript может читать и писать cookie через `document.cookie`, если это не запретили.

`HttpOnly` запрещает доступ из JavaScript. Скрипт, попавший на страницу через XSS, не прочитает сессию из `document.cookie`. Сам запрос браузер всё равно отправит, поэтому CSRF закрывают отдельно, не этим флагом.

`Secure` значит: браузер отправит cookie только по HTTPS. По голому HTTP она не уйдёт.

`SameSite` ограничивает отправку с чужого сайта. `Lax` шлёт cookie при обычном переходе на вас, но не при чужом POST. `Strict` не шлёт даже при переходе по ссылке с другого сайта. `None` шлёт кросс-сайтово и обязана стоять вместе с `Secure`.

На практике сессию и refresh-токен кладут в cookie с `HttpOnly`, `Secure` и `SameSite=Lax` или `Strict`. Access-токен тогда не торчит в `localStorage`, где его читает любой XSS. Короткий несекретный флаг интерфейса можно оставить доступным из JS. Размер cookie ограничен, и она уходит на каждый запрос, поэтому туда не кладут профиль целиком.

### Какие базы знаешь?

Фронтенд в базу почти никогда не ходит напрямую. Ходит бэкенд, а браузер видит контракт API. На собесе достаточно назвать классы и зачем они, не притворяясь администратором Postgres.

Реляционные — PostgreSQL, MySQL. Таблицы, связи, транзакции. Заказы, пользователи, платежи: то, что нельзя «примерно» записать.

Ключ-значение и кэш — Redis. Сессии, лимиты запросов, короткоживущие данные, очередь. Оттуда фронт получает быстрый повтор, но данные могут быть чуть старее источника правды.

Документные — MongoDB. Гибкая структура документа, когда набор полей плавает. Схема всё равно нужна на границе API, иначе клиент разъедется.

Аналитические — ClickHouse и похожие. События, отчёты, большие выборки. В интерфейс приходят уже агрегаты, не сырые миллионы строк.

Для фронта из этого следуют практические вещи: пагинация, а не «отдай всю таблицу», идемпотентность записи, понимание, что список может быть из кэша и устареть, и что фильтр лучше отдать на сервер, если данных много.

## React

### Что нового в React 18 и 19? Какие хуки появились?

React 18 сменил точку входа на `createRoot`. Обновления стали батчиться и в промисах, и в таймерах: несколько `setState` подряд дают один рендер. Появился конкурентный рендер. Срочное обновление (ввод в инпут) может обогнать несрочное (тяжёлый список), если несрочное завернуть в `startTransition`.

Новые хуки 18:

- `useTransition` и `useDeferredValue` помечают обновление как несрочное;
- `useId` даёт стабильный id и на сервере, и на клиенте, чтобы не разъехались `label` и поле;
- `useSyncExternalStore` подписывает компонент на внешний стор так, чтобы серверный HTML и клиент не разошлись;
- `useInsertionEffect` вставляет стили до layout. Это крюк для CSS-in-JS, в прикладном коде он почти не нужен.

Suspense в 18 нормально работает со стримингом SSR: оболочку отдают сразу, медленный кусок доезжает потоком.

React 19 добавляет хуки под формы и серверные сценарии:

- `use` читает промис или контекст;
- `useActionState` хранит результат экшена формы: данные, ошибку, признак отправки;
- `useOptimistic` показывает временное значение, пока запрос не подтвердил его;
- `useFormStatus` из `react-dom` даёт вложенной кнопке статус родительской формы, без прокидывания пропсов;
- `ref` передаётся обычным пропом, `forwardRef` для нового кода не нужен;
- провайдер контекста можно писать как `<Theme value={...}>`.

В 19.2 появился `useEffectEvent`: колбэк всегда видит свежие пропсы, но не входит в зависимости эффекта и не перезапускает подписку.

### Что делает `use`?

`use` принимает thenable или контекст.

```tsx
const user = use(userPromise);
const theme = use(ThemeContext);
```

Если передан промис и он ещё не завершён, компонент приостанавливается. Ближайший `Suspense` показывает fallback. Когда промис успешно завершится, рендер продолжится уже со значением. Если промис отклонится, ошибку поймает ближайший error boundary.

Промис должен быть стабильным между попытками рендера. Если создавать `fetch()` прямо в рендере, каждый проход получит новый промис, и компонент будет приостанавливаться снова. Промис поднимают выше, в кэш или в фреймворк, который умеет дедуплицировать запрос.

С контекстом `use` ведёт себя как `useContext`: возвращает текущее значение провайдера.

Главное отличие от остальных хуков: `use` можно вызывать после условия. Правила хуков про порядок вызовов на него не распространяются так же жёстко. Остальные хуки по-прежнему нельзя прятать в `if`.

### Какие хуки стоит держать в голове?

Хук нужен, чтобы данные жили между рендерами компонента. React узнаёт, какой вызов какому состоянию соответствует, по порядку вызовов. Поэтому хук нельзя ставить в цикл, условие и вложенную функцию: порядок разъедется, и состояние прилипнет не к тому вызову.

Состояние и ссылка: `useState`, `useReducer`, `useRef`. Редьюсер берут, когда следующее состояние зависит от нескольких связанных кусков и от типа события.

Эффекты: `useEffect` после отрисовки, `useLayoutEffect` до отрисовки кадра, `useInsertionEffect` для вставки стилей.

Мемоизация: `useMemo` кэширует значение, `useCallback` кэширует функцию.

Контекст и внешний мир: `useContext`, `useSyncExternalStore`.

Конкурентность: `useTransition`, `useDeferredValue`, `useId`.

React 19: `use`, `useActionState`, `useOptimistic`, `useFormStatus`, плюс `useEffectEvent` в 19.2.

На собесе не обязательно перечислять все. Достаточно сказать, чем состояние отличается от рефа и эффекта, и зачем появились хуки 18 и 19.

### Бывают ли компоненты без состояния?

Да. Компонент может быть функцией одних только пропсов: кнопка, строка таблицы, форматирование цены, иконка. Внутри нет `useState`, нет запросов, нет подписок.

Такой компонент всё равно участвует в рендере. Он перерисуется, когда родитель перерисуется и передаст новые пропсы, или когда изменится контекст, который он читает. Отсутствие своего состояния не означает, что React его пропускает. Пропуск — это уже `memo` и сравнение пропсов.

Состояние при этом живёт выше: в родителе, в сторе, в URL. Компонент получает уже готовые данные и колбэк «что сделать по клику». Так проще тестировать и переиспользовать кусок.

### Зачем `key` при рендере списка? Что происходит при смене `key`?

При обновлении списка React сопоставляет старых детей с новыми. `key` — это личность элемента в этом сопоставлении. По нему React понимает: этот пункт переехал на другую позицию, этот удалился, этот появился.

Если ключа нет, React использует индекс. Пока список только дописывается в конец, это часто незаметно. Как только элемент вставляют в середину, удаляют или сортируют, состояние позиции прилипает к номеру, а не к сущности. Инпут третьей строки начинает показывать текст, который пользователь вводил во второй. Фокус и локальный `useState` едут вместе с индексом.

Ключом делают стабильный id сущности. Индекс годится только для статичного списка, который не переставляют и у которого нет состояния у пунктов.

Смена `key` у уже стоящего компонента — это не обновление пропсов. React размонтирует старый экземпляр и монтирует новый. Сбрасываются `useState`, рефы и подписки. Сначала cleanup эффектов старого, потом монтирование нового: расчёт первого рендера, заполнение рефов на DOM, `useLayoutEffect`, отрисовка кадра, `useEffect`.

Этим пользуются сознательно. `key={userId}` на форме обнуляет её при смене пользователя, и не нужно руками сбрасывать десять полей. Менять `key` на каждом вводе нельзя: компонент будет умирать на каждый символ.

### Что такое Virtual DOM?

Virtual DOM — это описание дерева интерфейса обычными JavaScript-объектами. JSX компилируется в вызовы, которые возвращают такие объекты: тип, пропсы, дети. Это не настоящие узлы браузера и не копия экрана.

Цикл такой. Изменилось состояние или пропсы, функция компонента снова вернула описание. React сравнивает его с предыдущим описанием того же места в дереве. На этапе commit в настоящий DOM уходят только те операции, которые отличаются: вставить узел, поменять текст, снять атрибут.

Так UI можно описывать целиком «как он должен выглядеть», а не командами «создай div, потом поменяй третий ребёнок». Сравнение стоит своего времени. Если компонент рендерится слишком часто или каждый раз создаёт огромное новое поддерево, виртуальный DOM это не отменит. Он про модель обновления, а не про то, что любой React быстрее ручного DOM.

В современном React за сопоставление отвечает Fiber: у узла есть приоритет, работу можно дробить и более срочный ввод может пройти раньше тяжёлого пересчёта.

### Как оптимизировать ререндеры?

Сначала смотрят, кто рендерится и почему. React Profiler показывает длительность и причину: изменились пропсы, состояние, контекст или родитель. Оптимизировать без этого легко ускорить то, что и так дёшево.

Дальше убирают лишние причины:

- состояние опускают ближе к месту, где оно нужно. Стейт в корне перерисовывает всё дерево;
- дорогой расчёт не повторяют в рендере без нужды. Если он правда дорогой и входы те же, его кэширует `useMemo`;
- колбэк, который уходит в мемоизированного ребёнка, стабилизируют через `useCallback`;
- ребёнка оборачивают в `React.memo`, если он тяжёлый и часто получает те же пропсы;
- контекст дробят. Одно значение «тема + данные котировок» будет будить всех подписчиков темы на каждый тик;
- статичную часть передают через `children`: она не пересоздаётся, когда меняется состояние родителя-обёртки;
- несрочный кусок помечают через `startTransition` или `useDeferredValue`, чтобы ввод не ждал тяжёлый список.

Новый объект или функция в пропсах на каждом рендере ломают `memo`: ссылка другая, сравнение считает проп изменившимся. Мемоизация всех компонентов подряд сама сравнивает пропсы и держит прошлые значения. Её ставят на измеренный горячий путь.

### Чем `useMemo` отличается от `React.memo`? Можно ли не перерисовать `memo`-компонент, даже если пропсы изменились?

`useMemo` работает внутри функции компонента. Он запоминает результат вычисления, пока не изменятся зависимости. Компонент при этом рендерится как обычно.

`React.memo` оборачивает сам компонент. Перед вызовом функции React поверхностно сравнивает новые пропсы с прошлыми. Если все сравнились через `Object.is`, функцию не вызывают, на экран остаётся прошлый результат.

Второй аргумент `memo` — своя функция `(prev, next) => boolean`. `true` значит «считай, что пропсы те же, рендер не нужен». Она может вернуть `true`, даже если какое-то поле изменилось. Формально так можно заставить компонент не перерисоваться при новых пропсах.

Делать так стоит только если проигнорированное поле не влияет на то, что компонент рисует. Иначе пользователь увидит старые данные при уже новых пропсах, и баг будет выглядеть как «React завис». Обычный путь — не передавать лишнее поле, а не врать в сравнении.

### `useCallback`: что делает и когда нужен?

`useCallback(fn, deps)` возвращает ту же функцию, пока зависимости не изменились. Это тот же приём, что `useMemo(() => fn, deps)`, только сразу про функцию.

Сам родитель от этого быстрее не рендерится. Выгода появляется у потребителя. `React.memo`-ребёнок сравнивает проп `onSave`. Если каждый рендер родителя создаёт новую стрелку, сравнение всегда видит новую ссылку и ребёнок рендерится. Стабильный `useCallback` даёт ту же ссылку, и `memo` может пропустить рендер.

Вторая причина — зависимости другого хука. Эффект или `useMemo`, который принимает функцию, не должен перезапускаться только потому, что родитель перерисовался. Функцию тогда держат в `useCallback` и кладут в массив зависимостей.

Если функцию используют тут же в JSX обычного ребёнка без `memo` и без эффекта, `useCallback` ничего не меняет. Зависимости при этом должны быть честными: пустой массив и внутри чтение свежего стейта дадут устаревшее замыкание.

### Когда вызывается `useEffect`? Когда он, а когда другие хуки?

`useEffect` запускается после того, как React закоммитил изменения и браузер нарисовал кадр. Первый запуск — после монтирования. Дальше эффект запускается, только если изменилась зависимость (сравнение через `Object.is`). Перед новым запуском и при размонтировании вызывается cleanup предыдущего.

В Strict Mode в разработке React дополнительно монтирует, размонтирует и монтирует снова, чтобы проявился пропущенный cleanup. В проде этого двойного цикла нет.

Эффект нужен для синхронизации с миром снаружи React: запрос, подписка, таймер, лог, интеграция с библиотекой, которая сама трогает DOM.

Его не используют, если:

- значение считается из пропсов и стейта. Это просто код рендера. Копировать его в стейт эффектом — лишний кадр и источник рассинхрона;
- надо измерить DOM и что-то поправить до показа кадра. Это `useLayoutEffect`, иначе пользователь увидит мигание;
- надо отреагировать на клик. Это обработчик события. Эффект на каждое изменение значения тут лишний;
- надо подписаться на внешний стор. Это `useSyncExternalStore`;
- внутри эффекта нужен свежий колбэк, но подписку пересоздавать нельзя. В 19.2 это `useEffectEvent`.

### Чем `useEffect` отличается от `useLayoutEffect`?

Оба смотрят на массив зависимостей и оба умеют cleanup. Разница во времени.

`useLayoutEffect` выполняется после обновления DOM и до того, как браузер отдаст кадр пользователю. Можно измерить размер узла и сразу поменять состояние. Пользователь не увидит промежуточный неправильный кадр. Плата: пока эффект не закончится, отрисовка этого кадра ждёт. Тяжёлая работа здесь бьёт по отзывчивости.

`useEffect` выполняется уже после отрисовки. Подписка и запрос не задерживают первый кадр. Если из него тут же сделать `setState` на геометрию, пользователь может на миг увидеть старую позицию.

`useLayoutEffect` берут для тултипа, который не должен вылезти за экран, для фокуса и скролла к только что вставленному элементу, для измерения, от которого зависит позиция. Запрос данных там не делают. На сервере `useLayoutEffect` не выполняется, React предупреждает об этом: серверный HTML и первый клиентский кадр могут разойтись. Для кода, который должен жить и там и там, оставляют `useEffect`.

### Влияет ли `useRef` на жизненный цикл?

`useRef(initial)` возвращает один и тот же объект `{ current }` на всё время жизни экземпляра компонента. Запись в `ref.current` ничего не сообщает React. Повторного рендера нет, эффект с зависимостью `[ref]` не перезапустится, потому что сам объект рефа не менялся.

Поэтому реф не подходит для данных, от которых зависит картинка на экране. Подошёл ответ запроса, который надо показать, — это `useState`. Надо запомнить между рендерами id запроса, прошлый проп или экземпляр класса без отрисовки — это реф.

Реф на DOM-узел React заполняет перед эффектами, на том же коммите, что и `useLayoutEffect`. В `useLayoutEffect` узел уже доступен. Когда узел размонтируется, React запишет в такой реф `null`. Своё значение, положенное в реф руками, React не очистит: это делает cleanup эффекта, который значение туда положил.

Смена `key` у компонента создаёт новый экземпляр и новый реф. Старый уходит вместе со старым экземпляром.

### Реф заполнили для не-admin, потом пользователь стал admin. В чём проблема?

Реф не участвует в рендере и сам не сбрасывается при смене пропса. Если его заполнили в ветке «обычный пользователь», смена роли на admin не сотрёт `.current`.

Типичный хук выглядит так: эффект с пустым массивом зависимостей один раз находит узел или создаёт клиент для не-админа и кладёт его в реф. Позже `isAdmin` становится `true`, компонент перерисовывается, но эффект не запускается снова. Админская ветка видит, что реф уже заполнен, и считает инициализацию выполненной. Внутри остаётся клиент, подписка или DOM-узел с правами обычного пользователя. Либо узел уже снят с экрана, а реф всё ещё на него указывает: это detached node, вызовы на нём молча ничего не меняют в интерфейсе.

Чинится это зависимостью от роли и cleanup:

```tsx
useEffect(() => {
  if (!isAdmin) {
    ref.current = createUserClient();
  } else {
    ref.current = createAdminClient();
  }

  return () => {
    ref.current?.destroy();
    ref.current = null;
  };
}, [isAdmin]);
```

При смене роли старый клиент уничтожается, реф обнуляется, создаётся клиент уже новой роли. Проверка `if (ref.current) return` без учёта роли как раз и есть баг: она путает «уже инициализировали когда-то» с «инициализировали для текущих прав».

### Как обрабатывать ошибки и загрузку у асинхронных запросов?

У запроса четыре осмысленных состояния: ещё не начинали, идёт, успех, ошибка. Их лучше хранить явно, а не набором независимых флагов `isLoading` и `error`, которые можно включить одновременно.

На каждый статус свой интерфейс. Пока данных нет — скелет или спиннер. Ошибка сети — сообщение и повтор, не пустой экран. Успех — данные. Повторный запрос при уже показанных данных часто оставляют старый экран и показывают тихий индикатор, чтобы макет не прыгал.

Ошибку промиса ловят в `try/catch` вокруг `await` или вторым колбэком `then`. Error boundary ловит ошибку рендера и ошибку в `use`, если промис отклонился во время приостановки. Он не ловит `throw` внутри `onClick` и не ловит reject, который никто не пробросил в рендер. В обработчике события свой `catch`, затем `setError`.

Ошибку валидации поля не смешивают с падением сети. Первая рисуется у инпута, вторая — на уровне формы или страницы. При уходе со страницы поздний `setState` не должен всплыть: запрос отменяют или игнорируют результат.

### Когда нужен `AbortController`?

Контроллер нужен, когда ответ может приехать уже бесполезным, и запрос лучше остановить на сети, а не только выбросить результат.

Такие случаи:

- пользователь изменил строку поиска, старый запрос ещё идёт;
- сменился id на странице, маршрут или фильтр;
- компонент размонтировался;
- новый клик «сохранить» отменяет предыдущую попытку;
- таймаут: свой `abort()` по таймеру, если запрос завис.

`fetch` принимает `signal`. Вызов `controller.abort()` отклоняет промис ошибкой с именем `AbortError`. Её не показывают как ошибку продукта. В cleanup эффекта аборт вызывают всегда, когда зависимости эффекта изменились: именно смена зависимостей означает, что прошлый запрос больше не актуален.

Одного флага `ignore` достаточно, чтобы не записать старые данные в стейт, но запрос при этом докачается и займёт соединение. Аборт снимает и это. Флаг всё равно полезен: между `abort` и точкой `setState` уже разобранный ответ может успеть прийти.

### Как убрать гонку в `useFetch`, если второй запрос завершился раньше первого?

Гонка выглядит так. Ушли за `/users/1`. Быстро переключились на `/users/2`. Ответ про второго пришёл раньше и записал верные данные. Потом пришёл ответ про первого и затёр их. На экране первый пользователь при адресе второго.

Защита — при смене URL выкидывать предыдущий результат и по возможности отменять запрос:

```tsx
useEffect(() => {
  const controller = new AbortController();
  let ignore = false;

  setError(null);

  fetch(url, { signal: controller.signal })
    .then((response) => {
      if (!response.ok) throw new Error('Request failed');
      return response.json();
    })
    .then((data) => {
      if (!ignore) setData(data);
    })
    .catch((error: unknown) => {
      if (ignore) return;
      if (error instanceof DOMException && error.name === 'AbortError') return;
      setError(error);
    });

  return () => {
    ignore = true;
    controller.abort();
  };
}, [url]);
```

Cleanup этого эффекта выполняется перед запуском эффекта с новым URL и при размонтировании. Старый ответ либо оборвётся, либо дойдёт до `if (!ignore)` и не запишется. Актуальным остаётся последний URL.

RTK Query, React Query и похожие библиотеки делают то же внутри: ключ запроса, отмена предыдущего, кэш. Ручной `useEffect` с `fetch` на новом экране лучше не собирать, если в проекте уже есть такой слой.

### Как сделать тоггл показа и скрытия?

Состояние хранит один булев признак, обновление переворачивает предыдущее значение, а не то, что замкнулось в рендере:

```tsx
const [open, setOpen] = useState(false);

const toggle = () => {
  setOpen((value) => !value);
};
```

Функциональная форма нужна, если тоггл могут нажать дважды до следующего рендера или колбэк запомнился со старым `open`. `setOpen(!open)` в такой ситуации применит одно и то же старое значение дважды.

Кнопка, которая только раскрывает блок, имеет `type="button"`, иначе внутри формы она отправит форму. Связь с панелью для доступности: `aria-expanded={open}` и `aria-controls` на id панели.

`{open && <Panel />}` размонтирует панель. Внутренний стейт панели при закрытии пропадёт. Скрытие классом или `hidden` оставляет компонент живым: стейт сохранится, зато невидимое дерево продолжит участвовать в рендере. Что выбрать, зависит от того, надо ли помнить черновик внутри панели.

### Чем плохо кривое имя стейта и сеттера?

`useState` возвращает пару: текущее значение и функцию, которая планирует его замену. Имена читаются как сущность и действие над ней: `text` и `setText`, `isOpen` и `setIsOpen`.

Плохие имена ломают не рантайм, а смысл, и из этого вырастают баги:

- кортеж мысленно переворачивают, в обработчик уходит строка вместо функции;
- `setText` внутри ещё и ходит в сеть, пишет в аналитику и открывает модалку. Вызывающий ждёт смену строки;
- `text` оказывается объектом `{ value, error }`. Дальше появляется `text.text`;
- `data`, `value`, `flag` не говорят, что внутри. Рядом появляется второй `data`;
- булево без предиката (`menu` вместо `isMenuOpen`) делает `!menu` непрозрачным: неясно, что именно стало правдой.

Сеттер не называют глаголом бизнес-операции. `setOrder` кладёт новое значение заказа. `submitOrder` отправляет его. Если в одном имени смешать оба, через месяц в сеттере окажется побочный эффект, а рендер будет зависеть от удачного запроса.

Имя булева читается вслух в `if`: `if (isMenuOpen)`. Если фраза звучит криво, имя стоит сменить до того, как на него навесят тоггл.

### Почему `renderHeader` и `renderBody` часто лишние?

В React описание UI и так является выражением. Вызов `renderHeader()` внутри рендера прячет дерево в императивную функцию: по месту вызова не видно, какой это компонент, его труднее найти и обернуть в `memo` или `Suspense`.

Каждый рендер создаёт новую функцию `renderHeader`, если она объявлена внутри компонента. Само по себе это дёшево, пока её результат просто вызывают тут же. Как только функцию передают ребёнку пропом, это уже новый проп на каждый рендер.

Вместо этого кусок делают компонентом `<CardHeader />` или передают готовый узел: `<Card header={<CardHeader />} />`. Проп `header` типа `ReactNode` принимает и элемент, и строку, и `null`.

Render prop оставляют, когда родитель отдаёт ребёнку данные, без которых тот не построит разметку: `children={(api) => <Row item={api.item} />}`. Список с неизвестным заранее содержимым строки — нормальный случай. Заголовок карточки, который всегда один и тот же, — нет.

### Контролируемый компонент и два способа передать обработчик

В логе формулировка «консервированные компоненты». По следующему предложению про два способа передать обработчик это контролируемый компонент: источником значения является стейт React, а ввод идёт через `onChange`.

```tsx
<input
  value={text}
  onChange={(event) => setText(event.target.value)}
/>
```

```tsx
function handleChange(event: ChangeEvent<HTMLInputElement>) {
  setText(event.target.value);
}

<input value={text} onChange={handleChange} />
```

Оба варианта контролируемые. Пока `value` задан, DOM не хранит текст сам: что показывает поле, решает рендер. Если не обновить стейт в `onChange`, поле замрёт.

Именованный обработчик лучше, когда в нём больше присваивания: маска, фильтрация символов, вызов ещё и наружу. Его проще тестировать и проще отдать мемоизированному ребёнку одной стабильной ссылкой. Короткая стрелка в JSX нормальна, когда тело — один `setText`.

Неконтролируемое поле держит текст в DOM: `defaultValue` и чтение через реф в момент отправки. Его берут, когда на каждый символ рендерить форму не нужно. Смешивать `value` и `defaultValue` на одном инпуте не стоит: первое делает поле контролируемым, второе задаёт только начальное значение неконтролируемого.

### `React.lazy` и с чем его используют

`React.lazy` принимает функцию, которая возвращает динамический `import()`. Сборка выносит модуль в отдельный чанк. Компонент из этого модуля подгружается в момент первого рендера, а не вместе с основным бандлом.

```tsx
const Map = lazy(() => import('./Map'));

function Page() {
  return (
    <Suspense fallback={<MapSkeleton />}>
      <Map />
    </Suspense>
  );
}
```

Пока чанк не приехал, `Map` приостанавливает рендер. Без `Suspense` выше по дереву React некуда показать запасной UI. Ошибку сети при загрузке чанка `Suspense` не лечит: её ловит error boundary вокруг этого места, с кнопкой повторить.

Так выносят тяжёлое и редкое: карту, редактор, админский экран, виджет, который открывают по клику. Именованный экспорт подгружают обёрткой `import('./file').then((m) => ({ default: m.Map }))`, потому что `lazy` ждёт `default`.

`lazy` не ускоряет сам рендер компонента. Он уменьшает первый бандл ценой дополнительного запроса позже. Совсем маленький модуль выносить нет смысла: запрос дороже выигрыша.

### Профилирование и дампы памяти

Смотреть стоит на конкретный симптом, не «включить все инструменты».

React Profiler в devtools показывает, какой компонент рендерился, сколько это заняло и что его разбудило: пропсы, хук, контекст. Им проверяют гипотезу «список перерисовывается целиком на каждый символ». В проде эти замеры по умолчанию вырезаны.

Chrome Performance пишет длинные задачи, layout, paint, принудительную синхронную геометрию. Им смотрят, почему кадр не уложился во время, а не кто виноват в дереве React.

Дамп памяти снимают, когда сценарий пахнет утечкой: открыл экран, закрыл, память не вернулась. Делают heap snapshot до, повторяют действие, делают второй снимок, сравнивают. Ищут Detached DOM nodes, растущие массивы слушателей, кэши без вытеснения, подписки, снятые без cleanup. Один снимок почти ничего не говорит: нужен рост между двумя.

Lighthouse и полевые Web Vitals (LCP, INP, CLS) отвечают на другой вопрос: что видит пользователь на загрузке и на взаимодействии, а не какой компонент дорогой в dev.

### Стратегии рендеринга и когда какая

CSR. Сервер отдаёт почти пустой HTML и скрипт. Интерфейс появляется после выполнения JS. Подходит внутренним кабинетам, где поиск не нужен и пользователь уже авторизован. Первый осмысленный кадр ждёт бандл и данные.

SSR. Сервер на каждый запрос собирает HTML уже с данными. Браузер показывает разметку до того, как оживут обработчики. После загрузки JS происходит гидрация: React вешает события на готовый HTML. Подходит персональным страницам, которые должны быстро показать контент и быть читаемыми без клиентского рендера.

SSG. HTML тех же страниц собирают заранее, на билде. Отдача дешёвая, данные на момент сборки. Документация, лендинг, редко меняющийся каталог.

ISR. Статическая страница живёт с запасом свежести: по таймеру или по событию её собирают заново, не выкатывая весь сайт. Каталог, который меняется в течение дня.

Streaming SSR и серверные компоненты отдают оболочку сразу, а медленные куски дописывают в ответ. Тяжёлый виджет не блокирует заголовок и навигацию.

Выбор зависит от того, должны ли данные быть в первом HTML, персональные ли они, и как часто меняются. Один проект спокойно смешивает стратегии по маршрутам.

### Интерактив и пагинация в SSR-дашборде

Полная перезагрузка документа не обязательна. Сервер отдаёт первую страницу уже собранным HTML. После гидрации клики обрабатывает клиентский рантайм.

Пагинация тогда работает так: клик меняет search params или состояние, уходит запрос за следующей порцией либо за следующим RSC-пейлоадом, сервер или API возвращает данные, клиент подменяет список. Каркас дашборда не перезагружается. Фокус и введённые рядом фильтры можно сохранить.

Обычная ссылка `<a href="/dashboard?page=2">` без перехвата роутером запросит документ целиком. Это тоже рабочий SSR: просто дороже и сбрасывает клиентское состояние страницы. Роутер Next или React Router перехватывает переход и обновляет только изменившийся сегмент.

Интерактивный виджет внутри SSR-страницы после гидрации живёт как обычный клиентский компонент. До гидрации клик по нему либо ждёт скрипт, либо его сразу обрабатывает маленьким островом, если так собрали страницу. Серверные компоненты сами по себе обработчик клика не держат: кнопка, которой нужен `onClick`, лежит в клиентском компоненте.

### Валидация форм на клиенте и сервере. React Hook Form

Клиентская проверка нужна, чтобы человек сразу увидел пустое обязательное поле, кривую почту или зависимость «если юрлицо, нужен ИНН». Она не доказывает, что данные верные. Запрос можно послать мимо интерфейса.

Сервер проверяет всё ещё раз: права, уникальность, актуальность справочника, лимиты. Ошибку сервера возвращают так, чтобы клиент положил её к нужному полю, а не только баннером «что-то пошло не так».

React Hook Form хранит значения полей у себя и не перерисовывает всю форму на каждый символ. Поле подключают через `register` или, для своей обёртки из дизайн-системы, через `Controller`. Схему Zod или Yup подключают резолвером: одна схема описывает и обязательность, и зависимости полей. Режим `onSubmit` проверяет в конце, `onBlur` — когда человек ушёл из поля. `onChange` на каждое нажатие берут, только если проверка дешёвая.

Ошибку с API кладут точечно: `setError('email', { message })`. Общую — в `setError('root', ...)`. Зависимые поля описывают в `superRefine` или через `watch`, если от значения меняется сам состав формы: появилось поле, которого раньше не было в DOM, его всё равно надо зарегистрировать.

### Стили: чем пользовался, CSS Modules или CSS-in-JS

Обычный набор на таких проектах: обычный CSS, Sass, CSS Modules, CSS-in-JS вроде styled-components, утилитарный Tailwind и токены дизайн-системы. На собесе лучше назвать то, с чем реально собирал прод, и почему это было удобно именно там.

CSS Modules дают файл рядом с компонентом и локальный класс. Сборщик превращает `.card` в уникальное имя вроде `Card_card_x7`. Два компонента с классом `.title` не перебивают друг друга. Это по-прежнему CSS: переменные, медиазапросы, псевдоклассы. Рантайма нет, критический CSS проще вытащить на сборке.

CSS-in-JS удобен, когда стиль считается из пропсов и темы прямо в JS: цвет статуса, отступ из пропа. Цена — библиотека в бандле, генерация классов в рантайме и более тяжёлый SSR, потому что стили надо собрать до HTML. В новом коде без сильной нужды в рантайм-стилях чаще оставляют Modules или утилитарные классы.

Глобальные стили в модуле явно помечают, иначе они тоже захешируются:

```css
:global(.external-widget) {
  color: inherit;
}
```

Локальный класс с глобальным куском внутри: `.card :global(.icon) { }`. Подключение задаёт сборщик. В webpack это `css-loader` с `modules: true` на файлах `*.module.css`. Vite и Next так обрабатывают `*.module.css` без ручного лоадера.

`:global` не для того, чтобы писать всё приложение глобально. Им стыкуют сторонний виджет или редкий селектор, который должен совпасть с внешним классом.

## Redux

### Что такое middleware и какой поток данных в Redux?

Store хранит состояние. Единственный предусмотренный способ его изменить — отправить экшен. Экшен — это объект с полем `type` и, обычно, `payload`.

Поток такой. Компонент вызывает `dispatch(action)`. Экшен проходит цепочку middleware. Последним шагом он попадает в reducer. Reducer получает прошлый state и экшен и возвращает следующий state. Store заменяет состояние и зовёт подписчиков. Компоненты, у которых выбранный кусок изменился, перерисовываются.

Middleware стоит посередине и видит каждый экшен. Ей доступны `dispatch` и `getState`. Она может пропустить экшен дальше, проглотить его, отправить другой или сделать это позже. Так устроены лог, санки с запросом, обработка сокета. Запрос нельзя делать в reducer: reducer должен быть чистой синхронной функцией без `fetch` и без случайных чисел. Побочный эффект живёт в middleware или в thunk.

Порядок middleware важен. Логгер, стоящий до thunk, увидит сам thunk-экшен. Стоящий после — уже те экшены, которые thunk диспатчит по результату запроса.

### Почему компонент на Redux перерисовывается и как он узнаёт об изменении?

`useSelector(selector)` подписывает компонент на store. После каждого `dispatch`, который дошёл до reducer, селектор вызывают снова и сравнивают новое выбранное значение с прошлым через `===`.

Если ссылка или примитив изменились, компонент рендерится. Если селектор вернул тот же примитив или ту же ссылку, рендера из-за Redux нет. Родитель всё ещё может перерисовать компонент по своим причинам.

Лишний рендер появляется, когда селектор каждый раз собирает новый объект или массив: `state => ({ id: state.user.id })`. Содержимое то же, ссылка новая, `===` не проходит. Такой селектор мемоизируют через `createSelector`, либо выбирают примитив и собирают объект уже в компоненте, если это дёшево.

`connect` делает ту же подписку внутри. `mapStateToProps` пересчитывается после изменения store, и дальше работает поверхностное сравнение результата.

### Что даёт Redux Toolkit по сравнению с голым Redux?

Голый Redux требует руками написать константы типов, action creators, `switch` в reducer и аккуратно не мутировать состояние. Ошибка в строке `type` всплывает только в рантайме.

Toolkit собирает это в `createSlice`: имя слайса, начальное состояние, набор reducer-ов. Экшены создаются сами, типы не пересекаются между слайсами. Внутри reducer можно писать «мутирующий» код. Immer превращает его в иммутабельное обновление, наружу выходит новый state. Случайная мутация настоящего состояния по-прежнему ошибка, просто её не нужно изображать руками через spread на каждом уровне.

`configureStore` сразу ставит thunk, проверяет сериализуемость и включает DevTools. `createAsyncThunk` описывает запрос с состояниями pending, fulfilled, rejected. RTK Query поверх этого даёт кэш запросов, теги инвалидации и дедупликацию, если данные с сервера не хочется складывать в слайсы руками.

### Что такое нормализация state?

Нормализация убирает повторы и вложенные копии. Вместо заказа, внутри которого лежит полный объект пользователя, а в другом заказе ещё одна копия того же пользователя, хранят таблицы:

```ts
entities.users[id] = { id, name }
entities.orders[id] = { id, userId }
orderIds = ['o1', 'o2']
```

Список хранит только id. Карточка заказа достаёт пользователя селектором по `userId`.

Обновление имени пользователя происходит в одном месте. Не нужно обходить все заказы и надеяться, что копии не разъедутся. Проверять «это тот же человек» проще по id. Платой идёт более длинное чтение: селектор собирает форму для экрана из нескольких таблиц. Для глубоко вложенного ответа API нормализацию делают на входе в store, а не в компоненте.

### Можно ли из одного модуля вызвать селектор другого?

Да. Селектор — функция от всего состояния, ей не важно, в каком файле она объявлена. Слайс заказов может вызвать `selectUserById(state, userId)`, который читает таблицу пользователей.

Ограничение практическое, не теоретическое. Если файл заказов импортирует селекторы пользователей, а файл пользователей импортирует селекторы заказов, получится цикл модулей. Общие селекторы тогда выносят в третий файл, который зависит от обоих слайсов, но сам слайсам не нужен. Селектор не должен диспатчить экшены: он только читает.

### Минусы Context по сравнению с Redux

Контекст передаёт значение поддереву без прокидывания пропсов через каждый уровень. Когда меняется `value` провайдера, все компоненты, которые прочитали этот контекст, рендерятся снова. Выбрать «только имя пользователя» из большого значения контекста нельзя: подписка на весь value.

У контекста нет экшенов, middleware и путешествия по истории состояний. Отладка «кто записал это поле» превращается в поиск `setState` по дереву. Частые обновления, положенные в тот же провайдер, что и редкая тема, будут будить и потребителей темы.

Redux даёт селектор, поэтому компонент подписан на кусок, и даёт один поток `dispatch`, который видно в DevTools. За это платят устройством store и правилом не класть туда всё подряд.

Контекста хватает для темы, локали, текущего пользователя, если они меняются редко. Его не обязательно заменять Redux только потому, что данных стало несколько. Заменять стоит, когда появляются точечные подписки, сложные обновления и необходимость видеть цепочку изменений.

## Производительность, Next.js, PWA

### На чём построены Vite и Next.js?

Vite в разработке не собирает всё приложение в один бандл. Браузер сам грузит исходники как ES-модули. Зависимости из `node_modules` Vite заранее пребандлит через esbuild, потому что в них тысячи мелких файлов и отдавать их по одному медленно. Трансформация TypeScript и JSX тоже идёт быстрым трансформером, без отдельного шага проверки типов: типы по-прежнему проверяет `tsc`. Продакшен-сборку Vite отдаёт Rollup (в новых мажорных версиях на замену приходит Rolldown): там нужны чанки, tree-shaking и хеши имён.

Next.js — это уже фреймворк поверх React, не только бандлер. Код он компилирует через SWC, написанный на Rust. Долгое время саму сборку делал webpack. Turbopack — их бандлер на Rust, им заменяют webpack в разработке и постепенно в проде. Поверх сборки Next даёт файловый роутинг, серверный рендер, статические страницы и серверные компоненты. Сказать «Next построен на webpack» сегодня неточно: webpack ещё встречается, но компилятор и новый бандлер другие.

### Зачем Next.js и какие фичи применять

Next нужен, когда первый HTML должен быть уже с контентом, когда важны общие лейауты, данные на сервере и предсказуемый роутинг. Просто «у нас React» его не требует.

SSR собирает страницу на сервере на каждый запрос. Данные пользователя свежие, их можно прочитать из cookie запроса. HTML приезжает осмысленным, потом происходит гидрация.

SSG собирает HTML на билде. Страница одинакова для всех, отдача дешёвая. Документация и маркетинг.

ISR оставляет статику, но разрешает пересобрать страницу по истечении времени или по событию, без релиза всего приложения. Каталог, который меняется, но не на каждый чих.

Серверные компоненты исполняются на сервере и не попадают в клиентский бандл целиком. Запрос к API можно сделать рядом с разметкой. Клиентским делают только интерактивный кусок. Серверный экшен — функция, которую можно вызвать с клиента, а выполнится она на сервере.

Картинки и шрифты в Next тоже часть ответа, если ими пользовались: компонент изображения режет размеры и форматы, шрифт не устраивает скачок вёрстки.

Админку за логином без шаринга ссылок в поиск часто проще оставить клиентским приложением. Next тащат за серверные возможности, а не за привычку.

### Что такое PWA и чем она отличается от SPA? Как из SPA сделать PWA?

SPA — способ навигации. После загрузки документа переходы рисует JavaScript, браузер не запрашивает всю страницу заново. Это может быть и CSR, и уже гидратированное SSR-приложение.

PWA — способ поставки. Приложение можно поставить на устройство, у него есть иконка и своё окно, часть сценариев работает без сети или при плохой сети. PWA не обязано быть SPA, и SPA не обязано быть PWA.

Чтобы SPA стала ставиться как PWA, нужны четыре вещи. Сайт отдаётся по HTTPS. В корне подключён web app manifest: имя, иконки, цвет, `display: standalone`, стартовый URL. Service worker регистрируется со страницы, кэширует оболочку и решает, что отдавать из кэша, а что из сети. Обычно его собирают через Workbox, а не пишут кэш руками. Браузер предлагает установку, когда выполнены его условия: manifest, воркер, HTTPS и достаточная вовлечённость.

Офлайн при этом не появляется сам. Надо решить, какая оболочка кэшируется заранее, какие запросы можно отдать из кэша, и что показать, когда кэша нет.

### Двадцать команд портят фронт. Как это заметить и удержать?

Договорённость без измерения не удерживается. У каждой зоны есть владелец: маршрут, микрофронтенд или пакет. Регресс должен быть виден на этой зоне, а не «фронт в среднем стал хуже».

В проде смотрят полевые Web Vitals по страницам: LCP, INP, CLS, плюс свои тайминги критичных сценариев вроде «открылась лента операций». События режут по релизу и по команде-владельцу. Рядом Sentry: ошибки с тем же релизом, чтобы деградация скорости и деградация надёжности не жили в разных отчётах.

В CI на изменённый кусок вешают бюджет. Размер чанка сравнивают с порогом (`size-limit` или аналог), бандл-анализатор показывает, что именно приехало в общий файл. На ключевых страницах гоняют лабораторный профиль, хотя бы Lighthouse на затронутом маршруте. PR, который раздувает начальный бандл или роняет лабораторный LCP, не сливается без явного исключения.

Платформенная группа держит шелл, дизайн-систему, линтеры и шаблон микрофронтенда. Продуктовая команда не копирует свой сборщик. Иначе двадцать конфигов разъедутся, и метрика будет несравнимой.

Общий дашборд без владельца маршрута бесполезен: некому чинить. Метрика без бюджета в CI тоже: её увидят после релиза.

### Доступность

Доступность означает, что интерфейсом можно пользоваться с клавиатуры, со скринридером и при настройках вроде увеличенного шрифта или сниженного движения. Это не отдельный режим «для немногих», а свойство разметки.

Сначала родные элементы. Кнопка — `button`, переход — ссылка `a` с `href`, поле подписано через `label` или `aria-labelledby`. Заголовки идут по уровням, у страницы один `main`, повторяющиеся блоки вынесены в `nav`. У картинки с смыслом есть `alt`. У декоративной `alt` пустой, чтобы скринридер её пропустил.

Фокус должен быть виден. Стили `outline: none` без своей индикации фокуса ломают клавиатуру. Модалка удерживает фокус внутри и возвращает его туда, откуда открылась. Раскрывающийся блок сообщает состояние через `aria-expanded` и связан с панелью через `aria-controls`.

ARIA не заменяет тег. `div` с `role="button"` придётся вручную научить Enter и Space, и всё равно это хуже `button`. Живое сообщение об ошибке формы помечают так, чтобы скринридер его заметил (`aria-live` или связь поля с текстом ошибки через `aria-describedby`). Цвет не единственный носитель смысла: ошибка ещё и текстом.

На собесе достаточно одного своего примера: модалка, табы или форма, и что именно там сделано для клавиатуры и имени элемента.

## Микрофронтенды

### Что такое микрофронтенды и зачем они?

Микрофронтенд — часть интерфейса, которую отдельная команда разрабатывает, тестирует и выкатывает относительно самостоятельно. В браузере эти части собираются в один продукт: общий шелл даёт шапку, меню и авторизацию, а зона команды рисует свой раздел.

Это ответ на очередь релизов. Когда двадцать команд делят один репозиторий и один пайплайн, чужой красный тест блокирует всех. Своя зона выкатывается своим пайплайном.

Цена высокая. Дублируются зависимости, сложнее сквозные сценарии, дизайн разъезжается, ошибка на стыке воспроизводится только при конкретной комбинации версий. Маленькой команде на одном продукте микрофронтенды обычно вредны. Их имеет смысл обсуждать, когда боль общего релиза уже есть, а не заранее.

### Что такое Module Federation?

Module Federation — механизм webpack 5, который в рантайме подгружает код другого собранного приложения как модуль. У аналогов других сборщиков та же идея.

Удалённое приложение в конфиге объявляет `exposes`: какие модули оно готово отдать, например `./Payments`. Хост объявляет `remotes`: откуда взять `remoteEntry.js` этого приложения. При импорте хост загружает entry, а тот уже отдаёт нужный модуль.

Общие библиотеки описывают в `shared`. React и дизайн-систему можно загрузить один раз, если версии совместимы. Если каждая сторона увезёт свой React, на странице окажутся два экземпляра: сломаются хуки и контекст.

Хост не обязан иметь исходники ремоута на своей сборке. Ему нужен адрес уже выложенного entry. Поэтому ремоут можно выкатить отдельно, и хост подхватит его при следующей загрузке страницы.

### Чем микрофронтенды отличаются от npm-пакетов?

Пакет — зависимость на этапе сборки. Версия записана в `package.json` и зафиксирована в lockfile. Чтобы получить чужой фикс, хост обновляет версию и собирается заново. Контракт ломается в CI хоста, а не у пользователя в браузере.

Микрофронтенд подключается в браузере, когда страница уже открывается. Команда выкладывает свой бандл, шелл забирает его по URL. Хост можно не пересобирать. Откат — это выкладка предыдущего бандла ремоута или переключение URL, а не «зафиксировали 1.4.2».

Из-за этого пакет проще рассуждать по SemVer: несовместимое изменение — новая мажорная версия, старые хосты на неё не переедут сами. Микрофронтенд в проде может оказаться новее, чем шелл ожидал. Совместимость приходится держать контрактом пропсов, событий и общими типами, а не только номером версии в lockfile.

Пакет и микрофронтенд иногда смешивают: общий UI-kit остаётся пакетом, а продуктовая зона едет отдельным ремоутом. Тогда дизайн обновляется осознанно, через версию пакета, а фича команды выкатывается сама.

### Минусы независимого деплоя

Контракт может сломаться без сборки хоста. Ремоут переименовал проп или событие, шелл об этом узнает уже в браузере пользователя.

Общие библиотеки расходятся. Две версии React, два экземпляра дизайн-системы, два разных сброса CSS. Баг выглядит случайным и зависит от того, какие именно версии попали на страницу.

Сквозной сценарий труднее повторить. У тестировщика одна комбинация, у клиента другая. Нужны версии в логах ошибок и возможность закрепить набор на стенде.

Падение одного ремоута роняет весь экран, если шелл не обернул зону в свой error boundary и запасной UI. Ошибка загрузки `remoteEntry` — отдельный случай: сеть, а не исключение внутри React.

Авторизация, роутер и общее состояние легко задублировать. Каждый ремоут начинает сам читать токен и по-своему реагировать на 401.

Откат одной команды не откатывает то, что другая уже заложилась на новое поведение. Независимость деплоя не отменяет договорённости о совместимости.

### Могут ли микрофронтенды общаться и как?

Могут, и это лучше проектировать явно.

Нормальные каналы. Шелл передаёт в ремоут пропсы и колбэки: пользователь, локаль, `onNavigate`. Общий роутер и query-параметры шарят то, что и так видно в URL. Договорённые `CustomEvent` на `window` подходят для редких сигналов «логаут», «сменилась организация». Тонкий общий пакет содержит только типы этих событий и имена, без бизнес-логики.

Плохой канал — импорт внутренностей чужого ремоута и общий мутабельный синглтон, в который каждый пишет как хочет. Общий Redux на всех имеет смысл только с владельцем и жёстким контрактом слайсов. Иначе получается монолит, только собранный в браузере и без общей компиляции.

Данные лучше не гонять туда-сюда копиями. Источник правды один: либо шелл принёс их пропом, либо каждая зона сама сходила в свой API. Два ремоута, которые синхронизируют между собой копию одного стора, разъедутся на первой же гонке.

### Конфликт стилей двух микрофронтов и разных версий дизайн-системы

Глобальный класс `.button` из двух бандлов попадёт в одну страницу, и победит тот, кто подключился позже или у кого селектор специфичнее. Это и есть конфликт.

CSS Modules и другие схемы с хешем имени снимают случайное совпадение класса: `.button` становится уникальным. Этого мало, если обе версии дизайн-системы стилизуют голый `button`, `a` или пишут в одни и те же CSS-переменные на `:root`.

Дальше договариваются об одном экземпляре дизайн-системы через `shared` в Module Federation, чтобы на странице была одна версия, а не две. Пока версии всё же две, токены префиксуют по версии, глобальные правила в ремоутах запрещают, виджет можно изолировать Shadow DOM: чужой CSS снаружи внутрь теневого дерева не протекает, и свой наружу тоже. `@layer` задаёт явный порядок слоёв, чтобы побеждала не случайная специфичность, а названный слой.

Специфичность не чинят бесконечным `!important` и не наращивают цепочки селекторов. Так конфликт только переезжает на следующий уровень. Две мажорные версии одной дизайн-системы на одной странице — временное состояние на период миграции, с датой, когда старая версия уйдёт.

### Кроссбраузерность

Кроссбраузерность значит: в браузерах, которые вы официально поддерживаете, интерфейс выглядит и работает приемлемо. «Во всех браузерах мира» никто не обещает. Список фиксируют в `browserslist`. От него пляшут Autoprefixer, транспиляция и решение, нужен ли полифил.

Новые CSS-свойства проверяют через `@supports`, а не рисуют отдельный файл на каждый браузер. JS-фичу проверяют по наличию в `window` или прототипе и только тогда подключают полифил. Глобальный полифил «на всякий случай» раздувает бандл ради браузера, которого у пользователей уже нет.

Отдельно смотрят то, на чём чаще всего расходятся мобильные браузеры: `gap` у flex в старом Safari, единицы `vh` и `dvh`, дата и число у нативного `input`, появление клавиатуры, которое меняет высоту. Сброс отступов у кнопки и поля тоже часть совместимости: у браузеров разные дефолтные стили форм.

Проверяют не скриншотом в одном Chrome, а в тех движках, которые есть у аудитории. Для российского банка это как минимум актуальные Chromium, Safari на iOS и встроенный браузер на старых корпоративных машинах, если он ещё в поддержке.

## Сборка и пакеты

### Из чего состоит конфиг webpack?

Конфиг описывает, как из графа импортов получить файлы, которые можно отдать браузеру.

`mode` включает набор оптимизаций: `development` или `production`. `entry` — точка, с которой webpack начинает обход импортов. Их может быть несколько. `output` говорит, куда положить результат, как назвать файл, какой `publicPath` у чанков и надо ли чистить папку.

`module.rules` сопоставляет файлы лоадерам. Лоадер превращает содержимое файла в модуль, который понимает сборщик: TypeScript и JSX в JavaScript, CSS в код, который вставляет стили, картинку в URL. У правила есть `test`, часто `exclude: /node_modules/` и цепочка `use`.

`resolve.extensions` позволяет писать импорт без суффикса. `resolve.alias` подменяет путь, например `@` на `src`.

`plugins` подписываются на жизнь всей сборки, а не на один файл. `HtmlWebpackPlugin` собирает HTML и вставляет туда скрипты. `DefinePlugin` подставляет константы на этапе сборки. `MiniCssExtractPlugin` выносит CSS в файл. Лоадер обрабатывает модуль, плагин меняет компиляцию целиком.

`optimization` в проде минифицирует и режет `splitChunks`: общий код зависимостей уезжает в отдельный чанк. `devServer` поднимает сервер разработки и проксирует API, чтобы не упираться в CORS. `devtool` выбирает карту исходников: подробную в разработке, дешёвую или никакую в проде.

Рядом часто лежит `babel` или `swc` уже внутри лоадера, это не отдельный ключ webpack, но без него современный синтаксис в цель `browserslist` не приедет.

### Что такое SemVer?

SemVer — схема номера версии `major.minor.patch`.

Патч меняет поведение, которое было ошибочным, и не трогает контракт. Минор добавляет возможность так, чтобы старый код продолжил работать. Мажор ломает контракт: переименованный проп, удалённый экспорт, другая форма ответа.

Диапазон `^1.4.2` разрешает обновиться до любой `1.x` не ниже `1.4.2`. `~1.4.2` разрешает только патчи `1.4.x`. Точная версия без символа ставит только её.

Нулевая мажорная версия `0.y.z` по правилам ещё нестабильна: минор там могут выпускать с ломающими изменениями. Поэтому `^0.2.0` не такой безобидный, как `^1.2.0`.

Номер сам по себе ничего не гарантирует. Автор пакета может ошибиться и выпустить ломающее изменение патчем. Lockfile как раз фиксирует то, что уже проверили, а не то, что автор пообещал диапазоном.

### Какой командой ставить зависимости при `package-lock.json`? Коммитить ли lockfile?

`npm ci` ставит зависимости строго по lockfile. Если `package.json` и lock разошлись, команда падает, а не молча переписывает lock. Перед установкой она удаляет `node_modules`, поэтому результат ближе к чистой машине. Её используют в CI и когда надо просто получить то же дерево, что у коллег.

`npm install` нужен, когда набор зависимостей меняют. Он поставит пакеты и может обновить lock в пределах диапазонов из `package.json`.

Lockfile коммитят вместе с `package.json`. Без него `npm install` на другой машине разрешит диапазоны заново. Патч транзитивной зависимости приедет другой, и баг будет невоспроизводим. В ревью по diff lockfile видно, какая транзитивная версия реально изменилась, а не только прямая зависимость.

### Какие ещё есть виды зависимостей в `package.json`?

`dependencies` нужны приложению, когда оно работает у пользователя: React, рантайм-библиотеки, пакеты, которые импортирует клиентский или серверный код продакшена.

`devDependencies` нужны, чтобы это приложение собрать и проверить: webpack, Vite, TypeScript, тесты, линтеры, `@types`. В установке «только прод» их можно не ставить.

`peerDependencies` значит: этот пакет сам библиотеку не тащит, её должен предоставить хост. Так публикуют компоненты под React. Хост ставит одну копию React нужной версии, иначе их окажется две. `peerDependenciesMeta` может пометить такого пира необязательным.

`optionalDependencies` — пакет желателен, но установка может не получиться. Так живут бинарные дополнения под конкретную платформу. Код должен уметь работать без них.

`bundledDependencies` относится к публикации своего пакета: перечисленные зависимости кладутся внутрь публикуемого архива.

`npm install` на машине разработчика ставит и `dependencies`, и `devDependencies`. Разница проявляется при прод-установке и при публикации библиотеки.

### Что будет, если поменять местами `dependencies` и `devDependencies` и запустить `npm install`?

Обычный `npm install` ставит обе секции. Локально проект, скорее всего, соберётся и откроется: и React, и webpack окажутся в `node_modules`. По одному этому запуску ошибку не заметить.

Продакшен-установка ведёт себя иначе. `npm ci --omit=dev` или установка при `NODE_ENV=production` ставит только `dependencies` и пропускает `devDependencies`. После обмена местами в прод уедут сборщики и тесты, а рантайм-библиотеки, оказавшиеся в `devDependencies`, не встанут. Приложение упадёт при старте, потому что не сможет импортировать React или другую библиотеку, без которой оно работает.

Обратная сторона: то, что должно было остаться инструментом разработчика, теперь прод-зависимость. Установка тяжелее. Если этот пакет ещё и импортируют из прикладного кода, бандлер имеет полное право затянуть его в клиентский чанк.

Итог: локальный `npm install` обманчиво зелёный, прод-установка и состав бандла уже неправильные. Границу секций проверяют не «завелось ли у меня», а тем, ставится ли приложение с `--omit=dev` и не уехал ли туда лишний инструмент.
