# Решение: сброс state через key

```tsx
// src/Chat.tsx
import { useState } from "react";
import type { Contact } from "./data";

export function Chat({ contact }: { contact: Contact }) {
  const [draft, setDraft] = useState("");

  return (
    <div>
      <p>Чат с {contact.name}</p>
      <textarea
        value={draft}
        onChange={(e) => setDraft(e.target.value)}
        placeholder={`Сообщение для ${contact.name}`}
        rows={4}
        cols={40}
      />
    </div>
  );
}
```

```tsx
// src/App.tsx
<Chat key={contact.id} contact={contact} />
```

Если отдельный компонент поля всё же нужен, его объявляют снаружи `Chat` и передают `value` / `onChange` через props. Главное - не создавать функцию-компонент внутри рендера.

## Подробный разбор

**Как React решает, сохранить state или нет.**
State живёт не в переменной функции, а в узле дерева. При новом рендере React сравнивает старое и новое дерево. Для каждой позиции он смотрит на тип (`textarea`, `Chat`, конкретная функция) и на `key`. Совпали оба - это тот же узел: state и DOM сохраняются, обновляются только props. Не совпало - старый узел размонтирован со всем state, новый смонтирован с нуля.

**Почему поле теряло фокус.**
`Field` был объявлен внутри `Chat`. На каждом рендере это новая функция, то есть новый тип компонента. `prevType !== nextType`, поэтому React размонтирует старый `Field` и монтирует новый. DOM-узел создаётся заново, фокус пропадает. Линтер `react/no-unstable-nested-components` это ловит.

**Почему `key` лучше, чем `useEffect`.**
Вариант `useEffect(() => setDraft(""), [contact.id])` сработает хуже: сначала рендер с чужим черновиком у нового контакта, потом эффект, потом ещё один рендер. Легко забыть сбросить другие поля. `key={contact.id}` говорит React: это другой чат. Весь state сбрасывается за один рендер.

## Вопросы для обсуждения

1. Что будет, если два поля переключать тернарником без `key`: `isEditing ? <input placeholder="редактирование" /> : <input placeholder="просмотр" />`, и в первое уже ввели имя?

   Ответ: имя останется, поменяется только placeholder. На той же позиции тот же тип (`input`), поэтому React переиспользует тот же DOM-узел. Чтобы поле сбрасывалось, веткам нужны разные `key`.

2. Счётчик стоит рядом с `{showHint && <p>Подсказка</p>}`. Сбросится ли его state, если подсказку показать? А если вместо этого рендерить две разные структуры: в одной счётчик первый ребёнок, в другой второй?

   Ответ: в первом случае не сбросится. `{cond && ...}` при `false` оставляет пустой слот, соседние дети не сдвигаются. Во втором случае счётчик меняет позицию, для React это другой компонент: старый размонтирован, новый смонтирован с нуля.

3. Когда сброс через `key` лучше не делать? Что, если черновики нужно помнить по каждому контакту?

   Ответ: если поддерево тяжёлое, полный mount может быть дороже, чем точечно сбросить поля. Если черновики должны сохраняться, state поднимают выше, например в `Record<contactId, string>`, и не ставят `key` на чат. Ещё: `key={index}` в списке ломает state при вставке в начало, потому что индексы съезжают и React путает элементы.

**На что смотреть:** вынес ли вложенный компонент (или убрал его); поставил ли `key` на `Chat`, а не написал `useEffect`; понимает ли, что идентичность узла складывается из позиции, типа и `key`.
