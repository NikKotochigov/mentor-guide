# Решение: оптимистичное обновление

```tsx
import { useState } from "react";

function useOptimisticState<T>(
  initial: T
): [T, boolean, (next: T, request: () => Promise<void>) => void] {
  const [state, setState] = useState(initial);
  const [pending, setPending] = useState(false);

  const run = (next: T, request: () => Promise<void>) => {
    if (pending) return;

    const prev = state;
    setState(next);
    setPending(true);

    request().then(
      () => {
        setPending(false);
      },
      () => {
        setState(prev);
        setPending(false);
      }
    );
  };

  return [state, pending, run];
}
```

## Подробный разбор

**Как это работает.**
`run` сразу кладёт в state новое значение, поэтому UI не ждёт сеть. Старое значение запоминается в `prev`. Если промис реджектится, state возвращают к `prev`. Пока запрос идёт, `pending` блокирует повторный клик: иначе два отката легко перепутают результат.

## Вопросы для обсуждения

1. Что будет, если не блокировать кнопку и кликнуть дважды?

   Ответ: первый запрос, если он упадёт позже второго, откатит state к значению до первого клика и затрёт успешный второй. Нужен счётчик поколения (откатывать только если это ещё актуальный запрос) или очередь обновлений.

2. Чем отличается `useOptimistic` в React 19?

   Ответ: он завязан на `startTransition`. Оптимистичное значение живёт, пока переход не завершится, и откатывается само, если настоящий state так и не обновили. Не нужно вручную хранить `prev`.

3. Почему оптимистичный state меняют сразу в обработчике, а не ждут `then`?

   Ответ: смысл в том, чтобы пользователь увидел новый UI в текущем обновлении. Если делать `setState` только после ответа сервера, интерфейс будет казаться медленным, хотя откат всё равно нужно предусмотреть.

**На что смотреть:** сразу ли меняется значение до ответа; есть ли откат; блокируется ли повторный клик; может ли объяснить, зачем в React 19 это связано с переходами.
