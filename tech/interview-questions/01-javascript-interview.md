## Блок 1. Типы, равенство, приведение типов

*Разминка. Проверяем базу, на которой держится всё остальное.*

### 1. Какие типы данных есть в JavaScript? Чем примитивы отличаются от объектов?

**Зачем спрашивают:** базовая гигиена; без этого сложно говорить про сравнение, копирование, `this`.

**Эталонный ответ (для ментора):**

В JavaScript **8 типов данных**: **7 примитивов** и **1 объектный (ссылочный) тип**.

**Примитивы**

- **Number** — целые и с плавающей точкой (`42`, `3.14`). Сюда же `NaN`, `Infinity`, `-Infinity`.
- **BigInt** — целые произвольной точности, больше чем `2^53 - 1` (`Number.MAX_SAFE_INTEGER`). Пишутся с `n`: `9007199254740991n`.
- **String** — строки в `' '`, `" "` или `` `value: ${x}` ``.
- **Boolean** — `true` / `false`.
- **Null** — явное «пусто» / «значение неизвестно».
- **Undefined** — переменная объявлена, но не инициализирована (ещё: нет `return`, нет свойства).
- **Symbol** — уникальный неизменяемый идентификатор; часто как «скрытые» ключи объекта.

**Ссылочный тип**

- **Object** — коллекции и сложные сущности: обычные объекты, `Array`, `Function`, `Date`, `Map`/`Set` и т.д. Всё, что не примитив.

---

**Чем примитивы отличаются от объектов**

На Middle/Senior важны три различия: **значение vs ссылка**, **мутабельность**, **стек vs куча**.

**1. По значению vs по ссылке**

Примитивы **копируются по значению**: присваивание создаёт независимую копию.  
Объекты **копируются по ссылке**: в переменной лежит адрес в памяти; копия переменной указывает на тот же объект.

```javascript
let a = 10;
let b = a; // копия значения
b = 20;
console.log(a); // 10

let obj1 = { name: 'Alice' };
let obj2 = obj1; // та же ссылка
obj2.name = 'Bob';
console.log(obj1.name); // 'Bob'
```

**2. Мутабельность**

Примитивы **immutable**: операцию над значением нельзя «поменять на месте» — получается новое значение.  
Объекты **mutable**: свойства можно добавлять, удалять, перезаписывать без создания нового объекта.

```javascript
let str = 'hello';
str[0] = 'H'; // ошибки нет, строка останется "hello"
str = str.toUpperCase(); // новая строка "HELLO"
```

**3. Стек vs куча**

Примитивы (с оговоркой про оптимизации движка) обычно в **стеке** — быстрая память фиксированного размера.  
Объекты динамические → в **куче (heap)**; в стеке лежит только **ссылка** на объект в куче.

---

**Баг `typeof null`**

`typeof null === "object"` — историческая ошибка JS. Не чинят, чтобы не сломать существующий код. **`null` — примитив.**  
Ещё: `typeof function` → `"function"` (особый случай объекта), `typeof []` → `"object"`.

**Хороший ответ кандидата:** 7 примитивов + Object; value vs reference + пример; immutable; баг с `null`.

**Красные флаги:**
- Не знает `symbol` / `bigint` (для Middle допустимо забыть один, но не оба).
- «Массив — отдельный тип» без оговорки, что это объект.
- Путает `undefined` и `null`.
- Не знает, что `typeof null === "object"` — баг.

**Follow-up:** Чем `null` отличается от `undefined`?  
→ `undefined` — значение не задано. `null` — явное «пусто» от программиста.

**Упрощение:** «Как скопировать число и как скопировать объект? В чём разница?»

### 2. В чём разница между `==` и `===`? Что такое приведение типов?

**Зачем спрашивают:** классика любого РФ-собеса; ловит тех, кто пишет на автопилоте.

**Эталонный ответ:**

`===` проверяет **и значение, и тип** без их изменения (строгое равенство).  
`==` перед сравнением **автоматически приводит** разные типы к одному общему (нестрогое равенство).  
**Приведение типов** — смена типа значения на другой (например, строки в число).

**`===` (строгое равенство)**
- Сравнивает значение **и** тип.
- Если типы разные — сразу `false`.
- Безопаснее; в коде почти всегда его и используют.

```javascript
5 === '5' // false — число не равно строке
null === undefined // false
```

**`==` (нестрогое равенство)**
- Сравнивает значения.
- Если типы разные — делает приведение к общему типу.
- Часто даёт неожиданные баги.

```javascript
5 == '5' // true — строка '5' превращается в число 5
null == undefined // true
0 == false // true
```

**Что такое приведение типов**

Превращение значения одного типа в другой. Бывает двух видов.

**Неявное (автоматическое)** — JS сам меняет тип, когда этого требуют операторы: `==`, сложение строки с числом (`'5' + 1` → `'51'`), условие `if`.

**Явное (ручное)** — программист указывает цель: `Number()`, `String()`, `Boolean()`, `!!x`.  
Пример: `Number('5')` явно даёт число `5`.

Правило Middle: в коде `===` / `!==`. `==` — только осознанно, чаще `value == null` (сразу `null` и `undefined`).

**Красные флаги:**
- «`==` сравнивает значения, `===` ещё и типы» — слишком грубо, без понимания coercion.
- Не знает, что `[] == false` → `true` (через ToNumber).

**Follow-up:** Что выведет `[] + []`, `[] + {}`, `{} + []`?  
→ `""`, `"[object Object]"`, и для `{} + []` в statement-позиции `{}` может быть блоком → часто `0` (зависит от контекста). Не обязательно требовать идеал — смотрим ход мысли.

**Упрощение:** «Почему в линтерах запрещают `==`?»

### 3. Как работает оператор `typeof`? Какие есть сюрпризы?

**Эталонный ответ:**

`typeof` возвращает **строку** с типом операнда. Нужен для быстрой проверки базовых типов.

Синтаксис: `typeof значение` или `typeof(значение)`.

**Ожидаемые результаты**

```javascript
typeof 'Привет'  // "string"
typeof 42        // "number"
typeof true      // "boolean"
typeof undefined // "undefined"
typeof 42n       // "bigint"
typeof Symbol()  // "symbol"
```

---

**Сюрпризы и исторические баги**

**1. `typeof null` → `"object"`**  
Самый известный баг. `null` — примитив («ничего»), но `typeof` говорит `"object"`.  
Почему: в первой версии JS значения хранились как тег типа + значение. Тег объектов был `000`; `null` как нулевой указатель тоже был нулями — движок принял его за объект. Не чинят: сломает миллионы сайтов.

**2. `typeof []` → `"object"`**  
Массив не отдельный тип в системе типов — это специальный объект. Отличить массив от `{}` через `typeof` нельзя.  
Правильно: `Array.isArray([])`.

**3. `typeof function(){}` → `"function"`**  
Функции — тоже объекты (callable), но для них `typeof` делает **исключение**. Удобно, хотя с массивами логика другая.

**4. `typeof NaN` → `"number"`**  
NaN = Not a Number, появляется при неудачных числовых операциях, но относится к типу number.  
Правильно: `Number.isNaN(значение)`.

**5. `typeof` у необъявленной переменной не бросает ошибку**  
Чтение необъявленной переменной → `ReferenceError`. `typeof неизвестная` → `"undefined"`.  
Исключение: `let`/`const` в TDZ — `typeof` всё равно даст ошибку.

---

| Операнд | `typeof` | Статус |
|---------|----------|--------|
| `null` | `"object"` | баг языка |
| `[]` | `"object"` | неудобно → `Array.isArray` |
| `{}` | `"object"` | корректно |
| `NaN` | `"number"` | иронично → `Number.isNaN` |
| `function(){}` | `"function"` | удобное исключение |
| `undefined` | `"undefined"` | корректно |

**Follow-up:** Чем `instanceof` отличается от `typeof`?  
→ `instanceof` смотрит цепочку прототипов, работает с объектами; для примитивов обычно бесполезен (кроме boxed). Ломается между iframe / разными realm.

## Блок 2. Scope, hoisting, замыкания

*От «что храним» к «где и как видим переменные» — база для React (хуки, обработчики, stale closures).*

### 4. Чем отличаются `var`, `let` и `const`?

**Зачем спрашивают:** топ-1/топ-2 вопрос на JS-скрининге в РФ.

**Эталонный ответ:**

| | `var` | `let` | `const` |
|---|-------|-------|---------|
| Область видимости | function scope | block scope `{}` | block scope |
| Hoisting | да, инициализация `undefined` | да, но TDZ | да, но TDZ |
| Повторное объявление | можно | нельзя в той же области | нельзя |
| Переприсваивание | можно | можно | нельзя |
| Объект по `const` | — | — | ссылка константна, содержимое можно менять |

**TDZ (Temporal Dead Zone):** зона от начала блока до строки объявления `let`/`const`, где обращение к переменной даёт `ReferenceError`.

`var` «всплывает» и становится свойством `window`/функционального объекта активации (в браузере на верхнем уровне). `let`/`const` на верхнем уровне модуля/скрипта не становятся свойствами `window`.

В современном коде: `const` по умолчанию, `let` если нужна перезапись, `var` — легаси.

**Красные флаги:**
- «`const` делает объект иммутабельным».
- Не знает TDZ / block scope.
- Путает function scope и block scope.

**Follow-up:** Что выведет и почему?

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// vs let
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

→ `var`: 3, 3, 3 (одна переменная на цикл).  
→ `let`: 0, 1, 2 (на каждую итерацию своя привязка).

Это мост к замыканиям.

### 5. Что такое hoisting?

**Эталонный ответ:**

Hoisting — поведение, при котором объявления как будто «поднимаются» вверх области видимости на этапе создания контекста выполнения.

Уточнение для Middle (лучше, чем слово «поднимается»):
1. Движок сначала проходит фазу создания: регистрирует объявления.
2. Потом фазу исполнения.

На практике:
- `var x` → переменная создаётся сразу со значением `undefined`;
- `function foo() {}` (Function Declaration) → можно вызвать до объявления во всей области;
- `let`/`const` → имя резервируется, но до инициализации TDZ;
- Function Expression / стрелка: поднимается только переменная (`var`/`let`/`const`), не функция.

```js
console.log(a); // undefined
var a = 1;

console.log(b); // ReferenceError (TDZ)
let b = 2;

foo(); // OK
function foo() {}

bar(); // TypeError: bar is not a function (если var bar)
var bar = function () {};
```

**Красные флаги:** «Всё поднимается вместе со значением».

### 6. Что такое замыкание (closure)? Приведи пример

**Зачем спрашивают:** один из самых частых вопросов; критично для React (обработчики, хуки, module pattern).

**Эталонный ответ:**

Замыкание — способность функции **запоминать лексическое окружение** и иметь доступ к переменным из него даже после того, как внешняя функция завершилась.

Простыми словами: функция «тащит за собой» переменные, которые были вокруг неё в момент создания.

**Классический пример — счётчик**

```javascript
function createCounter() {
  let count = 0; // скрыта от внешнего мира

  return function () {
    count++;
    return count;
  };
}

const counter = createCounter(); // createCounter уже завершилась

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3
```

Как это работает:
1. `createCounter()` создаёт локальный `count = 0` и возвращает внутреннюю функцию.
2. Внешняя функция завершилась. В многих языках `count` уже удалили бы из памяти.
3. Внутренняя функция сохранена в `counter` и **замкнула** окружение, в котором создана, — `count` продолжает жить.
4. Каждый вызов `counter()` увеличивает **ту же** `count`. Снаружи к ней напрямую не достучаться.

Два вызова `createCounter()` → два независимых замыкания (два `count`).

**Зачем на практике**

- **Инкапсуляция / приватные данные** — спрятать состояние от случайного изменения.
- **Фабрики функций** — функции с предустановленными настройками.

```javascript
function createGreeter(greeting) {
  return function (name) {
    return `${greeting}, ${name}!`;
  };
}

const sayHello = createGreeter('Привет');
const sayBye = createGreeter('Пока');

console.log(sayHello('Алексей')); // "Привет, Алексей!"
console.log(sayBye('Иван'));     // "Пока, Иван!"
```

Ещё: колбэки, обработчики событий; в React функции внутри компонента замыкают props/state (отсюда **stale closure**).

Нюанс: замыкается **переменная** (binding), а не снимок значения на момент создания.

**Красные флаги:**
- Путает замыкание с областью видимости («это просто scope»).
- Не может привести свой пример.
- Думает, что замыкание — только IIFE.

**Follow-up:** Как связаны замыкания и утечки памяти?  
→ Если замыкание долго живёт (подписка, кэш, глобальный реестр) и держит большую структуру — GC не сможет её собрать.

**Упрощение:** «Почему внутренняя функция видит переменную внешней после return?»

## Блок 3. `this`, call/apply/bind, стрелочные функции

*Логическое продолжение: уже умеем scope/closures — теперь динамический контекст вызова.*

### 7. Как определяется `this` в JavaScript?

**Зачем спрашивают:** стабильный хит собесов; много багов в реальном коде и в классах/React (до хуков).

**Эталонный ответ:**

`this` (контекст вызова) определяется **не в момент создания функции, а в момент вызова**. Простыми словами: `this` — объект, который вызвал функцию в конкретный момент.

Исключение — **стрелки**: у них нет своего `this`, они берут его из лексического окружения (где функция написана).

---

**1. Вызов от имени объекта (неявное связывание)**

Метод через точку → `this` = этот объект.

```javascript
const user = {
  name: 'Алексей',
  greet() {
    console.log(`Привет, я ${this.name}`);
  },
};

user.greet(); // Привет, я Алексей  (this === user)
```

Ловушка потери контекста: скопировали метод в переменную — контекст пропал.

```javascript
const looseGreet = user.greet;
looseGreet(); // undefined (или ошибка в strict mode)
```

**2. Свободный вызов (по умолчанию)**

Функция «просто так», без точки и без `call`/`apply`/`bind`/`new`:

- обычный режим → глобальный объект (`window` / `global`);
- `"use strict"` и ES-модули → `undefined`.

```javascript
function showThis() {
  console.log(this);
}
showThis(); // window или undefined в strict
```

**3. Явное связывание: `call`, `apply`, `bind`**

- `call(context, arg1, arg2, …)` — вызвать сразу, аргументы списком;
- `apply(context, [args])` — то же, аргументы массивом;
- `bind(context)` — **не вызывает**, возвращает новую функцию с намертво привязанным `this`.

```javascript
function introduce(skill) {
  console.log(`Я ${this.name} и я знаю ${skill}`);
}

const developer = { name: 'Иван' };

introduce.call(developer, 'JavaScript'); // Я Иван и я знаю JavaScript
const boundIntro = introduce.bind(developer);
boundIntro('React'); // Я Иван и я знаю React
```

**4. Вызов через `new` (конструкторы)**

`new Fn()`:
1. создаёт новый пустой объект;
2. делает его `this` внутри конструктора;
3. выполняет тело и возвращает этот объект (если нет явного `return` объекта).

```javascript
function Car(model) {
  this.model = model;
}

const myCar = new Car('Tesla');
console.log(myCar.model); // Tesla
```

**5. Стрелочные функции `() => {}`**

Своего `this` нет. Берут `this` снаружи — там, где стрелка **написана**. `call` / `apply` / `bind` **не меняют** их `this`.

```javascript
const group = {
  title: 'Фронтенд',
  students: ['Аня', 'Дима'],
  showList() {
    this.students.forEach((student) => {
      console.log(`${this.title}: ${student}`);
    });
  },
};
group.showList(); // Фронтенд: Аня, Фронтенд: Дима
```

Если в `forEach` обычная `function (student) {}`, её `this` будет `undefined` / `window`, код упадёт.

---

**Шпаргалка: в каком порядке спрашивать себя**

1. Это **стрелка**? → `this` как у внешней функции / окружения (остальные правила не применяются).
2. Вызов с **`new`**? → новый объект.
3. Есть **`call` / `apply` / `bind`**? → переданный контекст.
4. Вызов **методом через точку** (`obj.fn()`)? → объект перед точкой.
5. Иначе → `undefined` (strict) или `window`/`global`.

**Красные флаги:**
- «`this` всегда указывает на объект, где функция написана».
- Не отличает method call от извлечённой функции.
- Думает, что `bind` у стрелки меняет `this`.

**Follow-up:** Что будет здесь?

```javascript
const obj = {
  g: () => this,
  h() {
    return () => this;
  },
};
```

→ `obj.g()` — внешний `this`. `obj.h()()` — стрелка из метода, `this === obj`.

---

### 8. Чем `call`, `apply` и `bind` отличаются?

**Эталонный ответ:**

Все три задают `this` для функции:
- `fn.call(thisArg, a, b, c)` — аргументы списком, **сразу вызывает**;
- `fn.apply(thisArg, [a, b, c])` — аргументы массивом, **сразу вызывает**;
- `fn.bind(thisArg, a, b)` — **возвращает новую функцию** с привязанным this (и опционально частичными аргументами), не вызывает сразу.

```js
function greet(greeting, punct) {
  return `${greeting}, ${this.name}${punct}`;
}
const user = { name: "Ada" };

greet.call(user, "Hello", "!");   // "Hello, Ada!"
greet.apply(user, ["Hi", "."]);  // "Hi, Ada."
const bound = greet.bind(user, "Hey");
bound("?"); // "Hey, Ada?"
```

`bind` можно использовать для partial application. У стрелок `call/apply/bind` **не меняют** `this`.

**Follow-up:** Можно ли перепривязать уже `bind`-нутую функцию новым `bind`?  
→ Второй `bind` не перебьёт this первой привязки (можно добавить аргументы, но this зафиксирован).

---

### 9. Чем стрелочные функции отличаются от обычных?

**Эталонный ответ:**

Стрелочные функции отличаются от обычных не только коротким синтаксисом. У них принципиальные различия в работе с контекстом и внутренними механизмами JavaScript.

**1. Отсутствие собственного `this`**

- **Обычная функция** — `this` определяется **в момент вызова** (метод объекта, свободный вызов, `new`, `call`/`apply`/`bind`).
- **Стрелочная** — своего `this` нет. Берёт `this` из **внешнего окружения** (где написана) и **не меняет** его.

**2. Невозможность использования с `new`**

- **Обычная** — может быть конструктором: `new MyFunc()` создаёт объект.
- **Стрелочная** — конструктором быть не может (нет `[[Construct]]`, нет `prototype`). `new Arrow()` → `TypeError`.

**3. Отсутствие объекта `arguments`**

- **Обычная** — внутри есть псевдопеременная `arguments` со всеми аргументами.
- **Стрелочная** — своего `arguments` нет; обращение к `arguments` идёт во **внешнюю** функцию. Собрать аргументы: rest — `(...args) => { console.log(args); }`.

**4. Нельзя изменить `this` через `call`, `apply`, `bind`**

- **Обычная** — `call` / `apply` / `bind` могут подменить `this`.
- **Стрелочная** — контекст в этих методах **игнорируется** (аргументы передать можно, первый параметр — нет). `this` остаётся лексическим.

**5. Синтаксические особенности**

- **Неявный return:** одно выражение без `{ }` — `return` можно опустить: `const double = x => x * 2;`
- Не могут быть **генераторами** (нет `yield`).

---

| Критерий | Обычная (`function`) | Стрелочная (`=>`) |
|----------|------------------------|-------------------|
| Как определяется `this` | динамически (при вызове) | лексически (при создании) |
| Можно вызвать через `new` | да | нет (`TypeError`) |
| Объект `arguments` | есть | нет → `...args` |
| Свойство `prototype` | есть | нет |
| Неявный return | нет (нужен `return`) | да (без `{ }`) |

**Стрелочное поле класса vs обычный метод**

```javascript
class Button {
  constructor(name) {
    this.name = name;
  }

  clickOrdinary() {
    console.log(`Кликнули на ${this.name}`);
  }

  clickArrow = () => {
    console.log(`Кликнули на ${this.name}`);
  };
}

const btn = new Button('Кнопку Отправить');
const callback1 = btn.clickOrdinary;
const callback2 = btn.clickArrow;

callback1(); // TypeError — потерян this
callback2(); // "Кликнули на Кнопку Отправить"
```

Под капотом: обычный метод лежит в **`Button.prototype`** — один на все экземпляры; передали как колбэк — `this` потерялся.  
Стрелочное поле по сути создаётся **в конструкторе** (`this.clickArrow = () => …`), внешнее окружение — конструктор, там `this` = новый объект. Стрелка «запоминает» его навсегда.

Минусы стрелочных полей:
- **Память** — метод на каждый экземпляр, не в прототипе (тысячи объектов → дороже).
- **Наследование** — нельзя вызвать `super.clickArrow()` (метода нет в прототипе родителя).

**Когда уместны стрелки:** колбэки, когда нужен внешний `this` (`forEach`, обработчики), короткие трансформации; **поля класса** — когда метод передают как колбэк без `bind`.  
**Когда нет:** методы объекта с динамическим `this`, конструкторы, когда нужен `arguments`; массовое создание экземпляров с arrow-полями.

Связь с React: стрелочные поля в class-компонентах сохраняют `this` без `bind`; в функциональных компонентах стрелки в JSX/колбэках — норма (мост к `useCallback`).

**Красные флаги:** «стрелки — просто короткий синтаксис» без `this` / `arguments` / `new`.

## Блок 4. Асинхронность: event loop, Promise, async/await

*Ключевой блок для Middle. Связка: колбэки держат замыкания и this — теперь как они встают в очередь.*

### 10. Что такое event loop? Чем микротаски отличаются от макротасок?

**Зачем спрашивают:** почти обязателен на Middle+ в РФ; отделяет тех, кто «юзал async», от тех, кто понимает модель.

**Эталонный ответ:**

**Event Loop** (цикл событий) — механизм, который даёт JavaScript асинхронность при **однопоточном** движке. Он следит за **стеком вызовов (Call Stack)** и **очередями задач**: когда стек пуст, loop забирает задачу из очереди и отправляет на выполнение.

**Алгоритм (один тик цикла)**

1. Выполняется **синхронный код** (текущая макротаска в стеке).
2. Выполняются **все** микротаски из очереди. Новые микротаски, добавленные по ходу, тоже выполняются **в этом же тике**, пока очередь не опустеет.
3. **Рендер** страницы (браузер обновляет экран, если нужно).
4. Берётся **одна** следующая макротаска → в стек.
5. Цикл повторяется с шага 2.

---

**Микротаски vs макротаски**

| Критерий | Микротаски | Макротаски |
|----------|------------|------------|
| Приоритет | высокий (сразу после sync) | низкий (ждут очереди) |
| Сколько за тик | **все** накопившиеся | **одна** |
| Влияние на UI | могут заблокировать, если бесконечно плодят себя | между макротасками браузер «дышит» и рисует |
| Примеры | `Promise.then/catch/finally`, `async/await`, `queueMicrotask`, `MutationObserver`; в Node ещё `process.nextTick` (ещё раньше) | `setTimeout` / `setInterval`, UI-события (клик, скролл), сеть/`fetch`, `setImmediate` (Node) |

---

**Пример**

```javascript
console.log('1. Синхронный код');

setTimeout(() => {
  console.log('2. Макротаска (setTimeout)');
}, 0);

Promise.resolve().then(() => {
  console.log('3. Микротаска (Promise)');
});

console.log('4. Конец синхронного кода');
```

Порядок: **1 → 4 → 3 → 2**

- `1`, `4` — синхронно, стек опустел.
- `3` — loop **обязан** очистить очередь микротасок перед следующей макротаской.
- `2` — `setTimeout(0)` только в **следующем** тике.

**Красные флаги:**
- «`setTimeout(fn, 0)` выполнится сразу».
- Думает, что Promise — отдельный поток.
- Не знает, что микротаски идут перед следующим `setTimeout`.

**Follow-up:** Что выведет?

```javascript
setTimeout(() => console.log('timeout'), 0);
Promise.resolve()
  .then(() => {
    console.log('then1');
    return Promise.resolve();
  })
  .then(() => console.log('then2'));
console.log('sync');
```

→ `sync`, `then1`, `then2`, `timeout`.

**Упрощение:** «В каком порядке выполнятся sync, `promise.then` и `setTimeout(0)`?»

### 11. Что такое Promise? Какие состояния? Как обработать ошибку?

**Эталонный ответ:**

**Promise** — объект, который представляет результат **ещё не завершённой** (обычно асинхронной) операции. «Обещание», что в будущем будет либо успешный результат, либо ошибка.

**Три состояния**

Промис всегда в **одном** из трёх взаимоисключающих состояний:

- **`pending`** — ожидание; операция не завершилась, результат неизвестен.
- **`fulfilled`** — успех; промис возвращает **value**.
- **`rejected`** — ошибка; промис возвращает **reason** (ошибку).

**Правило:** состояние меняется **один раз**. Из `pending` — только в `fulfilled` или `rejected`. Уже settled промис изменить нельзя.

---

**Как обработать ошибку**

**1. `.catch()` в цепочке**

При `reject()` или `throw` внутри executor / `.then()` выполнение переходит в ближайший `.catch()`.

```javascript
const loadData = new Promise((resolve, reject) => {
  const isSuccess = false;

  if (isSuccess) {
    resolve('Данные загружены!');
  } else {
    reject(new Error('Не удалось загрузить данные'));
  }
});

loadData
  .then((result) => console.log(result))
  .catch((error) => {
    console.error(`Произошла ошибка: ${error.message}`);
  });
```

**2. `try...catch` с `async/await`**

`await` на rejected-промисе бросает исключение → ловит `catch`.

```javascript
async function executeTask() {
  try {
    const result = await loadData;
    console.log(result);
  } catch (error) {
    console.error(`Поймали ошибку через async/await: ${error.message}`);
  } finally {
    console.log('Выполнится и при успехе, и при ошибке');
  }
}

executeTask();
```

**Нюанс: второй аргумент `.then()`**

`.then(onFulfilled, onRejected)` — второй колбэк ловит только reject **исходного** промиса, **не** ошибки внутри первого колбэка:

```javascript
// Так не рекомендуется:
loadData.then(
  (result) => {
    throw new Error('Ошибка внутри then'); // второй аргумент это не поймает!
  },
  (error) => console.error('Только reject из loadData'),
);
```

Безопаснее: **`.then().catch()`** или **`try/catch`**.

---

**Статические методы: массив промисов**

Принимают массив (или итерируемый объект) промисов и возвращают **один** общий промис.

**`Promise.all([...])` — «все или ничего»**

- **Когда:** нужны **все** результаты, они зависят друг от друга (данные страницы + настройки пользователя).
- **Как:** ждёт все промисы. Один reject → `all` сразу падает с этой ошибкой, остальные игнорируются.
- **Возвращает:** массив результатов **в том же порядке**.

**`Promise.allSettled([...])` — «ждём всех в любом случае»**

- **Когда:** важен статус **каждого** запроса (очистка кэша на пяти серверах).
- **Как:** **никогда** не падает по ошибке одного промиса; ждёт все.
- **Возвращает:** массив `{ status: 'fulfilled', value }` или `{ status: 'rejected', reason }`.

**`Promise.race([...])` — «кто первый — того и результат»**

- **Когда:** нужен **самый быстрый** исход — успех или ошибка (гонка запроса и таймера отмены).
- **Как:** результат или ошибка **первого** settled промиса; остальные игнорируются.

**`Promise.any([...])` — «кто первый успешный»**

- **Когда:** подойдёт **любой** первый успех (картинка с трёх зеркал-серверов).
- **Как:** ждёт первый `fulfilled`. Если **все** упали → `AggregateError` с массивом ошибок.

| Метод | Успех | Ошибка |
|-------|--------|--------|
| `all` | все fulfilled | первая rejected |
| `allSettled` | всегда fulfilled (массив статусов) | не падает |
| `race` | первый settled | первый settled |
| `any` | первый fulfilled | все rejected → `AggregateError` |

**Быстрое создание промисов**

- **`Promise.resolve(value)`** — уже `fulfilled` с `value`. Удобно, если по контракту функция возвращает промис, а данные уже в кэше.
- **`Promise.reject(error)`** — уже `rejected` с ошибкой.

Дополнительно: `.finally()` — и при success, и при fail.  
`fetch` не reject-ит на HTTP 404/500 — только на сетевой сбой; проверять `response.ok`.

**Красные флаги:**
- Путает Promise с «потоком».
- Глотает ошибки без `catch` / `try/catch`.
- Думает, что второй аргумент `.then` ловит всё.
- Путает `race` и `any`.

**Follow-up:** Зачем `allSettled`, если есть `all`?  
→ Когда нужен отчёт по каждому запросу, а не аварийный выход на первой ошибке.

### 12. Как работает `async/await`? Чем отличается от then-цепочек?

**Эталонный ответ:**

`async`-функция всегда возвращает Promise.
`await` ставит паузу **внутри** async-функции до settled промиса: возвращает значение или бросает исключение (удобно try/catch).

```js
async function loadUser(id) {
  try {
    const res = await fetch(`/users/${id}`);
    if (!res.ok) throw new Error("HTTP " + res.status);
    const data = await res.json();
    return data;
  } catch (e) {
    console.error(e);
    throw e;
  }
}
```

Отличия от then:
- читается как синхронный код;
- ошибки — через try/catch (или `.catch` на вызове);
- легко случайно сделать **последовательные** await там, где нужна параллельность:

```js
// медленно (последовательно)
const a = await fetchA();
const b = await fetchB();

// быстро (параллельно)
const [a, b] = await Promise.all([fetchA(), fetchB()]);
```

`await` «под капотом» близок к microtask-поведению Promise.

**Follow-up:** Что вернёт `async function f() { return 1; }`?  
→ Promise, fulfilled с `1`.

**Follow-up 2:** Можно ли `await` не в async?  
→ Только в top-level await в ES-модулях (или внутри async).

## Блок 5. Прототипы, наследование, объекты

*После функций и async — как устроены объекты «под капотом». Важно для понимания классов и библиотек.*

### 13. Что такое прототипное наследование? Чем `[[Prototype]]` отличается от свойства `prototype`?

**Зачем спрашивают:** классика middle-собесов; проверяет глубину, не только «пользовался class». Ловит путаницу `__proto__` vs `prototype`.

**Эталонный ответ (для ментора):**

В JavaScript наследование устроено **не через классы как в Java**, а через **цепочку прототипов** (prototype chain). У почти каждого объекта есть скрытая ссылка на другой объект — прототип. Если свойства/метода нет у самого объекта, движок ищет его дальше по цепочке, пока не найдёт или не дойдёт до конца (`null`).

Это и есть прототипное наследование: объекты «делятся» поведением через ссылки, а не через копирование методов в каждый экземпляр.

```js
const animal = {
  eats: true,
  walk() {
    return "walking";
  },
};

const rabbit = Object.create(animal); // [[Prototype]] rabbit → animal
rabbit.jumps = true;

rabbit.jumps; // true — своё свойство
rabbit.eats;  // true — взято из animal
rabbit.walk(); // "walking" — метод из прототипа

Object.getPrototypeOf(rabbit) === animal; // true
```

Схема lookup:

```text
rabbit  →  animal  →  Object.prototype  →  null
  ↓           ↓              ↓
jumps       eats          toString, hasOwnProperty...
            walk
```

---

#### Главная путаница: `[[Prototype]]` vs `prototype`

Это **разные вещи** с похожими именами.

| | `[[Prototype]]` | `Fn.prototype` |
|---|---|---|
| Что это | скрытая ссылка **у объекта-экземпляра** на его прототип | обычное свойство **у функции-конструктора** (и у class) |
| Зачем | цепочка поиска свойств | «шаблон», который станет `[[Prototype]]` у экземпляров при `new` |
| Как читать | `Object.getPrototypeOf(obj)`, устаревшее `obj.__proto__` | `Fn.prototype` |
| У кого есть | почти у всех объектов | у функций (callable); у стрелок/`Object.create`-объектов без конструктора — иначе |

Коротко:
- **`obj.[[Prototype]]`** — «кто мой прототип?» (связь экземпляра).
- **`Fn.prototype`** — «какой объект получат мои экземпляры как прототип?» (заготовка конструктора).

Связь между ними появляется при `new`:

```js
function User(name) {
  this.name = name; // собственное свойство экземпляра
}

User.prototype.sayHi = function () {
  return "Hi, " + this.name;
};

User.prototype.role = "user";

const u = new User("Ada");

u.name;   // "Ada" — own property
u.sayHi(); // "Hi, Ada" — метод с User.prototype
u.role;   // "user" — поле с прототипа

Object.getPrototypeOf(u) === User.prototype; // true
u.__proto__ === User.prototype;              // true (но __proto__ лучше не использовать в коде)
u.hasOwnProperty("name");  // true
u.hasOwnProperty("sayHi"); // false — метод не скопирован, он в прототипе
```

Что делает `new User(...)` упрощённо:
1. создаёт новый объект;
2. ставит ему `[[Prototype]] = User.prototype`;
3. вызывает `User` с `this =` этот объект;
4. возвращает объект (если конструктор не вернул другой объект явно).

---

#### `class` — сахар над той же моделью

```js
class User {
  constructor(name) {
    this.name = name;
  }
  sayHi() {
    return "Hi, " + this.name;
  }
}

const u = new User("Ada");
Object.getPrototypeOf(u) === User.prototype; // true
typeof User; // "function" — class всё ещё функция-конструктор
```

Отличия от «ручного» `function` + `prototype` (важно для Middle):
- методы в `class` попадают в `User.prototype`, но обычно **неenumerable**;
- class-конструктор нельзя вызвать без `new`;
- есть `extends` / `super`, которые тоже работают через прототипы (`Object.getPrototypeOf(Child.prototype) === Parent.prototype`).

```js
class Animal {
  walk() {
    return "walk";
  }
}
class Rabbit extends Animal {
  jump() {
    return "jump";
  }
}

const r = new Rabbit();
r.jump(); // own chain: Rabbit.prototype
r.walk(); // дальше: Animal.prototype
r instanceof Rabbit; // true
r instanceof Animal; // true
```

---

#### `instanceof` и цепочка

`u instanceof User` проверяет не «создан ли именно этим конструктором», а есть ли `User.prototype` **где-то в цепочке** `[[Prototype]]` у `u`.

```js
function A() {}
function B() {}
B.prototype = Object.create(A.prototype);

const b = new B();
b instanceof B; // true
b instanceof A; // true
```

Поэтому ломается между iframe / разными realm: разные `Array.prototype` → `[] instanceof Array` может быть `false`. Надёжнее `Array.isArray`.

---

#### `__proto__` vs `Object.getPrototypeOf` / `Object.setPrototypeOf`

- `__proto__` — устаревший / нестандартный по происхождению accessor (сейчас описан в спеке для совместимости), лучше не использовать в коде.
- Читать: `Object.getPrototypeOf(obj)`.
- Менять: `Object.setPrototypeOf(obj, proto)` — медленно и редко нужно; предпочтительнее задать прототип при создании через `Object.create(proto)`.

```js
const dict = Object.create(null); // нет прототипа вообще
dict.toString; // undefined — не унаследовал Object.prototype
// удобно как «чистый словарь» ключей без наследия
```

---

#### Зачем это в реальном frontend

- методы на прототипе **не дублируются** в каждом экземпляре (память);
- на этом стоят built-ins: `Array.prototype.map`, `Object.prototype.toString`;
- понимание `class`, библиотек, полифиллов, `instanceof`, ошибок вроде «потеряли прототип при structured clone / ручном копировании».

**Хороший ответ кандидата (1–2 мин):**
«Наследование через цепочку прототипов: если свойства нет — ищем в `[[Prototype]]`. `Fn.prototype` — объект для экземпляров при `new`. `Object.getPrototypeOf(u) === User.prototype`. Class — сахар. `instanceof` идёт по цепочке.»

**Красные флаги:**
- «В JS нет наследования, только копирование».
- Путает `prototype` и `__proto__` / `[[Prototype]]` и не может связать через `new`.
- Думает, что `class` — другая ООП-модель «как в Java».
- Говорит, что методы class лежат «внутри объекта экземпляра» как own properties (обычно нет).

**Follow-up:** Что делает `Object.create(null)`?  
→ Объект без прототипа — чистый словарь без `toString` / `hasOwnProperty` с цепочки.

**Follow-up 2:** Где лежит метод `sayHi` у `class User { sayHi() {} }` — у экземпляра или на `User.prototype`?  
→ На `User.prototype`; у экземпляра own обычно только поля из конструктора.

**Упрощение:** «Если у объекта нет метода, где JS его ищет?»  
→ В прототипе, потом у прототипа прототипа, пока не `null`.

### 14. Чем отличается копирование объектов: shallow vs deep? Как клонировать?

**Эталонный ответ:**

- **Shallow copy** — новый объект, но вложенные ссылки те же:  
  `Object.assign({}, obj)`, `{ ...obj }`.
- **Deep copy** — рекурсивно новые вложенные структуры.

Способы deep:
- `structuredClone(obj)` — современный нормальный способ (не клонирует функции, DOM-ноды ограниченно и т.д.);
- `JSON.parse(JSON.stringify(obj))` — ломает `undefined`, функции, `Date`, `Map`, циклические ссылки;
- библиотеки (`lodash.cloneDeep`) — когда нужны краевые случаи.

Связь с ранее: примитивы копируются по значению, объекты — по ссылке. Отсюда баги мутаций state в React, если мутировать вложенность.

**Follow-up:** Почему в React важно не мутировать state? Связь с копированием.

### 15. Что такое деструктуризация, spread и rest?

**Эталонный ответ:**

Деструктуризация, Spread и Rest — три синтаксические фичи ES6, которые упрощают работу с массивами и объектами.

Если коротко:
- **Деструктуризация** — извлечение значений из массивов или объектов в отдельные переменные.
- **Spread** (`...`) — распаковка (развертывание) элементов в другое место.
- **Rest** (`...`) — упаковка (сбор) оставшихся элементов в один массив или объект.

**1) Деструктуризация**

Вместо обращения через точку или индекс — «зеркальное» объявление переменных:

```js
// Объект
const user = { name: "Анна", age: 25, role: "admin" };
const { name, age } = user;
console.log(name); // "Анна"

// Массив
const coordinates = [55.75, 37.61];
const [lat, lng] = coordinates;
console.log(lat); // 55.75
```

Используйте код с осторожностью.

**2) Spread (распаковка)**

Три точки `...` справа от `=` (внутри нового массива/объекта или в аргументах вызова). "Убирает скобки" и высыпает содержимое наружу.

```js
// Копирование и объединение массивов
const fruits = ["яблоко", "банан"];
const allFoods = ["хлеб", ...fruits, "молоко"]; // ['хлеб', 'яблоко', 'банан', 'молоко']

// Копирование и расширение объектов
const baseConfig = { host: "localhost", port: 3000 };
const prodConfig = { ...baseConfig, host: "production.com" }; // host перезапишется

// Передача элементов массива как аргументов
const numbers = [5, 12, 8];
Math.max(...numbers); // Math.max(5, 12, 8) → 12
```

Используйте код с осторожностью.

**3) Rest (упаковка)**

Те же три точки `...`, но слева от `=` (при деструктуризации) или в объявлении параметров функции. Собирает «всё, что осталось».

```js
// Сбор оставшихся аргументов
function sum(first, ...others) {
  console.log(first); // 1
  console.log(others); // [2, 3, 4]
}
sum(1, 2, 3, 4);

// Сбор остатка при деструктуризации объекта
const product = { id: 1, title: "Телефон", price: 50000, rating: 4.8 };
const { id, ...allInfo } = product; // allInfo = { title, price, rating }
```

Используйте код с осторожностью.

⚖️ Как не путать Spread и Rest

| Критерий | Spread (распаковка) | Rest (упаковка) |
|---|---|---|
| Где в коде? | Там, куда значения передаются (справа от `=`) | Там, где значения принимаются (слева от `=`) |
| Что делает? | Из одного делает много (разбивает структуру) | Из многих делает одно (собирает в группу) |
| Ограничение? | Можно вставлять в любое место | Только в конце списка параметров |

Нюансы: spread объекта — **shallow** (неглубокая копия); порядок важен при перекрытии ключей; rest всегда должен быть последним.

### 16. Что такое debounce и throttle? Чем отличаются?

**Зачем спрашивают:** классика frontend Middle; связка замыканий + таймеров + практика (input, scroll). Часто дают live-coding на debounce.

**Эталонный ответ (для ментора):**

Оба приёма **ограничивают частоту вызова** функции при частых событиях. Разница — в стратегии «когда именно вызывать».

| | Debounce | Throttle |
|---|----------|----------|
| Идея | вызвать **после паузы** с последнего события | вызывать **не чаще**, чем раз в N мс |
| Метафора | «подожди, пока пользователь закончит» | «бери не чаще одного раза за окно» |
| Типичные кейсы | поиск по мере ввода, resize «в конце», автосейв | scroll, mousemove, resize «во время», кнопка «не долбить API» |
| Базовая реализация | `clearTimeout` + новый `setTimeout` | timestamp / флаг «занято» + `setTimeout` |

---

#### Debounce

Пока события сыплются — таймер сбрасывается. Функция выполнится только когда с последнего вызова прошло `delay` мс.

```js
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    const ctx = this;
    clearTimeout(timerId);
    timerId = setTimeout(() => {
      fn.apply(ctx, args);
    }, delay);
  };
}

const onSearch = debounce((query) => {
  // fetch(`/search?q=${query}`)
  console.log("search:", query);
}, 300);

input.addEventListener("input", (e) => onSearch(e.target.value));
```

Поведение: пользователь печатает `"react"` → запросы на каждую букву не уходят; уйдёт один, когда остановится на ~300 мс.

Варианты (follow-up):
- **trailing** (классика) — вызов в конце паузы;
- **leading** — вызов сразу при первом событии, потом игнор до паузы;
- `cancel()` — сбросить таймер (размонтирование React-компонента).

---

#### Throttle

Гарантирует: между успешными вызовами не меньше `delay`. Часть событий «прореживается», но во время активного потока вызовы всё равно происходят регулярно.

```js
function throttle(fn, delay) {
  let last = 0;
  let timerId;
  return function (...args) {
    const ctx = this;
    const now = Date.now();
    const remaining = delay - (now - last);

    if (remaining <= 0) {
      clearTimeout(timerId);
      timerId = undefined;
      last = now;
      fn.apply(ctx, args);
    } else if (!timerId) {
      // trailing-вызов в конце окна — чтобы не потерять последнее событие
      timerId = setTimeout(() => {
        last = Date.now();
        timerId = undefined;
        fn.apply(ctx, args);
      }, remaining);
    }
  };
}

window.addEventListener(
  "scroll",
  throttle(() => {
    // проверить позицию, lazy-load и т.д.
  }, 200)
);
```

Упрощённый вариант «только leading» (часто хватает на словах):

```js
function throttleSimple(fn, delay) {
  let locked = false;
  return function (...args) {
    if (locked) return;
    locked = true;
    fn.apply(this, args);
    setTimeout(() => {
      locked = false;
    }, delay);
  };
}
```

---

#### Как выбирать на собесе

- «Нужен результат, когда пользователь **закончил** действие» → debounce.
- «Нужны регулярные обновления **во время** действия» → throttle.
- Иногда комбинируют (например throttle для UI + debounce для финального запроса).

Связь с теорией: обе обёртки — **замыкание** над `timerId` / `last`; таймеры идут через **макротаски** event loop.

**Хороший ответ кандидата:** чётко отличает стратегии, приводит по кейсу, может набросать debounce на `setTimeout`/`clearTimeout`.

**Красные флаги:**
- Путает местами («throttle ждёт конца ввода»).
- Не понимает, зачем `clearTimeout` в debounce.
- Теряет `this`/`args` в обёртке.

**Follow-up:** Напиши debounce; добавь `cancel`. Чем leading отличается от trailing?  
**Упрощение:** «Поиск в инпуте: чтобы не бить API на каждую букву — что использовать?»

### 17. Что такое event bubbling / capturing? Как остановить всплытие?

**Зачем спрашивают:** база DOM-событий; мост к делегированию — очень частый практический вопрос на РФ-собесах.

**Эталонный ответ (для ментора):**

Когда происходит событие (click и т.д.), оно проходит **три фазы** по дереву DOM:

1. **Capturing (capture, погружение)** — от `window`/`document` вниз к целевому элементу.
2. **Target** — на самом элементе, где событие возникло.
3. **Bubbling (bubble, всплытие)** — от цели обратно вверх к корню.

```text
capture:  window → document → html → body → ul → li  (цель)
target:   li
bubble:   li → ul → body → html → document → window
```

По умолчанию `addEventListener` слушает **на фазе bubble** (третий аргумент `false` / `{ capture: false }`).

```js
parent.addEventListener("click", () => console.log("parent bubble"));
child.addEventListener("click", () => console.log("child bubble"));

// клик по child → сначала child, потом parent (всплытие)

parent.addEventListener(
  "click",
  () => console.log("parent capture"),
  true // или { capture: true }
);
child.addEventListener("click", () => console.log("child bubble"));

// клик по child → сначала parent capture, потом child bubble
```

---

#### Как остановить распространение и default

| Метод | Что делает |
|-------|------------|
| `e.stopPropagation()` | не пускает событие дальше по цепочке (остальные фазы/предки не получат) |
| `e.stopImmediatePropagation()` | то же + **не вызовет** другие слушатели на **этом же** элементе, которые ещё не сработали |
| `e.preventDefault()` | отменяет действие браузера по умолчанию (submit формы, переход по ссылке, чекбокс…). **Не** останавливает всплытие |

```js
link.addEventListener("click", (e) => {
  e.preventDefault(); // не переходить по href
  // событие всё ещё может всплыть к родителям
});

button.addEventListener("click", (e) => {
  e.stopPropagation(); // родительский click-handler не сработает
});
```

Частая ошибка кандидата: путать `preventDefault` и `stopPropagation`.

`e.cancelable` / возврат `false` в старых `onclick` — лучше не опираться; современный путь — `addEventListener` + явные методы.

---

#### Делегирование событий (почти всегда follow-up)

Вместо слушателя на каждом `li` — один на родителе, работаем с `event.target` (или `closest`):

```js
ul.addEventListener("click", (e) => {
  const li = e.target.closest("li");
  if (!li || !ul.contains(li)) return;
  console.log("clicked item:", li.dataset.id);
});
```

Зачем:
- меньше обработчиков (память/производительность);
- работает для элементов, добавленных позже динамически;
- проще централизовать логику списка/таблицы/меню.

Нюансы:
- `event.target` — самый глубокий элемент (может быть `span` внутри `button`);
- `event.currentTarget` — элемент, на котором висит слушатель (`ul`);
- не все события всплывают одинаково хорошо (например `focus` — лучше `focusin`; `scroll` не всплывает — для делегирования scroll обычно не подходит).

**Хороший ответ кандидата:** называет фазы capture → target → bubble, отличает stopPropagation / preventDefault, приводит делегирование.

**Красные флаги:**
- Знает только «событие всплывает», не знает capture.
- Путает `preventDefault` и `stopPropagation`.
- Не отличает `target` и `currentTarget`.

**Follow-up:** Зачем делегирование? Чем `target` отличается от `currentTarget`?  
**Follow-up 2:** Что сделает `stopImmediatePropagation` при двух click-слушателях на одной кнопке?  
**Упрощение:** «Клик по кнопке внутри div — кто получит событие первым при обычном addEventListener?»  
→ Сначала кнопка, потом div (bubble).

### 18. Чем `Map`/`Set` отличаются от объекта/массива?

**Краткий эталон:**
- `Map`: ключи любых типов, сохраняет порядок вставки, удобный size, нет прототипного мусора ключей.
- `Set`: уникальные значения, быстрый has.
- `WeakMap`/`WeakSet`: слабые ссылки на объекты-ключи → не мешают GC; не итерируются.

Для Middle хватит Map/Set + зачем WeakMap (приватные данные / кэш по объекту).

### 19. Как найти элементы в DOM? Чем отличаются методы поиска?

**Зачем спрашивают:** база любого фронта без React; в React всё равно полезно понимать, что под капотом и когда нужен `ref` / `querySelector` снаружи.

**Эталонный ответ (для ментора):**

| Метод | Что ищет | Результат | Заметки |
|-------|----------|-----------|---------|
| `getElementById('id')` | по `id` | элемент или `null` | самый быстрый точечный поиск |
| `querySelector(css)` | первый матч CSS-селектора | элемент или `null` | гибко: `.btn`, `[data-id="1"]`, `ul > li` |
| `querySelectorAll(css)` | все матчи | **статический** `NodeList` | удобно итерировать (`forEach`) |
| `getElementsByClassName` / `TagName` / `Name` | по классу / тегу / name | **живая** `HTMLCollection` | устаревающий стиль, но спрашивают |

Контекст поиска:
- `document.querySelector(...)` — по всему документу;
- `el.querySelector(...)` — **только внутри** `el` (важно для делегирования и изоляции).

```js
const list = document.querySelector("#todos");
const firstDone = list.querySelector(".todo.is-done");
const allDone = list.querySelectorAll(".todo.is-done");
```

**Хороший ответ кандидата:** знает `querySelector(All)`, понимает поиск от узла, отличает «первый» vs «все».

**Красные флаги:**
- Только jQuery-память (`$('.x')`) без нативных аналогов.
- Думает, что `querySelectorAll` возвращает массив (это `NodeList`; в массив — `Array.from` / spread).

### 20. Чем `HTMLCollection` отличается от `NodeList`? Что такое live-коллекция?

**Зачем спрашивают:** классическая ловушка циклов и «внезапно изменившейся» длины списка.

**Эталонный ответ (для ментора):**

| | `HTMLCollection` | `NodeList` |
|---|------------------|------------|
| Откуда | `getElementsBy*`, `.children` | `querySelectorAll`, `childNodes`, часть результатов API |
| Содержимое | только **элементы** | узлы (у `childNodes` — в т.ч. текст/комментарии) |
| Live? | обычно **живая** | `querySelectorAll` — **статическая**; некоторые NodeList (например устар. `childNodes` в смысле «отражют дерево») — live |
| Методы | больше похожа на «массив элементов», без `forEach` в старых движках | у современного `NodeList` есть `forEach` |

**Live (живая):** коллекция — «окошко» в текущее дерево. Добавил/удалил DOM → длина и содержимое коллекции меняются сами.

```js
const items = document.getElementsByClassName("item"); // live
console.log(items.length); // 3

document.querySelector(".item").classList.remove("item");
console.log(items.length); // 2 — коллекция обновилась
```

**Static (статическая):** снимок на момент вызова.

```js
const items = document.querySelectorAll(".item"); // static
document.querySelector(".item").classList.remove("item");
console.log(items.length); // как было при вызове querySelectorAll
```

Опасный паттерн: `for (let i = 0; i < live.length; i++) live[i].remove()` — индексы «плывут». Безопаснее: `while (live.length) live[0].remove()` или сначала скопировать в массив.

**Хороший ответ кандидата:** live vs static + пример с `getElementsByClassName` / `querySelectorAll`.

**Красные флаги:** «Это одно и то же»; не может объяснить баг в цикле удаления.

**Follow-up:** Чем `.children` отличается от `.childNodes`?  
→ `children` — только элементы (HTMLCollection); `childNodes` — все узлы, включая текстовые.

### 21. Как создать, вставить и удалить элементы в DOM?

**Зачем спрашивают:** проверяют, умеет ли кандидат работать с деревом без фреймворка и понимает ли стоимость частых вставок.

**Эталонный ответ (для ментора):**

**Создание**

```js
const li = document.createElement("li");
li.textContent = "Купить молоко";
li.dataset.id = "42";
li.classList.add("todo");
```

**Вставка** (современный API):

| Метод | Куда |
|-------|------|
| `parent.append(node, ...)` | в конец (можно строки и несколько узлов) |
| `parent.prepend(...)` | в начало |
| `node.before(...)` / `node.after(...)` | соседние |
| `node.replaceWith(...)` | заменить себя |
| `parent.insertBefore(newNode, refNode)` | старый, но всё ещё ок |

**Удаление:** `el.remove()` (или устар. `parent.removeChild(el)`).

```js
const ul = document.querySelector("ul");
const li = document.createElement("li");
li.textContent = "Новый пункт";
ul.append(li);

li.remove();
```

Связь с React: в приложении на React так почти не пишут — DOM меняет библиотека; руками — в интеграциях, порталах, canvas/виджетах, легаси.

**Хороший ответ кандидата:** `createElement` + `append`/`remove`, не путает с `innerHTML` как единственным способом.

**Красные флаги:** только `document.write`; собирает разметку через `+= innerHTML` в цикле без оговорок.

**Follow-up:** Как вставить много элементов эффективнее? → DocumentFragment / один `append` массива (вопрос 23).  
**Упрощение:** «Создай `button` с текстом "OK" и повесь в `#root`.»

### 22. Чем отличаются `innerHTML`, `textContent` и `innerText`? Где XSS?

**Зачем спрашивают:** безопасность + понимание, что именно пишется в DOM.

**Эталонный ответ (для ментора):**

| Свойство | Что делает | Парсит HTML? | Типичный кейс |
|----------|------------|--------------|---------------|
| `textContent` | читает/пишет **текст** узла и потомков | нет | безопасно вывести пользовательский ввод как текст |
| `innerHTML` | читает/пишет разметку как HTML | **да** | вставить доверенную разметку; опасно с user input |
| `innerText` | «видимый» текст с учётом стилей (не показывает `display:none` и т.п.) | нет | реже нужен; дороже (может трогать layout) |

```js
el.textContent = "<b>hi</b>"; // на экране буквально: <b>hi</b>
el.innerHTML = "<b>hi</b>";   // на экране жирный hi
```

**XSS:** `el.innerHTML = userInput` (или `insertAdjacentHTML` с недоверенной строкой) может выполнить разметку/`<img onerror=...>` и т.д. Правило: недоверенные данные → `textContent` / санитизация / фреймворк с экранированием (React по умолчанию экранирует текст; `dangerouslySetInnerHTML` — явный риск).

`outerHTML` — про весь элемент целиком (включая свой тег); на Middle достаточно упомянуть отличие от `innerHTML`.

**Хороший ответ кандидата:** textContent безопасен для текста; innerHTML парсит HTML → XSS; приводит пример.

**Красные флаги:** «innerHTML всегда норм»; не слышал про XSS в этом контексте.

**Follow-up:** Почему в React опасно `dangerouslySetInnerHTML`?  
**Упрощение:** «Пользователь ввёл имя — куда писать: innerHTML или textContent?»

### 23. Что такое `DocumentFragment`? Как уменьшить лишние reflow/repaint при массовых изменениях DOM?

**Зачем спрашивают:** связка производительности и DOM; мост к вопросам про layout thrashing (подробнее — в web/CRP блоке).

**Эталонный ответ (для ментора):**

**DocumentFragment** — «лёгкий контейнер» узлов **не в документе**. Пока собираешь дерево во fragment, браузер не пересчитывает layout страницы на каждую вставку. При `parent.append(fragment)` узлы переезжают в DOM **одним** действием (fragment сам в дереве не остаётся).

```js
const fragment = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = `Item ${i}`;
  fragment.append(li);
}
ul.append(fragment); // одна вставка в живой документ
```

Альтернативы того же духа:
- собрать массив узлов и `ul.append(...nodes)` (если не гигантский список);
- менять `display`/`visibility` осознанно; не читать layout (`offsetHeight`, `getBoundingClientRect`) между записью стилей в цикле — это **layout thrashing**.

**Reflow (layout)** — пересчёт геометрии. **Repaint** — перерисовка пикселей без смены раскладки. Частые синхронные «записал DOM/стиль → сразу прочитал размер» в цикле — главный антипаттерн.

**Хороший ответ кандидата:** fragment / батч-вставка; понимает, что 1000 `append` в живой `ul` дороже одной пачки.

**Красные флаги:** «Fragment ускоряет JS-вычисления» (нет — снижает стоимость работы с layout документа); путает reflow и event loop.

**Follow-up:** Приведи пример layout thrashing.  
**Упрощение:** «Добавить 500 `li` — по одному в `ul` или сначала собрать, потом вставить?»

### 24. Чем HTML-атрибут отличается от DOM-свойства? Как работать с `data-*`?

**Зачем спрашивают:** путаница `el.value` vs `getAttribute('value')`, `checked`, кастомные data-атрибуты — частые баги форм и делегирования.

**Эталонный ответ (для ментора):**

- **Атрибут (attribute)** — то, что в HTML-разметке / в DOM как атрибут узла: `getAttribute` / `setAttribute` / `removeAttribute`. Часто строка.
- **Свойство (property)** — поле JS-объекта DOM-элемента: `el.value`, `el.checked`, `el.disabled`. Живое состояние контрола.

Они **связаны, но не всегда равны**:

```js
input.setAttribute("value", "hello"); // атрибут value
input.value = "world";                // свойство value (то, что в поле сейчас)

console.log(input.getAttribute("value")); // "hello" — «начальный» атрибут
console.log(input.value);                 // "world" — текущее значение
```

Для булевых: наличие атрибута `disabled` vs свойство `el.disabled === true`.

**data-***:

```js
el.dataset.userId = "7";          // → data-user-id="7"
console.log(el.dataset.userId);   // "7" (строка!)
console.log(el.getAttribute("data-user-id"));
```

На Middle: `dataset` удобен; значения — **строки**; для чисел/JSON — парсить явно. В делегировании часто `e.target.closest("[data-action]")` + `dataset.action`.

**Хороший ответ кандидата:** приводит пример value attribute vs property; знает `dataset`.

**Красные флаги:** считает, что `getAttribute('value')` всегда равен `input.value`.

**Follow-up:** Как через делегирование обработать кнопки с разными `data-action`? (связь с вопросом 17)

### 25. Как подписать и отписать обработчик? Откуда берутся утечки с DOM?

**Зачем спрашивают:** связка замыканий + DOM + React `useEffect` cleanup; на собесах Mid очень любимо.

**Эталонный ответ (для ментора):**

```js
function onScroll() {
  /* ... */
}

window.addEventListener("scroll", onScroll);
// позже:
window.removeEventListener("scroll", onScroll); // та же ссылка на функцию!
```

Важно:
- снять можно только **ту же** функцию (та же ссылка). Анонимная `() => {}` в `add` и другая в `remove` — **не** снимет;
- третий аргумент / `capture` должен совпадать при remove;
- `{ once: true }` — сам снимется после первого срабатывания;
- `{ passive: true }` — для touch/scroll, нельзя `preventDefault` (производительность).

**Утечки (типичные на фронте):**
- слушатель на `window`/`document` забыли снять при «размонтировании»;
- замыкание слушателя держит большой объект / detached DOM-узел;
- `setInterval` без `clearInterval` (часто рядом с DOM-логикой).

Связь с React: подписки в `useEffect` → обязательно `return () => removeEventListener(...)`.

**Хороший ответ кандидата:** одинаковая ссылка на handler; приводит React-cleanup как практику.

**Красные флаги:** «removeEventListener не нужен»; снимает другой функцией-клоном.

**Follow-up:** Почему в `useEffect` нельзя писать `addEventListener(..., () => setState(...))` без cleanup?  
**Упрощение:** «Клик по document каждый раз добавляет listener в `useLayoutEffect` без deps — что будет?»  
→ Утечка слушателей на каждый рендер (как в задаче PleaseReviewMe).

## Задача A (обязательный минимум, если берёте live-coding): замыкание + таймеры

**Условие:** Напиши функцию `createEmitter` / или проще:

Реализуй `makeFunctions`, которая возвращает массив из `n` функций; вызов `i`-й функции возвращает `i`.

```js
function createFunctions(n) {
  const funcs = [];
  // TODO
  return funcs;
}

const fs = createFunctions(5);
fs[0](); // 0
fs[3](); // 3
```

**Ловушка:** с `var i` в цикле все вернут `n`. С `let` или IIFE/factory — ок.

**Эталон:**

```js
function createFunctions(n) {
  const funcs = [];
  for (let i = 0; i < n; i++) {
    funcs.push(() => i);
  }
  return funcs;
}
```

**Альтернатива без let:**

```js
for (var i = 0; i < n; i++) {
  funcs.push((function (j) {
    return function () { return j; };
  })(i));
}
```

**Связь с теорией:** блок 2 (var/let, closures).

**Follow-up:** Почему `var` ломает? Что именно замыкается?

## Задача C (средняя+, классика РФ): `Promise.all` своими руками

**Условие:** Реализуй `promiseAll(promises)` с поведением как `Promise.all`.

**Эталонная идея:**

```js
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const input = [...promises];
    if (input.length === 0) {
      resolve([]);
      return;
    }
    const result = new Array(input.length);
    let done = 0;

    input.forEach((p, i) => {
      Promise.resolve(p).then(
        (value) => {
          result[i] = value;
          done += 1;
          if (done === input.length) resolve(result);
        },
        (err) => reject(err)
      );
    });
  });
}
```

**На что смотреть:**
- сохранение порядка результатов;
- reject при первой ошибке;
- работа с non-promise значениями (`Promise.resolve`);
- пустой массив → resolve `[]`.

**Связь:** блок 4.

## Задача D (практика frontend): debounce

**Условие:** Напиши `debounce(fn, delay)`.

```js
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    const ctx = this;
    clearTimeout(timerId);
    timerId = setTimeout(() => {
      fn.apply(ctx, args);
    }, delay);
  };
}
```

**На что смотреть:** clearTimeout, сохранение this/args, понимание зачем.

**Follow-up:** Добавь `cancel()` или немедленный leading-edge вызов.  
**Follow-up 2:** Чем отличается throttle (на словах или кодом).

## Задача E (по желанию, harder): deepEqual или flatten

**Deep equal (упрощённо):**

```js
function deepEqual(a, b) {
  if (Object.is(a, b)) return true;
  if (typeof a !== "object" || a === null || typeof b !== "object" || b === null) {
    return false;
  }
  const keysA = Object.keys(a);
  const keysB = Object.keys(b);
  if (keysA.length !== keysB.length) return false;
  return keysA.every((key) => Object.prototype.hasOwnProperty.call(b, key) && deepEqual(a[key], b[key]));
}
```

Или **flatten массива** произвольной вложенности — тоже частая задача.

Бери E только если A–C легко и есть время.
