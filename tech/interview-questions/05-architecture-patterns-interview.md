## Блок 1. Принципы: SOLID, DRY, KISS, YAGNI

*База архитектурного мышления. Без этого FSD и Clean Architecture — просто папки.*

### 1. Что такое SOLID? Зачем эти принципы на фронтенде?

**Зачем спрашивают:** проверяют, умеет ли кандидат проектировать, а не только писать компоненты.

**Эталонный ответ:**

SOLID — пять принципов дизайна. На фронте они относятся не только к классам, но и к компонентам, хукам, модулям и контрактам API.

- **S** — Single Responsibility: одна причина для изменения.
- **O** — Open/Closed: открыт для расширения, закрыт для модификации.
- **L** — Liskov Substitution: подтип можно подставить вместо базового без поломки контракта.
- **I** — Interface Segregation: не зависеть от лишних методов/пропсов.
- **D** — Dependency Inversion: зависеть от абстракций, а не от конкретной реализации (`fetch`, Axios, localStorage).

На фронтенде эти принципы нужны, чтобы превратить хаотичный код (в компонентах, сторах или сервисах) в гибкую, масштабируемую и легко тестируемую систему, где изменение одной кнопки не ломает логику оформления заказа.

**Зачем SOLID на фронтенде**

Фронтенд-приложения развиваются стремительно: постоянно меняется дизайн, добавляются новые фичи, переписывается API. Без чётких правил код превращается в «спагетти» с высокой связанностью (coupling).

Применение SOLID решает три главные боли фронтендера:

1. **Простота поддержки (Maintainability):** код легче читать и понимать. Новые разработчики быстрее вливаются в проект.
2. **Низкая хрупкость:** изменение логики в одном месте не вызывает лавину багов в других частях приложения.
3. **Лёгкое тестирование:** изолированные компоненты и чистые функции покрываются юнит-тестами за пару минут.

Практически это значит:
- меньше «god-компонентов» на 400 строк, которые ломаются от любой правки дизайна или API;
- проще тестировать: хук с fetch отдельно, тупой UI отдельно;
- проще менять UI-kit / HTTP-клиент / стор, не расползаясь по всему приложению;
- проще онбордить людей: ответственность модуля читается из имени и границ.

SOLID — не цель сама по себе. Если команда из двух человек делает лендинг, натягивать все пять букв вредно (YAGNI). Принципы начинают окупаться, когда появляются повторные сценарии: каталог, корзина, кабинет, роли, несколько клиентов API.

**Где используется на практике:**
- продуктовый кабинет: профиль, заказы, уведомления — разные причины меняться, нельзя склеивать в один экран-компонент;
- дизайн-система: кнопки/инпуты расширяют через варианты и композицию, а не через правку ядра каждым дизайнером;
- B2B-админки: смена бэка с REST на GraphQL не должна требовать переписывать таблицы и формы, если UI зависит от сервиса, а не от `axios.get`.

**Красные флаги:** «SOLID только для бэкенда / Java»; пересказывает буквы без примера; применяет все принципы к каждому файлу.

**Follow-up:** Какой принцип чаще всего ломают в React?  
→ Обычно SRP: один компонент и fetch, и валидация, и форматирование, и UI.

### 2. Что такое Single Responsibility Principle? Покажи на React.

**Эталонный ответ:**

Каждый класс, модуль или компонент должен отвечать только за что-то одно — иметь **одну причину для изменения**. Не «один файл = одна функция», а «меняется по одной оси»: либо контракт API, либо вёрстка, либо правило валидации.

На фронтенде компонент не должен одновременно скачивать данные из сети, валидировать форму, форматировать даты и рендерить UI.

Практический приём: разделяйте «умные» контейнеры (fetch, стор) и «глупые» UI-компоненты (только props и отрисовка). Логику работы с API лучше выносить в кастомные хуки (React) или отдельные сервисы.

Плохо: `UserProfile` на 200 строк одновременно:
- грузит пользователя;
- грузит уведомления;
- валидирует email;
- форматирует дату;
- сохраняет форму;
- рисует UI.

Любая правка бэка, дизайна или правил валидации трогает один и тот же файл. Ревью огромное, конфликты в git, тесты хрупкие.

Хорошо — разрезать по осям изменения:

```js
function useUser(userId) { /* только загрузка пользователя */ }
function useNotifications(userId) { /* только уведомления */ }
export function validateEmail(email) { /* правило живёт в одном месте */ }
export function formatDate(date) { /* форматирование дат продукта */ }

function UserProfile({ userId }) {
  const { user, loading, error } = useUser(userId);
  const { notifications } = useNotifications(userId);
  if (loading) return <div>Loading...</div>;
  if (error) return <div>Error</div>;
  return <UserProfileView user={user} notifications={notifications} />;
}
```

Идея: экран **собирает** куски, но не владеет всеми правилами. `UserProfileView` можно отдать дизайнеру/Storybook без мока сети. `validateEmail` меняется один раз — и в профиле, и в регистрации.

Граница: не дробить до абсурда (`UserNameText.tsx`, `UserEmailText.tsx`). Если два куска всегда меняются вместе — это одна ответственность.

**Где используется на практике:**
- страница заказа: состав корзины, расчёт доставки, оплата, статус — разные сервисы и разные релизы;
- таблица в админке: колонки/UI отдельно, запрос фильтров и пагинации — в хуке или React Query;
- форма регистрации: схема валидации (zod) отдельно от полей, отдельно от `POST /auth/register`;
- аналитика: отправка событий не должна жить внутри кнопки «Купить», иначе кнопку нельзя переиспользовать в другом месте без трекинга.

**Красные флаги:** «один файл = одна ответственность» всегда; дробит атомы без выигрыша; выносит в хук то, что используется один раз и никогда не меняется отдельно.

### 3. Что такое Open/Closed Principle? Как расширять, не ломая базовый компонент?

**Эталонный ответ:**

Программные сущности должны быть **открыты для расширения**, но **закрыты для модификации**: новый вариант добавляем снаружи, а не бесконечными `if` в ядре, которое уже используют 40 экранов.

На фронтенде: если нужно добавить фичу в компонент (например, новую кнопку в модальное окно), не переписывайте внутренности самого компонента.

Практический приём — проп `children` (слоты во Vue/Angular). `Modal` даёт только каркас; содержимое передаётся извне. Новый тип модалки = новый контент снаружи, базовый `Modal` не трогаем:

```jsx
function Modal({ isOpen, onClose, children }) {
  if (!isOpen) return null;
  return (
    <div className="overlay" onClick={onClose}>
      <div className="dialog" onClick={(e) => e.stopPropagation()}>
        {children}
      </div>
    </div>
  );
}

// расширение контентом, без правки Modal
<Modal isOpen={open} onClose={() => setOpen(false)}>
  <h2>Оформить заказ</h2>
  <p>Подтвердите состав корзины</p>
  <button onClick={placeOrder}>Оплатить</button>
</Modal>
```

Плохо: `Button` с цепочкой `if (type === 'primary' / 'secondary' / 'danger' / 'success')`. Каждый новый тип из Figma — правки ядра, регресс всех кнопок, конфликт в design-system PR.

Хорошо: закрытое ядро + точки расширения (variant map, `...props`, композиция):

```js
function Button({ variant = "primary", children, ...props }) {
  const variants = {
    primary: { background: "blue", color: "white" },
    secondary: { background: "gray", color: "black" },
  };
  return (
    <button style={variants[variant] || variants.primary} {...props}>
      {children}
    </button>
  );
}

function IconButton({ icon, children, ...props }) {
  return (
    <Button {...props}>
      <span>{icon}</span>
      {children}
    </Button>
  );
}

function LoadingButton({ loading, children, ...props }) {
  return (
    <Button {...props} disabled={loading}>
      {loading ? "Loading..." : children}
    </Button>
  );
}
```

`IconButton` / `LoadingButton` не требуют лезть в `Button`. Новый способ оплаты на чекауте — новая strategy, а не ещё один `if` в `CheckoutPage`.

Связь с паттернами: Strategy (семейство алгоритмов), Decorator/HOC (нарастить поведение), Compound Components (слоты вместо пропсов на все случаи).

Противовес — YAGNI: не делать 15 plugin-точек «на будущее», если сейчас два варианта. OCP включают, когда варианты **уже начали плодиться**.

**Где используется на практике:**
- UI-kit банка/маркетплейса: `Button`, `Input`, `Modal` живут годы, продуктовые команды расширяют обёртками;
- конструктор форм: бэк шлёт `field.type`, фронт мапит в компоненты без правки рендерера на каждое поле;
- чекаут: карта / PayPal / СБП / Apple Pay — отдельные стратегии, общий `PaymentProcessor`;
- уведомления: email / push / in-app — общий интерфейс «отправить», разные адаптеры.

**Follow-up:** Чем OCP отличается от YAGNI?  
→ OCP: «расширяй без ломки ядра». YAGNI: «не проектируй 20 точек расширения заранее».

### 4. Что такое Liskov Substitution Principle? Как он выглядит на фронте?

**Эталонный ответ:**

Функции, которые используют базовый тип, должны иметь возможность использовать подтипы, не зная об этом. То, что выдаётся за `Button`, должно соблюдать контракт `Button`.

На фронтенде кастомные UI-компоненты (кнопки, инпуты) должны полностью сохранять ожидаемое поведение стандартных HTML-элементов.

Пример: `MyCustomButton` принимает все стандартные пропсы HTML-кнопки (`type`, `disabled`, `onClick`, `aria-*`) через spread. Если кастомный инпут вместо `onChange` требует `onCustomUpdate`, принцип нарушен: компонент нельзя подставить туда, где ждали обычный input.

```tsx
type ButtonProps = React.ComponentPropsWithoutRef<"button"> & {
  isLoading?: boolean;
};

function MyCustomButton({ isLoading, children, ...rest }: ButtonProps) {
  return (
    <button {...rest} disabled={rest.disabled || isLoading}>
      {isLoading ? "Loading..." : children}
    </button>
  );
}
```

Плохо: `DisabledButton` принимает `onClick` и молча игнорирует. В списке действий «все кнопки одинаковые» ломается аналитика и доступность: клик «есть», эффекта нет.

Хорошо: один `Button` с `disabled` — контракт честный. Или отдельный компонент без `onClick` в типах, чтобы нельзя было передать обработчик.

На практике LSP ломают ещё так: `UserCard` в списке и на странице профиля выглядят «одним компонентом», но в одном месте клик открывает профиль, в другом — выбирает строку, при этом общий тип врёт.

**Где используется на практике:**
- UI-kit: кастомная кнопка в формах, тулбарах и таблицах — тот же контракт, что у `<button>`;
- полиморфный список действий (сохранить / удалить / экспорт) — одинаковый контракт для хоткеев и аналитики;
- обёртки над `input`/`select` в дизайн-системе, чтобы работали с React Hook Form без адаптеров.

**Красные флаги:** объясняет LSP только на животных из учебника; кастомный инпут с `onCustomUpdate` вместо `onChange`.

**Follow-up:** Чем LSP отличается от «просто прокинуть ...rest»?  
→ Spread без соблюдения поведения (игнор `onClick`, другой event) всё равно нарушает контракт.

### 5. Что такое Interface Segregation Principle? Как не раздувать пропсы компонента?

**Эталонный ответ:**

Клиент не должен зависеть от пропсов/методов, которые не использует. Лучше несколько узких интерфейсов, чем один «на все случаи».

Плохо: `UserCard({ user, onEdit, onDelete, onShare, onReport, showEdit, ... })` — на странице «команда» нужен только просмотр, но TypeScript и рантайм требуют все колбэки.

Хорошо: `UserCard` только рисует; `UserCardActions` — edit/delete; extra-действия — ещё один кусок. Экран собирает композицией только нужное.

На практике ISP — это «не тащить весь `User` в кнопку», «не требовать `dispatch` Redux в чистом UI», «не делать один хук `useUserEverything`».

Конкретный front-end пример:
не передавайте в “глупый” компонент огромный объект, если ему нужны только 2–3 поля. Например, вместо:

```tsx
<UserAvatar user={user} />
```

сделайте интерфейс уже:

```tsx
<UserAvatar src={user.avatarUrl} alt={user.name} />
```

Так `UserAvatar` становится чище, а его можно переиспользовать для аватарок компаний, ботов или гостей, у которых нет полной структуры `User`.

**Где используется на практике:**
- карточка товара в каталоге vs в админке: в каталоге нет `onDelete`;
- таблица: колонка «действия» — отдельный слот, а не 8 колбэков на каждую строку;
- хуки: `useUser()` для профиля и `useUserPermissions()` для ACL, а не один хук на весь кабинет.

**Красные флаги:** ISP = «много мелких файлов»; один компонент с 20 optional-пропсами и флагами `show*`.

**Follow-up:** Как ISP стыкуется с Compound Components?  
→ Слоты (`Modal.Header`, `Modal.Footer`) — как раз узкие интерфейсы вместо гигантского `ModalProps`.

### 6. Что такое Dependency Inversion Principle? Зачем абстракции вместо прямого fetch?

**Эталонный ответ:**

Модули верхнего уровня (экран, use case) не зависят от деталей (`axios`, `localStorage`, Firebase). Оба зависят от абстракции: «есть сервис с `getUsers()`».

На фронтенде это обычно означает: компоненты не должны жёстко завязываться на конкретную библиотеку (например, напрямую импортировать `axios` в каждом компоненте).

Практика: создайте абстракцию `apiClient.ts` (или `userRepository.ts`) — внутри настройте `axios` или `fetch`, а компоненты импортируйте только методы из этого модуля.

```ts
// apiClient.ts
import axios from "axios";

export const apiClient = {
  getUsers: () => axios.get("/api/users").then((r) => r.data),
  // ...
};

// userList.tsx — компонент не знает, чем внутри делается HTTP
import { apiClient } from "./apiClient";

export function UserList() {
  useEffect(() => {
    apiClient.getUsers().then(/* ... */);
  }, []);
}
```

Если завтра руководство скажет заменить `axios` на другую библиотеку, вы перепишете код только в `apiClient.ts`, а компоненты даже не заметят подмены.

Плохо:

```js
function UserList() {
  useEffect(() => {
    fetch("/api/users").then(/* ... */);
  }, []);
}
```

Хорошо: хук принимает порт:

```js
function useUsers(userService) {
  const [users, setUsers] = useState([]);
  useEffect(() => {
    userService.getUsers().then(setUsers);
  }, [userService]);
  return users;
}

// прод: ApiUserService, тесты: MockUserService, Storybook: статичный stub
```

В реальном React DIP часто выглядит как: React Query + `apiClient` в одном модуле; или интерфейс репозитория + адаптер; или проп `storage` вместо прямого `localStorage` (SSR/тесты).

Это же ядро Hexagonal / Clean Architecture.

**Где используется на практике:**
- смена REST → BFF GraphQL без переписывания экранов;
- моки в e2e и Storybook без бэка;
- white-label: другой API под тем же экраном;
- подмена `localStorage` на cookie/memory в SSR.

**Красные флаги:** DIP = «просто прокинуть проп»; абстракция на каждый `console.log`; экран всё равно импортирует Axios напрямую.

**Follow-up:** Чем DIP отличается от Dependency Injection?  
→ DIP — принцип «зависеть от абстракции». DI — способ подставить реализацию (проп, контекст, контейнер).

### 7. Чем отличаются DRY, KISS и YAGNI? Когда DRY вреден?

**Эталонный ответ:**

Три разных ответа на «как не усложнить жизнь».

**DRY (Don't Repeat Yourself)** — одно и то же **знание** (правило, формула, контракт) не должно жить в трёх местах. Не про «запрещены одинаковые 5 строк JSX», а про единый источник правды.

Повторяющиеся `loading / error / data` вокруг fetch → `useQuery` / свой `useFetch`. Правило «скидка 10% от 5000 ₽» не копировать в корзине, карточке и письме — иначе бизнес поменяет правило в одном месте и забудет другое.

**KISS** — простое решение лучше «архитектурного». Кнопка с 15 пропсами, внутренним hover-state и 10 вариантами, когда нужна обычная CTA — вред. Лишний слой use case для `GET /health` — вред.

**YAGNI** — не делать абстракцию «нам понадобится мультитеннантность / плагины / своя мини-React». Делать то, что нужно сейчас, с запасом только там, где боль уже видна.

Порядок: **KISS + YAGNI на старте → DRY на стабильном дублировании → SOLID, когда осей изменения несколько**.

Ловушка DRY: два блока **похожи**, но меняются по разным причинам (карточка товара в каталоге и в письме). Общий компонент начинает обрастать `if (variant === 'email')` — это уже не DRY, а склеивание разного. Правило: объединять, когда меняются **вместе**, иначе копия дешевле.

**Где используется на практике:**
- DRY полезен: даты/валюта/ошибки API, схема пользователя, заголовки авторизации, фича-флаги;
- DRY вреден: «универсальная карточка» на весь продукт; общий хук на две формы, которые разъехались (регистрация vs приглашение в орг);
- KISS: админка на 3 экрана без FSD; модалка на `useState`, а не на глобальный стор;
- YAGNI: не внедрять микрофронтенды «на вырост», пока одна команда и один релиз.

**Follow-up:** Команда спорит «вынести в общий хук» vs «пока скопировать»?  
→ Если третьего места ещё нет и требования плывут — копия. Выносить после 2–3 стабильных повторов.

Эти три принципа — правила «здравого смысла»: они дополняют друг друга и помогают держать сложность под контролем.

**DRY (Don't Repeat Yourself)** — борется с дублированием.  
**KISS (Keep It Simple, Stupid)** — борется со сложностью.  
**YAGNI (You Aren't Gonna Need It)** — борется с избыточностью «на вырост».

📊 Различия между принципами

| Принцип | Девиз | Против чего направлен? |
|---|---|---|
| DRY | «Единое представление знания» | дублирование логики, из-за которого правки делаются в 10 местах |
| KISS | «Сделай просто» | overengineering, избыточная архитектура, заумные однострочники |
| YAGNI | «Не понадобится — не делай» | преждевременная оптимизация и будущие фантазии |

⚠️ Когда DRY становится вреден?

Слепое следование DRY — одна из самых частых ошибок. Правило из индустрии: «Дублирование кода часто дешевле, чем неправильная абстракция» (Sandi Metz).

DRY вредит в трёх основных случаях:

1. **Совпадение по форме, но не по смыслу (случайное дублирование)**  
Иногда два куска кода похожи внешне, но решают разные бизнес-задачи. Потом общий компонент превращается в монстра с `if/else` и флагами.  
Пример: одинаковая разметка карточки (картинка, заголовок, описание) для пользователя и для товара. Developer объединяет в `GenericCard`. Потом для товара нужен блок цены/скидок, для пользователя — статус «в сети». Монстр ломает независимость модулей и усложняет изменения.

2. **Преждевременный DRY (Rule of Three)**  
Вынести в общий хелпер стоит не после первого повтора, а после понимания, что код будет меняться одинаково.  
Практика: первая копия — норм, вторая — сигнал, третья — повод остановиться и построить аккуратную абстракцию.

3. **Ухудшение читаемости (убийство KISS ради DRY)**  
Иногда ради экономии 3–4 строк создают переусложнённые дженерики, фабрики функций и хитрые конфиги. Код становится “rigid”: править страшно, потому что всё связано со всем.  
Идея: лучше 4 читаемых строки, чем одна “магическая” конструкция в 5 файлах.

💡 Идеальный баланс

Если принципы конфликтуют, приоритет почти всегда такой: **KISS > YAGNI > DRY**.
- Сначала делаем просто и понятно (KISS).
- Не пишем «на будущее» (YAGNI).
- И только когда видим очевидное дублирование логики, которое будет меняться вместе — аккуратно применяем DRY.

*Классика GoF в контексте JS/TS/React. Важно: не названия, а задача и цена.*

### 8. Что такое Observer? Где это в React?

**Эталонный ответ:**

Observer (Наблюдатель) — поведенческий паттерн: объект-источник (**Subject**) хранит список зависимых (**Observers**) и **сам** уведомляет их при изменении. Общение идёт **напрямую**, без шины событий.

```ts
class Subject {
  private observers: Observer[] = [];
  subscribe(observer: Observer) {
    this.observers.push(observer);
  }
  unsubscribe(observer: Observer) {
    this.observers = this.observers.filter((o) => o !== observer);
  }
  notify(data: unknown) {
    this.observers.forEach((o) => o.update(data));
  }
}
```

Характеристики:
- связанность **плотная (tight)**: Subject знает своих observers (хотя бы как список ссылок);
- подписка на **конкретный объект**, а не на абстрактный топик;
- чаще **синхронный** режим;
- масштаб обычно **локальный** (модуль, класс, поддерево UI).

Аналогия: вы на лекции у профессора — он лично говорит слушателям в аудитории.

⚛️ Где Observer в React?

Каждый раз, когда есть реактивное состояние, работает идея наблюдателя:

- **React Context (`useContext`)**: провайдер — источник; компоненты с `useContext(MyContext)` — наблюдатели. Смена `value` → React уведомляет/перерисовывает подписчиков.
- **`useSyncExternalStore`**: подписка на внешний стор (`navigator.onLine`, кастомное хранилище) по классическому Observer: передаёте `subscribe`, который вешает слушатель.
- Узкий случай: `useState` + ре-рендер детей — локальный observer внутри дерева.

**Где используется на практике:**
- Context темы / локали / текущего пользователя;
- стор корзины → бейдж в шапке и мини-корзина подписаны на один источник;
- синхронизация UI с внешним API браузера через `useSyncExternalStore`.

**Красные флаги:** путает Observer с Pub/Sub (забывает, что Subject хранит прямые ссылки); не знает про отписку/`unsubscribe`.

**Follow-up:** Чем Observer отличается от Pub/Sub?  
→ В Observer нет посредника: Subject напрямую зовёт observers. В Pub/Sub издатель и подписчик изолированы через Event Bus.

### 9. Что такое Pub/Sub? Чем отличается от Observer? Где это в React?

**Эталонный ответ:**

Pub/Sub (Publish/Subscribe) — паттерн, где издатель и подписчик **ничего друг о друге не знают** и общаются через **посредника**: Event Bus / брокер / канал. Издатель шлёт событие в топик, подписчики слушают этот топик.

```js
eventBus.on("user:login", (user) => { /* шапка, аналитика, сокет */ });
eventBus.emit("user:login", { id: 1 });
```

📊 Отличие от Observer

| Критерий | Observer | Pub/Sub |
|---|---|---|
| Связанность | Плотная: Subject хранит ссылки на observers | Слабая: издатель и подписчик изолированы |
| Посредник | Нет | Есть (шина / брокер) |
| Адресация | На **конкретный объект** | На **топик/событие** |
| Режим | Чаще синхронный | Часто асинхронный / event-driven |
| Масштаб | Локально | Глобально (модули, микросервисы) |

Аналогия: вы подписались на журнал через почту. Издательство не знает ваш адрес — печатает тираж, почта доставляет подписчикам топика.

⚛️ Где Pub/Sub в React?

Встроенной глобальной шины в React нет (однонаправленный поток: события вверх, props вниз). Но Pub/Sub активно живёт вокруг:

- **Redux / Zustand / Effector**: `dispatch(action)` — publisher; `useSelector` / подписки — subscribers на срезы стора.
- **Vanilla Custom Events** — связать независимые куски UI без общего родителя:

```js
// Издатель (кнопка в шапке)
window.dispatchEvent(new CustomEvent("open-login-modal"));

// Подписчик (модалка в футере)
useEffect(() => {
  const handler = () => setIsOpen(true);
  window.addEventListener("open-login-modal", handler);
  return () => window.removeEventListener("open-login-modal", handler);
}, []);
```

Минусы шины: сложный дебаг («кто слушает `cart:updated`?»), порядок обработчиков, утечки без `removeEventListener` / `off` в cleanup.

**Где используется на практике:**
- после логина: закрыть модалку, рефетч профиля, analytics, сокет — без импорта экранов друг в друга;
- микрофронты: `host.emit('user-changed')`;
- чат/тикеты по WebSocket — подписка на канал.

Не замена локальному `useState` инпута: для поля формы шина — overkill.

**Красные флаги:** «Context и Redux — одно и то же»; предлагает event bus на каждый клик; забывает cleanup подписки.

**Follow-up:** Когда выбрать Observer, а когда Pub/Sub?  
→ Observer — локальная реакция на конкретный источник (Context, внешний store). Pub/Sub — слабосвязанные модули/фичи без общего родителя.

### 10. Что такое Singleton? Когда полезен и почему его часто ругают?

**Эталонный ответ:**

Singleton (Одиночка) — порождающий паттерн: у класса **один экземпляр** на приложение и **глобальная точка доступа**. Сколько ни создавай — вернётся та же ссылка.

В современном JS/TS самый простой способ — **ES Modules** (файл выполняется один раз при первой загрузке):

```ts
// apiService.ts — экспортируем экземпляр, не класс
class ApiService {
  private baseUrl = "https://example.com";
  fetchData() {
    return fetch(this.baseUrl);
  }
}

export const apiService = new ApiService(); // встроенный singleton модуля
```

Классика с `private constructor` + `getInstance()` тоже бывает, но для JS чаще избыточна.

🟢 Когда полезен

Нужен **один** разделяемый ресурс без конфликтов:
- store (Redux / Zustand) — один источник правды;
- logger — одно соединение/очередь логов;
- API-клиент (Axios с токеном и interceptors);
- in-memory cache — чтобы разные части не качали одно и то же дважды.

🔴 Почему ругают («антипаттерн»)

1. **Скрытые зависимости (DIP):** `createUser()` внутри тихо импортирует глобальный `apiService` — по сигнатуре не видно.
2. **Тесты:** состояние живёт между тестами; нужен `reset()` / мок модуля; изоляция ломается.
3. **Лишняя ответственность (SRP):** класс и делает работу, и контролирует «я единственный».
4. **Гонки в многопотоке** (Node/Java) — в браузере обычно не болит, на бэке важно.

🛠 Чем заменить

**Dependency Injection:** создаёте объект обычным способом и **передаёте** туда, где нужен (аргумент, конструктор, React Context). Единственность обеспечивает DI-контейнер / корень приложения, а не сам класс.

На собесе: синглтон ок для тонкого `apiClient`, плохо — для бизнес-стейта пользователя вместо сессии/React Query.

**Красные флаги:** не знает минусов для тестов; тащит весь app state в singleton.

**Follow-up:** Чем модульный singleton лучше `getInstance()`?  
→ Идиоматичнее JS, меньше бойлерплейта, тот же «один экземпляр на модуль».

### 11. Adapter, Facade, Proxy, Decorator — как отличить и где встречаются?

**Эталонный ответ:**

Все четыре — **структурные** паттерны, внешне «обёртки». Путают часто. Секрет различия — **цель (интенция)** обёртки.

📊 Как отличить по цели

| Паттерн | Что делает обёртка | Меняется ли интерфейс? | Аналогия |
|---|---|---|---|
| **Adapter** | Конвертирует один интерфейс в другой для совместимости | Да: старый → новый | Переходник розетки US → EU |
| **Facade** | Упрощает работу со сложной системой | Да: 10 методов → 1–2 простых | Пульт ТВ вместо ручной настройки |
| **Proxy** | Контролирует доступ (кэш, lazy, логирование) | Нет: интерфейс 1:1 | Секретарь фильтрует звонки директору |
| **Decorator** | Динамически добавляет обязанности | Нет (расширяет поведение) | Одежда: человек тот же, но теплее |

🛠 Разбор во фронтенде

**1) Adapter** — чужой/старый интерфейс не подходит под наши требования.

Где:
- ответы API: `{ user_id }` → `{ id }`, чтобы не править 50 компонентов;
- смена библиотеки графиков: обёртка принимает старые пропсы, внутри зовёт новую либу.

```ts
function mapUserDto(dto: { user_id: string; full_name: string }) {
  return { id: dto.user_id, name: dto.full_name };
}
```

**2) Facade** — спрятать хаос конфигураций и цепочек вызовов за понятной «стеной».

Цель: спрятать сложную логику (сеть, стейт, кэш) за одним кастомным хуком или модулем.

Где:
- `apiClient` / `api.get('/users')` вместо ручного `fetch` + headers + `.json()` в каждом компоненте;
- `useAuth()` → `{ user, login, logout }`, а внутри Context, storage, сеть, валидация токена;
- `useUserProfile()` вместо `useEffect` + `fetch` + `useState` прямо в компоненте — одна строка, чистые данные.

```tsx
function Profile() {
  const { user, loading } = useUserProfile();
  if (loading) return <Spinner />;
  return <UserCard name={user.name} />;
}
```

**3) Proxy** — перехватить обращение *до/после* оригинала, не меняя сам объект и его контракт.

Цель: обернуть компонент/объект, перехватить пропсы или события, добавить логику до или после — интерфейс остаётся 1:1.

Где:
- `<ProtectedRoute>` вокруг страницы профиля: те же пропсы, но сначала проверка авторизации — пускает дальше или редирект на логин;
- реактивность Vue 3 на `new Proxy()` — сеттер ловит изменение и триггерит ре-рендер;
- обёртка API: сначала `localStorage`/кэш, нет данных — пропуск запроса на сервер;
- lazy load картинки / `React.lazy` как прокси модуля.

```tsx
<ProtectedRoute>
  <ProfilePage />
</ProtectedRoute>
```

**4) Decorator** — навесить поведение на лету без бесконечных подклассов.

Где:
- HOC: `withAuth(MyComponent)` — тот же React-компонент + проверка доступа;
- синтаксис `@Component` / `@Injectable` в Angular/NestJS — метаданные и системная логика при инициализации.

Кратко: Adapter **меняет форму**. Facade **упрощает подсистему**. Proxy **стоит перед тем же интерфейсом**. Decorator **добавляет обязанности**.

**Красные флаги:** любой HOC = «прокси»; Adapter и Facade как синонимы; не может сказать, меняется ли интерфейс.

**Follow-up:** Почему adapter на границе с бэком важен?  
→ Сломался контракт API — правите один mapper, а не 30 компонентов.

## Блок 3. React-паттерны

*Как переиспользовать логику и собирать UI.*

### 12. HOC, Render Props и Custom Hooks — чем отличаются и что выбирать?

**Эталонный ответ:**

Все три паттерна решают одну задачу: **переиспользование логики** между компонентами. Они отличаются способом передачи данных и гибкостью.

📊 Главные отличия

| Паттерн | Как работает? | Плюсы | Минусы |
|---|---|---|---|
| Custom Hooks (хуки) | Функция, возвращающая состояние и методы | Чистый JS, нет лишней вложенности в DOM, отличный TypeScript | Только функциональные компоненты |
| Render Props (рендер-пропсы) | Компонент принимает функцию в пропсах и рендерит её результат | Максимальная гибкость разметки в рантайме | «Ад колбэков» (Callback Hell) при вложенности |
| HOC (компоненты высшего порядка) | Функция принимает компонент и возвращает его обёрнутую версию | Работают как декораторы, подходят для классовых компонентов | «Ад обёрток» (Wrapper Hell), неявные пропсы (конфликты имён), плохой TypeScript |

🛠 Один кейс: отслеживание мыши

**1. Custom Hooks (современный стандарт)** — хук отдаёт чистые данные, компонент сам решает, как их отрендерить:

```jsx
const { x, y } = useMousePosition();
return <p>Координаты: {x}, {y}</p>;
```

**2. Render Props (динамическая разметка)** — логика внутри `Mouse`, разметку передаём функцией «на лету»:

```jsx
<Mouse render={({ x, y }) => (
  <p>Координаты: {x}, {y}</p>
)} />
```

**3. HOC (старый паттерн-обёртка)** — данные прилетают скрытно через пропсы, их тяжело типизировать:

```jsx
const ComponentWithMouse = withMouse(MyComponent);
```

🤔 Что выбирать?

- **Custom Hooks — выбор №1** по умолчанию. Для ~95% задач: запросы к API, формы, подписки, анимации. Заменили HOC и Render Props в современных проектах.
- **Render Props** — для UI, где логика жёстко связана с кастомным отображением. Пример: виртуальный список сам считает скролл, но элементы рендерит так, как хочет пользователь.
- **HOC** — только в крайних случаях. Сквозной функционал (cross-cutting) поверх страниц: защита роутов `withAuth`, интеграция со старыми классовыми библиотеками.

Хук ≠ `utils`: если нет `useState` / `useEffect` / `useRef` — это обычная функция, не хук.

**Где используется на практике:**
- хуки: `useDebouncedValue` на поиске; `useLocalStorage` для темы; `useMediaQuery`; `usePermissions`;
- render props: Downshift / виртуальный список `renderItem`; React Router v5 `<Route render={...} />`;
- HOC: `connect` в старом Redux; `withTranslation` i18next; `withRouter` v5.

**Красные флаги:** «HOC не нужно знать»; хук без React API «для красоты»; думает, что хук шарит state между вызовами как синглтон.

### 13. Что такое Compound Components? Зачем они для Tabs/Modal?

**Эталонный ответ:**

Compound Components (составные компоненты) — паттерн, который позволяет создавать **группу компонентов, работающих вместе как единое целое** и неявно разделяющих общее состояние.

Вместо гигантского объекта конфигурации в один большой компонент вы разделяете его на логические части. Скрытая логика и стейт идут между ними через **React Context**.

Самый известный пример из HTML — `<select>` и `<option>`. Вы не передаёте массив опций в `select` через пропсы, вы пишете структуру руками. При этом `select` знает, какая `option` выбрана.

🎨 Зачем для Tabs или Modal

Для табов, модалок, дропдаунов паттерн даёт три преимущества:

1. **Полная свобода вёрстки:** можно поменять части местами, обернуть в `div`/`section`, вставить иконку или текст — компонент не сломается.
2. **Уход от «ада пропсов»:** не прокидывать «открыто/закрыто» и «активный таб» вручную в каждый подкомпонент.
3. **Декларативная структура:** код читается как HTML.

🛠 Пример: Tabs

❌ Без Compound Components — сложная структура данных в один компонент. Перенести табы вниз или добавить иконку = править внутренности `Tabs`:

```jsx
const tabConfig = [
  { id: "1", title: "Профиль", content: <Profile /> },
  { id: "2", title: "Настройки", content: <Settings /> },
];

<Tabs items={tabConfig} orientation="horizontal" />
```

✅ С Compound Components — набор связанных частей. Активный таб скрыт внутри `Tabs` и идёт через контекст:

```jsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">Профиль</Tabs.Trigger>
    <Tabs.Trigger value="settings">Настройки</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="profile">
    <Profile />
  </Tabs.Content>
  <Tabs.Content value="settings">
    <Settings />
  </Tabs.Content>
</Tabs>
```

То же для Modal: `Modal.Header` / `Body` / `Footer`, overlay и `onClose` внутри.

🧱 Под капотом

1. `React.createContext()` — скрытый канал связи.
2. Родитель (`Tabs`) — `useState` и `Provider` вокруг `children`.
3. Дети (`Tabs.Trigger`, `Tabs.Content`) — свойства родителя (`Tabs.Content = ...`), читают и меняют стейт через `useContext`.

Так устроены Radix UI, shadcn/ui, Chakra, Headless UI.

Минусы: сложнее внутри; дети вне провайдера падают. Не для кнопки и не для списка с бэка (там `.map`, не compound).

**Где используется на практике:**
- Tabs на карточке товара (описание / характеристики / отзывы);
- Modal оплаты со слотом под кастомный футер;
- Accordion, Select/Combobox, Dropdown.

### 14. Controlled vs Uncontrolled. Container/Presentational. Когда что?

**Эталонный ответ:**

**Controlled:** источник правды — React state. `value` + `onChange`. Родитель знает значение всегда: валидация на лету, маска телефона, disable submit, синхронизация двух полей (город ↔ индекс).

**Uncontrolled:** источник правды — DOM. `defaultValue` + `ref`. Читаем на submit. Меньше ре-рендеров, проще вкрутить неуправляемую либу (старый jQuery datepicker, file input).

Выбор:
- сложная форма, черновик, «живые» ошибки → controlled (или React Hook Form, который внутри смешивает, но снаружи controlled-like);
- «настройки на 3 поля, сохраняем пачкой» → uncontrolled ок;
- file / contentEditable — часто uncontrolled по природе.

**Container / Presentational:** контейнер знает «откуда данные» (query, стор), презентейшн — тупой UI от props. Сегодня чаще: `useOrderDetails(id)` + `OrderDetailsView`. Идея та же: Storybook и визуальные тесты без сети; смена RTK Query → React Query не трогает вёрстку.

Антипаттерн: Container вокруг каждой кнопки. KISS — контейнер на **границе экрана/фичи**, не на атоме.

**Где используется на практике:**
- controlled: поиск с подсказками (query в URL + инпут); калькулятор ипотеки; фильтры каталога, которые пишутся в query string;
- uncontrolled: форма «написать в поддержку» из 2 полей; скрытый CSRF; интеграция Stripe Elements (их iframe);
- container/view: страница «Заказ №»: хук грузит заказ, view рисует состав и статусы — дизайнер правит view, логика запроса не разъезжается.

**Follow-up:** Почему контейнер на каждый атом плохо?  
→ Шум файлов, проп-дриллинг наоборот, нет выигрыша в тестах.

### 15. Context и Provider pattern. Какие проблемы?

**Эталонный ответ:**

Context отдаёт значение поддереву без проп-дриллинга. Provider pattern — корень приложения обёрнут провайдерами: тема, сессия, i18n, QueryClient, модальный стек.

База: `createContext` + `Provider` + `useContext`. Сложный клиентский стейт: Context + `useReducer` (корзина на 5 действий ещё ок; весь интернет-магазин — уже нет).

Проблемы:
1. **Ре-рендеры:** новый `value={{user, setUser}}` каждый рендер родителя → все потребители обновились. Лечится мемоизацией value или сплитом Context (state отдельно от dispatch).
2. **Частые обновления:** курсор, скролл, `isTyping` в Context — убьёт дерево. Это локальный стейт или узкий стор.
3. **Матрёшка провайдеров:** 15 обёрток в `main.tsx`. Композиция `composeProviders` или группировка «app shell».
4. **Не для server state:** список заказов с пагинацией — React Query/SWR, не Context, иначе нет кэша, дедупа, рефетча.

Эвристика:
- редко меняется, нужно глубоко: theme, locale, currentUser id, feature flags → Context;
- серверные данные → React Query;
- сложный клиент между фичами (черновик конструктора) → Zustand/Redux.

**Где используется на практике:**
- `ThemeProvider` + CSS variables; `I18nProvider`; `AuthProvider` с user из `/me`;
- `QueryClientProvider` — тоже provider pattern;
- модальный `DialogProvider` (открыть confirm из глубокого виджета);
- дизайн-система: `TooltipProvider` (Radix) на корне.

Плохо: `CartContext` с каждым изменением количества, если шапка, сетка товаров и футер все подписаны на весь объект корзины — сплитовать селекторы (Zustand) или мемоизировать срезы.

### 16. Flux: что в основе Redux/Zustand? Чем отличается атомарный стейт и прокси (MobX/Valtio)?

**Эталонный ответ:**

В основе Redux и Zustand лежит **Flux-архитектура** (Facebook). Главный девиз — **однонаправленный поток данных** (Unidirectional Data Flow): стейт в больших приложениях меняется предсказуемо, а не хаотично.

Три ментальные модели клиентского стейта: Flux, атомы, прокси.

🌊 1. Flux: основа Redux и Zustand

Данные идут строго по кругу в одну сторону:

```
Action → Dispatcher → Store → View
```

Ключевые принципы:

- **Единый источник правды:** стейт в одном глобальном Store.
- **Стейт только для чтения:** компонент не пишет `store.user.name = "Иван"`.
- **Изменения через чистые функции (immutability):** View шлёт Action. Reducer (Redux) или функция в Zustand берёт старый стейт и возвращает **новый объект**.

Разница Redux vs Zustand:

- **Redux** — классический Flux: Action Types, Creators, Reducers, один глобальный Dispatcher.
- **Zustand** — «Flux на диете»: нет явных редюсеров и диспетчеров, actions лежат в сторе, синтаксис короткий. Под капотом те же иммутабельность и однонаправленный поток.

```ts
const useCart = create((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
}));
```

⚛️ 2. Атомарный стейт (Recoil, Jotai)

Ментальная модель: **распределённый стейт** — таблица независимых ячеек, а не один монолитный объект.

Каждый атом хранит одно значение (`themeAtom`, `userAtom`). Компоненты подписываются на отдельные атомы. Производное — селекторы: `filteredTodoAtom` пересчитается, если изменился `todosAtom` или `filterCriteriaAtom`.

Плюс: **точечная перерисовка** — только подписчики изменившегося атома. Нет глобального оверхеда плохо настроенного Redux.

```ts
const countAtom = atom(0);
const [count, setCount] = useAtom(countAtom);
```

🕵️‍♂️ 3. Прокси-стейт (MobX, Valtio)

Ментальная модель: **мутабельный код с автоматическим трекингом**. Полная противоположность Flux: пишете как с обычными объектами JS, за ре-рендер отвечает `Proxy`.

Состояние — обычный объект, обёрнутый в `new Proxy()`. `state.user.name = "Иван"` перехватывается сеттером. Библиотека знает, кто читал это поле через геттер во время рендера, и обновляет только их.

Пример на React + MobX. Стор — обычный класс: `makeAutoObservable` делает свойства observables, методы — actions. Экспортируем один экземпляр (singleton).

```js
import { makeAutoObservable } from "mobx";

class UserStore {
  name = "Алексей";
  age = 25;

  constructor() {
    makeAutoObservable(this); // Proxy под капотом
  }

  changeName() {
    this.name = "Иван";
  }

  celebrateBirthday() {
    this.age += 1;
  }
}

export const userStore = new UserStore();
```

Компонент оборачивают в `observer`: он сам трекает, какие поля `userStore` читались в рендере.

```jsx
import { observer } from "mobx-react-lite";
import { userStore } from "./UserStore";

const App = observer(() => (
  <div>
    <p>Имя: {userStore.name}</p>
    <p>Возраст: {userStore.age}</p>
    <button onClick={() => userStore.changeName()}>Поменять имя</button>
    <button onClick={() => userStore.celebrateBirthday()}>День рождения</button>
  </div>
));
```

Клики мутируют стор «в лоб» — `observer` перерисует только то, что реально читалось. Если компонент смотрит только на `age`, смена `name` его не тронет.

Главные плюсы прокси-стейта:

- **Минимум кода (no boilerplate):** не нужны экшены, редюсеры, типы и бесконечный spread (`...state`). Пишете чистый JavaScript.
- **Fine-grained reactivity:** если в объекте 100 полей, а компонент читает только `state.user.age`, он не перерисуется при смене `state.user.name`. Прокси знает зависимости с точностью до поля.
- **Идеально для OOP:** классы, геттеры, сеттеры, инкапсуляция — MobX встаёт как родной.

Минусы и подвохи:

- **«Магия» в коде:** поток данных неявный. Во Flux видно `dispatch` / `set`; в MobX/Valtio объект изменился в глубине хелпера — трудно ответить «почему этот компонент перерисовался?».
- **Деструктуризация ломает реактивность:** `const { count } = state` вне специальных хуков снимает Proxy-обёртку, свойство становится обычным числом, шпион теряет связь.
- **Плохо дружит с иммутабельными либами:** графики, Undo/Redo и инструменты, которые ждут чистые неизменяемые данные.

Ключевое отличие: во Flux (Zustand/Redux) вы **явно объявляете намерение** изменить стейт через функции и создаёте новые копии. В прокси-стейте вы **меняете данные руками**, а библиотека сама считает, что обновить на экране.

📊 Сводная таблица

| Критерий | Flux (Redux, Zustand) | Атомарный (Jotai, Recoil) | Прокси (MobX, Valtio) |
|---|---|---|---|
| Философия | Иммутабельность | Иммутабельность (разделённая) | Мутабельность (прямое изменение) |
| Структура | Глобальный монолитный объект | Набор независимых атомов | Объект/класс под Proxy |
| Как меняют | `dispatch` / action | Сеттер атома | Присвоение через `.` |
| Как трекают | Сравнение ссылок (`old === new`) | Граф зависимостей атомов | Геттеры/сеттеры Proxy |
| Сложность | Высокая (Redux) / средняя (Zustand) | Средняя | Низкая (как чистый JS) |

Что выбирать:

- **Zustand** — стандарт по умолчанию для большинства React-приложений: плюсы Flux без его сложности.
- **Jotai / Recoil** — графические редакторы, дашборды со сложными связями, тысячи мелких независимых элементов.
- **MobX / Valtio** — команды с OOP (классы, геттеры) и желанием писать меньше инфраструктурного кода.

Это **клиентский** стейт; серверные списки сюда не кладут (см. следующий вопрос).

**Красные флаги:** «Redux и MobX — одно и то же, оба сторы»; кладёт fetch-списки в Flux «потому что стор уже есть».

**Follow-up:** Zustand — это Flux или атомы?  
→ Flux на диете: один store и иммутабельный `set`. Это не граф атомов как в Jotai.

### 17. Server State vs Client State. Почему нельзя смешивать API и UI в одном сторе?

**Эталонный ответ:**

Разделение на **Server State** и **Client State** — один из главных архитектурных трендов во фронтенде. Смешивать их в одном глобальном сторе (список товаров из БД + флаг модалки в одном Redux/Zustand) — антипаттерн: переусложнение и баги синхронизации.

📊 В чём принципиальная разница

| Критерий | Server State | Client State |
|---|---|---|
| Где лежат данные | На удалённом сервере (БД) | В памяти браузера |
| Кто владеет | Сервер. Фронт видит лишь **снимок** на момент запроса | Только ваше приложение |
| Могут устареть? | Да: другой пользователь уже изменил данные на бэке | Нет: вы сами ими управляете |
| Главные задачи | Кэш, инвалидация, refetch, сетевые ошибки | Мгновенный UI, синхронные флаги |
| Примеры | Список пользователей, профиль, корзина, статьи | Тема dark/light, открыта ли модалка, язык, текст в инпуте |

🔴 Почему нельзя смешивать в одном сторе

Засовывать Server State в Zustand/Redux заставляет писать тонны boilerplate и порождает проблемы:

1. **Ручное управление кэшем.** «Устарели ли данные? Как часто обновлять? Рефетчить ли при возврате на вкладку?» — в обычном сторе это `useEffect`, `isLoading`, `isError` и таймеры на каждый эндпоинт. Вы изобретаете велосипед.

2. **Несколько источников правды.** Скачали профиль в Zustand — две копии: на сервере и в браузере. Админ забанил пользователя на бэке — стор не узнает, пока не сделаете принудительный fetch. Вы управляете тем, чем не владеете.

3. **Раздувание стора.** UI (табы) смешивается с бизнес-логикой и сырыми DTO. Тяжело читать, тестировать, поддерживать. Рефетч профиля не должен сбрасывать `isSidebarOpen`.

🛠 Как правильно разделять

**Выселить Server State** из обычных стейт-менеджеров в специализированные библиотеки.

```
        [ ВАШЕ ПРИЛОЖЕНИЕ ]
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
[ SERVER STATE ]      [ CLIENT STATE ]
React Query / RTK     Zustand / MobX / Valtio
SWR / Apollo          Context / useState
кэш, сеть, статусы    UI-флаги, темы, ввод
```

Для данных с сервера — React Query (не создаёте стор, хук сам качает, кэширует, обновляет):

```js
const { data: products, isLoading } = useQuery({
  queryKey: ["products"],
  queryFn: fetchProducts,
});
```

Для локального UI — Zustand (только синхронные флаги):

```js
const useUiStore = create((set) => ({
  isSidebarOpen: false,
  toggleSidebar: () => set((s) => ({ isSidebarOpen: !s.isSidebarOpen })),
}));
```

Мутация на сервере → `invalidateQueries`, а не ручной `setCart` в Zustand. RTK Query — тот же принцип server state, просто внутри Redux; это не повод класть `isModalOpen` в slice с `users`.

💡 Резюме

Zustand/Redux — для UI-стейта, React Query — для серверных данных. Меньше `useEffect` на загрузку, UI-стор крошечный и читаемый.

**Красные флаги:** «у нас всё в Redux, и список постов тоже»; путает `isLoading` Query с `useState(true)` без отмены запроса.

**Follow-up:** Куда положить `selectedOrderId`?  
→ Если URL (`/orders/42`) — роутер. Если подсветка в таблице — `useState`. Не в кэш Query и не в «бога-стор», пока id не шарится между далёкими фичами.

### 18. Что такое Clean Architecture? Правило зависимостей?

**Эталонный ответ:**

Главная идея Clean Architecture во фронтенде — **полная изоляция бизнес-логики** от UI-фреймворка (React) и инфраструктуры (Axios, Fetch, LocalStorage).

Бизнес-логика (расчёты, правила, валидация) — самая ценная часть приложения. Она пишется на чистом JS/TS и должна работать одинаково в React, Vue, React Native или Node-скрипте.

🧱 Три слоя. Зависимости только **внутрь**

Внешние слои знают о внутренних; внутренние ничего не знают о внешних.

| Слой | Что внутри | Правило |
|---|---|---|
| **Domain (ядро)** | Модели, правила, Use Cases | Ноль импортов React/Axios |
| **Data (инфраструктура)** | Реализации доступа к данным: API, кэш, БД | Реализует контракты Domain |
| **Presentation** | React-компоненты, хуки, стили | Рисует UI, вызывает Domain |

🛠 Пример: скидки и кэшбэк в корзине

**1. Domain** — чистые типы и use case. Никакого React.

```ts
// domain/models.ts
export type User = { id: string; name: string; discountRate: number };
export type CartItem = { id: string; title: string; price: number; quantity: number };

export interface UserRepository {
  getUserProfile(id: string): Promise<User>;
}

// domain/useCases/calculateCart.ts
export function calculateCart(items: CartItem[], userDiscountRate: number) {
  const rawTotal = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const discountedTotal = rawTotal * (1 - userDiscountRate);
  const cashback = discountedTotal >= 5000 ? discountedTotal * 0.05 : 0;

  return {
    totalPrice: Math.round(discountedTotal),
    cashback: Math.round(cashback),
  };
}
```

**2. Data** — реализует контракт. Только здесь axios/fetch/localStorage. Смена REST → GraphQL = правка этого слоя.

```ts
// data/repositories/HttpUserRepository.ts
import axios from "axios";
import { UserRepository, User } from "../../domain/models";

export class HttpUserRepository implements UserRepository {
  async getUserProfile(id: string): Promise<User> {
    const response = await axios.get(`/api/v1/users/${id}`);
    return {
      id: response.data.uid,
      name: response.data.full_name,
      discountRate: response.data.meta.discount || 0,
    };
  }
}
```

**3. Presentation** — React не знает про axios. Зовёт репозиторий и чистую функцию.

```tsx
import { useEffect, useState } from "react";
import { calculateCart } from "../../domain/useCases/calculateCart";
import { HttpUserRepository } from "../../data/repositories/HttpUserRepository";
import { CartItem, User } from "../../domain/models";

const userRepository = new HttpUserRepository(); // лучше DI / Context

export function CartSummary({ cartItems, userId }: { cartItems: CartItem[]; userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    userRepository.getUserProfile(userId).then(setUser);
  }, [userId]);

  if (!user) return <div>Загрузка профиля...</div>;

  const { totalPrice, cashback } = calculateCart(cartItems, user.discountRate);

  return (
    <div>
      <h3>Итого: {totalPrice} ₽</h3>
      {user.discountRate > 0 && <p>Скидка: {user.discountRate * 100}%</p>}
      {cashback > 0 && <p>Кэшбэк: +{cashback} ₽</p>}
    </div>
  );
}
```

📊 Плюсы и минусы

Плюсы:
- **Тестируемость:** `calculateCart` — обычная функция, без рендера и моков стора.
- **Независимость от фреймворка:** выкинули `presentation`, перенесли `domain` + `data` на Vue/RN без правок ядра.
- **Смена технологий:** axios → fetch только в `HttpUserRepository`.

Минусы:
- **Boilerplate:** интерфейс + репозиторий + use case + модель + компонент — для простой формы overkill (нарушение KISS).
- **Порог входа:** сложно перестроиться с «всё в хуках и компонентах» на интерфейсы и репозитории.

Не использовать: лендинг, хакатон, CRUD-админка «на неделю». Имеет смысл: финтех, биллинг, white-label, долгоживущий B2B.

**Красные флаги:** domain импортирует React; use case знает Axios; «Clean» = просто папки без правила зависимостей.

**Follow-up:** Связь с DIP?  
→ Use case зависит от порта `UserRepository`, не от `HttpUserRepository`. Реализация подставляется снаружи.

### 19. Что такое Feature-Sliced Design? Слои и правило импортов.

**Эталонный ответ:**

Feature-Sliced Design (FSD) — методология, которая делит код по **бизнес-ценности (фичам)**, а не по техническим типам файлов (`components/`, `hooks/`, `styles/`).

Цель: масштабируемость, низкая связанность (coupling), понятность большой команде.

🧱 Слои → слайсы → сегменты

**1. Слои (Layers)** — иерархия сверху вниз (от «умного» к «глупому»):

| Слой | Роль |
|---|---|
| `app` | Инициализация: провайдеры, глобальные стили, роутинг |
| `pages` | Страницы; собирают UI из нижележащих слоёв |
| `widgets` | Крупные блоки: Header, Sidebar, ProductGrid |
| `features` | Действия с бизнес-ценностью: AddToCart, ChangePassword, SearchProduct |
| `entities` | Бизнес-сущности: User, Product, Order (модель, UI-карточки, сторы) |
| `shared` | Код без бизнес-логики: UI-kit, хелперы, Axios-клиент, базовые хуки |

*(В полной спецификации FSD ещё бывает слой `processes` — сквозные сценарии; на практике часто обходятся без него.)*

**2. Слайсы (Slices)** — папки внутри слоёв (`pages`…`entities`) по теме: `entities/user`, `entities/product`, `features/auth-by-email`, `features/add-to-cart`.

**3. Сегменты (Segments)** — техника внутри слайса:

- `ui` — компоненты и стили;
- `model` — сторы, экшены, типы;
- `api` — сетевые запросы, хуки React Query;
- `lib` — локальные хелперы.

📐 Правило импортов (два закона)

**Rule 1. Линейная иерархия — только «сверху вниз».**  
Нижний слой ничего не знает о верхних.

- `features` может импортировать `entities` и `shared`.
- ❌ `entities` не импортирует `features` или `widgets`. Сущность «Продукт» не знает, какая фича «Добавить в корзину» её использует.
- Слайсы **одного** слоя не импортируют друг друга напрямую (иначе циклы) — общее вниз в `entities`/`shared` или composition на `page`/`widget`.

**Rule 2. Публичный API — запрет глубоких импортов.**  
У слайса наверху `index.ts`: наружу только то, что готовы отдать.

```ts
// ✅
import { UserCard } from "@/entities/user";

// ❌
import { UserCard } from "@/entities/user/ui/UserCard.tsx";
```

Проверяется ESLint (`boundaries` / FSD-плагин).

📊 Структура папок

```text
src/
├── app/                  # провайдеры, стили, роутинг
├── pages/
│   └── profile/
│       ├── ui/
│       └── index.ts
├── widgets/              # Header, Footer
├── features/             # add-to-cart, login
├── entities/
│   └── product/
│       ├── api/
│       ├── model/
│       ├── ui/           # ProductCard, ProductRow
│       └── index.ts      # Public API
└── shared/               # shared/ui/button, утилиты
```

Цена: дисциплина команды. На 5 экранах может быть рано. Антипаттерн: папка `features` есть, но все импортируют всё; бизнес-кнопка в `shared/ui`.

**Красные флаги:** «FSD = просто features»; импорт фичи из фичи «на минутку»; глубокий импорт в обход `index.ts`.

### 20. DDD на пальцах: Entity, Value Object, Aggregate, Bounded Context. Нужен ли он фронту?

**Эталонный ответ:**

Domain-Driven Design (DDD) — проектирование вокруг **бизнес-логики и процессов компании**, а не вокруг удобств фреймворка или схемы БД.

Цель: код говорит **на одном языке с бизнесом**.

🗣️ Ключевые понятия

Стратегический уровень (как резать проект) и тактический (как писать код внутри).

**1. Ubiquitous Language (единый язык)**  
Разработчики, менеджеры, дизайнеры и аналитики используют одни термины в разговорах, ТЗ и коде.

Пример: маркетинг зовёт пользователя «Лид» до оплаты и «Клиент» после — в коде `Lead` и `Client`, а не один `User` со 150 флагами.

**2. Bounded Context (ограниченный контекст)**  
Одна сущность в разных отделах — разные вещи. Контексты изолируют.

`Product` в каталоге: картинка, описание, отзывы.  
В доставке: вес, габариты, хрупкость.  
В бухгалтерии: артикул, себестоимость, НДС.

Вместо одного класса-монстра — **три независимых** `Product` в трёх контекстах.

📁 Структура папок на фронте (в отличие от FSD)

Верхний уровень — **бизнес-домены**, не слои `features`/`entities`:

```text
src/
├── domains/
│   ├── catalog/
│   │   ├── components/
│   │   ├── store/
│   │   ├── types.ts      # Product с картинками и описанием
│   │   └── index.ts
│   ├── checkout/
│   │   ├── types.ts      # Product: id, цена, quantity
│   │   └── index.ts
│   └── delivery/
│       ├── types.ts      # Product: вес, объём
│       └── index.ts
├── shared/               # кнопки, axios без бизнес-логики
└── App.tsx
```

🧱 Тактические инструменты

- **Entity:** есть `id`, свойства меняются, идентичность сохраняется. `User`, `Order`.
- **Value Object:** без `id`, равенство по значению, **immutable**. `Money(amount, currency)`, `Address`.
- **Aggregate:** кластер сущностей/VO с **корнем** (Aggregate Root). Снаружи общаются только с корнем. `Order` держит `OrderLineItem[]` и `Address`; снаружи не правят позицию — только `order.addItem(product)`.
- **Domain Service:** логика не принадлежит одному объекту. `CurrencyConverter`.

🛠 Пример: Value Object + Aggregate Root

```ts
export class Money {
  constructor(
    public readonly amount: number,
    public readonly currency: string,
  ) {
    if (amount < 0) throw new Error("Сумма не может быть отрицательной");
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error("Разные валюты!");
    return new Money(this.amount + other.amount, this.currency);
  }
}

export class Order {
  public readonly id: string;
  private items: { productId: string; price: Money; quantity: number }[] = [];
  private total: Money;

  constructor(id: string, currency: string) {
    this.id = id;
    this.total = new Money(0, currency);
  }

  public addProduct(productId: string, price: Money, quantity: number): void {
    this.items.push({ productId, price, quantity });
    const itemCost = new Money(price.amount * quantity, price.currency);
    this.total = this.total.add(itemCost);
  }

  public getTotalPrice(): Money {
    return this.total;
  }
}
```

⚖️ Плюсы и минусы

Плюсы:
- большие команды («Каталог» / «Доставка») в разных папках, меньше конфликтов в Git;
- низкая связанность: правка корзины не ломает ЛК;
- легко удалить модуль: `domains/referrals/` целиком.

Минусы:
- **намеренное** дублирование типов `Product` — новичкам кажется нарушением DRY, в DDD это изоляция контекстов;
- высокий порог: нужна сессия с бизнесом (Event Storming), нельзя «просто сесть и писать».

На фронте полный учебник DDD редок. Часто берут кусок: VO для денег/дат, явные правила, разные типы `CatalogProduct` vs `WarehouseProduct`. Для простой витрины хватит DTO + mapper. Комбо: DDD описывает домен, Clean — изоляцию от UI, FSD — слои внутри приложения.

**Красные флаги:** один божественный `Product` на весь холдинг; путает Entity и DTO.

**Follow-up:** Entity vs DTO?  
→ DTO — провода с API. Entity — правила. На границе — mapper.

### 21. Модульная (компонентная) архитектура. Что такое Colocation и зачем public API модуля?

**Эталонный ответ:**

Модульная (компонентная) архитектура — классический подход на принципе **Colocation**: «всё, что используется вместе, лежит вместе».

Вместо раскидывания одной фичи по глобальным `components/`, `hooks/`, `types/` весь контекст страницы или бизнес-фичи упаковывают в **изолированный модуль**.

Так устроен файловый роутинг Next.js, Remix, Nuxt, SvelteKit.

📁 Структура

Две зоны: общий UI-кит и изолированные бизнес-модули.

```text
src/
├── components/          # глобальный UI-kit без бизнес-логики
│   ├── Button/
│   ├── Input/
│   └── Spinner/
├── modules/
│   ├── AuthForm/
│   │   ├── components/  # только для этой формы
│   │   ├── hooks/
│   │   ├── store/
│   │   ├── types.ts
│   │   ├── AuthForm.tsx
│   │   └── index.ts     # Public API
│   └── ProductCard/
│       ├── components/
│       ├── useProduct.ts
│       ├── ProductCard.tsx
│       └── index.ts
├── utils/
└── App.tsx
```

📐 Три правила

1. **Публичный API (`index.ts`).** Модуль — чёрный ящик. Снаружи только разрешённый экспорт.

```ts
// ✅
import { AuthForm } from "@/modules/AuthForm";

// ❌
import { PasswordInput } from "@/modules/AuthForm/components/PasswordInput";
```

2. **Запрет лезть внутрь чужого модуля.** Нужна кнопка из `AuthForm` в `UserProfile` → вынести в `components/` или общий модуль.

3. **Локальный стейт по умолчанию.** Хуки, Zustand, API — внутри модуля. Глобальный стор — только для сквозного: токен, тема.

🛠 Пример: `ProductCard`

```ts
// modules/ProductCard/types.ts
export type Product = { id: string; title: string; price: number; image: string };

// modules/ProductCard/useProduct.ts
export function useProduct(productId: string) {
  const [isAdding, setIsAdding] = useState(false);
  const addToCart = async () => {
    setIsAdding(true);
    await fetch("/api/cart", {
      method: "POST",
      body: JSON.stringify({ productId }),
    });
    setIsAdding(false);
  };
  return { addToCart, isAdding };
}
```

```tsx
// modules/ProductCard/ProductCard.tsx
import { Button } from "@/components/Button";
import { Product } from "./types";
import { useProduct } from "./useProduct";

export function ProductCard({ product }: { product: Product }) {
  const { addToCart, isAdding } = useProduct(product.id);
  return (
    <div>
      <img src={product.image} alt={product.title} />
      <h3>{product.title}</h3>
      <p>{product.price} ₽</p>
      <Button onClick={addToCart} disabled={isAdding}>
        {isAdding ? "Добавление..." : "Купить"}
      </Button>
    </div>
  );
}
```

```ts
// modules/ProductCard/index.ts
export { ProductCard } from "./ProductCard";
export type { Product } from "./types";
```

⚖️ Плюсы и минусы

Плюсы:
- **KISS:** понятно стажёру с первого дня; нет гимнастики слоёв FSD/Clean;
- легко удалить фичу — одна папка `modules/AuthForm`;
- меньше прыжков по файлам при баге.

Минусы:
- без ESLint границы размываются, модули связываются «клубком»;
- при сотнях модулей сложно понять, что пора вынести в глобальный `components/` (дубли в пяти местах).

Vs FSD: модульная проще и ближе к colocation «фича = папка»; FSD жёстче режет слои (`features`/`entities`/`shared`) и импорты сверху вниз. Часто начинают с модулей, при росте команды/кода ужесточают до FSD.

**Красные флаги:** глубокий импорт внутрь модуля; общий Zustand «на всё» вместо локального стора модуля.

**Follow-up:** Чем отличается от FSD?  
→ Colocation по модулю/странице без обязательной иерархии слоёв. FSD добавляет строгие слои и запрет импорта «вбок» между фичами через eslint.

### 22. Микрофронтенды. Зачем, как устроены, когда не внедрять?

**Эталонный ответ:**

Микрофронтенды — подход, при котором гигантский фронтенд-монолит режут на **несколько независимых мини-приложений**. Каждое разрабатывает, тестирует и деплоит своя команда на свой сервер; в браузере они собираются в один бесшовный сайт.

🧱 Зачем (боль монолита при 50+ разработчиках)

- конфликты в Git на одних и тех же файлах;
- долгий деплой: опечатка в футере → пересборка всего (30–40 мин);
- технологический тупик: старый React, целиком не переписать.

Микрофронты дают командам **автономию**.

🗺️ Архитектура

Всегда есть **Container (Host / «ракушка»)** и **Remote**-приложения.

```text
              [ БРАУЗЕР ]
                   │
                   ▼
         ┌─────────────────────┐
         │  Container (Host)   │
         └──────────┬──────────┘
                    │
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
  Каталог        Корзина      Личный кабинет
 (Vite+React)  (Webpack+Vue)  (Rspack+React)
```

Фичи подхода:
- **независимый релиз** — корзина деплоится 10 раз в день, не ломая каталог;
- **разные технологии** возможны (на практике чаще один фреймворк, иначе раздутый бандл);
- **изоляция** — ошибка в ЛК не роняет весь сайт, корзина ещё работает.

🛠️ Технически: Module Federation

Стандарт сегодня — Module Federation (Webpack 5, Rspack, плагины Vite/Rollup): Host динамически качает JS Remote из сети.

Remote (корзина) отдаёт наружу:

```js
new ModuleFederationPlugin({
  name: "cart_app",
  filename: "remoteEntry.js",
  exposes: {
    "./CartWidget": "./src/components/CartWidget.tsx",
  },
});
```

Host подключает:

```js
new ModuleFederationPlugin({
  name: "host_app",
  remotes: {
    cart: "cart_app@http://localhost:3002/remoteEntry.js",
  },
});
```

В React — как «импорт из сети» через `lazy` + `Suspense`:

```tsx
const RemoteCartWidget = React.lazy(() => import("cart/CartWidget"));

export function Header() {
  return (
    <header>
      <Logo />
      <Suspense fallback={<div>Загрузка корзины...</div>}>
        <RemoteCartWidget />
      </Suspense>
    </header>
  );
}
```

🔴 Минусы (за что ругают)

Дорогая архитектура: лечит **организацию людей**, усложняет технику.

- **бандл:** без `shared` React/ReactDOM скачается несколько раз;
- **CSS:** глобальный `.btn { color: red }` перекрашивает чужие модули → CSS Modules / Tailwind / Shadow DOM;
- **дебаг и E2E:** локально поднимать 5–6 реп или прокси на staging;
- **разный UX:** без корпоративного UI Kit как npm-пакета кнопки и шрифты разъедутся.

🤔 Когда внедрять

- ❌ стартап / команда до ~20–30 человек — утонете в CI/CD и сборщиках, просядете по скорости;
- ✅ энтерпрайз (крупный банк, маркетплейс), где команды **физически блокируют** релизы друг друга.

Не путать с модульной папочной структурой в одном репо (colocation) и с FSD — там один деплой. Микрофронты — отдельные артефакты и деплои.

**Красные флаги:** «давайте микрофронты, потому что Netflix»; два React в бандле без shared; нет единого UI Kit.

**Follow-up:** Module Federation vs iframe?  
→ Federation — общий JS-рантайм и композиция компонентов; iframe — жёсткая изоляция, тяжелее UX и коммуникация (postMessage).
