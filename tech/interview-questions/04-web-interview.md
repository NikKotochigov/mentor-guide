## Блок 1. HTML, семантика, доступность

*База, на которой держатся SEO, a11y и качество вёрстки.*

### 1. Что такое семантическая вёрстка? Для чего она нужна?

**Зачем спрашивают:** классика любого фронтенд-скрининга.

**Эталонный ответ (для ментора):**

Семантика — использование HTML-элементов **по смыслу**, а не только как «коробки для стилей»: `header`, `nav`, `main`, `article`, `section`, `aside`, `footer`, `button`, `a`, `ul`/`ol`, заголовки `h1`–`h6`, формы `label`/`input` и т.д.

Зачем:
- **доступность** — скринридеры и клавиатура опираются на роли/структуру документа;
- **SEO** — поисковики лучше понимают структуру страницы;
- **поддерживаемость** — код читаемее, проще стилизовать и тестировать;
- **браузерные дефолты** — фокус, поведение кнопок/ссылок, нативные контролы.

Плохой паттерн: всё на `div`/`span` + клики на `div` без роли и клавиатуры.

**Хороший ответ кандидата:** смысл тегов + a11y/SEO/поддержка, пример `button` vs `div onclick`.

**Красные флаги:**
- «Семантика нужна только для SEO».
- Путает `section` и `div`, не знает зачем `main` один на страницу.

**Follow-up:** Чем `button` лучше `div` с `onClick`?  
→ Фокус, Enter/Space, роль, формы (`type="submit"`), без JS базовая доступность выше.

**Упрощение:** «Какие теги поставишь на шапку, меню, основной контент и подвал?»

### 2. Что обозначает «доступность» (accessibility) веб-сайта? За счёт чего она достигается?

**Зачем спрашивают:** Middle+ почти всегда; в продуктовых компаниях — must.

**Эталонный ответ:**

**Accessibility (a11y)** — возможность пользоваться сайтом людям с разными ограничениями: зрение, слух, моторика, когнитивные особенности; также удобство для всех (клавиатура, высокий контраст, Slow connection).

Достигается за счёт:
1. **Семантика** — правильные теги и структура заголовков.
2. **Клавиатура** — всё интерактивное доступно Tab/Enter/Space/Esc; видимый `:focus`.
3. **ARIA** — дополняет HTML, когда семантики не хватает (`aria-label`, `aria-expanded`, `role` осторожно). Правило: **не чини ARIA то, что чинится нативным HTML**.
4. **Текст вместо «только цвет/иконка»** — подписи, `alt` у информативных картинок, `alt=""` у декоративных.
5. **Контраст, размеры зон клика, масштабирование** (до ~200% без поломки).
6. **Формы** — связанный `label`, понятные ошибки, не блокировать paste без причины.

Проверка: клавиатура, VoiceOver/NVDA, Lighthouse/axe, ручной чеклист.

**Follow-up:** Когда нужен `aria-label`, а когда достаточно видимого текста?  
→ Если видимого имени нет (иконка-кнопка) — `aria-label` / `aria-labelledby`. Если текст на кнопке есть — дублировать не нужно.

**Упрощение:** «Как сделать кнопку-иконку доступной?»

### 3. Box model: что входит в ширину элемента? `content-box` vs `border-box`?

**Зачем спрашивают:** часто вместе с вёрсткой; ловит тех, кто «плавает» в CSS.

**Эталонный ответ:**

Классическая модель: `width`/`height` по умолчанию относятся к **content**. Padding и border добавляются снаружи → элемент становится шире, чем «задали».

`box-sizing: border-box` — `width` включает content + padding + border (margin всё ещё снаружи). Так проще считать сетки и «100% ширины».

Практика: глобально

```css
*, *::before, *::after { box-sizing: border-box; }
```

**Follow-up:** Влияет ли margin на `offsetWidth`?  
→ Нет; `offsetWidth` ≈ content + padding + border (без margin).

## Блок 2. CSS: раскладка, адаптив, препроцессоры

### 4. Подходы к адаптивной вёрстке (резиновая, media-запросы, flex/grid)?

**Эталонный ответ:**

1. **Резиновая / fluid** — ширины в `%`, `max-width`, относительные единицы; контент «тянется» с экраном.
2. **Media queries** — брейкпоинты под раскладку (`min-width` / `max-width`, `prefers-reduced-motion`, `hover: hover`).
3. **Flexbox** — одномерная раскладка (ряд/колонка): выравнивание, распределение свободного места, навбары, карточки в ряд.
4. **Grid** — двумерная: страницы, галереи, сложные сетки (`fr`, `minmax`, `auto-fit`/`auto-fill`).
5. **Современные дополнения:** `clamp()` для fluid-типографики, container queries (стили от размера контейнера, не viewport), `dvh`/`svh` для мобильного viewport.

Частый подход Middle: **mobile-first** (`min-width` вверх) + flex/grid + немного media/container queries.

**Красные флаги:**
- «Адаптив = только Bootstrap breakpoints».
- Не отличает flex и grid.

**Follow-up:** Когда Grid, когда Flex?  
→ Grid — двумерная структура страницы/секции. Flex — выравнивание в одном направлении, компоненты.

### 5. Чем `rem` / `em` / `%` / `vw` отличаются? Что выбрать для шрифтов и отступов?

**Эталонный ответ:**

**В чем разница (шпаргалка)**

- `rem` (Root EM): зависит от размера шрифта корня страницы (`<html>`). По умолчанию в браузерах `1rem = 16px`. Если изменить размер шрифта в настройках браузера или у `<html>`, все `rem` пропорционально изменятся.
- `em`: зависит от размера шрифта текущего элемента (или его родителя). Если у блока `font-size: 20px`, то `1em` внутри этого блока равен `20px`, а `2em` — `40px`.
- `%` (проценты): зависит от размеров родительского элемента. Для ширины (`width`) — процент от ширины родителя. Для шрифта (`font-size`) — процент от размера шрифта родителя.
- `vw` (Viewport Width): зависит от ширины экрана (окна браузера). `1vw` равен ровно `1%` от ширины экрана. Если ширина экрана `1920px`, то `1vw = 19.2px`.

**Что выбрать для шрифтов?**

Для текста стандарт индустрии — это `rem`, с редким добавлением `em`.

- Для основного текста и заголовков используйте `rem`. Если пользователь со слабым зрением увеличит базовый шрифт в настройках телефона или браузера, сайт масштабируется и сохранит читаемость.
- Для элементов, связанных с текстом, используйте `em`. Например, маленькая иконка рядом с текстом: если задать ей размер в `em`, она будет автоматически уменьшаться или увеличиваться вместе с текстом (например, при переходе заголовка с десктопа на мобильный).
- Никогда не используйте `vw` для обычного текста в чистом виде — на маленьких телефонах буквы станут микроскопическими, а на огромных мониторах — гигантскими.

**Что выбрать для отступов (`padding`, `margin`)?**

Выбор зависит от того, как должен вести себя отступ при изменении интерфейса.

- `rem` — для глобальных отступов и сеток. Расстояния между секциями, отступы в карточках товаров, внешние поля страницы. Вся структура сайта будет увеличиваться синхронно со шрифтом.
- `em` — для внутренних отступов кнопок и тегов. Идеально для `padding` внутри кнопок: если меняется `font-size`, отступы увеличатся пропорционально, и кнопка не «сломается».
- `%` — для ширины колонок и сетки. Когда блоку нужно занять ровно половину родительского контейнера (`width: 50%`).
- `vw` (и `vh`) — для крупных декоративных отступов. Например, огромный отступ перед подвалом на весь экран или баннер строго по высоте/ширине дисплея.

### 6. Что такое CSS-препроцессоры? Чем отличаются от постпроцессоров и нужны ли они сейчас?

**Зачем спрашивают:** классика фронтенд-скрининга. Ловят, понимает ли кандидат *зачем* Sass существовал и что из этого уже умеет сам CSS — а не только «пишем вложенность и переменные».

**Эталонный ответ (для ментора):**

**Препроцессор** — язык/надстройка над CSS, который **компилируется в обычный CSS до браузера**. Браузер `.scss` / `.less` не понимает: в бандле или CI должен быть шаг сборки (dart-sass, less, сборщик Vite/Webpack).

Исторически закрывали дыры CSS: переменные, вложенность, миксины, модули, циклы, цветная математика. Популярные: **Sass/SCSS** (де-факто стандарт), **Less**, **Stylus**. На РФ-собесах почти всегда имеют в виду Sass.

**SCSS vs Sass:** один движок. SCSS — CSS-подобный синтаксис с `{ }`; `.sass` — indented-синтаксис без скобок. В проектах почти везде SCSS.

---

**Что даёт препроцессор (Sass)**

- **Переменные** `$color-brand` — подстановка **на этапе сборки**. В итоговый CSS уходит уже конкретное значение.
- **Вложенность** и `&` (`&:hover`, `&.is-active`, `&__item` в БЭМ).
- **Миксины** `@mixin` / `@include` — переиспользуемые куски правил (часто с аргументами).
- **Функции** `@function`, встроенные `lighten()`, `math.div()`, работа с цветом/единицами.
- **Модули:** `@use` / `@forward` вместо устаревшего `@import` (глобальное пространство имён, повторные импорты).
- **Управление:** `@if`, `@each`, `@for`, maps/lists — генерация утилит, брейкпоинтов, палитры из токенов.
- **`@extend`** — шаринг селекторов; на Middle лучше знать, что легко раздувает CSS и хуже миксина; в новых кодовых базах часто избегают.

Плюсы: DRY, единые токены на билде, удобно в больших легаси-стилях.  
Минусы: ещё один язык и шаг сборки; исходники ≠ то, что в DevTools; легко увлечься вложенностью (специфичность, «селекторный ад»).

---

**Препроцессор vs постпроцессор**

| | Препроцессор | Постпроцессор |
|--|--------------|----------------|
| Вход | другой синтаксис (SCSS, Less) | уже CSS |
| Выход | CSS | CSS (префиксы, минификация, полифилы) |
| Примеры | Sass, Less, Stylus | **PostCSS** (Autoprefixer, nesting), **Lightning CSS**, cssnano |

PostCSS — пайплайн плагинов, не «ещё один Sass». Autoprefixer по Browserslist дописывает `-webkit-` и т.п. Vite/современная сборка часто гоняет CSS через PostCSS или Lightning CSS **под капотом**, даже если в проекте нет `.scss`.

Путаница: Tailwind — не препроцессор CSS, а utility-генератор (часто через PostCSS). CSS Modules — изоляция имён на сборке, тоже не препроцессор.

---

**Нужны ли сейчас**

Нативный CSS закрыл часть кейсов Sass:

- **custom properties** (`var(--token)`) — живут **в рантайме**: темы, `dark`, смена с JS;
- **nesting**, **`@layer`**, **`:is()` / `:where()`**, **`color-mix()`**, **container queries**, **`clamp()`**.

Sass-переменная ≠ CSS-переменная: `$x` исчезает после компиляции, `--x` можно читать/менять в браузере. Для тем и динамических значений — custom properties. Для генерации на билде (палитра, миксины, циклы) — Sass ещё удобен.

**Где Sass ещё жив:** крупные/легаси кодовые базы, дизайн-системы с токенами на билде, письма/вне SPA, команды без Tailwind.  
**Где часто не нужен:** новый Vite + CSS Modules / Tailwind + CSS variables. Добавлять Sass «по привычке» — слабый ответ.

Актуально: **dart-sass**; `node-sass` (libsass) — мёртвый стек, красный флаг, если предлагают его на новый проект.

**Хороший ответ кандидата:** определение → Sass/SCSS и 3–4 фичи → pre vs post (Autoprefixer) → native CSS vs Sass vars → «в легаси да, в новом стеке не обязателен».

**Красные флаги:**
- «Препроцессор работает в браузере».
- Путает Sass и PostCSS / Tailwind / CSS Modules.
- «Sass не нужен, потому что есть CSS variables» — без разницы compile-time vs runtime.
- Не знает, что `@import` в Sass deprecated в пользу `@use`.
- Глубокая вложенность как «лучшая практика».

**Follow-up:** Когда `$variable`, когда `var(--token)`?  
→ `$` — константа сборки, нет в runtime. `--` — тема, брейкпоинт «на лету», доступ из JS (`getComputedStyle` / `style.setProperty`). Часто оба: Sass собирает палитру → пишет custom properties.

**Follow-up:** Зачем Autoprefixer, если есть Sass?  
→ Sass не решает префиксы под целевые браузеры. Это постпроцессинг (или Lightning CSS) по Browserslist.

**Упрощение:** «Что умеет Sass, чего долго не было в CSS? Браузер понимает `.scss`?»

### 7. Для чего существуют reset и нормализация стилей?

**Эталонный ответ:**

У браузеров разные **user styles** (отступы у `ul`, размеры заголовков, `button`).

- **Reset** — жёстко обнуляет многие дефолты (margin/padding → 0 и т.п.), дальше всё задаёшь сам.
- **Normalize.css** (и аналоги) — *выравнивает* поведение между браузерами, сохраняя полезные дефолты.

Сейчас часто: лёгкий reset + `box-sizing` + базовые стили под дизайн-систему (типографика, focus), либо preflight у Tailwind.

### 8. Что такое специфичность селекторов? Как считать и чем чинить «войну важностей»?

**Эталонный ответ:**

Специфичность — правило, **какой селектор победит** при конфликте (если одинаковая — побеждает тот, что ниже в каскаде).

Грубо (кортеж):
1. inline-style;
2. число `#id`;
3. число `.class` / атрибутных / псевдоклассов;
4. число тегов / псевдоэлементов.

`!important` ломает игру — использовать редко (утилиты, overrides сторонних либ).  
Современные инструменты: **каскадные слои** `@layer` — порядок слоёв важнее «раздутой» специфичности внутри договорённостей.

Практика Middle: короткие классы, избегать `#id` в CSS, не накручивать `.a .b .c .d`.

**Follow-up:** Кто победит: `.list .item` или `#item`?  
→ `#item` (id выше).

### 9. Какие значения есть у `position`? Что такое stacking context?

**Эталонный ответ:**

- `static` — по потоку, `top/left` не работают;
- `relative` — смещение от своей позиции в потоке, место сохраняется;
- `absolute` — относительно ближайшего positioned-предка (`relative`/`absolute`/`fixed`/`sticky`), вынимается из потока;
- `fixed` — относительно viewport (с оговорками про `transform`/`filter` у предков);
- `sticky` — гибрид: в потоке, пока не «прилипнет» к краю scroll-контейнера.

**Stacking context** — «слой», внутри которого работает `z-index`. Новый контекст создают, например: positioned + `z-index` не `auto`, `opacity < 1`, `transform`, `filter`, `isolation: isolate` и др. Поэтому «z-index: 9999 не помогает» — часто элемент в другом контексте.

**Follow-up:** Почему `fixed` внутри `transform` ведёт себя странно?  
→ Предк с `transform` создаёт containing block / влияет на fixed.

### 10. Способы отцентрировать элемент?

**Эталонный ответ (несколько рабочих):**

1. Flex: `display: flex; justify-content: center; align-items: center;`
2. Grid: `display: grid; place-items: center;`
3. Absolute + `inset: 0; margin: auto;` (нужны размеры или inset)
4. Absolute + `top: 50%; left: 50%; transform: translate(-50%, -50%);`
5. Text-align / margin auto — для простых inline/block кейсов

На Middle достаточно flex/grid + понимание absolute-трюка.

### 11. Что нового появилось в HTML и CSS за последние годы? (актуализировать под год собеса)

**Эталонный ответ (ориентир 2024–2026):**

**CSS:** cascade layers (`@layer`), container queries, `:has()`, nesting, `color-mix()` / относительные цвета, `text-wrap: balance`, scroll-driven animations (по поддержке), `popover`/`anchor` (по поддержке), subgrid (шире поддержка), `dvh`/`svh`/`lvh`.

**HTML:** `<dialog>`, `popover` attribute, улучшение форм/инпутов, `loading="lazy"` (уже привычно), интерес к native details/accordion-паттернам, View Transitions API (по мере поддержки).

Важно: Middle называет 3–5 реальных фич и **зачем** они, а не список ради списка.

**Упрощение:** «Что такое `:has()` или container query — одним примером?»

## Блок 3. Браузер: загрузка, perf, storage, runtime

### 12. Что происходит, когда ты открываешь сайт? (Critical Rendering Path)

**Зачем спрашивают:** топ-вопрос «про браузер»; показывает, понимает ли кандидат сеть + парсинг + отрисовку как одну цепочку, а не «магию React».

**Эталонный ответ (подробный пайплайн):**

Ниже — путь от адреса в строке до пикселей на экране. На собесесе Middle достаточно уверенно пройти шаги 1→9 и уметь углубиться в 1–2 места по follow-up.

#### 0. Старт навигации

Пользователь вводит URL / кликает ссылку / делает redirect.

Браузер:
- разбирает URL (схема `https`, host, path, query, hash);
- проверяет **внутренние кэши** (memory/disk HTTP cache, bfcache при Back/Forward — страница может восстановиться почти без сети);
- смотрит HSTS / закреплённые политики безопасности;
- решает: нужен ли новый сетевой запрос документа.

Hash (`#section`) на сервер **не** уходит; это уже клиентская навигация внутри документа.

#### 1. DNS: имя → IP

Нужен IP сервера для `example.com`.

Типичный порядок поиска:
1. кэш браузера;
2. кэш ОС / hosts;
3. резолвер (часто DNS провайдера / DoH);
4. иерархия DNS (рекурсивный резолвер → authoritative).

Результат: IP (или несколько), TTL.  
Оптимизации: `dns-prefetch` / `preconnect`, HTTP/3 с 0-RTT в удачных случаях, CDN с anycast.

**TTFB** ещё не начался — это только «куда стучаться».

#### 2. Соединение: TCP (+ TLS для HTTPS)

1. **TCP handshake** (SYN → SYN-ACK → ACK) — установка соединения.  
2. Для HTTPS — **TLS handshake**: согласование шифра, проверка сертификата, ключи сессии.  
3. На **HTTP/2** поверх одного TLS-соединения мультиплексируются потоки.  
4. На **HTTP/3** транспорт — **QUIC/UDP**: handshake часто короче, лучше при потере пакетов.

Дополнительно: keep-alive / connection reuse, connection pooling к CDN, иногда уже открытый сокет после `preconnect`.

#### 3. HTTP-запрос HTML-документа

Браузер шлёт запрос (часто `GET /`):
- method, path, headers (`Host`, `User-Agent`, `Accept`, `Accept-Encoding`, `Cookie`, `If-None-Match` / `If-Modified-Since` при кэше и т.д.);
- сервер/CDN отвечает: статус, headers (`Content-Type`, `Cache-Control`, `Content-Encoding`), тело — HTML (иногда сжатый gzip/br).

Метрика **TTFB** (Time To First Byte) — время до первого байта ответа документа. На неё влияют DNS+TCP+TLS+серверная работа (SSR, БД, edge cache hit/miss).

Браузер может начать **streaming-парсинг**, не дожидаясь всего файла.

#### 4. Парсинг HTML → DOM

Токенизатор/парсер строит **DOM-дерево**.

По ходу документа встречаются:
- `<link rel="stylesheet">` — CSS считается **render-blocking** (пока CSSOM не готов, первая отрисовка обычно ждёт критические стили);
- `<script src>` без `async`/`defer`/`type="module"` — **parser-blocking**: парсер останавливается, скрипт качается (если ещё не) и **выполняется**, затем парсинг продолжается;
- картинки, шрифты, iframe — ставятся в очередь загрузки с приоритетами (не обязаны блокировать первый paint так же, как CSS);
- `<link rel="preload">` / `modulepreload` / `preconnect` — подсказки приоритета сети.

Современные браузеры делают **preload scanner**: быстро пробегают HTML байтами и раньше стартуют загрузку CSS/JS/картинок, даже пока основной парсер занят.

Итог этапа: растущее **DOM**-дерево (+ очередь сетевых запросов).

#### 5. CSS → CSSOM

Скачанные/инлайн-стили парсятся в **CSSOM**.

- CSS блокирует **рендер** (чтобы не было FOUC — вспышки нестилизованного контента).  
- CSS **не** обязан блокировать построение DOM так же, как синхронный JS, но первая осмысленная отрисовка ждёт CSSOM.  
- `@import` в CSS ухудшает цепочку (поздние доп. запросы).  
- Некритичный CSS лучше грузить иначе (media-условия, отложенная подгрузка) — аккуратно, без ломания FOUC.

#### 6. JavaScript вмешивается в путь

Когда выполняется JS (синхронный / после `defer` / module):
- может читать/менять DOM и стили;
- может делать `document.write` (плохо для perf);
- любые forced layout (`offsetHeight` после изменения DOM) вызывают **layout thrashing**.

Поэтому «тяжёлый бандл в `<head>` без defer» убивает и парсинг, и время до интерактива.

События жизненного цикла (упрощённо):
- **`DOMContentLoaded`** — DOM построен, отложенные `defer`/modules из документа отработали; картинки могут ещё грузиться;
- **`load`** — загружены ресурсы страницы (картинки и т.п., с оговорками);
- дальше — гидратация фреймворка, soft-навигации SPA уже без полной перезагрузки документа.

#### 7. Render tree

Браузер объединяет DOM + CSSOM → **render tree** (иногда говорят layout tree / frame tree — термины движка могут отличаться).

В render tree **нет**:
- элементов с `display: none`;
- чисто служебных узлов, которые не рисуются.

`visibility: hidden` обычно **остаётся** в дереве (место занимает).  
Есть нюансы с `content-visibility`, слоями и т.д. — для Middle достаточно идеи «не всё из DOM идёт в отрисовку».

#### 8. Layout (reflow) → Paint → Composite

1. **Layout (reflow)** — расчёт геометрии: размеры, позиции (box model, flex/grid, шрифты). Дорого при частых пересчётах всего дерева.  
2. **Paint** — заполнение пикселей в слоях: текст, цвета, тени, границы.  
3. **Composite** — слои складываются (часто с GPU): scroll, `transform`, `opacity` могут идти дешевле без полного layout/paint.

Первая отрисовка даёт метрики вроде **FP/FCP**; появление основного контента — **LCP**. Потом возможны дорисовки по мере прихода шрифтов/картинок → риск **CLS**, если место не зарезервировано.

#### 9. Critical Rendering Path — что это и как укорачивать

**CRP** — критическая цепочка работы до первой полезной отрисовки:

> сеть документа → HTML → (блокирующий CSS/JS) → DOM+CSSOM → render → layout → paint

Рычаги ускорения:
- быстрее сеть: CDN, HTTP/2–3, сжатие, кэш, хороший TTFB (edge/SSR cache);
- меньше блокирующего CSS (critical CSS inline / разделение), нет лишнего `@import`;
- JS: `type="module"` / `defer`, code splitting, не блокировать парсер;
- приоритеты: `preconnect` к origin API/CDN, `preload` LCP-картинки/шрифта;
- размеры картинок, `font-display`, резерв места под медиа;
- для контентных сайтов — SSR/SSG/streaming HTML, чтобы первый байт уже был полезным markup.

#### Картинка ответа «на салфетке» (можно нарисовать на собесе)

```text
URL → DNS → TCP/TLS → HTTP(HTML)
         ↓
    parse HTML ──► DOM
         ↓
    load CSS  ──► CSSOM     load JS (может блокировать)
         ↓           ↓
         └──► render tree ──► layout ──► paint ──► composite ──► экран
```

**Хороший ответ кандидата (2–3 мин):**  
идёт по цепочке DNS → TCP/TLS → HTML → DOM/CSSOM → render → layout/paint, упоминает блокирующий CSS/JS и хотя бы одну оптимизацию CRP.

**Красные флаги:**
- «Браузер сразу рисует React Virtual DOM» без сети/HTML.
- Путает DNS и HTTP, или говорит «сначала всегда скачивается весь JS».
- Не знает, что CSS блокирует первую отрисовку, а sync JS — парсинг.

**Follow-up:** Чем reflow отличается от repaint?  
→ Reflow — пересчёт геометрии (дорого). Repaint — перерисовка без смены layout (цвет, тень). Composite — ещё дешевле при смене `transform`/`opacity` на композитном слое.

**Follow-up:** Что такое FOUC и как связан с CSS?  
→ Flash of Unstyled Content — отрисовка до готовности стилей; поэтому CSS render-blocking; лечится корректной подачей критического CSS, а не «убрать все стили из head».

**Follow-up:** Чем `DOMContentLoaded` отличается от `load`?  
→ DCL — DOM готов (и defer-скрипты обычно уже выполнены); `load` — дождались ресурсов вроде картинок.

**Упрощение:** «Перечисли по порядку 5–7 шагов от ввода URL до пикселей».

### 13. Для чего нужны и чем отличаются атрибуты `async` и `defer`?

**Эталонный ответ:**

Для классического `<script src>`:

| | Парсинг HTML | Порядок выполнения | Типичный кейс |
|---|---|---|---|
| без атрибутов | блокируется на время скачивания+выполнения | по месту в документе | редко нужно |
| `async` | не ждёт; выполняется **сразу после загрузки** (может врезаться в парсинг) | **порядок не гарантирован** | независимая аналитика |
| `defer` | не блокирует парсинг; выполняется **после парсинга DOM**, перед `DOMContentLoaded` | **сохраняет порядок** | основное приложение |

`type="module"` по умолчанию ведёт себя похоже на defer (и с defer-семантикой порядка/отложенности).

**Красные флаги:** путает async и defer местами.

### 14. Метрики Core Web Vitals? На что влияют и где посмотреть?

**Эталонный ответ:**

Ключевые (актуальный набор уточнять по году; база Middle):

- **LCP** (Largest Contentful Paint) — скорость появления основного контента.  
- **INP** (Interaction to Next Paint) — отзывчивость на ввод (заменил FID как CWV).  
- **CLS** (Cumulative Layout Shift) — визуальная стабильность (скачки вёрстки).

Влияют на UX и учитываются в сигналах ранжирования/качестве. Смотреть:
- Chrome UX Report / Search Console;
- PageSpeed Insights, Lighthouse;
- Performance/Experience в DevTools, RUM (web-vitals.js).

Связь с работой фронта: размеры картинок, шрифты, тяжёлый JS на main thread, резервирование места под медиа (CLS), SSR/streaming для LCP.

### 15. Способы оптимизации производительности веб-сайта?

**Эталонный ответ (группы рычагов):**

1. **Сеть:** сжатие, HTTP/2–3, CDN, кэш (`Cache-Control`), меньше запросов, code splitting, tree shaking.  
2. **Ресурсы:** современные форматы картинок (AVIF/WebP), `srcset`/`sizes`, lazy-load, preload критичного.  
3. **CSS/JS:** критический CSS, меньше блокирующего JS, `defer`/modules, не тащить тяжёлые либы зря.  
4. **Runtime:** меньше layout thrashing, виртуализация длинных списков, `content-visibility`, мемоизация там, где измерили.  
5. **Рендеринг:** SSR/SSG для LCP, streaming, edge cache.  
6. **Измерение:** сначала профиль, потом оптимизация.

**Follow-up:** Что оптимизируешь первым при плохом LCP?  
→ Обычно картинка/hero, серверный TTFB, блокирующие ресурсы в head.

### 16. Способы хранения данных в браузере и их отличие?

**Эталонный ответ:**

| | Объём (порядок) | Уходит на сервер | Срок | Доступ из JS |
|---|---|---|---|---|
| **cookies** | ~4KB на cookie | да (если не `HttpOnly` только серверу; обычные — с запросами по правилам) | expires/session | да, кроме HttpOnly |
| **localStorage** | ~5MB | нет | пока не очистят | да, sync API |
| **sessionStorage** | ~5MB | нет | вкладка/сессия | да |
| **IndexedDB** | много | нет | пока не очистят | async, сложные данные |
| **Cache Storage** | много | нет | управляется SW | через Cache API |

Нюансы безопасности cookies: `Secure`, `HttpOnly`, `SameSite`.  
Не хранить токены в `localStorage` без понимания XSS-риска; часто предпочтительнее HttpOnly cookie + грамотный CSRF/`SameSite`.

**Также:** memory (состояние приложения) — не переживает reload.

### 17. Как работает Garbage Collector в браузере (JS)?

**Эталонный ответ (уровень Middle):**

GC автоматически освобождает память объектов, до которых **нет достижимых ссылок** от корней (стек, глобальные объекты и т.д.).

Алгоритмы движка (V8 и др.): в основном **generational** + mark-and-sweep / mark-compact идеи: молодое поколение собирается чаще.

Утечки на фронте: забытые слушатели, замыкания на большие объекты, глобальные кэши, detached DOM, подписки без unsubscribe.

**Не ждать** от Middle деталей mark-sweep vs reference counting — важнее «достижимость» и типичные утечки.

### 18. Расскажи про Web Workers и Service Workers

**Эталонный ответ:**

**Web Worker** — JS в **отдельном потоке**, без доступа к DOM. Общение через `postMessage`. Для тяжёлых вычислений (парсинг, крипт, обработка данных), чтобы не блокировать UI.

**Service Worker** — прокси между страницей и сетью: работает в фоне, может кэшировать ответы, отдавать offline, пуши (с разрешениями), background sync (по поддержке). Жизненный цикл: register → install → activate. HTTPS почти всегда обязателен.

Отличие: Worker ≠ Service Worker; SW не для «посчитать в фоне на странице», а для сети/кэша/PWA-сценариев.

---

### 19. Что такое Shadow DOM?

**Эталонный ответ:**

**Shadow DOM** — инкапсулированное DOM-дерево внутри элемента (часто Web Components). Стили и разметка «внутри» не протекают наружу так же легко, как у обычного DOM (с оговорками про CSS parts/`::part`, custom properties).

Зачем: изоляция виджетов, дизайн-системные компоненты на нативе, меньше конфликтов CSS.

Связь с React: у React свой композиционный модель; Shadow DOM чаще в Web Components / design system на чистом custom elements.

## Блок 4. Сеть и API

### 20. Что такое протокол HTTP? Какие есть версии и их отличия?

**Эталонный ответ:**

HTTP — протокол запрос/ответ прикладного уровня для передачи гипермедиа (и API JSON и т.д.).

- **HTTP/1.1** — текстовый, keep-alive, но head-of-line blocking на уровне соединений; много параллельных TCP.  
- **HTTP/2** — бинарный, мультиплексирование потоков в одном соединении, HPACK-сжатие заголовков, server push (редко важен сейчас).  
- **HTTP/3** — поверх **QUIC/UDP**: быстрее рукопожатие, лучше при потере пакетов, меньше head-of-line на транспорте.

Фронту важно: много мелких файлов на h1 больно; на h2/h3 лучше; всё равно нужен бандлинг/приоритеты по делу.

---

### 21. Отличие HTTP от HTTPS?

**Эталонный ответ:**

HTTPS = HTTP поверх **TLS**: шифрование, целостность, аутентификация сервера (сертификат).

Без HTTPS: cookies/`Service Worker`/многие API ограничены или небезопасны; риск MITM. В проде HTTPS обязателен.

---

### 22. Из чего состоит HTTP-запрос? Методы HTTP? Частые статус-коды?

**Эталонный ответ:**

Запрос: **метод**, **URL/path**, **версия**, **заголовки**, опционально **тело**.  
Ответ: **статус**, заголовки, тело.

Методы: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS` (и др.).

Статусы (группы):
- `2xx` — успех (`200`, `201`, `204`);
- `3xx` — редирект (`301`, `302`, `304`);
- `4xx` — ошибка клиента (`400`, `401`, `403`, `404`, `409`, `422`);
- `5xx` — ошибка сервера (`500`, `502`, `503`).

**Follow-up:** Чем `401` отличается от `403`?  
→ `401` — не аутентифицирован (нужен логин). `403` — аутентифицирован, но нет прав.

---

### 23. Что такое идемпотентный запрос?

**Эталонный ответ:**

**Идемпотентный** — повторный такой же запрос даёт тот же *эффект на ресурс* (с точки зрения состояния сервера), даже если ответов несколько.

Обычно: `GET`, `PUT`, `DELETE`, `HEAD`, `OPTIONS` — идемпотентны по контракту.  
`POST` — обычно **не** идемпотентен (каждое создание — новый эффект).  
`PATCH` — зависит от семантики.

Зачем фронту: ретраи безопаснее на идемпотентных; для `POST` нужны ключи идемпотентности/защита от double-submit.

---

### 24. Принципы построения RESTful API?

**Эталонный ответ:**

Идеи REST на практике в API:
- ресурсы как URL (`/users/42`);
- глаголы через HTTP-методы;
- статусы по смыслу;
- JSON (чаще всего) без лишнего RPC-стиля в path (`/getUser`);
- статистичность сервера (токен/сессия передаётся явно);
- единообразие, пагинация, фильтрация через query.

Строгий академический REST с HATEOAS на собесах редко требуют — важнее здравый resource-oriented дизайн.

---

### 25. В чём отличие REST API и GraphQL?

**Эталонный ответ:**

| | REST | GraphQL |
|---|---|---|
| Контракт | много endpoints | обычно один `/graphql` |
| Данные | фиксированная форма ответа | клиент запрашивает поля |
| Over/under-fetching | чаще проблема | гибче |
| Кэш HTTP | естественно для GET | сложнее (часто POST) |
| Сложность | проще операционно | схема, N+1, пермишены на поля |

Выбор: публичные простые CRUD/кэшable API → REST; сложные клиентские формы данных (много экранов/мобилки) → GraphQL; иногда оба.

### 26. Что такое CORS и как браузер применяет preflight?

**Эталонный ответ:**

**Same-Origin Policy** ограничивает чтение ответов другим origin из JS.  
**CORS** — механизм *ослабленных* разрешений через заголовки сервера (`Access-Control-Allow-Origin` и др.).

**Simple request** — некоторые GET/POST с «простыми» заголовками.  
**Preflight** — заранее `OPTIONS`: браузер спрашивает, можно ли делать «непростой» запрос (кастомные заголовки вроде `Authorization`, `Content-Type: application/json` в ряде случаев, странные методы). Сервер отвечает allow-методами/заголовками.

Важно: CORS — **браузерная** защита. Postman/curl её не «ломают» как дыру сервера — сервер всё равно должен проверять auth.

**Красные флаги:** «CORS настраивается только в React» / «выключи CORS в браузере» как решение.

---

### 27. WebSockets vs SSE vs long-polling? Типичные кейсы на фронте

**Эталонный ответ:**

- **Long-polling** — клиент держит HTTP-запрос, сервер отвечает когда есть событие, клиент сразу открывает новый. Устаревающий fallback.  
- **SSE (Server-Sent Events)** — односторонний поток **сервер → клиент** по HTTP; просто для нотификаций/ленты событий.  
- **WebSocket** — полнодуплексное соединение, низкая задержка в обе стороны: чаты, коллаб, онлайн-курсоры, игры, тикеры.

На фронте: WS через нативный API или Socket.IO (с fallbacks); переподключение, heartbeat, auth на connect.

---

## Блок 5. Виды рендеринга и гидратация

### 28. Виды рендеринга страницы (SSR, SSG, CSR, ISR)?

**Эталонный ответ:**

- **CSR** — HTML-оболочка, UI строится в браузере JS (SPA). Гибко, но хуже TTFB/LCP/SEO без доп. мер.  
- **SSR** — HTML на сервере на каждый запрос → быстрее первый контент, лучше SEO.  
- **SSG** — HTML на билде, раздаётся статикой/CDN — максимальная скорость для относительно статичного контента.  
- **ISR** (и аналоги) — статическая генерация с **фоновым обновлением** страниц по истечении revalidate / on-demand.

На практике (Next/Nuxt и др.) часто микс по роутам.

**Follow-up:** Что выбрать для лендинга, кабинета пользователя и новостной статьи?  
→ Лендинг — SSG; кабинет — CSR/SSR с auth; статьи — SSG/ISR.

---

### 29. Что такое гидратация (и регидратация)?

**Эталонный ответ:**

**Hydration** — после SSR/SSG браузер загружает JS и «оживляет» HTML: навешивает обработчики, восстанавливает состояние фреймворка, сверяет дерево.

Проблемы: большой JS → долгая гидратация; **hydration mismatch** — серверный HTML ≠ клиентский рендер (случайные id, `Date`, `window` в рендере).

**Регидратация** иногда называют повторное/частичное оживление (в т.ч. после навигации или в островной архитектуре). На собесе достаточно чётко объяснить hydration + mismatch.

Связанные идеи: streaming SSR, selective/partial hydration, islands architecture.

## Блок 6. Дизайн-системы

*Часто спрашивают на Middle в продуктовых командах: «работали ли с DS?».*

### 30. Что такое дизайн-система? Из чего состоит?

**Зачем спрашивают:** проверка опыта масштабирования UI, а не только «умею сверстать макет».

**Эталонный ответ:**

**Дизайн-система** — единый язык продукта для дизайна и разработки: правила + токены + компоненты + документация + процессы.

Обычно включает:
1. **Design tokens** — цвет, типографика, spacing, радиусы, тени, z-index, motion (часто JSON → CSS variables / платформы).  
2. **UI-kit / компоненты** — Button, Input, Modal… с API (props), состояниями (hover/disabled/loading), a11y.  
3. **Паттерны** — формы, пустые состояния, навигация, даты.  
4. **Документация** — Storybook / Confluence / Zeroheight: когда какой компонент, do/don’t.  
5. **Гайдлайны** — голос бренда, контент, иллюстрации.  
6. **Процесс** — contribution, versioning, deprecation, RFC на breaking changes.

Зачем: скорость фич, консистентность, меньше дублей, проще a11y и темизация (light/dark), онбординг.

**Хороший ответ:** токены + компоненты + дока + governance, не только «библиотека кнопок».

**Follow-up:** Чем токен отличается от «просто CSS-переменной в проекте»?  
→ Токен — контракт между дизайном и кодом (имя/уровень: core → semantic → component), может генериться в несколько платформ; не любой `--blue-500` уже система.

---

### 31. Как организовать работу с дизайн-системой во фронтенд-команде?

**Эталонный ответ:**

- Отдельный пакет/монорепо (`@company/ui`), семантическое версионирование.  
- Storybook + визуальные регрессии (Chromatic/Playwright screenshots).  
- Дизайнеры в Figma с теми же токенами; синхронизация (Tokens Studio / style dictionary).  
- Правила: сначала искать в DS → расширять DS → только потом one-off в продукте.  
- Breaking changes — major, миграционные гайды.  
- Theming через semantic tokens (`--color-bg-primary`), не хардкод hex в продуктах.

**Красные флаги:** «дизайн-система = просто Storybook без процесса»; копипаст кнопок по репозиториям без версии.

**Упрощение:** «Зачем компании общая библиотека кнопок и инпутов?»

---

### 32. Какие проблемы бывают у дизайн-систем и как их избегают?

**Эталонный ответ:**

- DS отстаёт от продуктов → обходные костыли.  
- Слишком жёсткая — продукты блокируются.  
- Слишком гибкая — снова хаос.  
- Нет ownership / «чужой код».  
- Проп-ад и 50 вариантов Button.

Митигации: чёткий ownership, SLA на запросы, RFC, метрики adoption, composition API вместо бесконечных boolean-пропсов, регулярный audit неиспользуемого.

## Блок 7. Git, тесты, CI/CD

### 33. В чём разница между `git fetch` и `git pull`?

**Эталонный ответ:**

- `git fetch` — скачивает изменения с remote **без** слияния в текущую ветку (обновляет `origin/*`).  
- `git pull` — по сути `fetch` + интеграция в текущую ветку (`merge` или `rebase` — зависит от настроек).

Практика: часто `fetch` + посмотреть diff/log, потом осознанно merge/rebase. `pull` на «автомате» может создать неожиданный merge-commit.

---

### 34. Какая разница между `git rebase` и `git merge`?

**Эталонный ответ:**

- **merge** — соединяет истории merge-коммитом, сохраняет реальную хронологию веток.  
- **rebase** — переигрывает коммиты поверх другой базы → линейная история.

Правила безопасности: **не rebase коммиты, которые уже запушены и ими пользуются другие** (без договорённости). Для локальной feature-ветки rebase на `main` — обычная практика; для shared — осторожно.

**Follow-up:** Что такое conflict и когда появляется?  
→ Одни и те же строки/файлы изменены по-разному в двух линиях истории.

---

### 35. Какие виды тестов ты знаешь (unit, integration, e2e)? Что ещё бывает на фронте?

**Эталонный ответ:**

- **Unit** — маленькая единица (функция, хук, чистый компонент) в изоляции; быстро, много.  
- **Integration** — несколько модулей вместе (форма + валидация + API-mock).  
- **E2E** — сценарий в реальном браузере (Playwright/Cypress): логин → покупка.

Пирамида: больше unit/integration, меньше e2e (дороже и хрупче).

На фронте ещё: **visual regression**, a11y-checks, contract tests (Pact) к API, snapshot (осторожно).

**Follow-up:** Что мокать в integration-тесте кнопки «Сохранить»?  
→ Обычно сеть (MSW), не реализацию кнопки целиком.

---

### 36. Что такое CI/CD? Как выглядит типичный пайплайн фронтенда?

**Зачем спрашивают:** Middle в команде почти наверняка касается PR-checks и деплоя.

**Эталонный ответ:**

- **CI (Continuous Integration)** — на каждый push/PR автоматически: install → lint → typecheck → unit/integration → build (иногда e2e). Цель — рано ловить поломки, держать `main` зелёным.  
- **CD (Continuous Delivery/Deployment)** — автоматическая доставка артефакта: preview-окружения на PR, деплой на staging/production (вручную «кнопкой» или автоматически).

Типичный фронтовый пайплайн:
1. `npm ci` / `pnpm i --frozen-lockfile`
2. lint + `tsc --noEmit`
3. unit tests
4. build (`vite build` / `next build`)
5. (опционально) e2e / lighthouse CI / visual
6. publish static/docker artifact → CDN / hosting (Vercel/Netlify/S3+CloudFront / k8s)
7. миграции не фронтовые, но feature flags / env по окружениям

Понятия: **pipeline**, **job/stage**, **artifact**, **cache зависимостей**, **preview deploy**, **rollback**, **secrets** в CI (не в репозитории).

**Хороший ответ кандидата:** объясняет зачем checks на PR + чем staging отличается от prod + где хранятся секреты.

**Красные флаги:**
- «CI — это когда Jenkins просто билдит иногда».
- Коммитит `.env` с ключами.

**Follow-up:** Чем Continuous Delivery отличается от Continuous Deployment?  
→ Delivery — всегда *можно* выкатить (артефакт готов), решение о prod может быть ручным. Deployment — каждый успешный `main` едет в prod автоматически.

**Упрощение:** «Что должно произойти само, когда ты открываешь Pull Request?»

---

### 37. Окружения, feature flags и откат релиза — что важно фронтенду?

**Эталонный ответ:**

- Окружения: `dev` / `staging` / `prod` с разными API URL и ключами.  
- **Feature flags** — включить фичу без редеплоя / постепенно / для % пользователей; быстрее rollback «выключил флаг».  
- Откат: предыдущий артефакт на CDN/hosting, или revert + pipeline.  
- Версионирование статики: хэши в именах файлов + корректный cache (`immutable` для hashed assets, короткий cache для `index.html`).

## ★ Live-coding / DevTools (опционально)

Идеи на 15–20 минут:
