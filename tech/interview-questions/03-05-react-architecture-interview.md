## Что нужно выучить менти (план подготовки)

### React (12 ключевых тем)
1. **Декларативный UI, Virtual DOM, Reconciliation и React Fiber** — зачем нужен VDOM, две фазы работы React (*Render* vs *Commit*), эвристики сравнения дерева $O(n)$ и роль `React.createElement` / JSX Runtime.
2. **Устройство `useState` и батчинг** — почему мутация не вызывает рендер (`Object.is`), функциональное обновление `setState(prev => ...)`, ленивая инициализация `useState(() => ...)` и Automatic Batching в React 18.
3. **Жизненный цикл эффекта: `useEffect` vs `useLayoutEffect`** — когда выполняются относительно отрисовки браузера (paint), зачем нужен массив зависимостей, когда вызывается cleanup и почему в Strict Mode (dev) эффект срабатывает дважды.
4. **Правила хуков (Rules of Hooks) и внутреннее устройство** — как React хранит хуки в связном списке (`memoizedState`) на Fiber-ноде и почему условие `if` перед хуком ломает приложение.
5. **`useRef` и `forwardRef` / `useImperativeHandle`** — два сценария `useRef` (DOM-элемент и мутабельный контейнер без ре-рендера), почему нельзя читать/писать `ref.current` в рендере, отличие от `useState`.
6. **Причины ре-рендера и роль `key` в списках** — 3 истинные причины ре-рендера (state, context, рендер родителя), миф про «изменение пропсов», почему `key={index}` ломает стейт и инпуты при сортировке/удалении, сброс компонента через `key={userId}`.
7. **Мемоизация и оптимизация рендеров** — как работают `React.memo`, `useMemo`, `useCallback`, когда они реально нужны, а когда бесполезны, и архитектурная альтернатива без мемоизации (*State Colocation* и передача `children` / слотов).
8. **React Context и проблема лишних ре-рендеров** — как устроен `Provider`, почему обновление поля в контексте будит всех подписчиков и 3 способа это починить (разделение контекстов, мемоизация `value`, `useSyncExternalStore` / селекторы).
9. **Работа с формами: Controlled vs Uncontrolled** — плюсы, минусы, таблица выбора, устройство современных библиотек форм (`React Hook Form` + `Zod`) без ре-рендера всей страницы на каждое нажатие клавиши.
10. **Порталы (`createPortal`), Error Boundaries и `Suspense` / `React.lazy`** — почему в портале всплывают синтетические события React, какие ошибки (не) ловит Error Boundary, как работает code splitting и `Suspense`.
11. **Переиспользование логики и композиция в React** — эволюция *HOC → Render Props → Custom Hooks*, паттерн *Compound Components* (`<Tabs><Tabs.Trigger /></Tabs>`) и *Slots / Children*.
12. **Отладка, тестирование и продакшен-практики** — пирамида тестирования на фронтенде (`React Testing Library` vs `Playwright`), поиск причин лишних ре-рендеров в React DevTools Profiler, обработка гонок и Optimistic UI.

### Принципы, паттерны и архитектура (10 ключевых тем)
13. **SOLID во фронтенде (SRP, OCP, LSP, ISP, DIP)** — без ООП-воды: как каждый из 5 принципов выглядит в реальных React-компонентах, хуках и сетевом слое.
14. **DRY, KISS и YAGNI: границы применимости** — чем опасен преждевременный DRY («AHA — Avoid Hasty Abstractions») и раздутый компонент с 25 булевыми пропсами.
15. **Паттерны GoF на фронтенде: Observer vs Pub/Sub и Singleton** — в чём ключевая разница между Observer и Event Bus (Pub/Sub), где они живут в React/Zustand/браузере, плюсы и опасности Singleton.
16. **Структурные паттерны: Adapter (Mapper), Facade, Proxy, Decorator** — как быстро отличить их по цели на собеседовании и реальные примеры (DTO → Domain Mapper, кастомный хук-фасад, MobX `Proxy`, HOC/interceptor).
17. **Server State vs Client State** — почему серверный кэш (`TanStack Query` / `RTK Query`) нельзя смешивать с UI-стейтом, что дают `staleTime` vs `gcTime`, дедупликация запросов, инвалидация и `AbortController`.
18. **Архитектура клиентского стейта: Flux (Redux Toolkit / Zustand) vs Atomic (Jotai) vs Proxy (MobX)** — сравнение моделей обновления, селекторов и критерии выбора под проект.
19. **Модульная архитектура, Colocation и Public API (`index.ts`)** — почему группировка по типам файлов (`components/`, `hooks/`, `reducers/`) плохо масштабируется, правило колокации и защита границ модуля через Public API (и ловушки barrel-файлов для бандлера).
20. **Clean Architecture и Dependency Rule во фронтенде** — 3 главных слоя (*Domain / Application / UI & Infrastructure*), куда направлены стрелки зависимостей и как отвязать бизнес-логику от React и `axios`.
21. **Feature-Sliced Design (FSD)** — 7 слоёв сверху вниз (`app → pages → widgets → features → entities → shared`), сегменты (`ui`, `model`, `api`, `lib`), жёсткое правило импортов и 3 способа разрешить связь между фичами без кросс-импорта.
22. **DDD во фронтенде и Микрофронтенды (MFE)** — *Ubiquitous Language, Entity vs Value Object, Bounded Context*; когда микрофронтенды (`Module Federation` / `iframe`) оправданы, а когда превращаются в распределённый монолит.

# Часть 1. React — подробные вопросы и ответы

## Блок 1. Устройство React, рендер и хуки состояния

### 1. Что такое Virtual DOM, Reconciliation и React Fiber? Как React обновляет экран?

**Зачем спрашивают:** Проверить базовую ментальную модель React: понимает ли кандидат разницу между вызовом функции компонента (Render phase) и реальным изменением DOM в браузере (Commit phase).

**Эталонный подробный ответ:**
- **Декларативный подход:** Вместо ручных императивных команд (`el.appendChild`, `el.textContent = ...`) мы описываем функции $UI = f(state)$. JSX при сборке транспилируется в вызовы `_jsx(type, props)` (или `React.createElement`), которые возвращают **легковесные JS-объекты** (React Elements) — описание того, каким должен быть интерфейс:
  ```js
  // Результат <button className="primary">OK</button>
  { type: 'button', key: null, props: { className: 'primary', children: 'OK' } }
  ```
- **Virtual DOM и Reconciliation (согласование):**
  На каждом обновлении состояния React вызывает функцию компонента, получает новое дерево React-элементов и сравнивает его с предыдущим деревом (алгоритм **Reconciliation**).
  Классическое сравнение двух произвольных деревьев имеет сложность $O(n^3)$, поэтому React вводит **две эвристики**, снижающие сложность до **$O(n)$**:
  1. **Разные типы элементов (`type`) дают разные деревья:** если `<div>` сменился на `<section>` или `<AdminPanel>` на `<UserPanel>`, React **не пытается** сравнивать их внутри — он полностью размонтирует старое поддерево (вызывая cleanup всех эффектов и удаляя DOM-узлы) и монтирует новое с нуля.
  2. **Ключи (`key`) для списков:** подсказывают React, какой именно элемент переместился, добавился или удалился среди соседей одного уровня.
- **Две фазы обновления:**
  | Фаза | Что происходит | Можно ли прервать? |
  |---|---|---|
  | **1. Render Phase** | React вызывает функции компонентов, считает хуки и строит новое Fiber-дерево (diffing). Никаких изменений реального DOM ещё нет. Должна быть **чистой** (без сайд-эффектов). | **Да** (в Concurrent React 18 рендер можно приостановить, отложить или отменить). |
  | **2. Commit Phase** | React за один синхронный проход применяет вычисленные минимальные изменения к реальному DOM, обновляет `ref.current`, синхронно вызывает `useLayoutEffect`, затем отдаёт управление браузеру для отрисовки (paint), после чего асинхронно запускает `useEffect`. | **Нет** (выполняется атомарно, чтобы пользователь не увидел полусобранный UI). |
- **Что такое React Fiber:**
  Это внутренняя архитектура движка React (с версии 16+). Раньше рекурсивный обход дерева (Stack Reconciler) шёл синхронно в одном стеке вызовов и блокировал главный поток, пока не обойдёт всё дерево.
  **Fiber** заменил рекурсию на **связный список узлов** (у каждой Fiber-ноды есть ссылки `child`, `sibling`, `return`), а также хранит два дерева: `current` (то, что сейчас на экране) и `workInProgress` (то, что строится в памяти). Это позволило разбивать рендер на мелкие единицы работы и ввело приоритеты обновлений (`startTransition`, `useDeferredValue` в React 18).

**Красные флаги:**
- «Virtual DOM быстрее прямого обращения к DOM» (нет, нативные операции DOM сами по себе быстрее; VDOM позволяет писать декларативный код без ручной синхронизации и не пересоздавать весь DOM целиком).
- Думает, что ре-рендер компонента = полное пересоздание его DOM-узлов в браузере.

**Follow-up:**
- *Что произойдёт со стейтом дочернего `<Counter />`, если в родителе по условию `isDark ? <div><Counter /></div> : <section><Counter /></section>` изменился `isDark`?*
  *(Ответ: корневой тег сменился с `div` на `section` → старое поддерево размонтируется, стейт `<Counter />` сбросится).*

### 2. Как работает `useState`? Иммутабельность, функциональное обновление, ленивая инициализация и Batching

**Зачем спрашивают:** База повседневной работы. Здесь сразу всплывают баги с мутацией массивов/объектов, потерей обновлений при нескольких `setState` подряд и тяжёлыми вычислениями в `useState(expensive())`.

**Эталонный подробный ответ:**
1. **Почему нельзя мутировать state напрямую (`Object.is`):**
   Когда вы вызываете `setState(nextValue)`, React сравнивает старое и новое значение через **`Object.is(prevState, nextState)`**.
   Если сделать `items.push(newItem); setItems(items)`, ссылка на массив останется прежней (`Object.is(items, items) === true`). React решит, что состояние не изменилось, и **пропустит ре-рендер** (bailout). Поэтому любые объекты и массивы обновляются иммутабельно (созданием новой ссылки: `[...items, newItem]`, `items.filter(...)`, `items.map(...)`).
2. **Замыкание снимка рендера и функциональное обновление (`setState(prev => ...)`):**
   Каждый рендер видит свой «снимок» (snapshot) переменной `count`. Вызов `setCount(count + 1)` **не меняет** переменную `count` в текущей функции — он лишь ставит обновление в очередь на следующий рендер:
   ```tsx
   // ❌ Баг: три вызова подряд увеличат count только на +1, т.к. во всех трёх count === 0
   const handleTriple = () => {
     setCount(count + 1); // 0 + 1
     setCount(count + 1); // 0 + 1
     setCount(count + 1); // 0 + 1
   };

   // ✅ Правильно: функциональный апдейтер получает самое свежее значение из очереди
   const handleTripleFixed = () => {
     setCount((prev) => prev + 1); // 0 -> 1
     setCount((prev) => prev + 1); // 1 -> 2
     setCount((prev) => prev + 1); // 2 -> 3
   };
   ```
3. **Ленивая инициализация (`Lazy Initial State`):**
   ```tsx
   // ❌ ПЛОХО: JSON.parse и чтение localStorage выполняются НА КАЖДОМ рендере компонента,
   // хотя результат нужен только при монтировании!
   const [filters, setFilters] = useState(
     JSON.parse(localStorage.getItem("filters") ?? "{}")
   );

   // ✅ ХОРОШО: передаём функцию-инициализатор. React вызовет её ровно ОДИН раз на маунте.
   const [filters, setFilters] = useState(() =>
     JSON.parse(localStorage.getItem("filters") ?? "{}")
   );
   ```
4. **Automatic Batching (пакетная обработка в React 18):**
   Если в одном обработчике вызвать `setLoading(false)`, `setData(res)`, `setError(null)`, React **не делает 3 отдельных ре-рендера** — он объединяет (батчит) их в **один** ре-рендер в конце микротаски/обработчика.
   - До React 18 батчинг работал только внутри React-событий (`onClick`), а внутри `Promise.then`, `setTimeout` или нативного `addEventListener` каждый `setState` вызывал отдельный синхронный рендер.
   - С **React 18 (`createRoot`)** работает **Automatic Batching везде** — и в промисах, и в таймерах, и в нативных обработчиках. (Если в редком случае нужно принудительно применить DOM синхронно до следующей строчки кода — используется `flushSync` из `react-dom`).

**Красные флаги:**
- Не знает разницу между `useState(fn())` и `useState(() => fn())`.
- Считает, что `setState` меняет переменную стейта сразу на следующей строчке кода.

### 3. `useEffect` vs `useLayoutEffect`: порядок выполнения, зависимости, cleanup и двойной вызов в Strict Mode

**Зачем спрашивают:** Неправильное использование `useEffect` — главный источник багов, утечек памяти, гонок запросов и бесконечных циклов во фронтенде.

**Эталонный подробный ответ:**
- **Хронология рендера и разница `useEffect` vs `useLayoutEffect`:**
  ```
  1. Render Phase: React вызывает функцию компонента -> строит виртуальное дерево
  2. Commit Phase: React обновляет реальные DOM-узлы и проставляет ref.current
  3. [СИНХРОННО ДО ОТРИСОВКИ] Выполняется cleanup старого useLayoutEffect, затем новый useLayoutEffect
  4. Browser Paint: браузер реально рисует пиксели на экране
  5. [АСИНХРОННО ПОСЛЕ ОТРИСОВКИ] Выполняется cleanup старого useEffect, затем новый useEffect
  ```
  | Критерий | `useEffect` (99% случаев) | `useLayoutEffect` (1% случаев) |
  |---|---|---|
  | **Когда запускается** | Асинхронно **после** того, как браузер отрисовал кадр (paint). | Синхронно **после мутации DOM, но ДО** отрисовки кадра браузером. |
  | **Блокирует ли отрисовку** | Нет, пользователь сразу видит интерфейс. | **Да**, тяжёлый код внутри задержит появление кадра. |
  | **Когда использовать** | Запросы к API, подписки (`addEventListener`, WebSocket), аналитика, таймеры. | Измерение размеров/координат DOM (`getBoundingClientRect`, `scrollHeight`) и немедленная правка стилей/позиции тултипа или скролла, чтобы **не было визуального мигания (flicker)** на 1 кадр. |

- **Массив зависимостей (`deps`) и как работает cleanup:**
  React сравнивает каждый элемент массива `deps` с предыдущим рендером через `Object.is`:
  - `useEffect(fn)` *(без массива)* — запускается после **каждого** рендера.
  - `useEffect(fn, [])` *(пустой массив)* — запускается при монтировании, а `cleanup` — при размонтировании.
  - `useEffect(fn, [a, b])` — запускается при маунте и при каждом рендере, где изменились `a` или `b`. **Важно:** перед запуском нового эффекта React сначала вызывает **функцию `cleanup` от предыдущего рендера** (со старыми значениями из прошлого замыкания!), и только потом запускает новый эффект.
- **Почему в React 18 с пустым `[]` запрос уходит дважды в dev-режиме?**
  В `<React.StrictMode>` только в режиме разработки (`development`) React намеренно прогоняет цикл **`mount → cleanup (unmount) → mount`** для каждого компонента.
  **Зачем:** проверить, что ваш компонент устойчив к повторному монтированию и что вы не забыли написать корректный `cleanup` (отписку от слушателя, `clearInterval`, `controller.abort()`). Если во время первого маунта запустился `fetch`, а в `cleanup` стоит `controller.abort()`, первый запрос аккуратно отменится, и данные придут только от второго. На продакшен-сборке (`production`) эффект вызывается ровно один раз.

**Красные флаги:**
- «Cleanup вызывается только тогда, когда компонент удаляется со страницы (unmount)» — на самом деле он вызывается перед **каждым** перезапуском эффекта при смене зависимостей.
- Предлагает «починить» двойной запрос в dev отключением `StrictMode` или костылём через глобальный флаг вместо нормального `AbortController` / TanStack Query.
- Объявляет функцию `useEffect(async () => { ... })` напрямую (асинхронная функция возвращает `Promise`, а `useEffect` ждёт либо `undefined`, либо функцию очистки `() => void`).

### 4. Правила хуков (Rules of Hooks): как React хранит хуки под капотом?

**Зачем спрашивают:** Проверить понимание внутренней механики Fiber.

**Эталонный подробный ответ:**
- **Два правила хуков:**
  1. Вызывать хуки **только на верхнем уровне** функции компонента или кастомного хука — никогда внутри `if`, циклов `for`, `switch` или после раннего `return`.
  2. Вызывать хуки только из функциональных компонентов React или из кастомных хуков.
- **Почему так (как это устроено внутри Fiber):**
  У `useState` нет имени или строкового ключа — вы просто пишете `const [a, setA] = useState(1); const [b, setB] = useState(2)`.
  Внутри Fiber-ноды каждого экземпляра компонента есть поле `memoizedState`, которое указывает на **односвязный список ячеек хуков**:
  ```
  Fiber.memoizedState ---> [Hook 0: state=1] --next--> [Hook 1: state=2] --next--> [Hook 2: effect]
  ```
  Во время каждого рендера React просто двигает внутренний курсор по этому списку по порядку вызовов: 1-й вызов хука читает ячейку №0, 2-й вызов — ячейку №1 и т.д.
  Если на втором рендере первый хук оказался внутри `if (false)` и не вызвался, то второй хук прочитает ячейку №0 (чужой стейт!), весь список сдвинется, и React выбросит ошибку `Rendered fewer/more hooks than during the previous render`.

### 5. `useRef`: чем отличается от `useState`, зачем нужен и почему нельзя читать/писать `ref.current` в рендере?

**Зачем спрашивают:** Проверить умение работать с мутабельными данными без лишних ре-рендеров и с императивным DOM API.

**Эталонный подробный ответ:**
`useRef(initialValue)` возвращает один и тот же мутабельный объект `{ current: initialValue }`, ссылка на который сохраняется на протяжении всей жизни компонента.

| Критерий | `useState` | `useRef` |
|---|---|---|
| **Вызывает ли изменение ре-рендер?** | **Да**, `setState` планирует ре-рендер. | **Нет**, запись `ref.current = x` происходит синхронно и тихо, React о ней не знает. |
| **Когда обновляется значение?** | На следующем рендере. | Мгновенно в той же строчке кода. |
| **Где читать/писать?** | Читать в рендере, менять в обработчиках/эффектах. | Читать и менять в **эффектах (`useEffect`) и обработчиках событий** (не в рендере!). |

**Два главных применения `useRef`:**
1. **Доступ к реальному DOM-элементу:** фокус (`inputRef.current?.focus()`), скролл (`scrollIntoView`), измерение размеров, управление `<video>` или `<canvas>`.
2. **Хранение «служебных» данных между рендерами, от которых не зависит вёрстка:** ID таймера (`intervalId`), экземпляр WebSocket, флаг или предыдущее значение пропса (`usePrevious`), актуальный колбэк в паттерне *Latest Ref* для борьбы со Stale Closure.

**Почему нельзя менять `ref.current` прямо во время рендера (кроме ленивой инициализации):**
Фаза рендера должна быть чистой функцией. В React 18 (Strict Mode и Concurrent Rendering) функция компонента может вызываться несколько раз до коммита или рендер может быть отменён, поэтому мутация `ref.current` в теле рендера приводит к непредсказуемому поведению.

## Блок 2. Ре-рендеры, ключи, мемоизация и Context

### 6. Когда именно компонент ре-рендерится? Зачем нужен `key` в списках и как ещё используют `key`?

**Зачем спрашивают:** Развенчать главный миф «компонент рендерится, когда меняются его пропсы» и проверить понимание Reconciliation на списках.

**Эталонный подробный ответ:**
- **3 единственные причины ре-рендера компонента в React:**
  1. **Изменился его собственный `state`** (`useState` / `useReducer`).
  2. **Ре-рендерился его родительский компонент** (по умолчанию, если родитель рендерится, React рекурсивно рендерит **всех** его детей — даже если у ребёнка вообще нет пропсов или его пропсы не изменились, пока ребёнок не обёрнут в `React.memo`).
  3. **Изменилось значение `Context`**, на который этот компонент подписан через `useContext`.
  *(А что насчёт пропсов? Пропсы сами по себе измениться не могут — чтобы пропсы изменились, сначала должен отрендериться родитель!)*

- **Зачем нужен `key` в списках и что будет при `key={index}`:**
  При перерисовке списка React сопоставляет старые и новые Fiber-узлы по паре `(type, key)`.
  Если использовать **индекс массива `key={index}`**, а затем **вставить элемент в начало, удалить из середины или отсортировать список**, то у всех сдвинувшихся элементов останутся старые ключи `0, 1, 2...`, но под ними окажутся другие данные:
  1. **Поедет внутренний стейт и неконтролируемые поля:** если в первом ряду `<li key={0}>` был отмечен чекбокс или введён текст в `<input>`, после удаления первого элемента этот текст и фокус останутся на позиции `key={0}` — то есть перепрыгнут на второй элемент!
  2. **Лишние мутации DOM:** вместо вставки одного нового узла в начало React будет перезаписывать `textContent` и пропсы у каждого элемента списка.
  *Когда `key={index}` допустим:* только если список полностью статичен (не сортируется, не фильтруется, не меняется состав) и элементы не имеют внутреннего состояния/фокуса.

- **Второй мощный приём с `key` — принудительный сброс состояния компонента:**
  Если передать компоненту `<UserProfileForm key={userId} userId={userId} />`, то при смене `userId` React увидит новый `key`, мгновенно размонтирует старый экземпляр формы со всеми его локальными стейтами и смонтирует чистый новый — без единого костыльного `useEffect` для сброса полей!

### 7. `React.memo`, `useMemo`, `useCallback` и как оптимизировать рендеры без них (State Colocation и `children`)

**Зачем спрашивают:** Отличить разработчика, который слепо оборачивает каждую функцию в `useCallback`, от того, кто понимает цену мемоизации и архитектурные способы изоляции рендеров.

**Эталонный подробный ответ:**

| Инструмент | Что кэширует | Как работает |
|---|---|---|
| **`React.memo(Component)`** | **Результат рендера компонента** (пропускает ре-рендер при рендере родителя). | Перед рендером поверхностно сравнивает все пропсы старого и нового вызова через `Object.is`. Если все пропсы равны — пропускает рендер всего поддерева. |
| **`useMemo(() => compute(), [deps])`** | **Значение** (результат вызова функции). | Вызывает функцию только при изменении `deps`, на остальных рендерах возвращает сохранённую ссылку/результат. |
| **`useCallback(fn, [deps])`** | **Саму ссылку на функцию** (`fn`). | Эквивалентно `useMemo(() => fn, [deps])`. Нужно, чтобы не ломать `React.memo` у дочернего компонента или не перезапускать `useEffect`, зависящий от этой функции. |

- **Когда `useCallback` и `useMemo` БЕСПОЛЕЗНЫ (антипаттерн):**
  - Передача `onClick={useCallback(...)}` в обычный HTML-тег `<button>` или в дочерний компонент, который **не обёрнут в `React.memo`** (дочерний компонент всё равно ре-рендерится от рендера родителя!).
  - `useMemo` вокруг копеечных операций (`a + b`, склейка двух строк).

- **2 архитектурных приёма оптимизации БЕЗ `memo` / `useMemo` (уровень Senior):**
  1. **State Colocation (спуск состояния вниз):**
     Если в большом компоненте `Page` есть состояние `searchQuery` для одного инпута, и при вводе каждой буквы перерендеривается вся страница с графиками (`<HeavyChart />`), не нужно оборачивать графики в `memo` — нужно вынести `searchQuery` и `<input>` в маленький отдельный компонент `<SearchBar />`. Тогда рендериться будет только он.
  2. **Передача через `children` (Slots / Lifting Content Up):**
     Если состояние (например, позиция скролла или открытый тултип) нужно на самом верху обёртки `<ScrollWrapper>`, передайте тяжёлые компоненты внутрь через проп `children`:
     ```tsx
     function ScrollWrapper({ children }: { children: React.ReactNode }) {
       const [scrollY, setScrollY] = useState(0);
       return <div onScroll={(e) => setScrollY(e.currentTarget.scrollTop)}>{children}</div>;
     }

     // В родителе App:
     function App() {
       return (
         <ScrollWrapper>
           <VeryHeavyComponent /> {/* Не ре-рендерится при скролле! */}
         </ScrollWrapper>
       );
     }
     ```
     *Почему `<VeryHeavyComponent />` не ре-рендерится при изменении `scrollY`?* Потому что JSX `<VeryHeavyComponent />` был создан в `App`. Когда рендерится `ScrollWrapper`, ссылка на объект `props.children` остаётся **той же самой** (`Object.is(prevChildren, nextChildren) === true`), и React пропускает рендер `children` автоматически!

### 8. Как устроен React Context? Почему он вызывает лишние ре-рендеры и как это исправить?

**Зачем спрашивают:** Классическая ошибка — положить в один `AppContext` и тему, и профиль пользователя, и корзину, и модалки, после чего любое изменение кладёт производительность приложения.

**Эталонный подробный ответ:**
- **Зачем нужен Context:** Избежать *Prop Drilling* (прокидывания пропсов через 5–10 промежуточных компонентов, которым эти данные не нужны).
- **Главная проблема производительности Context:**
  В стандартном `useContext(MyContext)` **нет встроенных селекторов**. Если в `Provider` передан объект `{ user, theme, notifications }`, то при изменении `notifications` **все компоненты**, вызвавшие `useContext(MyContext)`, принудительно ре-рендерятся — даже если компонент читает только `theme` и даже если он обёрнут в `React.memo`!
- **4 правила безопасной работы с Context:**
  1. **Всегда мемоизировать объект `value` в провайдере**, иначе на каждый рендер родителя создаётся новый литерал `{ state, dispatch }` и рендерятся все подписчики:
     ```tsx
     const value = useMemo(() => ({ user, logout }), [user, logout]);
     return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
     ```
  2. **Разделять State и Dispatch на два разных контекста (`StateContext` + `ActionsContext`):**
     Кнопки, которым нужна только функция `openModal()` или `dispatch`, подписываются на `ActionsContext` (ссылка на него никогда не меняется) и **вообще никогда не ре-рендерятся** при смене стейта!
  3. **Дробить контексты по доменам и частоте обновлений:** `ThemeContext` отдельно, `AuthContext` отдельно, `LocaleContext` отдельно.
  4. **Не использовать Context для часто меняющегося глобального стейта** (координаты мыши, ввод в форму, фильтры большой таблицы) — для этого нужны внешние сторы с атомарными селекторами (`Zustand`, `Redux Toolkit`, `Jotai`), работающие через `useSyncExternalStore`.

## Блок 3. Формы, Порталы, Suspense, Композиция и Отладка

### 9. Controlled vs Uncontrolled компоненты: в чём разница и как строить формы в продакшене?

**Зачем спрашивают:** Проверить понимание того, где живёт «источник истины» (в React-стейте или в DOM-узле) и почему современные библиотеки форм (`React Hook Form`) выбирают гибридный подход.

**Эталонный подробный ответ:**

| Критерий | Controlled (Управляемый) | Uncontrolled (Неуправляемый) |
|---|---|---|
| **Где хранится значение** | В стейте React (`value={state}` + `onChange`). | Внутри самого DOM-элемента `<input>` (читается через `ref.current.value` или `new FormData(e.currentTarget)`). |
| **Ре-рендер на каждую букву** | **Да** (если стейт лежит в компоненте формы). | **Нет** (нулевой оверхед при наборе текста). |
| **Когда удобен** | Мгновенная валидация на лету, маска ввода телефона/карты, условное отображение полей, синхронизация нескольких инпутов. | Простые формы с валидацией по `onSubmit`, `<input type="file" />` (он всегда неуправляемый), большие формы на 30+ полей через **React Hook Form** (использует `ref` и точечные подписки `useWatch`). |

**Важная ловушка:** Нельзя менять проп `value` у `<input>` с `undefined` на строку — React выдаст предупреждение `A component is changing an uncontrolled input to be controlled`. Начальное значение контролируемого инпута всегда должно быть строкой (`useState("")`, а не `useState()`).

### 10. Порталы (`createPortal`), Error Boundaries и `React.lazy` + `Suspense`

**Зачем спрашивают:** Три важных механизма продакшен-приложений: модалки/тултипы поверх `overflow: hidden`, изоляция падений UI и разделение бандла (code splitting).

**Эталонный подробный ответ:**
1. **React Portal (`createPortal(child, containerDomNode)`):**
   Рендерит дочернее поддерево в **другой DOM-узел** (обычно в `document.body` или `#modal-root`), чтобы модальное окно, дропдаун или тултип не обрезались родительским `overflow: hidden` и не попадали в чужой `z-index` stacking context.
   *Главный вопрос с подвохом:* **Как ведут себя события (`onClick`) внутри Портала?**
   В реальном DOM элемент лежит в `body`, но **в дереве React (Fiber tree) портал остаётся ребёнком своего React-родителя**! Поэтому синтетические события React (`onClick`, `onKeyDown`) **всплывают по React-дереву** к родителю, который вызвал `createPortal` (будьте осторожны: клик внутри модалки может случайно триггернуть `onClick` на карточке, открывшей эту модалку, если не остановить всплытие `e.stopPropagation()`).
2. **Error Boundary (Предохранители ошибок):**
   Компонент (пишется как классовый с `static getDerivedStateFromError` и `componentDidCatch`, либо берётся готовый пакет `react-error-boundary`), который перехватывает ошибки во время **рендера, в методах жизненного цикла и в конструкторах** дочернего поддерева и показывает fallback-интерфейс вместо «белого экрана смерти» всего SPA.
   *Что Error Boundary НЕ ловит:*
   - ошибки внутри обработчиков событий (`onClick` — их не нужно ловить для рендера, там обычный `try/catch`);
   - асинхронный код (`setTimeout`, `Promise`, `fetch`);
   - ошибки в самом Error Boundary.
3. **`React.lazy` и `<Suspense fallback={<Skeleton />}>`:**
   Позволяют загружать код тяжёлых страниц, графиков или админок динамическим `import('./AdminPage')` (Code Splitting — отдельный чанк). Пока чанк скачивается по сети (или в React 18/19 ждут данные в Suspense-совместимом источнике), компонент «выбрасывает» промис вверх по дереву, ближайший `<Suspense>` перехватывает его и рисует `fallback`.

### 11. Эволюция переиспользования в React: HOC vs Render Props vs Custom Hooks и паттерн Compound Components

**Зачем спрашивают:** Это мостик между чистым React и архитектурой компонентов. Собеседующий проверяет, умеете ли вы проектировать удобный UI-кит и переиспользовать бизнес-логику.

**Эталонный подробный ответ:**

| Подход | Суть | Плюсы и минусы (почему ушли / где остался) |
|---|---|---|
| **1. HOC (Higher-Order Component)** `withAuth(Component)` | Функция, принимающая компонент и возвращающая компонент-обёртку с новыми пропсами. | **Минусы:** *Wrapper Hell* в DevTools, неявное происхождение пропсов, коллизии имён пропсов, сложная типизация в TS. **Где живёт сейчас:** защита роутов, аналитика, `React.memo`, `forwardRef`. |
| **2. Render Props** `<DataProvider render={(data) => ...} />` | Компонент принимает функцию в проп `render` или `children` и вызывает её, передавая своё внутреннее состояние. | **Плюсы:** явный поток данных. **Минусы:** вложенная «лесенка» колбэков в JSX. **Где живёт сейчас:** библиотеки виртуализации (`react-virtualized`), `<Controller render={...} />` в React Hook Form. |
| **3. Custom Hooks** `const { data } = useData()` | Функция с префиксом `use`, композирующая базовые хуки React. | **Стандарт для 95% логики:** плоский код, идеальная типизация в TS, ноль лишних узлов в дереве компонентов. **Важно:** кастомный хук переиспользует **логику работы со стейтом, а НЕ сам стейт** (у каждого компонента, вызвавшего хук, свой изолированный стейт). |
| **4. Compound Components (Составные компоненты)** `<Tabs><Tabs.List><Tabs.Trigger/></Tabs.List></Tabs>` | Группа компонентов, которые неявно делятся состоянием через внутренний Context родителя. | **Идеально для UI-китов** (`Select`, `Accordion`, `Tabs`, `Modal`, `DropdownMenu` — как в Radix UI / Shadcn): даёт пользователю полную свободу верстать и переставлять элементы внутри, не превращая родителя в монстра с 30 пропсами. |

### 12. Как тестировать и дебажить React-приложение на проде и стейдже?

**Зачем спрашивают:** Проверить зрелость инженера: как он ищет баги (бесконечные рендеры, просадку FPS, рассинхрон стейта) и как пишет тесты, которые не падают при каждом переименовании CSS-класса.

**Эталонный подробный ответ:**
- **Подход к тестированию (Testing Trophy во фронтенде):**
  1. **Unit-тесты (`Vitest` / `Jest`):** чистые бизнес-функции, калькуляторы, мапперы, валидаторы, редьюсеры — работают за миллисекунды, покрывают краевые случаи.
  2. **Интеграционные компонентные тесты (`React Testing Library` + `@testing-library/user-event`):**
     Главный принцип RTL — **тестировать поведение так, как видит пользователь, а не детали реализации**. Ищем элементы по доступным ролям и тексту (`getByRole('button', { name: /сохранить/i })`, `getByLabelText`), а не по классам `.btn-primary` или внутреннему стейту. Сетевой слой мокается на уровне HTTP через **MSW (Mock Service Worker)**.
  3. **E2E-тесты (`Playwright`):** критические пользовательские пути (логин, корзина, оплата) в реальном браузере.
- **Чеклист отладки проблем в React на проде/стейдже:**
  - **Тормозит интерфейс / лагает ввод:** открываем **React DevTools Profiler** (включаем *Record why each component rendered*) → смотрим Flamegraph, какие компоненты рендерятся зря и из-за какого пропса/контекста; параллельно **Chrome Performance tab** (Long Tasks > 50ms).
  - **Мерцают или перетираются данные после быстрых кликов:** вкладка **Network** → ищем гонку запросов (Race Condition), проверяем наличие `AbortController` или ключей кэша `queryKey` в TanStack Query.
  - **Падает только в продакшене:** проверяем Source Maps в **Sentry**, гидратацию (SSR mismatch), разницу переменных окружения (`VITE_*` / `NEXT_PUBLIC_*`) и отсутствие мутаций кэша.

## Блок 4. Принципы проектирования: SOLID, DRY, KISS, YAGNI на фронтенде

### 13. Как работают все 5 принципов SOLID в реальном React/TypeScript-коде?

**Зачем спрашивают:** На собеседованиях не нужна википедийная расшифровка про «прямоугольник и квадрат в Java» — проверяют, как кандидат применяет SOLID к компонентам, пропсам, хукам и API-слою.

**Эталонный подробный ответ:**

| Буква | Принцип и суть одной фразой | Как нарушают в React (Антипаттерн) | Как делать по SOLID в React / TS |
|---|---|---|---|
| **S — SRP** *(Single Responsibility)* | У модуля/компонента должна быть **одна причина для изменения** (одна зона ответственности). | **God Component** на 600 строк: сам ходит в `fetch`, сам парсит даты, сам считает скидку корзины и сам рендерит модалку с таблицей. | Разделить слои: чистая функция расчёта `calculateCartTotal(items)`, хук получения данных `useCartQuery()`, презентационные компоненты `<CartSummary />` и `<CartItemList />`. |
| **O — OCP** *(Open/Closed)* | Открыт для **расширения** снаружи, но закрыт для **модификации** исходного кода при каждом новом требовании. | Компонент `<Header page="home" \| "profile" \| "cart">`, внутри которого гигантский `if/switch`, и для каждой новой страницы приходится править файл `Header.tsx`. | Использовать **композицию (`children` / слоты)**: `<Header rightSlot={<CartButton />} />` или передавать конфигурацию/рендер-стратегию снаружи, не трогая код `Header`. |
| **L — LSP** *(Liskov Substitution)* | Подтип или обёртка должны без сюрпризов заменять базовый контракт, не ломая ожидания вызывающего кода. | Кастомный `<Button>` называется кнопкой, но не принимает `disabled`, `type="submit"`, `onClick` или ломает `ref` при использовании внутри формы. | Наследовать нативный контракт HTML-элемента: `type ButtonProps = ComponentPropsWithoutRef<'button'> & { variant?: 'primary' \| 'ghost' }` и пробрасывать `...rest` и `ref`. |
| **I — ISP** *(Interface Segregation)* | Клиент не должен зависеть от полей/пропсов, которые он реально не использует. | Карточка `<UserAvatar user={fullUserEntity} />` требует на вход весь объект `User` из 40 полей БД: в итоге её невозможно вызвать в шапке, где есть только `{ name, avatarUrl }`, и сложно мокать в тестах. | Сужать пропсы до минимально необходимых: `interface UserAvatarProps { name: string; avatarUrl?: string }` (или `Pick<User, 'name' \| 'avatarUrl'>`). |
| **D — DIP** *(Dependency Inversion)* | Бизнес-логика и UI зависят от **абстракций (контрактов/хуков)**, а не от конкретных деталей инфраструктуры (`axios`, `localStorage`, Firebase). | Вызов `axios.post('https://api.prod/pay')` и `localStorage.getItem('token')` прямо в `onClick` кнопки оплаты. | Компонент вызывает абстракцию: хук `usePayment()` или сервис, реализующий интерфейс `PaymentGateway`. Замена `axios` на `fetch` или мок в тестах не затрагивает UI. |

**Пример OCP + LSP + ISP в коде (правильный базовый компонент):**
```tsx
import { ComponentPropsWithoutRef, ReactNode } from "react";

interface ButtonProps extends ComponentPropsWithoutRef<"button"> {
  variant?: "primary" | "secondary";
  leftIcon?: ReactNode; // OCP: любая иконка снаружи без правки Button.tsx
}

export function Button({
  variant = "primary",
  leftIcon,
  children,
  className,
  ...rest // LSP: поддерживает все стандартные атрибуты <button> (disabled, type, aria-*)
}: ButtonProps) {
  return (
    <button className={`btn btn-${variant} ${className ?? ""}`} {...rest}>
      {leftIcon}
      {children}
    </button>
  );
}
```

### 14. DRY, KISS и YAGNI: в чём разница и когда DRY приносит вред во фронтенде?

**Зачем спрашивают:** Проверить, не строит ли разработчик «космолёты» на вырост и не сливает ли два случайно похожих экрана в один нечитаемый компонент.

**Эталонный подробный ответ:**
- **KISS (*Keep It Simple, Stupid*):** Из двух работающих решений выбирай самое простое и прямолинейное для чтения. Простой `switch` или объект-словарь лучше хитрой фабрики классов с рефлексией.
- **YAGNI (*You Aren't Gonna Need It*):** Не пиши код, абстракции, плагинную систему или дженерики «на будущее, вдруг через год понадобится». Решай сегодняшнюю задачу, оставляя код легко изменяемым.
- **DRY (*Don't Repeat Yourself*):** Каждое **бизнес-знание (правило)** в системе должно иметь одно авторитетное представление.
- **Когда DRY вреден (принцип AHA — *Avoid Hasty Abstractions* и *Rule of Three*):**
  Главная ошибка Middle-разработчиков — путать **одинаковое бизнес-правило** и **случайное визуальное сходство вёрстки**.
  *Пример:* Карточка товара в каталоге и карточка товара в админке на старте выглядят похоже (картинка, название, цена). Разработчик ради DRY объединяет их в один `<UniversalProductCard isAdmin isCatalog showCheckbox showEditModal isCompact />`.
  Через полгода в этом компоненте 25 булевых флагов, 15 `if/else`, и правка для админки ломает витрину покупателя (нарушены SRP и KISS).
  **Правило:** Выноси в общую абстракцию тогда, когда паттерн устоялся минимум в **3 местах** (*Rule of Three*) или когда это единое доменное правило. **Дублирование кода обходится намного дешевле, чем неправильная абстракция.**

### 15. Observer vs Pub/Sub (Event Bus) и Singleton: как они устроены и где живут во фронтенде?

**Зачем спрашивают:** Самый частый вопрос по поведенческим и порождающим паттернам. Почти все путают Observer и Pub/Sub.

**Эталонный подробный ответ:**
- **Разница между Observer (Наблюдатель) и Pub/Sub (Издатель — Подписчик):**
  | Критерий | Observer (Наблюдатель) | Pub/Sub (Event Bus / Брокер событий) |
  |---|---|---|
  | **Кто кого знает?** | **Прямая связь:** `Subject` (источник) хранит список своих `Observers` и уведомляет их напрямую (`subject.subscribe(fn)`). | **Полная развязка через посредника (Event Bus / Broker):** Издатель (`Publisher`) просто кидает событие `bus.emit('order:paid', data)` и понятия не имеет, кто и в каком модуле его слушает. |
  | **Где во фронтенде?** | Стор `Zustand` / `Redux` (`store.subscribe(listener)`), `RxJS Observable`, браузерные `IntersectionObserver`, `ResizeObserver`, `MutationObserver`. | `window.addEventListener('storage', ...)`, кастомный `EventEmitter` / `mitt` между микрофронтендами, шина аналитики. |

- **Singleton (Одиночка):**
  Гарантирует, что у класса/модуля есть только один экземпляр в приложении. В современном JS/TS благодаря системе ES-модулей (`export const apiClient = new ApiClient()`) любой экспортированный инстанс уже ведёт себя как Singleton внутри бандла.
  - **Где полезен:** инстанс `QueryClient`, HTTP-клиент (`axios.create`), логгер, пул WebSocket-соединения.
  - **Почему его ругают (опасности):**
    1. Это **скрытое глобальное мутабельное состояние** (нарушает DIP, если импортировать напрямую): в unit-тестах мутация синглтона в тесте №1 ломает тест №2.
    2. **Катастрофа в SSR (Next.js / Node.js):** если сохранить данные пользователя в модульный Singleton на сервере, они станут общими для **всех запросов разных пользователей** (утечка чужих персональных данных и токенов!). В SSR инстансы создаются на каждый запрос (per-request) и передаются через Context.

### 16. Структурные паттерны: Adapter (Mapper), Facade, Proxy, Decorator — как быстро отличить?

**Зачем спрашивают:** Проверить умение называть своими именами то, что разработчик и так пишет каждый день.

**Эталонный подробный ответ:**
Шпаргалка «4 паттерна — 4 разных намерения»:

| Паттерн | Главная цель (одним словом) | Реальный пример во фронтенде |
|---|---|---|
| **1. Adapter (Адаптер / Mapper)** | **Совместить несовместимые интерфейсы** (перевести с «языка бэкенда» на «язык фронта»). | Бэкенд присылает кривой легаси-JSON `{ usr_id: 1, created_at_unix: 1710000000, flg_active: "Y" }`. Функция `mapUserDtoToDomain(dto): User` превращает его в чистую модель `{ id: "1", createdAt: Date, isActive: true }`. Если бэкенд переименует поле — правим только 1 строчку в адаптере, а не 50 компонентов! |
| **2. Facade (Фасад)** | **Упростить сложную систему**, спрятав несколько подсистем за одним простым вызовом. | Кастомный хук `useCheckout()`, который внутри координирует вызовы `useCartStore`, `useAuth`, валидацию адреса, отправку метрики и редирект роутера, а компоненту отдаёт просто `{ submitOrder, isSubmitting }`. |
| **3. Proxy (Заместитель)** | **Тот же самый интерфейс**, но с **перехватом чтения/записи** к объекту (контроль доступа, ленивость, реактивность). | Нативный `new Proxy(target, handler)` в JS: на нём построена автоматическая реактивность **MobX** и **Valtio** (при чтении `state.user.name` прокси записывает зависимость, при записи — триггерит рендер), а также `immer` (Draft state в Redux Toolkit). |
| **4. Decorator (Декоратор)** | **Динамически добавить новое поведение** поверх объекта/функции, не меняя её код. | В функциональном мире — обёртки `withLogging(fn)`, `withRetry(fetchUser)`, `axios.interceptors` (добавляющие заголовок `Authorization: Bearer ...` и рефреш токена на `401`), а в React — `React.memo(Component)` и HOC. |

### 17. Server State vs Client State: почему нельзя смешивать API-данные и UI-стейт в одном сторе?

**Зачем спрашивают:** Ключевой архитектурный сдвиг современного фронтенда. В легаси-проектах 80% кода Redux составляли тройки `FETCH_USERS_REQUEST / SUCCESS / FAILURE`. Собеседующий хочет услышать, почему от этого ушли к `TanStack Query` / `RTK Query`.

**Эталонный подробный ответ:**
- **Принципиальное отличие:**
  | Критерий | Client State (Клиентский стейт) | Server State (Серверное состояние / Кэш) |
  |---|---|---|
  | **Кто владеет данными?** | Только текущая вкладка браузера. | Удалённый сервер (БД). У нас на клиенте — лишь **временный снимок (кэш)**, который может устареть в любую секунду без нашего ведома. |
  | **Синхронность** | Синхронный, всегда актуален. | Асинхронный, требует сети, может упасть с ошибкой. |
  | **Примеры** | Открыта ли модалка, тема оформления, выбранная вкладка, черновик несохранённой формы, локальные фильтры. | Профиль пользователя, список заказов, товары каталога, баланс счёта. |
  | **Инструменты** | `useState`, `useReducer`, `Zustand`, `Redux Toolkit` (чистые слайсы), `Jotai`. | **`TanStack Query` (React Query)**, **`RTK Query`**, **`SWR`**, **`Apollo Client`**. |

- **Какие задачи Server State решает из коробки `TanStack Query` (и что пришлось бы писать руками в `useEffect` / обычном сторе):**
  1. **Дедупликация запросов:** если 5 компонентов на экране одновременно вызвали `useQuery({ queryKey: ['user', 1] })`, по сети уйдёт **ровно 1 HTTP-запрос**.
  2. **Разделение `staleTime` и `gcTime` (`cacheTime`):**
     - `staleTime` — сколько времени данные считаются **свежими** (пока они свежие, повторный маунт компонента берёт их из памяти мгновенно **без сетевого запроса**; по умолчанию `0`).
     - `gcTime` — сколько времени неиспользуемый кэш хранится в памяти после того, как размонтировался последний подписчик (по умолчанию 5 минут), чтобы при нажатии кнопки «Назад» показать старые данные мгновенно (*stale-while-revalidate*).
  3. **Автоматическая инвалидация (`invalidateQueries`) и Optimistic Updates** после мутаций (`useMutation`).
  4. **Отмена гонок, ретраи с экспоненциальной задержкой, фоновое обновление при возврате фокуса на вкладку (`refetchOnWindowFocus`) и пагинация/Infinite Scroll.**

### 18. Flux (Redux Toolkit / Zustand) vs Атомарный стейт (Jotai) vs Реактивный Proxy (MobX): что когда выбирать?

**Зачем спрашивают:** Проверить кругозор в стейт-менеджменте и умение обосновать выбор инструмента под команду и бизнес-задачу.

**Эталонный подробный ответ:**

| Семейство | Представители | Как устроено обновление | Когда выбирать |
|---|---|---|---|
| **1. Однонаправленный поток (Flux-подобные)** | **Zustand**, **Redux Toolkit (RTK)** | Единое дерево состояния. Обновление строго иммутабельное через экшены/сеттеры (`Action → Reducer/Setter → New State`). Подписка компонентов через **селекторы** (`useStore(s => s.count)`). | **Zustand** — дефолтный выбор для 80% средних и крупных SPA (минимум бойлерплейта, работает вне React, ноль провайдеров). **RTK** — для больших энтерпрайз-команд, где нужны жёсткий стандарт, middleware, DevTools Time Travel и `RTK Query`. |
| **2. Атомарные (Bottom-up)** | **Jotai**, Recoil | Состояние разбито на мелкие независимые атомы (`const countAtom = atom(0)`), которые можно комбинировать в вычисляемые (derived) атомы, как ячейки в Excel. | Сложные дашборды, графические редакторы (Canvas/Figma-like), формы с сотнями взаимозависимых ячеек, где нужно точечное обновление без селекторов. |
| **3. Реактивные на Proxy (OOP / Mutable API)** | **MobX**, Valtio | Мутабельный синтаксис (`store.count++`), под капотом `Proxy` автоматически отслеживает, какие именно поля прочитал компонент во время рендера (`observer`), и перерисовывает только его. | Проекты со сложной доменной моделью и графами объектов, где команде ближе ООП-классы и вычисляемые геттеры (`@computed`), без ручного написания селекторов. |

## Блок 6. Архитектура фронтенд-приложений

### 19. Модульная архитектура: почему папка `components/` не масштабируется, что такое Colocation и зачем нужен Public API (`index.ts`)?

**Зачем спрашивают:** Первый вопрос про организацию файловой структуры проекта.

**Эталонный подробный ответ:**
- **Проблема группировки «по техническим типам» (`src/components`, `src/hooks`, `src/types`, `src/api`):**
  На маленьком проекте из 10 файлов это работает. На проекте из 300 файлов в папке `components/` лежит 150 файлов вперемешку, а чтобы поменять одну фичу «Оформление заказа», разработчику приходится прыгать по 6 разным папкам в разных концах проекта (низкая связность *Cohesion*, высокая сцепленность *Coupling*).
- **Принцип Colocation (Колокация):**
  *«Храни вещи, которые меняются вместе, максимально близко друг к другу».*
  Код группируется **по бизнес-доменам / фичам** (`features/checkout/{ui, model, api, lib}`): компоненты, их локальные хуки, стили, тесты и типы этой фичи лежат рядом в одной папке. Если фичу нужно удалить — вы просто удаляете одну папку.
- **Зачем модулю нужен Public API (`index.ts` на входе в модуль):**
  `index.ts` работает как **инкапсуляция (`public` vs `private`)**:
  - Наружу экспортируется только то, чем разрешено пользоваться другим модулям (`export { CheckoutForm } from './ui/CheckoutForm'`).
  - Внутренние хелперы, подкомпоненты и структура папок внутри модуля остаются скрытыми: мы можем свободно рефакторить внутренности модуля, не боясь сломать импорты в 40 других местах проекта.
  - *Важная оговорка для Senior (проблема Barrel-файлов):* Нельзя делать один гигантский `shared/index.ts`, который реэкспортирует вообще все 200 компонентов и тяжёлые библиотеки (`chart.js`) — это ухудшает Tree-shaking и замедляет старт dev-сервера / тестов (Vitest/Jest). В `shared` делают покомпонентные точки входа (`@/shared/ui/button`, `@/shared/lib/date`).

### 20. Clean Architecture (Чистая архитектура) и Dependency Rule во фронтенде

**Зачем спрашивают:** Проверить понимание того, как отделить бизнес-правила приложения от фреймворка (React) и транспорта (REST/GraphQL).

**Эталонный подробный ответ:**
- **Главное правило Чистой архитектуры (The Dependency Rule):**
  Код делится на концентрические слои, и **все стрелки зависимостей (`import`) направлены строго снаружи внутрь** — в сторону бизнес-логики (Domain). Внутренний слой ничего не знает о внешнем.
  ```
  [ UI (React компоненты) & Infrastructure (Axios, LocalStorage) ]
                         │  зависят от ↓
  [ Application / Use Cases (сценарии: оформление заказа, авторизация) ]
                         │  зависят от ↓
  [ Domain / Entities (чистый TS: модели, инварианты, бизнес-формулы) ]
  ```
- **Что это даёт на практике во фронтенде:**
  1. **Слой `Domain` (чистый TypeScript без единого импорта `react` или `axios`):** содержит типы сущностей и чистые функции бизнес-правил (например, `canUserApproveDocument(user, doc): boolean`, `calculateLoanSchedule(amount, rate)`). Его можно протестировать за миллисекунды без JSDOM и переиспользовать хоть в React Native, хоть в Node.js.
  2. **Слой `Application` (Use Cases / Сторы / Хуки сценариев):** оркестрирует сценарий («проверить данные → вызвать порт репозитория → обновить стейт → показать уведомление»).
  3. **Слой `UI & Infrastructure`:** React-компоненты только отображают состояние и пробрасывают события пользователя в Use Case, а API-адаптеры реализуют сетевые запросы и маппинг DTO.

### 21. Feature-Sliced Design (FSD): слои, слайсы, сегменты и как связать две фичи без нарушения правил?

**Зачем спрашивают:** FSD — де-факто самая популярная архитектурная методология в русскоязычных продуктовых компаниях (Т1, Яндекс, Сбер, Авито, Ozon и др.).

**Эталонный подробный ответ:**
- **Три оси координат в FSD:**
  1. **Layers (Слои — стандартизированы, сверху вниз по уровню знаний и ответственности):**
     ```
     1. app       — инициализация приложения, провайдеры, роутер, глобальные стили
     2. pages     — полноценные страницы (привязаны к роутам), собирают виджеты и фичи
     3. widgets   — крупные самостоятельные блоки страницы (Header, Sidebar, OrderCardWithActions)
     4. features  — действия пользователя, несущие бизнес-ценность (auth-by-phone, add-to-cart, like-post)
     5. entities  — бизнес-сущности предметной области (user, product, order, comment)
     6. shared    — переиспользуемый фундамент без знания о бизнесе (ui-kit, api-client, lib, config)
     ```
     *(Слой `processes` устарел и депрекейтнут в FSD v2).*
  2. **Slices (Слайсы — бизнес-разделение внутри `pages`, `widgets`, `features`, `entities`):**
     Например, внутри `entities/` лежат слайсы `user/`, `product/`, `order/`. У `app` и `shared` слайсов нет (так как в `shared` ещё нет бизнес-доменов, а `app` объединяет всё).
  3. **Segments (Сегменты — техническое назначение внутри слайса):**
     - `ui/` — компоненты отображения;
     - `model/` — стейт, сторы, хуки бизнес-логики, схемы валидации;
     - `api/` — запросы к бэкенду и DTO этого слайса;
     - `lib/` — внутренние хелперы и мапперы;
     - `config/` — константы и фича-флаги.

- **Главное правило импортов в FSD (контролируется линтером `steiger` / `eslint-plugin-boundaries`):**
  > **Модуль может импортировать ТОЛЬКО из слоёв, расположенных строго НИЖЕ него.**
  > **Кросс-импорты между разными слайсами одного слоя (`features/A` → `features/B`) ЗАПРЕЩЕНЫ.**

- **Вопрос на засыпку: «Как тогда подружить две фичи или вставить кнопку фичи `AddToCart` внутрь карточки сущности `ProductCard` (`entities/product`), если `entities` ниже `features`?»**
  Есть **3 законных способа в FSD**:
  1. **Композиция через слоты (`ReactNode` props) на уровне выше (`widgets` или `pages`):**
     В `entities/product/ui/ProductCard.tsx` делаем проп `actionSlot?: ReactNode`. А на уровне `widgets/product-catalog` или `pages/catalog` собираем их вместе:
     `<ProductCard product={p} actionSlot={<AddToCartButton productId={p.id} />} />`.
  2. **Опускание общей логики/данных на слой ниже (`entities` или `shared`):**
     Если две фичи пытаются читать одно и то же состояние, значит это состояние принадлежит самой бизнес-сущности (`entities/cart`), и обе фичи законно импортируют его снизу.
  3. **Инверсия зависимостей (DI через Context / Event / Колбэк пропсы):**
     Нижний слой объявляет только интерфейс или колбэк `onSuccess?: () => void`, а верхний слой (`pages` / `widgets`) передаёт в него вызов второй фичи.

### 22. DDD (Domain-Driven Design) на фронтенде и Микрофронтенды (MFE): когда нужны, а когда это оверинжиниринг?

**Зачем спрашивают:** Проверить кругозор уровня Senior: понимает ли кандидат границы применимости тяжёлых архитектурных подходов.

**Эталонный подробный ответ:**
- **Что из DDD (Domain-Driven Design) реально полезно на фронтенде:**
  1. **Ubiquitous Language (Единый язык):** переменные, типы, компоненты и эндпоинты в коде называются **точно так же**, как их называют бизнес и продуктологи (не абстрактный `ItemType2`, а `LoanApplication` — заявка на кредит).
  2. **Entity vs Value Object:**
     - **Entity (Сущность):** определяется своим уникальным `id` и имеет жизненный цикл (два объекта `User` с одинаковым именем, но разным `id` — это разные сущности).
     - **Value Object (Объект-значение):** не имеет `id`, иммутабелен и определяется только набором своих значений (например, `Money { amount: 100, currency: 'RUB' }` или `DateRange { from, to }`).
  3. **Bounded Context (Ограниченный контекст) и ACL (Anti-Corruption Layer):**
     Одно и то же слово «Товар» (`Product`) в контексте Витрины (фото, отзывы, рейтинг) и в контексте Складской логистики (вес, габариты паллеты, штрихкод) — это **две разные модели**, и не нужно сливать их в один интерфейс на 80 полей. А **ACL (Антикоррупционный слой)** на фронте — это слой адаптеров/мапперов на границе с API, который не пускает уродливые структуры легаси-бэкенда внутрь компонентов.

- **Микрофронтенды (Microfrontends — MFE):**
  Архитектура, в которой единое веб-приложение собирается из независимых фронтенд-приложений, разрабатываемых и **деплоящихся независимо** разными командами.
  - **Как реализуют технически:**
    1. **Webpack / Vite Module Federation** (runtime-подгрузка JS-бандлов удалённых приложений `remotes` в общее `host/shell`-приложение с шарингом `react`, `react-dom` и дизайн-системы).
    2. **Single-SPA** (оркестратор роутинга между микрофронтами).
    3. **`<iframe>`** (максимальная изоляция CSS/JS и безопасности в банках/энтерпрайзе, но сложная коммуникация через `postMessage`, проблемы с модалками, роутингом и медленная загрузка).
  - **Когда MFE реально нужны:** в компании **5–15+ независимых продуктовых команд** (50+ фронтендеров), которым критично выкатывать свои разделы в прод независимо друг от друга без единого релизного поезда.
  - **Когда MFE — зло (когда НЕ внедрять):** если у вас 1–2 команды (до 10–15 человек). Вы получите сложнейший CI/CD, дублирование зависимостей в бандле, рассинхрон версий UI-кита, сложную отладку и «распределённый монолит» — вместо этого в 10 раз лучше подойдёт **Монорепозиторий (Nx / Turborepo / pnpm workspaces) + FSD**.

**Что проверяет:** Понимание разницы между фазой рендера и фазой коммита (`useEffect`), устройство `useRef` и поведение в React 18 Strict Mode.

```tsx
/*
Реализовать два кастомных хука:
1) useFirstRender(): boolean — возвращает true только на самом первом рендере,
   а на всех последующих — false (должен корректно работать в React 18 Strict Mode).
2) usePrevious<T>(value: T): T | undefined — возвращает значение пропса/стейта
   с предыдущего рендера.
*/

import { useEffect, useRef } from "react";

export function useFirstRender(): boolean {
  // TODO
}

export function usePrevious<T>(value: T): T | undefined {
  // TODO
}
```

<details>
<summary><b>Подробный разбор и эталонное решение</b></summary>

**Главная ловушка, в которую попадают 70% кандидатов:**
Пытаются менять `ref.current` прямо в теле функции во время рендера:
```tsx
// ❌ НЕВЕРНО: ломается в React 18 Strict Mode!
function useFirstRenderBad() {
  const isFirst = useRef(true);
  if (isFirst.current) {
    isFirst.current = false;
    return true;
  }
  return false;
}
```
В React 18 Strict Mode (dev) React вызывает функцию компонента **дважды подряд** во время первого рендера, чтобы проверить чистоту функции. При первом вызове `isFirst.current` станет `false`, и уже при втором вызове того же самого первого рендера хук вернёт `false`!

**Как правильно:**
Мутировать `ref.current` нужно внутри `useEffect`, который гарантированно выполняется **после** того, как рендер закоммичен на экран:

```tsx
import { useEffect, useRef } from "react";

export function useFirstRender(): boolean {
  const isFirstRef = useRef(true);

  useEffect(() => {
    isFirstRef.current = false;
  }, []);

  return isFirstRef.current;
}

export function usePrevious<T>(value: T): T | undefined {
  const prevRef = useRef<T | undefined>(undefined);

  useEffect(() => {
    prevRef.current = value;
  }, [value]);

  return prevRef.current;
}
```

## Задача 2 (React: Code Review). Найти 7 багов в `PleaseReviewMe` и отрефакторить

**Что проверяет:** Внимательность к утечкам памяти, зависимостям хуков, Stale Closure, батчингу `setState` и ключам списков.

```tsx
const PleaseReviewMe = () => {
  const [count, setCount] = React.useState(1);
  const [items, setItems] = React.useState([{ id: 1 }]);

  React.useLayoutEffect(() => {
    document.addEventListener("click", () => {
      setInterval(() => console.log(count), 1000);
    });
  });

  const click = React.useCallback(() => {
    setCount(count + 1);
    setItems([...items, { id: count + 1 }]);
  });

  return (
    <>
      Current count: {count}
      <ul>
        {items.map((item) => (
          <li>{item.id}</li>
        ))}
      </ul>
      <button onClick={() => click()}>add one</button>
    </>
  );
};
```

<details>
<summary><b>Подробный разбор всех 7 проблем и эталонный код</b></summary>

1. **`useLayoutEffect` без массива зависимостей:** запускается синхронно после **каждого** рендера и блокирует отрисовку. Для подписки на `document` нужен `useEffect(..., [])`.
2. **Утечка слушателей `document.addEventListener`:** на каждый рендер навешивается новая анонимная функция и никогда не снимается через `removeEventListener`.
3. **Лавинообразная утечка таймеров `setInterval`:** каждый клик в любом месте документа создаёт новый бесконечный `setInterval`, который никогда не очищается через `clearInterval`.
4. **Stale Closure (устаревшее замыкание) на `count`:** колбэк внутри `setInterval` навсегда замыкает значение `count` того рендера, в котором был создан слушатель. Чтобы читать свежий `count` без пересоздания слушателя и таймера, используем `useRef` (*Latest Ref pattern*).
5. **`useCallback` без массива зависимостей:** не мемоизирует ничего — функция создаётся заново на каждом рендере.
6. **Небезопасное обновление стейта `setCount(count + 1)`:** при пустом массиве зависимостей в `useCallback([])` замкнётся `count = 1`. Нужно функциональное обновление `setCount(prev => prev + 1)`.
7. **Отсутствует `key` у `<li>`** в `.map()`, а `onClick={() => click()}` создаёт лишнюю обёртку вместо `onClick={click}`.

```tsx
import React, { useCallback, useEffect, useRef, useState } from "react";

export const PleaseReviewMe = () => {
  const [count, setCount] = useState(1);
  const [items, setItems] = useState([{ id: 1 }]);

  const countRef = useRef(count);
  countRef.current = count;

  useEffect(() => {
    let intervalId: ReturnType<typeof setInterval> | undefined;

    const handleDocumentClick = () => {
      clearInterval(intervalId);
      intervalId = setInterval(() => {
        console.log(countRef.current);
      }, 1000);
    };

    document.addEventListener("click", handleDocumentClick);
    return () => {
      document.removeEventListener("click", handleDocumentClick);
      clearInterval(intervalId);
    };
  }, []);

  const handleAdd = useCallback(() => {
    setCount((prevCount) => {
      const nextCount = prevCount + 1;
      setItems((prevItems) => [...prevItems, { id: nextCount }]);
      return nextCount;
    });
  }, []);

  return (
    <>
      Current count: {count}
      <ul>
        {items.map((item) => (
          <li key={item.id}>{item.id}</li>
        ))}
      </ul>
      <button onClick={handleAdd}>add one</button>
    </>
  );
};
```

## Задача 3 (React: Асинхронность и Race Condition). Поиск с `useDebounce` и `AbortController`

**Что проверяет:** Умение писать живой поисковый компонент без гонки ответов (когда медленный запрос на `"re"` приходит позже быстрого запроса на `"react"` и затирает экран старыми данными).

```tsx
/*
Реализовать:
1) Хук useDebounce<T>(value: T, delay: number): T
2) Компонент UserSearch, который ждёт 300 мс после ввода,
   отменяет предыдущий запрос через AbortController при новом вводе или размонтировании
   и корректно отображает состояния loading / error / users.
*/
```

<details>
<summary><b>Подробный разбор и эталонное решение</b></summary>

```tsx
import { useEffect, useState } from "react";

interface User {
  id: string;
  name: string;
}

export function useDebounce<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState<T>(value);

  useEffect(() => {
    const timerId = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timerId);
  }, [value, delay]);

  return debounced;
}

export function UserSearch() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebounce(query.trim(), 300);

  const [users, setUsers] = useState<User[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!debouncedQuery) {
      setUsers([]);
      setError(null);
      setIsLoading(false);
      return;
    }

    const controller = new AbortController();
    setIsLoading(true);
    setError(null);

    fetch(`/api/users?q=${encodeURIComponent(debouncedQuery)}`, {
      signal: controller.signal,
    })
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json() as Promise<User[]>;
      })
      .then((data) => {
        setUsers(data);
        setIsLoading(false);
      })
      .catch((err: unknown) => {
        // Отменённый запрос бросает AbortError — это штатная отмена, а не ошибка для UI!
        if (err instanceof DOMException && err.name === "AbortError") return;
        setError(err instanceof Error ? err.message : "Ошибка сети");
        setIsLoading(false);
      });

    return () => controller.abort();
  }, [debouncedQuery]);

  return (
    <div>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Введите имя..."
      />
      {isLoading && <p>Загрузка...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {users.map((u) => (
          <li key={u.id}>{u.name}</li>
        ))}
      </ul>
    </div>
  );
}
```
</details>

## Задача 4 (React: Оптимизация рендеров). Почему `React.memo` не работает и 2 способа починить

**Что проверяет:** Понимание ссылочного сравнения пропсов в `React.memo` и умение предложить как мемоизацию (`useMemo` + `useCallback`), так и архитектурную колокацию состояния (*State Colocation*).

```tsx
/*
При каждом нажатии клавиши в поле заметки (note) компонент ExpensiveList
перерендеривается, хотя он обёрнут в React.memo. Почему и как исправить двумя способами?
*/

export function Catalog({ rawItems }: { rawItems: Item[] }) {
  const [note, setNote] = useState("");
  const [selectedId, setSelectedId] = useState<string | null>(null);

  const activeItems = rawItems.filter((item) => item.category === "active");
  const handleSelect = (id: string) => setSelectedId(id);

  return (
    <div>
      <input value={note} onChange={(e) => setNote(e.target.value)} />
      <p>Выбрано: {selectedId}</p>
      <ExpensiveList items={activeItems} onSelect={handleSelect} />
    </div>
  );
}
```

<details>
<summary><b>Подробный разбор и два способа решения</b></summary>

**Почему `React.memo` сломан:**
На каждый символ в `note` компонент `Catalog` рендерится заново. При этом:
1. `rawItems.filter(...)` возвращает **новый экземпляр массива** (новую ссылку в памяти).
2. `const handleSelect = ...` создаёт **новую функцию** (новую ссылку).
`React.memo` сравнивает старые и новые пропсы через `Object.is` и видит две новые ссылки → запускает полный ре-рендер `ExpensiveList`.

**Способ 1 (через мемоизацию ссылок `useMemo` + `useCallback`):**
```tsx
const activeItems = useMemo(
  () => rawItems.filter((item) => item.category === "active"),
  [rawItems]
);
const handleSelect = useCallback((id: string) => setSelectedId(id), []);
```

**Способ 2 (Архитектурный — State Colocation, ещё лучше):**
Состояние `note` используется **только** внутри `<input>`. Выносим его в отдельный маленький компонент `<NoteInput />` — тогда при наборе заметки родитель `Catalog` вообще не будет ре-рендериться!
</details>

```tsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">Профиль</Tabs.Trigger>
```

<details>
<summary><b>Подробный разбор и эталонное решение</b></summary>

```tsx
import React, { createContext, useContext, useMemo, useState, ReactNode } from "react";

interface TabsContextValue {
  activeTab: string;
  setActiveTab: (value: string) => void;
}

const TabsContext = createContext<TabsContextValue | null>(null);

function useTabsContext(): TabsContextValue {
  const ctx = useContext(TabsContext);
  if (!ctx) {
    throw new Error("Компоненты Tabs.* должны использоваться внутри <Tabs>");
  }
  return ctx;
}

export function Tabs({
  defaultValue,
  children,
}: {
  defaultValue: string;
  children: ReactNode;
}) {
  const [activeTab, setActiveTab] = useState(defaultValue);
  const value = useMemo(() => ({ activeTab, setActiveTab }), [activeTab]);

  return <TabsContext.Provider value={value}>{children}</TabsContext.Provider>;
}

Tabs.List = function TabsList({ children }: { children: ReactNode }) {
  return <div role="tablist">{children}</div>;
};

Tabs.Trigger = function TabsTrigger({
  value,
  children,
}: {
  value: string;
  children: ReactNode;
}) {
  const { activeTab, setActiveTab } = useTabsContext();
  return (
    <button
      type="button"
      role="tab"
      aria-selected={activeTab === value}
      onClick={() => setActiveTab(value)}
    >
      {children}
    </button>
  );
};

Tabs.Content = function TabsContent({
  value,
  children,
}: {
  value: string;
  children: ReactNode;
}) {
  const { activeTab } = useTabsContext();
  if (activeTab !== value) return null;
  return <div role="tabpanel">{children}</div>;
};
```

## Задача 6 (Паттерны GoF + TS). Типобезопасный `EventBus` (Pub/Sub)

**Что проверяет:** Умение написать классический паттерн Pub/Sub на `Set` с дженериками TypeScript и возвратом функции отписки `unsubscribe`.

```tsx
type AppEvents = {
  "auth:logout": { reason: string };
  "toast:show": { message: string; type: "info" | "error" };
};
// Реализовать класс EventBus<Events> с методами on, off, emit
```

<details>
<summary><b>Подробный разбор и эталонное решение</b></summary>

```tsx
type Handler<Payload> = (payload: Payload) => void;

export class EventBus<Events extends Record<string, unknown>> {
  private listeners: {
    [K in keyof Events]?: Set<Handler<Events[K]>>;
  } = {};

  on<K extends keyof Events>(event: K, handler: Handler<Events[K]>): () => void {
    let set = this.listeners[event];
    if (!set) {
      set = new Set();
      this.listeners[event] = set;
    }
    set.add(handler);
    return () => this.off(event, handler);
  }

  off<K extends keyof Events>(event: K, handler: Handler<Events[K]>): void {
    this.listeners[event]?.delete(handler);
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    const handlers = this.listeners[event];
    if (!handlers) return;
    // Копируем Set в массив, чтобы отписка внутри обработчика не сбила итерацию
    [...handlers].forEach((handler) => handler(payload));
  }
}
```

```tsx
// 1. Domain: чистая функция (покрывается unit-тестом без React и моков сети)
export interface OrderItem {
  id: string;
  price: number;
  qty: number;
}
export interface Order {
  id: string;
  items: OrderItem[];
  isVip: boolean;
}

export function calculateFinalPrice(order: Order): number {
  const subtotal = order.items.reduce((sum, item) => sum + item.price * item.qty, 0);
  return order.isVip ? subtotal * 0.85 : subtotal;
}

// 2. Application contract (DIP): порт репозитория
export interface OrderRepository {
  getById(orderId: string, signal?: AbortSignal): Promise<Order>;
}

// 3. UI: чистый презентационный компонент
export function OrderView({ order }: { order: Order }) {
  return <div>К оплате: {calculateFinalPrice(order).toFixed(2)} ₽</div>;
}
```

## Задача 8 (Архитектура: FSD). Найти и исправить 4 нарушения правил Feature-Sliced Design

**Что проверяет:** Практическое знание правил импортов между слоями, запрета кросс-импортов между слайсами и инкапсуляции через Public API.

```tsx
// 1) src/entities/user/model/userStore.ts
import { loginModalOpen } from "@/features/auth-by-phone/model/modalSlice";

// 2) src/features/add-to-cart/ui/AddToCartButton.tsx
import { PromoBanner } from "@/widgets/promo-header/ui/PromoBanner";

// 3) src/features/transfer-money/model/submitTransfer.ts
import { validateCard } from "@/features/card-binding/lib/validateCard";

// 4) src/pages/profile/ui/ProfilePage.tsx
import { Avatar } from "@/entities/user/ui/Avatar/AvatarInternal";
```

<details>
<summary><b>Подробный разбор всех 4 нарушений</b></summary>

1. **`entities/user` → `features/auth-by-phone` (импорт снизу вверх):**
   Слой `entities` лежит ниже `features` и не имеет права знать про фичи. Реакцию на истечение сессии или открытие модалки нужно поднять на уровень `features`, `widgets` или `app`.
2. **`features/add-to-cart` → `widgets/promo-header` (импорт снизу вверх):**
   Слой `features` ниже `widgets`. Нужно либо собирать кнопку и баннер наверху через композицию (слоты) в самом виджете/странице, либо опустить переиспользуемый UI-баннер в `entities/promo` или `shared/ui`.
3. **`features/transfer-money` → `features/card-binding` (горизонтальный кросс-импорт внутри одного слоя):**
   Две фичи не могут импортировать друг друга напрямую. Валидацию карты `validateCard` нужно опустить на слой ниже — в `entities/card` или `shared/lib`.
4. **`@/entities/user/ui/Avatar/AvatarInternal` (обход Public API слайса):**
   Импорт лезет во внутреннюю файловую структуру чужого слайса. Нужно экспортировать `Avatar` в `src/entities/user/index.ts` и импортировать только как `import { Avatar } from "@/entities/user"`.
</details>
