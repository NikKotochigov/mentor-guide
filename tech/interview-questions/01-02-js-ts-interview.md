# Часть 1. JavaScript — подробные вопросы и ответы

## Блок 1. Типы, ссылки, область видимости и замыкания

### 1. Примитивы vs объекты: как копируются и почему мутация ломает React?

**Зачем спрашивают:** базовый вопрос, который сразу показывает, понимает ли разработчик модель памяти JS, почему мутация пропсов/стейта приводит к багам и чем поверхностная копия отличается от глубокой.

**Эталонный ответ:**

В JavaScript **8 типов данных**:
- **7 примитивных типов:** `string`, `number`, `bigint`, `boolean`, `undefined`, `symbol`, `null`.
- **1 ссылочный тип:** `object` (к нему относятся обычные объекты `{}`, массивы `[]`, функции, `Date`, `RegExp`, `Map`, `Set`, `Error`).

**Ключевая разница:**
1. **Примитивы неизменяемы (immutable)** и передаются **по значению**. При `let b = a` создаётся независимая копия значения.
2. **Объекты мутабельны (mutable)** и хранятся в куче (Heap), а в самой переменной лежит **ссылка (адрес в памяти)**. При присваивании `const b = a` или передаче объекта в функцию копируется **значение ссылки** — обе переменные указывают на один и тот же объект в памяти.

**Мутация против переприсваивания:**

```js
const first = { name: "Alice", tags: ["js"] };
const second = first; // скопировали ссылку на тот же объект

// 1. Мутация: меняем содержимое объекта по ссылке
first.name = "Bob";
console.log(second.name); // "Bob" — оба имени смотрят на один объект

// 2. Переприсваивание: меняем только локальную переменную
let third = first;
third = { name: "Charlie", tags: [] };
console.log(first.name); // "Bob" — исходный объект не изменился
```

**Поверхностное (Shallow) vs Глубокое (Deep) копирование:**

| Способ | Тип копии | Как работает и ограничения |
|--------|-----------|----------------------------|
| `{ ...obj }`, `Object.assign({}, obj)` | **Shallow** | Копирует только собственные перечисляемые свойства **верхнего уровня**. Вложенные объекты (`obj.profile`, `obj.tags`) остаются общими по ссылке! |
| `[...arr]`, `arr.slice()`, `Array.from(arr)` | **Shallow** | Создаёт новый массив, но объекты внутри него ведут на те же ссылки. |
| `structuredClone(obj)` | **Deep** | Нативный стандарт глубокого клонирования. Копирует вложенные объекты, массивы, `Date`, `Map`, `Set`, `RegExp` и даже **циклические ссылки**. Не клонирует функции, DOM-узлы и прототипы классов (бросит `DataCloneError`). |
| `JSON.parse(JSON.stringify(obj))` | **Deep (костыль)** | Старый способ. Теряет `undefined`, функции и `Symbol`, превращает `Date` в строку, `NaN`/`Infinity` — в `null`, `Map`/`Set` — в `{}`, и падает с ошибкой на циклических ссылках. |

**Почему мутация ломает React:**
React сравнивает предыдущее и новое значение в `useState`, `useMemo`, `useEffect` и `React.memo` по ссылке через `Object.is(prevState, nextState)`.
Если написать:

```js
state.items.push(newItem);
setState(state); // Ссылка та же! Object.is(prev, next) === true → ре-рендера НЕ будет
```

Нужно создавать новую ссылку на каждом изменённом уровне вложенности: `setState(prev => ({ ...prev, items: [...prev.items, newItem] }))`.

**Красные флаги:**
- Думает, что `const user = {}` делает объект неизменяемым (`const` запрещает только переприсваивание `user = ...`, а не `user.name = ...`).
- Уверен, что `{ ...user }` делает глубокую копию.
- Для глубокой копии в современном коде знает только `JSON.stringify` и не слышал про `structuredClone`.

**Follow-up:** Как запретить изменение объекта в рантайме?  
→ `Object.freeze(obj)` делает объект неизменяемым (нельзя добавлять, удалять и менять свойства, в `strict mode` попытка бросит `TypeError`), но тоже **только поверхностно** (вложенные объекты нужно замораживать рекурсивно).

### 2. Приведение типов, `==` vs `===`, `Object.is`, `||` vs `??`, сюрпризы `typeof`

**Зачем спрашивают:** проверяют, не напишет ли разработчик баг на пустой строке или числе `0` в условии рендера и понимает ли тонкости проверок в JS.

**Эталонный ответ:**

**1. Три вида сравнения в JS:**
- `===` (**строгое равенство**): сравнивает без приведения типов. Если типы разные — сразу `false`. Исключения для чисел: `NaN === NaN` даёт `false`, а `+0 === -0` даёт `true`.
- `==` (**нестрогое равенство**): приводит типы к одному по сложным табличным правилам:
  - `null == undefined` → `true` (и ни с чем другим они при `==` не равны: `null == 0` → `false`).
  - Строка и число: строка приводится к числу (`"5" == 5` → `true`, `"" == 0` → `true`).
  - `boolean` приводится к числу (`true` → `1`, `false` → `0`).
  - Объект и примитив: объект приводится к примитиву через `valueOf()` / `toString()` (`[1, 2] == "1,2"` → `true`, `[] == ![]` → `[] == false` → `"" == 0` → `0 == 0` → `true`).
- `Object.is(a, b)`: ведёт себя как `===`, но исправляет два крайних случая:
  - `Object.is(NaN, NaN)` → `true`
  - `Object.is(+0, -0)` → `false`
  Именно `Object.is` используется внутри React для сравнения зависимостей хуков и пропсов в `React.memo`.

**2. Все 8 falsy-значений (приводятся к `false` в `Boolean(x)` и `if (x)`):**
1. `false`
2. `0`
3. `-0`
4. `0n` (BigInt ноль)
5. `""` (пустая строка)
6. `null`
7. `undefined`
8. `NaN`

**Все остальные значения — truthy**, включая пустой массив `[]`, пустой объект `{}`, строку `"0"` и `"false"`.

**3. Разница между `||` и `??` (Nullish Coalescing):**
- Оператор `a || b` возвращает `b`, если `a` — **любое falsy** значение (включая `0`, `""`, `false`).
- Оператор `a ?? b` возвращает `b`, только если `a` равно **`null` или `undefined`**.

```js
const discount = 0;
console.log(discount || 10); // 10 ❌ (баг: скидка 0% заменилась на 10%)
console.log(discount ?? 10); // 0  ✅ (сработает только на null/undefined)
```

**4. Сюрпризы оператора `typeof`:**
- `typeof null === "object"` — историческая ошибка в первой реализации JS (первые биты тега типа у `null` были `000`, как у объектов). Для проверки на `null` используем `val === null`.
- `typeof function() {} === "function"` — хотя функция является объектом, `typeof` выделяет её отдельно.
- `typeof [] === "object"` — массивы от обычных объектов через `typeof` не отличить, используем `Array.isArray(val)`.
- `typeof NaN === "number"` — `NaN` («Not-a-Number») технически относится к типу `number`. Проверить на `NaN`: `Number.isNaN(val)` (в отличие от глобального `isNaN("abc")`, который сначала приводит аргумент к числу).

**Красные флаги:**
- В JSX пишет `{items.length && <List />}` — при `items.length === 0` React отрендерит на экран цифру `0` (нужно `{items.length > 0 && <List />}`).
- Использует `isNaN()` вместо `Number.isNaN()`.

### 3. `var`, `let`, `const`, Hoisting и TDZ (Temporal Dead Zone)

**Зачем спрашивают:** классика любого скрининга; проверяет понимание фаз выполнения кода и блочной области видимости.

**Эталонный ответ:**

| Характеристика | `var` | `let` | `const` |
|----------------|-------|-------|---------|
| **Область видимости** | Функциональная (`function scope`) — не видит границ `if`, `for`, `{}` | Блочная (`block scope`) — любой блок `{ ... }` | Блочная (`block scope`) |
| **Hoisting (всплытие)** | Да, сразу инициализируется `undefined` | Да, но **без инициализации** — попадает в **TDZ** | Да, но **без инициализации** — попадает в **TDZ** |
| **Повторное объявление в том же scope** | Разрешено (`var x = 1; var x = 2;`) | Ошибка `SyntaxError` | Ошибка `SyntaxError` |
| **Переприсваивание** | Разрешено | Разрешено | Запрещено (`TypeError`), но свойства объекта внутри менять можно |
| **Глобальный объект (вне модулей)** | Создаёт свойство в `window` | Не попадает в `window` | Не попадает в `window` |

**Что такое Hoisting на самом деле:**
Код не «перемещается физически наверх файла». Перед выполнением кода функции или блока движок проходит **фазу создания лексического окружения (Creation Phase)** и заранее регистрирует все объявления в памяти:
- **`Function Declaration`** (`function sum() {}`) регистрируется целиком вместе с телом функции — её можно вызывать до строки объявления.
- **`var`** регистрируется и сразу получает значение `undefined`.
- **`let`, `const` и `class`** тоже регистрируются движком (поэтому они **тоже всплывают!**), но остаются в состоянии *uninitialized* до тех пор, пока поток выполнения не дойдёт до строки их объявления.
- **`Function Expression` и стрелочные функции** (`const fn = () => {}`) подчиняются правилам той переменной (`const`/`let`/`var`), в которую они записаны.

**Что такое TDZ (Temporal Dead Zone — временная мёртвая зона):**
Это участок кода от начала блока `{` до строки, где переменная `let` или `const` объявлена. Любое обращение к переменной в этой зоне выбрасывает `ReferenceError: Cannot access 'x' before initialization`.

```js
const x = "outer";
{
  // Здесь для внутренней x уже началась TDZ!
  // Если бы let не всплывал, вывелось бы "outer", но движок уже знает про локальную x:
  console.log(x); // ❌ ReferenceError: Cannot access 'x' before initialization
  let x = "inner";
}
```

**Классический вопрос про цикл с `setTimeout`:**

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3, 3, 3
}

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 0, 1, 2
}
```
Почему: `var i` создаётся один раз на всю внешнюю функцию; к моменту срабатывания таймеров цикл давно закончился и `i === 3`. А `let i` в заголовке `for` по спецификации создаёт **новое лексическое окружение на каждую итерацию цикла**, и каждый колбэк замыкает свою собственную переменную `i`.

### 4. Лексическое окружение, замыкания (Closures) и проблема Stale Closure в React

**Зачем спрашивают:** замыкания — фундамент как для функциональных паттернов в JS (`once`, `debounce`, каррирование), так и для понимания хуков в React.

**Эталонный ответ:**

**Как устроено под капотом (Lexical Environment):**
Каждый раз при вызове функции (или входе в блок `{}`) создаётся внутренний скрытый объект — **Лексическое окружение (Lexical Environment)**, состоящий из двух частей:
1. **Environment Record** — таблица всех локальных переменных, констант и аргументов этой функции.
2. **`[[OuterEnv]]`** — ссылка на внешнее лексическое окружение (то место в коде, где функция была **объявлена**, а не вызвана!).

При создании любая функция получает скрытое свойство `[[Environment]]`, указывающее на то лексическое окружение, где она родилась.

**Определение замыкания:**
**Замыкание (Closure)** — это функция вместе со всеми внешними переменными, которые ей доступны по цепочке `[[Environment]]` → `[[OuterEnv]]`. Когда внешняя функция завершилась, её контекст выполнения удаляется из стека вызовов, но само лексическое окружение **остаётся в памяти (в куче)**, пока жива хотя бы одна вложенная функция, ссылающаяся на него.

```js
function createCounter(initial = 0) {
  let count = initial; // приватная переменная в Environment Record createCounter

  return {
    increment: () => ++count,
    getCount: () => count,
  };
}

const counter = createCounter(10);
counter.increment(); // 11 — напрямую к count снаружи доступа нет
```

**Где замыкания применяются в реальной работе:**
- Инкапсуляция и приватное состояние (фабрики, модули).
- Функции высшего порядка и декораторы: `debounce`, `throttle`, `once`, `memoize`.
- Частичное применение и каррирование, обработчики событий в React (`onClick={() => handleDelete(id)}`).

**Проблема Stale Closure (устаревшего замыкания) в React:**
В функциональном компоненте каждый рендер — это новый вызов функции со своими константами `count`. Если `useEffect` или `useCallback` зафиксировал функцию на первом рендере (`deps: []`), эта функция навсегда смотрит в лексическое окружение первого рендера, где `count === 0`:

```tsx
useEffect(() => {
  const id = setInterval(() => {
    console.log(count); // ❌ Всегда печатает 0 (Stale Closure)!
    setCount(count + 1); // ❌ Всегда ставит 0 + 1 = 1!
  }, 1000);
  return () => clearInterval(id);
}, []);
```

**Как чинить Stale Closure:**
1. Для обновления стейта — использовать функциональный апдейтер: `setCount(prev => prev + 1)`.
2. Указывать честный массив зависимостей `[count]` (тогда эффект пересоздаст таймер/подписку).
3. Если пересоздавать подписку нельзя — хранить актуальное значение в `useRef` (или использовать `useEffectEvent`), так как `ref` — это один и тот же мутабельный объект `{ current }` между всеми рендерами.

**Красные флаги:** говорит просто «функция внутри функции», не может объяснить, почему переменная не удаляется сборщиком мусора и почему в React возникает stale closure.

## Блок 2. Контекст `this` и прототипы

### 5. Как определяется `this`? Стрелочные функции vs обычные, `bind` / `call` / `apply`

**Зачем спрашивают:** проверка понимания динамического контекста в JS и отличия стрелочных функций от `function`.

**Эталонный ответ:**

В обычной функции (`function`) значение `this` **не зависит от того, где функция объявлена**, а определяется исключительно **в момент вызова** по 4 правилам (в порядке убывания приоритета):

1. **Вызов через `new` (конструктор):** `new User()` — `this` указывает на **новый только что созданный объект**.
2. **Явная привязка (`call`, `apply`, `bind`):** `this` равен первому переданному аргументу:
   - `fn.call(context, arg1, arg2)` — вызывает функцию сразу, аргументы через запятую.
   - `fn.apply(context, [arg1, arg2])` — вызывает функцию сразу, аргументы массивом.
   - `const bound = fn.bind(context, arg1)` — **не вызывает** функцию, а возвращает новую функцию-обёртку с навсегда зашитым `this` (повторный `.bind()` или вызов как метода другого объекта уже **не смогут** изменить `this` у `bound`; перебить `bind` может только `new`).
3. **Неявная привязка (вызов как метода объекта):** `obj.method()` — `this` равен объекту **перед точкой** в момент вызова (`obj`). Если цепочка `a.b.c.method()`, то `this === a.b.c`.
4. **Вызов по умолчанию (без точки):** `fn()`:
   - В строгом режиме (`'use strict'`, а также автоматически во всех ES-модулях `import/export` и внутри `class`) — `this === undefined`.
   - В нестрогом режиме — `this` указывает на глобальный объект (`window` в браузере, `globalThis`).

**Чем стрелочные функции `() => {}` отличаются от обычных `function`:**
1. **Нет своего `this`:** стрелка берёт `this` лексически из внешнего окружения в момент своего создания.
2. **`call`, `apply` и `bind` не могут поменять `this` стрелки** (первый аргумент просто игнорируется, работают только остальные аргументы).
3. **Нельзя вызвать с `new`:** у стрелки нет внутреннего метода `[[Construct]]` и нет свойства `.prototype` (`new arrow()` выбросит `TypeError: arrow is not a constructor`).
4. **Нет псевдомассива `arguments`** (вместо него используют rest-параметры `(...args)`).
5. **Нельзя использовать как генератор** (`function*` / `yield`).

**Типичная ловушка — потеря контекста:**
```js
const service = {
  prefix: "[API]",
  log(msg) {
    console.log(this.prefix, msg);
  },
};

setTimeout(service.log, 100); // ❌ Внутрь setTimeout передали саму функцию без объекта → вызов fn() → this === undefined!
setTimeout(() => service.log("ok"), 100); // ✅ Способ 1: обернуть в стрелку
setTimeout(service.log.bind(service, "ok"), 100); // ✅ Способ 2: привязать через bind
```

### 6. Прототипное наследование: `[[Prototype]]` (`__proto__`) vs `.prototype`, `new`, `Object.create(null)`

**Зачем спрашивают:** проверяют, понимает ли кандидат, как реально устроены объекты и классы в JS и почему методы массива доступны на любом `[]`.

**Эталонный ответ:**

**1. Главная путаница: `[[Prototype]]` vs `.prototype`**
- **`[[Prototype]]`** — это скрытое внутреннее свойство **любого объекта** (может быть другим объектом или `null`). Оно указывает на родителя в цепочке прототипов. Читать и задавать его в современном коде нужно через `Object.getPrototypeOf(obj)` и `Object.create(proto)`, а `__proto__` — это исторический геттер/сеттер в `Object.prototype`.
- **`.prototype`** — это обычное свойство, которое есть **только у функций-конструкторов и классов** (у стрелочных функций его нет). Это объект-чертеж, который автоматически записывается в `[[Prototype]]` каждого экземпляра, созданного через `new Fn()`.

Формула, которую ждут на собеседовании:
```js
class User {
  sayHi() {}
}
const u = new User();

console.log(Object.getPrototypeOf(u) === User.prototype); // true!
console.log(Object.getPrototypeOf(User.prototype) === Object.prototype); // true!
console.log(Object.getPrototypeOf(Object.prototype)); // null (конец цепочки)
```

**2. Как работает поиск и запись свойств:**
- **Чтение (`u.toString()`):** движок сначала ищет собственное свойство на самом объекте `u`. Если не находит — идёт по `[[Prototype]]` в `User.prototype`, затем в `Object.prototype`, и так до `null` (если нигде нет — возвращает `undefined`).
- **Запись (`u.name = "Max"`):** всегда создаёт или перезаписывает свойство **на самом объекте `u`**, не трогая прототип (исключение — если в прототипе объявлен `set`-аксессор).
- Проверить, собственное ли свойство (не из прототипа): `Object.hasOwn(obj, 'key')` (современная замена `obj.hasOwnProperty('key')`).

**3. Что делает оператор `new Fn(a, b)` за 4 шага:**
1. Создаёт новый пустой объект `const instance = {}`.
2. Устанавливает его прототип: `Object.setPrototypeOf(instance, Fn.prototype)`.
3. Вызывает функцию `const res = Fn.call(instance, a, b)` с `this === instance`.
4. Если конструктор явно вернул **объект** (`typeof res === 'object' && res !== null` или функцию), возвращается `res`; иначе (если ничего не вернул или вернул примитив) — возвращается `instance`.

**4. Зачем нужен `Object.create(null)`:**
Создаёт чистый словарь вообще без прототипа (`[[Prototype]] === null`). В нём нет унаследованных свойств `toString`, `valueOf`, `constructor`, `__proto__`, поэтому в него безопасно класть произвольные пользовательские ключи без риска коллизий и `prototype pollution`.

## Блок 3. Асинхронность, Event Loop, память и коллекции

### 7. Event Loop: микротаски, макротаски, `requestAnimationFrame` и рендеринг

**Зачем спрашивают:** вопрос №1 на каждом собеседовании по фронтенду. Позволяет понять, знает ли кандидат, почему зависает UI и в каком порядке исполняется асинхронный код.

**Эталонный ответ:**

JavaScript в главном потоке браузера (Main Thread) **однопоточный**: в один момент времени выполняется только одна команда в **Call Stack (стеке вызовов)**. Всю асинхронность обеспечивают браузерные **Web API** (таймеры, сеть, DOM-события) и **Event Loop (цикл событий)**.

**Как устроена одна итерация (тик) Event Loop по шагам:**

```text
[ 1. Call Stack (синхронный код / одна Macrotask) ]
                       │
                       ▼ (стек полностью опустел)
[ 2. Выполнение ВСЕХ Microtasks до полного опустошения очереди ]
  (Promise.then/catch/finally, await, queueMicrotask, MutationObserver)
                       │
                       ▼ (если пора рисовать кадр ~16.6 мс)
[ 3. Рендер-фаза браузера: rAF → Style → Layout → Paint → Composite ]
                       │
                       ▼
[ 4. Берётся ОДНА следующая Macrotask из очереди ]
  (setTimeout, setInterval, DOM events, MessageChannel, I/O)
```

**Критические правила, которые нужно проговорить:**
1. **Сначала всегда синхронный код** до конца текущего скрипта/функции (включая конструктор `new Promise((resolve) => { /* это синхронно! */ })` и код внутри `async`-функции **до первого `await`**).
2. **Все микротаски против одной макротаски:** после каждой макротаски движок выполняет **абсолютно всю** очередь микротасок. Если микротаска во время работы ставит новую микротаску (`Promise.then` внутри `.then`), она выполнится **в этом же тике**, до перехода к рендеру и следующей макротаске!
3. **Когда происходит рендер:** браузер перерисовывает экран **после** очистки очереди микротасок и **между** макротасками.
   - `requestAnimationFrame(cb)` выполняется прямо **перед** пересчётом стилей и отрисовкой кадра (идеально для плавных анимаций).
   - Если забить поток рекурсивным `queueMicrotask`, вкладка намертво зависнет (браузер никогда не дойдёт до шага 3). А если планировать через `setTimeout(..., 0)`, между вызовами браузер сможет прорисовывать интерфейс.

**Follow-up:** Почему `setTimeout(fn, 0)` выполняется не через 0 мс, а через 1–4+ мс?  
→ Во-первых, он ждёт опустошения Call Stack и всех микротасок. Во-вторых, по спецификации HTML после 5 вложенных таймеров браузер принудительно ставит минимальную задержку **не менее 4 мс** (а в фоновых вкладках — до 1000 мс и выше для экономии батареи).

### 8. `Promise`, `async/await` и сравнение `all` / `allSettled` / `race` / `any`

**Зачем спрашивают:** базовая работа с сетью и асинхронной логикой.

**Эталонный ответ:**

**1. Устройство и состояния `Promise`:**
Промис — это объект-контейнер для результата отложенной операции. Имеет 3 состояния:
- `pending` (ожидание)
- `fulfilled` (успешно выполнен со значением `value`)
- `rejected` (отклонён с ошибкой `reason`)

Переход из `pending` происходит **только один раз** (состояние становится *settled* — неизменным; все последующие вызовы `resolve()`/`reject()` внутри конструктора игнорируются).

**2. Тонкости цепочек `.then / .catch / .finally`:**
- Каждый `.then` и `.catch` возвращает **новый промис**.
- Если колбэк внутри `.catch()` возвращает обычное значение (и не кидает `throw`), цепочка **восстанавливается** и следующий `.then()` получит это значение как успешное!
- `.finally(cb)` выполняется всегда, **не принимает аргументов** (`cb()` вызывается без параметров) и прозрачно **пробрасывает дальше** предыдущий результат или ошибку (если только сам `finally` не бросит `throw`).

**3. Таблица статических методов `Promise`:**

| Метод | Когда резолвится (`fulfilled`) | Когда падает (`rejected`) | Типичный кейс в продакшене |
|-------|--------------------------------|---------------------------|----------------------------|
| `Promise.all(iter)` | Когда **все** промисы успешны (возвращает массив результатов в порядке передачи) | **Сразу же** при падении любого первого промиса (остальные запросы при этом в сети сами не отменяются!) | Загрузить страницу, которой обязательно нужны и профиль, и настройки, и корзина. |
| `Promise.allSettled(iter)` | Когда **все** завершились (любым исходом). Возвращает массив `{ status: 'fulfilled', value } \| { status: 'rejected', reason }` | **Никогда не падает** | Дашборд с 5 независимыми виджетами: если один упал, остальные 4 нужно показать. |
| `Promise.race(iter)` | Когда завершился **самый первый** промис (если он успешен) | Когда завершился **самый первый** промис (если он упал) | Ограничение запроса по таймауту (`Promise.race([fetch(), timeout(3000)])`). |
| `Promise.any(iter)` | Когда успешно завершился **первый успешный** (`fulfilled`) | Только если **все** промисы упали — бросает `AggregateError` со списком всех ошибок в `err.errors` | Запрос к 3 зеркалам CDN: берём ответ от самого быстрого рабочего сервера. |

**4. Ловушка `return fn()` vs `return await fn()` в `try/catch`:**
```js
async function loadData() {
  try {
    return fetchUser(); // ❌ ОПАСНО: возвращаем промис напрямую без ожидания!
    // Если fetchUser() отклонится, ошибка полетит наружу, МИМО этого catch!
  } catch (e) {
    console.error("Локальная обработка", e);
  }
}
```
Внутри `try/catch` обязательно писать **`return await fetchUser()`**, чтобы отказ промиса был перехвачен локальным блоком `catch`.

### 9. Отмена запросов (`AbortController`), гонки (Race Conditions), `debounce` и `throttle`

**Зачем спрашивают:** проверяют, умеет ли кандидат писать надёжный UI для поиска, фильтров и переключения вкладок.

**Эталонный ответ:**

**1. Почему возникает гонка запросов (Race Condition):**
Пользователь вводит в поиск `"re"`, уходит запрос №1 (медленный, 800 мс). Через 100 мс он допечатывает `"react"`, уходит запрос №2 (быстрый, 150 мс).
Ответ №2 приходит первым и рисует результаты для `"react"`. Затем доезжает старый ответ №1 и **затирает** экран устаревшими результатами для `"re"`.

**2. Как правильно отменять запросы через `AbortController` в React:**

```tsx
useEffect(() => {
  const controller = new AbortController();

  async function search() {
    try {
      const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
        signal: controller.signal, // привязываем сигнал отмены
      });
      const data = await res.json();
      setResults(data);
    } catch (err) {
      // При отмене fetch кидает AbortError — это штатная ситуация, не ошибка UI!
      if (err instanceof DOMException && err.name === "AbortError") return;
      setError(err);
    }
  }

  search();

  // При смене query или размонтировании отменяем предыдущий запрос:
  return () => controller.abort();
}, [query]);
```
*Примечание:* TanStack Query (React Query) автоматически передаёт `signal` в `queryFn: ({ signal }) => fetch(url, { signal })` и сам отменяет устаревшие запросы.

**3. `debounce` против `throttle`:**
- **`debounce(fn, delay)` (устранение дребезга):** откладывает вызов `fn` до тех пор, пока с момента **последнего** вызова не пройдёт `delay` мс. Каждый новый вызов сбрасывает таймер.
  - *Где:* поисковая строка (ждём, пока пользователь допечатает слово), автосохранение текста в редакторе, валидация на сервере.
- **`throttle(fn, interval)` (дросселирование):** гарантирует, что `fn` вызывается **не чаще одного раза** в `interval` мс, даже если событие стреляет 100 раз в секунду.
  - *Где:* обработка `scroll` (подгрузка ленты, параллакс), `resize` окна, движение мыши `mousemove` (drag-and-drop), ограничение частоты кликов по кнопке.

### 10. `Map` / `Set` vs `Object` / `Array`, `WeakMap` и `WeakSet`

**Зачем спрашивают:** проверяют знание структур данных, алгоритмической сложности и работы со слабыми ссылками.

**Эталонный ответ:**

**1. Чем `Map` отличается от обычного `Object`:**

| Критерий | `Map` | `Object` `{}` |
|----------|-------|---------------|
| **Типы ключей** | **Любые** (примитивы, объекты, функции, DOM-элементы) | Только `string` и `symbol` (числа и объекты приводятся к строке: `obj[{}] → obj["[object Object]"]`) |
| **Количество элементов** | `map.size` за $O(1)$ | `Object.keys(obj).length` за $O(n)$ |
| **Порядок ключей** | Строго порядок вставки | Числовые ключи (`"1"`, `"2"`) всплывают наверх по возрастанию, затем строковые по порядку вставки |
| **Чистота ключей** | Пуст из коробки | Наследует ключи `Object.prototype` (`toString`, `constructor`), если не создан через `Object.create(null)` |
| **Производительность** | Оптимизирован под частые добавления и удаления ключей | Лучше для статических структур (движок V8 строит для них Hidden Classes / Shapes) |
| **Сериализация в JSON** | Не сериализуется напрямую (`JSON.stringify(new Map())` → `"{}"`) | Нативная поддержка `JSON.stringify` / `JSON.parse` |

**2. Чем `Set` отличается от `Array`:**
- `Set` хранит **только уникальные значения** (сравнение по алгоритму `SameValueZero` — как `Object.is`, но `+0` и `-0` считаются равными, а `NaN` равен `NaN`).
- Проверка наличия элемента **`set.has(val)` и удаление `set.delete(val)` работают за $O(1)$** (хэш-таблица), тогда как `arr.includes(val)` и `arr.splice()` требуют полного перебора за **$O(n)$**.

**3. Зачем нужны `WeakMap` и `WeakSet`:**
В обычном `Map` ссылка на объект-ключ **сильная (strong)**: пока объект лежит ключом в `Map`, сборщик мусора **никогда его не удалит**, даже если в остальной программе ссылок на него больше нет (классическая утечка памяти).

В `WeakMap` и `WeakSet`:
- Ключами в `WeakMap` (и значениями в `WeakSet`) могут быть **только объекты** (и нерегистрированные символы).
- Ссылки на эти объекты — **слабые (weak)**: если на объект больше нет сильных ссылок из кода, сборщик мусора спокойно удаляет объект из памяти, и запись в `WeakMap` исчезает автоматически.
- **Следствие:** у `WeakMap` / `WeakSet` **нет `.size` и по ним нельзя итерироваться** (`keys()`, `values()`, `for..of` отсутствуют), потому что состав коллекции зависит от непредсказуемого момента срабатывания GC.

**Практический пример `WeakMap`:**
Кэширование тяжёлых вычислений для объекта пользователя или хранение приватных метаданных для DOM-узла. Когда DOM-узел удаляется со страницы или объект `user` заменяется новым, кэш очищается сам без ручного `.delete()`.

```js
const cache = new WeakMap();

function getHeavyMetrics(userObj) {
  if (cache.has(userObj)) return cache.get(userObj);
  const result = computeExpensiveMetrics(userObj);
  cache.set(userObj, result);
  return result;
}
```

### 11. Сборщик мусора (GC) и 4 главные причины утечек памяти во фронтенде

**Зачем спрашивают:** проверяют, понимает ли кандидат, как работает память в браузере и почему SPA начинает тормозить после часа работы.

**Эталонный ответ:**

**1. Как работает Garbage Collector в V8:**
Используется алгоритм **достижимости (Mark-and-Sweep — «пометь и подмети»)**:
- Есть базовое множество **корней (Roots)**, которые нельзя удалить: глобальные переменные (`window`), локальные переменные и аргументы функций в текущем стеке вызовов, активные таймеры и DOM-дерево.
- Сборщик мусора стартует от корней, проходит по всем ссылкам и помечает каждый достижимый объект как «живой».
- Все непомеченные объекты (даже если два объекта ссылаются друг на друга в цикле `a.ref = b; b.ref = a`, но из корней до них добраться нельзя!) удаляются, а память освобождается.
- *Дополнительно для Middle+:* V8 делит кучу на поколения (**Generational GC**): **Young Generation (Nursery)** для короткоживущих объектов (очищается очень быстро частым Minor GC / Scavenger) и **Old Generation** для объектов, переживших несколько сборок (очищается более тяжёлым Major GC).

**2. 4 главные причины утечек памяти в React / SPA:**
1. **Забытые таймеры и интервалы (`setInterval`, `setTimeout`):** пока интервал не остановлен через `clearInterval`, его колбэк считается корнем и удерживает в памяти всё своё замыкание (включая стейт и ссылки на компонент).
2. **Неснятые подписки на внешние источники:** `window.addEventListener('resize', onResize)`, подписки на WebSocket, Event Bus, `IntersectionObserver` или сторонние сторы без `removeEventListener` / `disconnect()` в функции очистки `useEffect`.
3. **Неограниченные глобальные кэши и замыкания:** складывание данных в модульный `const cache = new Map()` или массив логов без лимита размера (LRU) и без очистки.
4. **Оторванные DOM-узлы (Detached DOM Elements):** узел удалили из документа (`el.remove()`), но ссылка на него (или на его дочерний узел) осталась лежать в JS-переменной или ref. Из-за ссылок на родителя (`parentNode`) один сохранённый `<td>` может удерживать в памяти всю удалённую таблицу целиком.

**Как искать утечку:** вкладка **Memory** в Chrome DevTools → снять **Heap Snapshot** до открытия модалки/страницы → открыть и закрыть несколько раз → нажать иконку корзины (Force GC) → снять второй Heap Snapshot и выбрать режим **Comparison** (или фильтр `Detached`).

### 12. Методы массивов (мутация vs иммутабельность) и события DOM (делегирование)

**Эталонный ответ:**

**1. Мутирующие vs немутирующие методы массивов:**

| Мутируют исходный массив (менять в стейте нельзя!) | Не мутируют (возвращают новый массив) | Современная иммутабельная замена (ES2023) |
|----------------------------------------------------|---------------------------------------|-------------------------------------------|
| `push`, `pop`, `shift`, `unshift` | `concat`, `[...arr, item]`, `slice` | — |
| `sort(compareFn)` | — | **`arr.toSorted(compareFn)`** |
| `reverse()` | — | **`arr.toReversed()`** |
| `splice(start, deleteCount, ...items)` | `slice(start, end)` (только вырезка) | **`arr.toSpliced(start, deleteCount, ...items)`** |
| `fill(value)` | `map`, `filter`, `flat`, `flatMap` | **`arr.with(index, newValue)`** (вместо `arr[i] = val`) |

**Подвох с `.sort()`:** по умолчанию `[10, 2, 100].sort()` сортирует элементы **как строки по UTF-16 кодам** и возвращает `[10, 100, 2]` (при этом мутируя исходный массив!). Для чисел обязательно передавать компаратор: `arr.toSorted((a, b) => a - b)`.

**2. События в браузере (Bubbling, Capturing, Delegation):**
- **3 фазы распространения события:**
  1. **Capturing (перехват / погружение):** событие идёт сверху вниз от `window` → `document` → `body` до целевого элемента. Чтобы поймать событие на этой фазе, передают `{ capture: true }` третьим аргументом в `addEventListener`.
  2. **Target (цель):** событие дошло до самого элемента.
  3. **Bubbling (всплытие):** событие поднимается обратно вверх до `window` (по умолчанию все обработчики срабатывают именно здесь). Не всплывают только специфические события вроде `focus`/`blur` (у них есть всплывающие аналоги `focusin`/`focusout`), `scroll`, `mouseenter`/`mouseleave`.
- **`event.target` vs `event.currentTarget`:**
  - `event.target` — самый глубокий элемент, по которому реально кликнули (например, `<span>` с иконкой внутри кнопки).
  - `event.currentTarget` — элемент, на котором висит текущий обработчик (например, `<button>`).
- **`stopPropagation()` vs `preventDefault()`:**
  - `e.stopPropagation()` останавливает движение события дальше по дереву DOM (`stopImmediatePropagation()` ещё и отменяет остальные обработчики на том же элементе).
  - `e.preventDefault()` отменяет стандартное действие браузера (переход по `<a href>`, перезагрузку при `submit` формы, скролл при `touchmove` — если слушатель не `{ passive: true }`).
- **Делегирование событий (Event Delegation):** вместо 1000 обработчиков на каждый `<li>` вешаем один обработчик на `<ul>` и находим нужный пункт через `const item = e.target.closest('li')`.

## Блок 4. Система типов, сужение и контракты

### 13. Зачем нужен TypeScript, что такое Type Erasure и почему `as User` на ответе API опасен?

**Зачем спрашивают:** проверяют понимание границы между compile-time и runtime.

**Эталонный ответ:**
- **Compile-time vs Runtime:** TypeScript работает **только на этапе компиляции и в IDE**. При сборке в JS происходит **Type Erasure (полное стирание типов)** — все `interface`, `type`, дженерики и модификаторы доступа (`private`/`protected`) бесследно удаляются.
- **Почему `(await res.json()) as User` — антипаттерн:**
  Оператор `as` (type assertion) не конвертирует данные и не добавляет никаких проверок в рантайме — он просто приказывает компилятору «поверь мне на слово». Если бэкенд поменял контракт (прислал `user_name` вместо `userName` или `null` вместо массива), TS промолчит, а приложение упадёт с `Cannot read properties of undefined` уже у пользователя в браузере.
- **Как правильно на границе с внешним миром (`fetch`, `JSON.parse`, `localStorage`, `postMessage`):**
  1. Считать входные данные типом `unknown`.
  2. Прогонять через runtime-валидатор схем (**Zod**, **Valibot**, **ArkType**), который и проверит данные в рантайме, и автоматически выведет TS-тип (`z.infer<typeof UserSchema>`), либо через честный пользовательский **type guard**.

**Красные флаги:** думает, что типы существуют в браузере и по ним можно сделать `if (x instanceof MyInterface)`; лепит `as` при любой ошибке типов.

### 14. Разница между `any`, `unknown`, `never` и `void`

**Зачем спрашивают:** топ-1 вопрос по базе TypeScript; проверяет понимание иерархии типов (top types vs bottom type).

**Эталонный ответ:**

| Тип | Роль в системе типов | Что можно присвоить в него? | Что можно делать со значением? | Где применять? |
|-----|----------------------|-----------------------------|--------------------------------|----------------|
| **`any`** | Отключение системы типов | Что угодно | Что угодно (`x.foo.bar()`, передать в любую функцию) — **заражает** код вокруг | Почти нигде (только временная миграция легаси) |
| **`unknown`** | Безопасный **Top Type** (супертип всех типов) | Что угодно | **Ничего**, пока тип явно не сужен (`typeof`, `instanceof`, type guard) | `catch (err: unknown)`, результат `JSON.parse`, внешние API |
| **`never`** | **Bottom Type** (пустое множество значений) | Ничего (кроме самого `never`) | Значения этого типа в рантайме никогда не существует | Функции, которые всегда кидают `throw`, и **exhaustive check** в `switch` |
| **`void`** | Отсутствие возвращаемого значения | `undefined` | Вызвать функцию ради сайд-эффекта и не использовать её результат | Функции-обработчики `onClick: () => void` |

**Два важных нюанса, которые выделяют сильного кандидата:**
1. **Почему в `catch` должен быть `unknown`:** в JS можно сделать `throw "строка"` или `throw { code: 500 }`, поэтому в `strict`-режиме переменная ошибки имеет тип `unknown`. Перед чтением `err.message` обязательно сузить: `if (err instanceof Error) console.log(err.message)`.
2. **Особенность `() => void` в типах колбэков:** если функция типизирована как `type Cb = () => void`, TypeScript **разрешает** передать туда функцию, которая реально что-то возвращает (например, `items.forEach(item => result.push(item))`, где `.push()` возвращает `number`). Здесь `void` означает: «вызывающий код обязуется игнорировать возвращаемое значение». Но если объявить саму функцию с явным возвратом `function fn(): void { return 123; }` — это будет ошибкой компиляции.

### 15. Union (`|`), Intersection (`&`), Discriminated Unions и Exhaustive Check через `never`

**Зачем спрашивают:** проверяют умение моделировать состояния приложения без багов.

**Эталонный ответ:**

**1. Union (`A | B`) vs Intersection (`A & B`):**
- **Union (`A | B`):** значение может быть либо типом `A`, либо типом `B`. Без сужения доступны **только общие** для обоих типов свойства.
- **Intersection (`A & B`):** тип объединяет **все свойства** и из `A`, и из `B`.
  - *Подвох при конфликте полей:* если в `A` поле `id: string`, а в `B` поле `id: number`, то у `A & B` поле `id` получит тип `string & number`, что схлопывается в **`never`**!

**2. Discriminated Unions (размеченные объединения):**
Вместо объекта с кучей опциональных полей `{ loading?: boolean; data?: User; error?: string }` (который допускает невозможные состояния вроде `loading: true` и `error: "500"` одновременно) создаётся Union с общим литеральным полем-дискриминантом (`status` или `type`):

```ts
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };
```

**3. Exhaustive Check (проверка исчерпываемости через `never`):**
Позволяет заставить компилятор ругаться, если кто-то добавил в `RequestState` новый статус (например, `"retrying"`), но забыл обработать его в `switch`:

```ts
function assertNever(value: never): never {
  throw new Error(`Необработанный вариант: ${JSON.stringify(value)}`);
}

function renderStatus<T>(state: RequestState<T>): string {
  switch (state.status) {
    case "idle":
      return "Ожидание";
    case "loading":
      return "Загрузка...";
    case "success":
      return `Данные загружены`; // здесь TS точно знает, что есть state.data
    case "error":
      return state.message;      // здесь TS точно знает, что есть state.message
    default:
      // Если все кейсы разобраны, тип state здесь сузился до never.
      // Если добавить новый статус и забыть case — TS выдаст ошибку компиляции прямо на этой строке!
      return assertNever(state);
  }
}
```

### 16. Все способы сужения типов (Type Narrowing) и пользовательские Type Guards (`is`, `asserts`)

**Эталонный ответ:**

Type Narrowing — это процесс, при котором TypeScript на основе проверок в коде сужает широкий тип (`unknown` или `A | B`) до конкретного подтипа внутри ветки `if` / `switch`.

**Основные способы сужения:**
1. **`typeof` (для примитивов):** `if (typeof x === "string")`. *(Помним, что `typeof null === "object"`, поэтому `typeof x === "object"` не отсекает `null`!).*
2. **Проверка на truthiness / равенство:** `if (x !== null && x !== undefined)` или `if (!x) return`.
3. **Оператор `in` (проверка наличия ключа в объекте):** `if ("swim" in animal)`.
4. **`instanceof` (проверка прототипа класса):** `if (err instanceof Error)`.
5. **`Array.isArray(x)`:** сужает до массива.
6. **Проверка поля-дискриминанта:** `if (action.type === "LOGIN_SUCCESS")`.
7. **Пользовательский Type Guard (`param is Type`):**
   Когда проверка вынесена в отдельную функцию, обычный возврат `boolean` не сузит тип снаружи. Нужен **предикат типа (`x is User`)**:

```ts
interface User {
  id: number;
  name: string;
}

function isUser(val: unknown): val is User {
  return (
    typeof val === "object" &&
    val !== null &&
    "id" in val &&
    typeof (val as Record<string, unknown>).id === "number" &&
    "name" in val &&
    typeof (val as Record<string, unknown>).name === "string"
  );
}

// Бонус: в фильтрации массивов с TS < 5.5 предикат убирает undefined:
const validUsers: User[] = rawItems.filter(isUser);
```

### 17. Чем отличаются `type` и `interface`? Что выбирать?

**Эталонный ответ:**

В 90% описания обычных объектов `type` и `interface` взаимозаменяемы, но между ними есть **4 принципиальных отличия**:

| Возможность | `type` (Type Alias) | `interface` |
|-------------|---------------------|-------------|
| **Какие типы может описывать** | **Любые:** примитивы, Union (`A \| B`), кортежи (`[number, string]`), функции, Mapped Types (`[K in keyof T]`), Conditional Types | **Только объектные структуры** (и функции как вызываемые объекты) |
| **Declaration Merging (слияние объявлений)** | **Нет:** два `type User` в одной области дадут `Duplicate identifier` | **Да:** два `interface User` автоматически сольются в один интерфейс |
| **Расширение (`extends` vs `&`)** | Через пересечение `type Admin = User & { role: string }`. При конфликте типов одного поля ошибки в месте объявления не будет — поле молча станет `never`! | Через `interface Admin extends User`. При конфликте типов поля TS **сразу выдаст явную ошибку** и быстрее кеширует проверку типов |
| **Работа с `implements` в классах** | Можно (`class A implements MyType`), кроме union-типов | Можно (`class A implements MyInterface`) |

**Когда обязательно нужен `interface`:**
Когда нужно дополнить глобальные типы (`Window`, `ImportMetaEnv`) или расширить типы сторонней библиотеки через **Declaration Merging**:

```ts
declare global {
  interface Window {
    __APP_CONFIG__?: { apiUrl: string };
  }
}
```

### 18. Литеральные типы, `as const` и оператор `satisfies`

**Эталонный ответ:**

**1. Почему происходит расширение типа (Type Widening):**
- `const method = "GET"` имеет литеральный тип `"GET"`, потому что константу нельзя переприсвоить.
- Но в объекте `const req = { url: "/api", method: "GET" }` поле `req.method` выводится как широкий `string`, потому что свойства объекта мутабельны (`req.method = "POST"` разрешено в JS). Из-за этого `fetch(req.url, { method: req.method })` может ругаться, если ждёт узкий тип `'GET' | 'POST'`.

**2. Что делает `as const` (Const Assertion):**
Замораживает тип на уровне компилятора:
- все свойства объекта на любой глубине становятся `readonly`;
- все строки, числа и булевы значения сужаются до **точных литеральных типов** (`"GET"`, `200`);
- массивы превращаются в фиксированные **`readonly`-кортежи** (`readonly ["admin", "user"]`).

```ts
export const ROLES = ["admin", "editor", "viewer"] as const;
// ROLES имеет тип: readonly ["admin", "editor", "viewer"]
// Получить union всех элементов кортежа:
export type Role = (typeof ROLES)[number]; // "admin" | "editor" | "viewer"
```

**3. Зачем появился оператор `satisfies` (TS 4.9+) и чем он лучше `: Type` и `as Type`:**
- Если написать **аннотацию** `const theme: Record<string, string | string[]> = { primary: "#0055ff", shades: ["#111", "#222"] }`, TypeScript **забудет** точные ключи и типы каждого поля — для `theme.primary.toUpperCase()` придётся делать сужение, потому что тип расширился до `string | string[]`.
- Если написать **`as`**, можно случайно соврать компилятору и пропустить ошибку.
- Оператор **`satisfies`** проверяет, что объект соответствует контракту (ловит опечатки и неверные типы значений), но **сохраняет самый узкий выведенный тип каждого поля**:

```ts
type Palette = Record<"primary" | "secondary", string | [number, number, number]>;

const palette = {
  primary: "#0055ff",
  secondary: [255, 128, 0],
} satisfies Palette;

palette.primary.toUpperCase(); // ✅ TS точно знает, что primary — это string!
palette.secondary.map((n) => n); // ✅ TS точно знает, что secondary — это кортеж чисел!
```

## Блок 5. Дженерики, Utility Types, `infer` и React

### 19. Generics и связка `extends`, `keyof`, `typeof`, `T[K]`

**Эталонный ответ:**

**Дженерики (Generics)** — это параметры типа (как аргументы функции, но на уровне типов), которые позволяют писать универсальный код, **сохраняя связь между типами аргументов и возвращаемого результата**.

Четыре строительных кирпича, которые спрашивают вместе с дженериками:
1. **`extends` (Constraint / ограничение):** сужает допустимый набор типов для параметра `T` (`<T extends { id: string }>`).
2. **`keyof T`:** возвращает union всех публичных ключей типа `T` (`keyof { a: number; b: string }` → `"a" | "b"`).
3. **`typeof val` (в позиции типа):** получает TS-тип из рантайм-значения (объекта конфига, функции, Zod-схемы).
4. **`T[K]` (Indexed Access / Lookup Type):** получает тип значения свойства `K` внутри типа `T` (по аналогии с обращением `obj[key]` в JS).

**Классический пример — типобезопасный геттер свойства:**
```ts
function getProperty<T extends object, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const product = { id: 42, title: "Laptop", inStock: true };
const title = getProperty(product, "title"); // тип автоматически: string
// getProperty(product, "price"); // ❌ Ошибка компиляции: "price" нет в keyof typeof product
```

### 20. Ходовые Utility Types и как они написаны под капотом (Mapped Types)

**Зачем спрашивают:** на собесах постоянно просят объяснить разницу между `Omit` и `Exclude` и написать руками `Partial` или `Pick`.

**Эталонный ответ:**

**1. Утилиты для работы с объектами (через Mapped Types `[K in ...]`):**

```ts
// Делает все поля необязательными
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};

// Делает все поля обязательными (модификатор -? снимает опциональность)
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
};

// Делает все поля верхнего уровня доступными только для чтения
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

// Оставляет в объекте T только выбранные ключи K
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// Удаляет из объекта T указанные ключи K
type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;

// Создаёт объект-словарь с ключами K и значениями V
type MyRecord<K extends keyof any, V> = {
  [P in K]: V;
};
```

**2. Утилиты для работы с Union-типами (важно не путать с `Pick` / `Omit`!):**
- **`Pick` и `Omit` работают со свойствами объекта (`{ a: 1, b: 2 }`)**.
- **`Exclude` и `Extract` работают с элементами объединения (`"a" | "b" | "c"`)**:
  - `Exclude<T, U>` — вычитает из union `T` все типы, подходящие под `U` (`Exclude<"a" | "b" | "c", "a">` → `"b" | "c"`).
  - `Extract<T, U>` — оставляет в union `T` только те типы, которые подходят под `U`.
  - `NonNullable<T>` — убирает `null` и `undefined` из типа (`Exclude<T, null | undefined>`).

**3. Утилиты для функций и промисов:**
- `ReturnType<typeof fn>` — вытаскивает возвращаемый тип функции `fn`.
- `Parameters<typeof fn>` — возвращает кортеж типов аргументов функции `fn`.
- `Awaited<T>` — рекурсивно разворачивает тип промиса (`Awaited<Promise<User>>` → `User`, нужно для `Awaited<ReturnType<typeof fetchUser>>`).

### 21. Conditional Types (`T extends U ? X : Y`) и ключевое слово `infer`

**Эталонный ответ:**
- **Conditional Types (условные типы)** позволяют выбирать результирующий тип в зависимости от условия совместимости типов: `T extends U ? TrueType : FalseType`.
- Если `T` — это параметрический union-тип (например, `"a" | "b"`), условный тип работает **дистрибутивно** — применяется к каждому элементу объединения по отдельности (именно так устроен `Exclude<T, U> = T extends U ? never : T`).
- **Ключевое слово `infer`** используется только в правой части условия `extends` и позволяет объявить переменную типа «на лету», чтобы **извлечь (распаковать)** внутренний тип из сложной обёртки:

```ts
// 1. Как устроен ReturnType:
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;

// 2. Вытащить тип первого аргумента функции:
type FirstArg<F> = F extends (first: infer A, ...rest: any[]) => any ? A : never;

// 3. Распаковать значение из Promise или массива:
type Unwrap<T> = T extends Promise<infer U>
  ? U
  : T extends (infer Item)[]
    ? Item
    : T;
```

### 22. Практика: типизация компонентов, пропсов, событий и хуков в React

**Эталонный ответ:**

**1. `React.ReactNode` vs `React.ReactElement` (`JSX.Element`):**
- **`React.ReactNode`** — самый широкий тип для пропа `children`: включает JSX-элементы, строки, числа, массивы, фрагменты, `null`, `undefined`, `boolean`. Для `children` почти всегда используют именно `ReactNode`.
- **`React.ReactElement`** — только результат вызова `React.createElement` / JSX-тега (`<div />`), примитивы и `null` туда не входят.

**2. Как правильно типизировать обёртку над нативным HTML-элементом (например, `Button` или `Input`):**
Используем `React.ComponentPropsWithoutRef<"button">` (или `React.ComponentProps<"button">` в React 19, где `ref` передаётся как обычный проп):

```tsx
type ButtonProps = React.ComponentPropsWithoutRef<"button"> & {
  variant?: "primary" | "secondary";
  isLoading?: boolean;
};

export function Button({ variant = "primary", isLoading, children, ...rest }: ButtonProps) {
  return (
    <button {...rest} disabled={rest.disabled || isLoading}>
      {isLoading ? "Загрузка..." : children}
    </button>
  );
}
```
Если у нас есть свой проп `onChange: (value: string) => void`, который конфликтует с нативным `onChange` у `<input>`, используем `Omit`:
`type CustomInputProps = Omit<React.ComponentPropsWithoutRef<"input">, "onChange"> & { onChange: (val: string) => void }`.

**3. Типизация событий и `useRef`:**
- **События:**
  - `React.ChangeEvent<HTMLInputElement>`
  - `React.MouseEvent<HTMLButtonElement>`
  - `React.FormEvent<HTMLFormElement>` (или `React.SubmitEvent`)
  - `React.KeyboardEvent<HTMLInputElement>`
- **Два режима `useRef`:**
  - `const inputRef = useRef<HTMLInputElement>(null)` — ссылка на DOM-элемент.
  - `const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null)` — мутабельный контейнер для хранения значения между рендерами без вызова перерисовки.

## Задача 1 (JS: `this` и замыкания). Потеря контекста и стрелка в классе

**Условие:** Что выведет код в каждом из 5 вызовов и почему?

```js
const user = {
  name: "Alice",
  greetArrow: () => console.log("1:", this?.name),
  greetFn() {
    console.log("2:", this?.name);
  },
};

user.greetArrow();
user.greetFn();

const { greetFn } = user;
greetFn();

class Timer {
  seconds = 10;
  tickArrow = () => console.log("4:", this.seconds);
  tickFn() {
    console.log("5:", this?.seconds);
  }
}

const timer = new Timer();
const { tickArrow, tickFn } = timer;
tickArrow();
tickFn();
```

<details>
<summary><b>Подробный разбор и ответ</b></summary>

1. `user.greetArrow()` → **`1: undefined`**  
   У стрелочной функции нет своего `this` — она берёт его из внешнего лексического окружения. Фигурные скобки объекта `const user = { ... }` **не создают** своего `this` или области видимости, поэтому `this` берётся с уровня модуля (`undefined` в ES-модуле) или `window`.
2. `user.greetFn()` → **`2: Alice`**  
   Обычный метод вызван через точку `user.greetFn()`, поэтому `this === user`.
3. `greetFn()` → **`2: undefined`**  
   При деструктуризации `const { greetFn } = user` мы скопировали ссылку на саму функцию и вызвали её без точки (`greetFn()`). В строгом режиме `this === undefined`.
4. `tickArrow()` → **`4: 10`**  
   Поле класса `tickArrow = () => ...` инициализируется **внутри конструктора `new Timer()`**, где `this` равен создаваемому экземпляру `timer`. Стрелка навсегда замыкает этот `this`, поэтому даже после деструктуризации `tickArrow()` помнит свой экземпляр. *(Цена такого приёма: функция создаётся заново на каждом экземпляре класса, а не лежит в одном экземпляре на `Timer.prototype`).*
5. `tickFn()` → **`5: undefined`**  
   Обычный метод класса лежит на `Timer.prototype` и определяет `this` в момент вызова. Вызов без точки даёт `this === undefined`.
</details>

## Задача 2 (JS: Event Loop). Порядок вывода с `async/await`, `Promise` и `setTimeout`

**Условие:** В каком порядке выведутся числа?

```js
console.log(1);

setTimeout(() => console.log(2), 0);

async function run() {
  console.log(3);
  await Promise.resolve();
  console.log(4);
}

run();

Promise.resolve()
  .then(() => {
    console.log(5);
    throw new Error("boom");
  })
  .then(() => console.log(6))
  .catch(() => console.log(7));

console.log(8);
```

<details>
<summary><b>Подробный разбор и ответ</b></summary>

**Ответ:** `1, 3, 8, 4, 5, 7, 2` (число `6` не выведется никогда).

**Пошагово по очередям:**
1. **Синхронный стек (Call Stack):**
   - `console.log(1)` → печатает **`1`**.
   - `setTimeout(..., 0)` → планирует макротаску `(2)`.
   - Вызов `run()`: код внутри `async`-функции **до первого `await` выполняется синхронно!** Поэтому сразу печатается **`3`**.
   - `await Promise.resolve()` приостанавливает `run()` и ставит её продолжение (`console.log(4)`) в очередь микротасок: `Microtasks: [log(4)]`.
   - `Promise.resolve().then(...)` ставит первый `.then` в очередь микротасок: `Microtasks: [log(4), log(5)+throw]`.
   - `console.log(8)` → печатает **`8`**. Синхронный стек пуст.
2. **Очередь микротасок (выгребается полностью):**
   - Выполняется продолжение `run()` → печатает **`4`**.
   - Выполняется первый `.then`: печатает **`5`** и выбрасывает `throw new Error("boom")`.
   - Из-за выброшенной ошибки промис переходит в `rejected`, поэтому `.then(() => console.log(6))` **пропускается**, а колбэк `.catch(() => console.log(7))` ставится в очередь микротасок и тут же выполняется → печатает **`7`**.
3. **Макротаска:**
   - Срабатывает колбэк `setTimeout` → печатает **`2`**.
</details>

## Задача 3 (JS: Замыкания). Декоратор `once(fn)` и `callLimit(fn, limit)`

**Условие:** Напиши функцию `once(fn)`, которая позволяет вызвать переданную функцию `fn` только один раз. Все последующие вызовы должны возвращать результат первого вызова, не вызывая `fn` повторно (с сохранением аргументов и контекста `this`).

```js
function once(fn) {
  // TODO
}

const init = once((x) => {
  console.log("Инициализация!");
  return x * 2;
});

console.log(init(5));  // "Инициализация!", 10
console.log(init(99)); // 10 (без повторного вызова)
```

<details>
<summary><b>Решение и важные тонкости</b></summary>

```js
function once(fn) {
  let called = false;
  let result;

  return function (...args) {
    if (!called) {
      called = true;
      result = fn.apply(this, args);
      fn = null; // бонус: освобождаем ссылку на исходную функцию для GC
    }
    return result;
  };
}
```

**Два частых вопроса от интервьюера:**
1. *Почему нельзя проверять `if (result === undefined)` без флага `called`?* — Потому что целевая функция `fn` может легально вернуть `undefined` при первом вызове, и тогда она ошибочно вызовется во второй раз.
2. *Почему возвращаем обычную `function (...args)`, а не стрелку?* — Чтобы сохранить динамический `this`, если обёрнутую функцию положат методом в объект (`obj.init = once(...)`) и передавать его через `fn.apply(this, args)`.
</details>

## Задача 4 (JS: Асинхронность). `withTimeout` и `retry` для промисов

**Условие:** Реализуй обёртку `withTimeout(promise, ms)`, которая резолвится результатом `promise`, если он успел за `ms` миллисекунд, иначе отклоняется с `new Error('Timeout')`. Не забудь очистить таймер после завершения!

```js
function withTimeout(promise, ms) {
  // TODO
}
```

<details>
<summary><b>Решение + бонус с `retry`</b></summary>

```js
function withTimeout(promise, ms) {
  let timerId;

  const timeoutPromise = new Promise((_, reject) => {
    timerId = setTimeout(() => {
      reject(new Error(`Timeout after ${ms}ms`));
    }, ms);
  });

  // finally гарантирует, что таймер очистится, если основной promise завершился раньше
  return Promise.race([promise, timeoutPromise]).finally(() => {
    clearTimeout(timerId);
  });
}
```

**Частое продолжение — реализовать `retry(fn, retries, delayMs)`:**
```js
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function retry(fn, retries = 3, delayMs = 300) {
  let lastError;

  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      if (attempt < retries) {
        await sleep(delayMs);
      }
    }
  }

  throw lastError;
}
```
</details>

## Задача 5 (JS + TS). Строго типизированный `groupBy` без `any`

**Условие:** Реализуй и строго типизируй функцию `groupBy(items, keyGetter)`, которая группирует массив элементов по ключу, возвращаемому колбэком `keyGetter`.

```ts
const users = [
  { id: 1, role: "admin" as const, name: "Ann" },
  { id: 2, role: "user" as const, name: "Bob" },
  { id: 3, role: "admin" as const, name: "Max" },
];

const grouped = groupBy(users, (u) => u.role);
// Ожидаемый результат: { admin: [...], user: [...] }
```

<details>
<summary><b>Решение</b></summary>

```ts
function groupBy<T, K extends PropertyKey>(
  items: readonly T[],
  keyGetter: (item: T) => K,
): Partial<Record<K, T[]>> {
  const result: Partial<Record<K, T[]>> = {};

  for (const item of items) {
    const key = keyGetter(item);
    const list = result[key];
    if (list) {
      list.push(item);
    } else {
      result[key] = [item];
    }
  }

  return result;
}
```

**Почему возвращаемый тип `Partial<Record<K, T[]>>`, а не просто `Record<K, T[]>`?**  
Потому что если `K` — это union `'admin' | 'user' | 'guest'`, а в массиве не оказалось ни одного `'guest'`, ключа `'guest'` в итоговом объекте в рантайме не будет (`grouped.guest` может быть `undefined`).
</details>

```ts
function pick(obj, keys) {
  // TODO

const user = { id: 1, name: "Nikolay", isAdmin: true };
const short = pick(user, ["id", "name"]); // тип: { id: number; name: string }
// pick(user, ["unknown"]); // ❌ Ошибка компиляции TS
```

<details>
<summary><b>Решение</b></summary>

```ts
function pick<T extends object, K extends keyof T>(
  obj: T,
  keys: readonly K[],
): Pick<T, K> {
  const result = {} as Pick<T, K>;

  for (const key of keys) {
    if (key in obj) {
      result[key] = obj[key];
    }
  }

  return result;
}
```
